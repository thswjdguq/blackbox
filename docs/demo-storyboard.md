# 시연 스토리보드

핵심 흐름을 화면에서 차례로 보여 주는 순서다. 준비는 `docs/demo-setup.md`를 따른다.

- 기준: main `8089b9c`. 이 순서 그대로 브라우저 스크립트로 눌러 확인했다(6장)
- 모두 하면 14분쯤이다. 어림이고 재지 않았다
- ☆는 시간이 모자라면 빼는 장면이다. 나머지는 앞 장면이 뒤 장면의 조건이라 빼지 않는다

## 1. 이야기

한 줄: **과제 공지를 받은 팀이, 무엇을 내야 하는지부터 누가 무엇을 했는지까지 한 곳에 남기며 제출까지 간다.**

처음에 문제 셋을 꺼내고, 막마다 하나씩 답한 뒤, 끝에 셋으로 돌아온다.

| 꺼내는 문제 | 답하는 막 | 장면 | 화면이 보여 주는 답 |
| --- | --- | --- | --- |
| 무엇을 내야 하는지 흩어져 있다 | 1. 무엇을 내야 하는가 | 2~3 | 제출물, 그 요구사항, 요구사항에서 나온 업무 |
| 했다는 말만 있고 확인이 없다 | 2. 하고, 검토받고, 확정한다 | 4~13 | 업무 완료 → 충족 확인 → 검토와 피드백 → 승인 → 세 검사 → 확정 → 제출 기록 |
| 누가 무엇을 했는지, 평가자는 과정을 볼 수 없다 | 3. 남은 기록 | 14~15 | 기여도와 경보, 읽기만 하는 교수 시점 |

### 끝까지 따라가는 한 줄기: "참고 문헌"

기능을 하나씩 소개하지 않고 요구사항 하나가 생겨서 제출되기까지를 따라간다. 장면마다 이 줄기가 어디까지 왔는지를 말한다.

| 장면 | 이 줄기에 일어나는 일 |
| --- | --- |
| 3 | 김팀장이 빠진 요구사항 "참고 문헌을 넣는다"를 더하고, 거기서 업무 "참고 문헌 목록 작성"을 만들어 이팀원에게 맡긴다 |
| 7 | 검토에서 김팀장이 "참고 문헌에 인터뷰 출처가 빠졌습니다"를 남기고, 그 피드백을 업무 "출처 추가"로 만든다 |
| 8~9 | 이팀원이 두 업무를 끝내고 수정본을 올린 뒤, 피드백을 사유와 함께 해결한다 |
| 10~11 | 김팀장이 수정본을 승인하고, 요구사항이 채워졌는지 확인한 뒤 확정한다 |
| 12~13 | 확정된 제출물은 바뀌지 않고, 어디에 냈는지 기록이 남는다 |
| 14~15 | 이 모든 일이 사람별 기록이 되고, 교수는 같은 화면을 읽는다 |

### 등장인물

| 계정 | 역할 | 시연에서 하는 일 | 창 |
| --- | --- | --- | --- |
| 김팀장 | 팀장 | 계획, 충족 확인, 피드백, 승인, 확정 | 브라우저 일반 창 |
| 이팀원 | 팀원 | 업무, 검토 요청, 수정본, 제출 기록 | 시크릿 창 |
| 박팀원 | 팀원 | 등장하지 않는다. 맡은 일을 하지 않아 기록에 드러나는 사람 | - |
| 최교수 | 관찰자 | 읽기만 하는 교수 시점 | 다른 브라우저(또는 다른 프로필) |

세 창을 미리 로그인해 두고 창만 바꿔 가며 진행한다. 창은 일곱 번 바뀐다(김 → 이 → 김 → 이 → 김 → 이 → 김 → 최).

프로젝트는 스크립트가 만든 "캡스톤 디자인 — 우리 동네 재활용 안내 앱"이다. 지어낸 것이다. 시작할 때는 제출물 둘, 중간 보고서의 요구사항 넷(필수 셋), 업무 다섯, 파일 둘, 충족 확인 하나가 있다.

## 3. 줄이는 법과 넣지 않은 것

- 시간이 모자라면 12와 PDF 리포트를 뺀다. 12분쯤이다. 나머지 장면은 뒤 장면의 조건이라 빼면 흐름이 막힌다(예: 7의 피드백을 9에서 해결해야 10의 승인이 열린다)
- 회의록과 일정 조율은 넣지 않았다. 이번에 돌려 보지 않았다
- 확정된 제출물의 업무에 "확정됨"을 보이는 화면(#110)은 병합 전이다. 12에서는 서버가 거절하는 문구가 보인다

## 4. 예상 질문

| 질문 | 답 |
| --- | --- |
| 업무가 끝났는데 왜 충족 확인을 또 하나 | 업무는 한 일이고 요구사항은 채워야 할 조건이다. 끝난 업무가 조건을 채웠는지는 사람이 판단한다. 그래서 숫자를 따로 센다 |
| 끝나지 않은 업무가 있는데 확정이 되나 | 된다. 막는 조건은 필수 요구사항, 승인된 파일, 미해결 피드백 셋이다. 남은 업무는 확정 창이 몇 건인지 알려 준다 |
| 확정을 잘못하면 | 되돌릴 수 없다. 그래서 세 검사를 통과해야 하고 확정 창이 바뀌지 않는 것들을 먼저 보여 준다 |
| 제출을 시스템이 대신 하나 | 아니다. 제출 기록은 팀이 남기는 것이고 화면에도 "학교 시스템의 접수 여부를 확인하지 않습니다"라고 적혀 있다 |
| 교수 계정에 왜 무임승차 경보가 뜨나 | 알려진 문제다. 기여도 계산이 관찰자를 가리지 않는다. 고칠 예정이다 |

## 5. 잘못됐을 때

| 일 | 대처 |
| --- | --- |
| 페이지가 안 열림 | `docker ps`로 넷이 Up인지 본다. `blackbox_nginx`가 없으면 `docker start blackbox_nginx` |
| 로그인이 풀림 | 다시 로그인한다. 세 창 모두 시작 직전에 한 번 새로 고쳐 둔다 |
| "요구사항 추가"가 눌리지 않음 | 입력 칸에 글을 써야 켜진다 |
| 승인 버튼이 계속 꺼져 있음 | 미해결 피드백이 남아 있다. 검토 탭에서 해결한다(9) |
| "최종본 확정"이 꺼져 있음 | 최종 제출 탭의 세 검사 가운데 막힌 줄에 다음 할 일이 적혀 있다 |
| 확정을 잘못 누름 | 되돌릴 수 없다. 리허설용 계정으로 넘어가 이어서 보여 준다. 본 시연용 프로젝트는 시연 전에 누르지 않는다 |
| 최교수에게도 무임승차 경보가 보임 | 준비 자료로는 없앨 수 없다. 14에서 박팀원의 경보만 짚는다. 물으면 4장의 답을 한다 |

## 6. 확인한 것과 확인하지 않은 것

**확인한 것**

- main을 띄우고 `scripts/demo-seed.mjs`의 리허설용 자료로 2~15를 이 순서 그대로 브라우저 스크립트로 눌렀다. 48가지가 맞았고 세 창 모두 화면 오류가 없었다. 실패한 요청은 12에서 일부러 받은 거절 하나뿐이다
- 장면에 적은 숫자와 문구(진척 현황, 세 검사, "끝나지 않은 연결 업무 2건", 활성 경보 둘, 참여 표)는 그때 화면에서 읽은 것이다
- 11에서 충족 확인하는 두 요구사항은 그 시점에 연결 업무가 모두 끝나 있다

**확인하지 않은 것**

- 이 순서를 돌린 것은 개발용으로 띄운 화면이다. Docker와 nginx로 빌드한 화면에서는 순서를 고치기 전의 판(같은 기능, 장면 순서가 다름)으로 52가지를 확인했다
- 시연할 PC에서의 실행
- 사람이 직접 누른 것이 아니다. 스크립트는 화면의 글자와 요청의 응답을 보므로, 글자가 잘리거나 겹치는 모양의 문제는 잡지 못한다. 시간도 재지 않았다
- 보드에서 카드를 끌어 놓는 것, 파일 금고에 끌어 놓는 것. 버튼과 파일 고르기로만 눌렀다
- PDF 리포트의 내용
- 발표용 화면 해상도에서의 모습(가로 1440으로 확인했다)

시작 전에 시연할 PC에서 리허설용 계정으로 처음부터 끝까지 한 번 돌려 본다.
