# K-59 · AI 문서 초안 작성

- 버전 0.1 DRAFT / 2026-11-25 / A 생산자(에이전트·파일 금고·검토 회차), B 협력(회의 조회), C 소비자(화면)
- 근거: 12주차 계획(#231) 정할 것 5, K-30 제안서(`docs/team/handoffs/A-K30-proposal-20261007.md`) 부록 C "문서 초안 작성"
- K-30의 실행·카드 구조를 그대로 쓰고, 실행 종류 둘과 카드 종류 둘, 읽기 도구 하나를 더한다. DB 마이그레이션은 없다(V25가 실행·카드·결과 종류를 코드 등록으로 늘리게 되어 있다)
- 합의 전에는 HTTP·DB·운영 동작을 바꾸지 않는다

## 1. 무엇을 약속하는가

제출물 하나의 문서(보고서 등)를 에이전트와 함께 **목차 → 초안 → 검토 요청**까지 진행한다. 단계마다 제안 카드에서 멈추고 사람이 확인한다.

1. **목차**: 요구사항과 업무·회의 기록을 읽고 장 구성을 제안한다. 사람이 장을 빼거나 더하고 메모를 고친 후 채택한다
2. **초안**: 채택한 목차대로 장마다 본문을 쓴다. 장마다 근거가 된 업무·회의를 표시하고, 기록에 없는 내용은 지어내지 않고 "[작성 필요: 무엇]"으로 둔다
3. **검토 요청**: 초안 카드를 채택하면 .docx 파일로 파일 금고에 올리고 그 파일로 검토 회차를 연다. 채택한 사람이 올린 사람이 되므로 다른 팀원이 검토한다(K-10)

초안은 출발점이다. 작성자는 내려받아 고친 후 같은 이름으로 다시 올려 다음 버전을 만든다. 피드백을 반영한 수정본을 AI가 다시 쓰는 기능은 이번 범위가 아니다.

## 2. 실행 종류

K-30 2장의 실행 종류 표에 더한다.

| `skill` | 하는 일 | `input` | 결과 | 역할 |
| --- | --- | --- | --- | --- |
| `DRAFT_OUTLINE` | 제출물의 요구사항·업무·회의를 읽고 문서의 목차를 제안한다 | `{ "deliverableId": "…" }` | `DOCUMENT_OUTLINE` 카드 1장. 쓸 기록이 없으면 카드 없이 글로 이유를 답한다 | 팀장·팀원 |
| `DRAFT_DOCUMENT` | 채택한 목차대로 장별 초안을 쓴다 | `{ "outlineProposalId": "…" }` | `DOCUMENT_DRAFT` 카드 1장 | 팀장·팀원 |

- 두 실행 모두 제출물이 확정·제출된 상태면 409다(K-20, 기존 문장). 보관된 프로젝트면 409 `PROJECT_ARCHIVED`다(K-60)
- `DRAFT_DOCUMENT`의 목차 카드는 같은 프로젝트의 `DOCUMENT_OUTLINE`이고 채택(`ACCEPTED`)된 것이어야 한다. 없거나 다른 프로젝트면 404, 채택 전이거나 거절된 카드면 409 `OUTLINE_NOT_ACCEPTED`
- 같은 목차로 초안을 여러 번 만들 수 있다. 앞의 초안 카드는 그대로 남고, 사람이 고를 수 있다
- 연속 실행 409, 시간당 상한 429 등 K-30의 실행 규칙을 그대로 따른다

## 3. 카드

### `DOCUMENT_OUTLINE`

| 필드 | 규칙 |
| --- | --- |
| `deliverableId` | 서버가 채운다. 카드를 고쳐도 바뀌지 않는다 |
| `title` | 문서 제목. 필수, 255자까지 |
| `sections[]` | 1-6개 |
| `sections[].title` | 장 제목. 필수, 100자까지 |
| `sections[].requirementIds[]` | 이 장이 다루는 요구사항. 같은 제출물의 요구사항이어야 한다. 비어도 된다 |
| `sections[].note` | 이 장에 무엇을 쓸지, 쓸 자료가 얼마나 있는지. 사람이 메모를 덧붙인다. 500자까지 |

- 채택하면 기록을 만들지 않는다(`results`의 목록은 비어 있고 id 칸은 `null`). 채택은 "이 목차로 초안을 쓴다"는 확정이고, 채택한 카드만 `DRAFT_DOCUMENT`의 입력이 된다. K-30의 "채택하면 기록을 만든다"에 대한 예외로 K-30 3장에 적는다
- 필수 요구사항 중 어느 장에도 걸리지 않은 것이 있으면 카드에 표시한다(`uncoveredRequirementIds[]`). 서버가 채우고, 사람이 카드를 고칠 때마다 다시 계산한다. 채택을 막지는 않는다

### `DOCUMENT_DRAFT`

| 필드 | 규칙 |
| --- | --- |
| `deliverableId`, `outlineProposalId` | 서버가 채운다. 카드를 고쳐도 바뀌지 않는다 |
| `title` | 문서 제목. 필수, 255자까지 |
| `sections[]` | 1-6개. 목차의 장 순서를 따른다. 사람이 고칠 때 장을 빼거나 순서를 바꿀 수 있다 |
| `sections[].title` | 필수, 100자까지 |
| `sections[].body` | 본문. 필수, 1200자까지. 빈 줄로 문단을 나누고, `- `로 시작하는 줄은 목록이다. 그 밖의 서식은 없다 |
| `sections[].sources.taskIds[]`, `meetingIds[]`, `requirementIds[]` | 이 장의 근거. 같은 프로젝트의 업무·회의와 그 제출물의 요구사항이어야 한다. 서버가 확인해 없는 id는 빼고, 뺀 개수를 실행의 글 끝에 "근거를 확인할 수 없어 n건은 뺐습니다"로 알린다(K-31 5장과 같은 방식). 같은 칸에 겹친 id는 한 번만 남기고 개수에 넣지 않는다. 사람이 카드를 고칠 때도 같은 기준으로 거른다 |

- 기록에 없는 내용은 본문에 "[작성 필요: 무엇]"으로 쓴다. 모델 지시문이 이를 요구하고, 서버는 그 개수를 카드에 함께 보인다(`missingCount`). 사람이 고칠 때마다 다시 센다. 콜론 앞의 공백과 전각 콜론(：)도 같은 표시로 센다
- 채택하면 한 트랜잭션에서 다음을 한다. 하나라도 실패하면 DB 기록은 남지 않고, 이미 디스크에 쓴 파일도 지운다
  1. 카드 내용으로 .docx를 만든다(4장)
  2. 파일 금고에 올린다. 파일 이름은 `{제출물 제목} 초안.docx`다. 같은 이름이 있으면 다음 버전이 된다. 올린 사람은 채택한 사람이고, 화면에서 올릴 때처럼 활동 기록(`FILE_CREATE`·`FILE_EDIT`)이 남아 파일 참여로 집계된다(9장, B 합의). 이 기록은 파일을 등록한 증빙이며 본문을 직접 작성했다는 증명이 아니다. 같은 내용의 초안을 다시 채택하면 해시가 같아 내용 변경 기록(`REUPLOAD`)은 남지 않고, 버전은 늘며 `FILE_EDIT`는 남는다
  3. 그 파일로 제출물의 검토 회차를 연다(K-10). 검토 요청 알림과 이메일은 회차를 열 때의 기존 동작 그대로다
- `results`: `FILE`(파일 id), `REVIEW_ROUND`(회차 id). 대상 종류를 `TargetTypes`에 더하고, 응답에서는 `results.fileId`, `results.reviewRoundId`로 나간다(K-30 3장)
- 검토 회차를 열 수 없는 상태(확정·제출된 제출물 등)면 채택은 409이고 파일도 올리지 않는다

## 4. .docx 형식

- 새 라이브러리 없이 서버가 Office Open XML을 직접 쓴다. 워드·한컴오피스·구글 문서에서 열고 고칠 수 있어야 한다
- 들어가는 것: 문서 제목, 장 제목(제목 스타일), 문단, 목록, 장 끝의 근거 한 줄("근거: 업무 「제목」, 회의 「제목」(날짜)"), "[작성 필요: …]"는 굵게 표시
- 들어가지 않는 것: 표, 그림, 머리글·바닥글, 목차 필드, 쪽 번호. 필요하면 작성자가 편집기에서 더한다
- 글꼴은 지정하지 않고 편집기 기본값을 쓴다

## 5. 읽기 도구

K-30 5장의 도구 표에 더한다.

| 도구 | 돌려주는 것 | 자료의 출처 |
| --- | --- | --- |
| `list_meetings` | 회의의 id·제목·날짜·목적·결정 사항, 회의록 앞 1000자(코드 포인트 기준, 잘렸으면 `notesTruncated`). 글 속의 이메일 주소와 전화번호는 가려서 보낸다 | B (회의 조회) |

- 요청한 사람의 권한으로 기존 회의 목록 조회를 부른다. 출석 기록, 체크인 코드, 외부 연동 정보는 돌려주지 않는다
- 회의에서 만든 액션 아이템은 돌려주지 않는다. 지금은 업무와 회의를 잇는 칸이 없고 업무 설명 끝에 회의 제목 글자만 붙기 때문이다(`MeetingService.createActionItem`). 업무는 `list_tasks`로 따로 읽는다
- 건수 상한과 잘림 표시는 K-30 5장의 다른 목록 도구와 같다
- 두 실행 모두 `list_deliverables`(요구사항 포함), `list_tasks`, `list_meetings`, `get_project`를 쓸 수 있다

## 6. 크기와 실패

- 초안은 한 번의 모델 응답으로 만든다. 본문 상한(장 6개 × 1200자, 7200자)에 제목·근거 id·카드 형식을 더해도 모델 출력 토큰 상한(8192, A-70) 안에 들도록 정한 값이다. 한글의 토큰 수는 모델마다 달라 이 값은 어림이며, 실제 모델 테스트에서 넘으면 장당 길이를 줄인다
- 출력이 상한에 걸리면 기존처럼 실행이 실패하고 "모델의 답이 출력 상한에 걸려 잘렸습니다"로 알린다(A-70). 실제 모델 테스트에서 요구사항이 많은 제출물로 확인한다

## 7. 화면(C)

- 제출물 상세에 "문서 초안 만들기"를 둔다. 확정·제출된 제출물과 보관된 프로젝트에서는 서버의 409 문장을 보인다
- 목차 카드: 장 목록을 보여 주고 장 빼기·더하기·순서 바꾸기·메모 고치기를 할 수 있다. 다루지 않은 필수 요구사항(`uncoveredRequirementIds`)을 표시한다. 채택하면 "초안 쓰기" 버튼으로 `DRAFT_DOCUMENT`를 실행한다
- 초안 카드: 장마다 본문과 근거(업무·회의로 이동하는 링크)를 보이고, "[작성 필요: …]"를 눈에 띄게 표시한다. `missingCount`를 위쪽에 보인다. 본문을 고칠 수 있다
- 초안을 채택하면 제출물의 검토 탭으로 이동한다

## 8. 수용 테스트

1. 요구사항·업무·회의가 있는 제출물로 `DRAFT_OUTLINE`을 실행하면 목차 카드 1장, 장 1-6개, 장의 요구사항 id가 그 제출물의 것
2. 목차 카드를 채택하면 `results`가 비어 있고, 채택 전 카드로 `DRAFT_DOCUMENT`를 실행하면 409 `OUTLINE_NOT_ACCEPTED`
3. 채택한 목차로 `DRAFT_DOCUMENT`를 실행하면 초안 카드 1장, 근거 id가 모두 같은 프로젝트의 업무·회의와 그 제출물의 요구사항
4. 초안 카드를 채택하면 파일 금고에 `{제출물 제목} 초안.docx`가 생기고, 그 파일로 검토 회차가 열리며, 채택한 사람은 그 회차를 결정할 수 없다(K-10)
5. 만든 .docx를 열 수 있고 제목·장 제목·문단·목록·근거 줄이 들어 있다(압축을 풀어 XML을 검사한다)
6. 확정된 제출물, 보관된 프로젝트, 관찰자는 각각 409, 409 `PROJECT_ARCHIVED`, 403
7. 실제 모델 테스트: 요구사항 10개 이상인 제출물에서 초안이 출력 상한에 걸리지 않고, 기록에 없는 내용은 "[작성 필요]"로 남는다

## 9. 합의 요청

- B(합의, 11/26 #238): `list_meetings`는 기존 `MeetingService.listMeetings`의 회원 검사와 목록 상한을 그대로 쓰고, 5장의 칸과 회의록 앞 1000자, 연락처 가리기로 충분하다. 이 합의는 자료의 모양에 대한 것이며 실제 기록을 모델로 보내는 데 대한 참가자 동의를 대신하지 않는다(K-30 9장의 미결)
- B(합의, 11/26 #238): 초안 채택으로 저장한 파일은 기존 업로드와 같이 `FILE_CREATE`·`FILE_EDIT`로 집계한다. 점수는 파일 참여 여부만 보므로 버전이 늘어도 가산되지 않는다. AI 초안 파일을 빼거나 새 산식을 두지 않는다
- C: 3장의 카드 칸, 7장의 화면 흐름. 목차 카드의 장 편집과 초안 카드의 본문 편집 범위
