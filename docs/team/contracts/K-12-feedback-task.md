## 요청과 응답

POST `/api/projects/{projectId}/deliverables/{deliverableId}/reviews/{reviewId}/comments/{commentId}/task`
기존 인증 필터를 사용한다. K-10과 같은 인증 경로를 사용하며 팀장·팀원만 허용하고 관찰자는 403. ID는 UUID.

```json
{ "title": "보고서 출처 보완", "completionCriteria": "인용한 문장마다 출처 기재" }
```

title trim 후 1~255자 필수. 기존 CreateTaskRequest와 업무 화면의 기준에 맞췄다. completionCriteria는 trim 후 최대 2000자 선택, null·생략·빈 문자열은 미설정(null)으로 제안한다. 상세 설명은 코멘트 원문을 복사한다. 담당자·기한은 기존 업무 수정 API에서 지정하며 이 API는 임의로 팀원을 배정하지 않는다.
업무는 TODO, 해당 프로젝트·제출물에 연결, requirementId는 null. 업무 DONE은 K-11 조회에서 REFLECTION_PENDING으로 표시될 뿐 자동 해결하지 않는다. 코멘트 status 열이나 업무 변경 시 코멘트 갱신은 만들지 않는다.

성공 예(제안): `{ "commentId": "33333333-3333-4333-8333-333333333333", "taskId": "66666666-6666-4666-8666-666666666666", "created": true }`.
최초 201, 같은 피드백 재시도는 기존 업무를 200·created=false로 반환한다. 다른 title로 재시도해도 기존 업무를 수정하지 않는다. 이미 연결된 경우에는 업무 편집 화면으로 안내한다.

## 원자성과 상태

권한·프로젝트·제출물·회차·코멘트 소속을 확인하고 K-11과 같은 제출물 잠금을 잡는다. 기존 연결 조회 → 없을 때 상태 검사 → 업무 생성 → 연결 생성 → 활동 기록을 한 트랜잭션으로 처리한다. 어느 단계가 실패해도 업무만 남지 않아야 한다.
승인 회차 또는 CONFIRMED·SUBMITTED에서 새 연결은 409. RESOLVED에 새 업무 연결도 409 제안. 재시도 응답의 반환 허용 범위는 권한 확인 후 기존 연결이 있을 때만이며 새 쓰기는 하지 않는다.
별도 연결 테이블 대신 `review_comments.linked_task_id` nullable UNIQUE 열을 제안한다. `(linked_task_id, deliverable_id, project_id)`는 `tasks(id, deliverable_id, project_id)`를 참조하며 업무 삭제 시 linked_task_id만 NULL로 바꾼다. 필요한 tasks 복합 유일 제약과 PostgreSQL 16의 `ON DELETE SET NULL (linked_task_id)`는 A가 V22에 작성한다. 경쟁 삽입 오류를 실패한 트랜잭션 안에서 catch 후 계속하지 않는다. 동일 제출물 잠금으로 직렬화하고 제약은 최종 방어로 사용한다.
다른 제출물로 이동·제출물 연결 해제는 409로 거절한다. 연결 업무 삭제는 허용하되 피드백과 해결 기록을 지우지 않는다. 삭제 후 미해결 피드백은 OPEN, 이미 해결한 피드백은 RESOLVED를 유지한다(K-11의 해결 정보 우선 계산). 업무만 바꿔 연결하는 재지정 API는 범위 밖이다. 삭제 후 미해결 피드백에서 이 API를 다시 호출하면 새 업무를 생성하는 안을 제안한다. 따라서 멱등 반환은 현재 연결 업무가 존재하는 동안 적용한다. 삭제와 재생성 경쟁의 잠금 정책은 구현 전에 A·B가 확인한다.

## 오류와 DB

기존 ProblemDetail: 400 입력/UUID, 401 미인증, 403 비회원/관찰자, 404 소속 불일치/없음, 409 상태·연결 변경 충돌, 500 내부 오류. 서버 실패를 생성 성공으로 표시하지 않는다.
시각은 이 응답에 없고 목록·정렬·페이지 처리도 없다. K-10 #69에서 A가 V22를 K-11·K-12용으로 예약했다. 합의 후 A가 작성한다. 회차 검사와 단일 제출물 잠금은 K-10의 ReviewRoundReader.lockForWrite를 같은 트랜잭션에서 사용한다.
K-11·K-12 합의 → A 스키마 → B-20 → B-21 → C 실제 연결 순서. C fixture와 타입은 합의 후 갱신한다.

검증 예정: 최초 1건 생성·재시도 동일 taskId, 동시 요청에서도 1건, 생성 실패 시 업무·연결·활동 모두 롤백, 역할·타 프로젝트 ID, 승인 후 생성 차단, 업무 DONE·복구 상태 반영, 연결 업무 이동 차단, 삭제 후 피드백·해결 기록 보존과 미해결 피드백의 새 업무 생성.

## 소비자 확인 및 다음 구현 준비 (2026-10-06)

C가 PR #60에서 v0.3의 경로·입력 길이·응답·재시도·해결된 피드백 차단·삭제 후 재생성 화면·관찰자 권한을 확인하고 승인했다. 이는 화면 코드와 계약의 대조이며 실제 서버 연결 검사가 아니다. A도 PR #60에서 최종 승인했으며 계약은 2026-10-07 병합됐다. 2026-10-08 AGREED로 정리했다. B-21 운영 구현 완료를 뜻하지 않는다.

A와 최종 확인할 사항은 삭제·재생성의 경쟁이다. 일반 업무 삭제와 피드백 업무 생성이 모두 같은 제출물 잠금을 사용해야 하는지, 삭제 먼저/생성 먼저의 경우 어느 taskId와 linked_task_id가 남아야 하는지 정한다. A의 회차 잠금은 B가 호출하되 기존 TaskService의 삭제 경로도 B 담당으로 검토한다. 삭제 후 해결 기록은 유지하며, 미해결 상태의 새 업무 생성만 제안한다.

합의 후 B-21 검사 자료는 다음 네 경우를 포함한다: 현재 연결 업무가 있는 중복 요청은 200·같은 ID·새 저장 없음, 연결이 비어 있는 미해결 피드백의 동시 요청은 업무 한 건만 생성, 해결된 피드백의 삭제 후 생성은 409·해결 기록 보존, 생성/연결/활동 기록 어느 단계가 실패해도 모두 롤백. 실제 검사 실행은 A-11/V22와 B-20 이후다.
