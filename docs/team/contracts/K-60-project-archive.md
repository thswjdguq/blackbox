# K-60 · 프로젝트 보관

- 버전 0.1 DRAFT / 2026-11-24 / A 생산자(DB·프로젝트 API·권한 검사·AI 실행), B 협력(회의·스케줄러·이메일 발송), C 소비자(화면)
- 근거: 12주차 계획(#231) 정할 것 5, A-03 처리안 (다). 기록이 있는 프로젝트는 삭제가 409로 막혀(A-03 처리안 (라)), 끝난 프로젝트를 정리할 방법이 없다
- 합의 전에는 HTTP·DB·운영 동작을 바꾸지 않는다

## 1. 무엇을 약속하는가

팀장은 끝난 프로젝트를 **보관**할 수 있다. 보관된 프로젝트는 기록을 그대로 남긴 채 **읽기 전용**이 된다. 다시 쓰려면 팀장이 **보관을 해제**한다.

규칙은 하나다. "보관하면 보기만 된다. 다시 쓰려면 팀장이 해제한다." 기능마다 허용 여부를 나누지 않는다. AI 실행도 새 실행 기록과 모델 사용량을 만드는 쓰기이므로 막는다. 예외는 3장의 "본인 계정에 관한 것"과 해제뿐이다.

삭제 규칙은 바꾸지 않는다. 기록이 없는 프로젝트는 지금처럼 지울 수 있고, 기록이 있으면 409다.

## 2. 명령

| 메서드·경로 | 입력 | 성공 | 권한 |
| --- | --- | --- | --- |
| POST `/api/projects/{projectId}/archive` | 없음 | 200, 프로젝트 응답(4장) | 팀장 |
| POST `/api/projects/{projectId}/unarchive` | 없음 | 200, 프로젝트 응답 | 팀장 |

- 이미 보관된 프로젝트를 다시 보관하면 지금 응답을 그대로 돌려준다(중복 클릭). 보관 시각과 보관한 사람은 처음 값을 유지한다. 보관되지 않은 프로젝트의 해제도 같다
- 팀원·관찰자는 403, 회원이 아니면 지금 프로젝트 조회와 같은 오류다
- 보관과 해제는 활동 기록에 남기지 않는다(점수·경보에 영향을 주지 않는다). 해제하면 보관 시각과 보관한 사람을 지우므로, 누가 언제 해제했는지는 남지 않는다

## 3. 보관 중 허용하는 것과 막는 것

| 구분 | 보관 중 | 비고 |
| --- | --- | --- |
| 모든 조회(프로젝트, 업무, 제출물, 검토, 회의, 파일 목록, 기여도, 지난 AI 실행과 카드) | 허용 | |
| 내려받기(파일, 교수용 PDF 보고서, 증빙 ZIP) | 허용 | 읽기다 |
| 프로젝트의 기록을 만들거나 바꾸는 모든 명령 | **409** | 업무, 제출물, 요구사항, 검토 회차·피드백, 확정·제출, 회의·액션 아이템, 파일 업로드, 안내문, 프로젝트 정보·멤버 역할, 초대 코드 재발급, 외부 연동 설정 |
| AI 실행 시작과 제안 카드의 수정·채택·거절 | **409** | 물어보기(`ASK`)·상태 요약(`STATUS_BRIEF`)처럼 글로만 답하는 실행도 막는다 |
| 초대 코드로 참여 | **409** | 새 멤버를 받지 않는다 |
| 프로젝트 나가기 | **409** | 멤버 구성도 기록이다. 필요하면 팀장이 해제한 후 나간다 |
| 본인 계정에 관한 것: 알림 읽음 표시, 데이터 수집 동의 변경(철회 포함) | 허용 | 프로젝트 기록이 아니라 본인의 상태다. 동의 철회는 보관과 상관없이 막지 않는다 |
| 보관 해제 | 허용(팀장) | |
| 프로젝트 삭제 | 지금 규칙 그대로 | 기록이 있으면 409 |

### 오류 응답

막힌 명령은 409 ProblemDetail로 답한다.

```json
{ "status": 409, "code": "PROJECT_ARCHIVED", "detail": "보관된 프로젝트입니다. 팀장이 보관을 해제하면 다시 사용할 수 있습니다." }
```

- `detail`은 화면이 그대로 보여 줄 서버 문장이다. 화면은 `code`로 보관 상태임을 알아보고, 문장을 따로 만들지 않는다
- 프로젝트가 없는지(404), 회원인지·역할이 맞는지(403)는 보관 여부보다 먼저 판정한다. 회원이 아닌 사람에게 보관 여부를 알리지 않고, 관찰자가 쓰기를 시도하면 지금처럼 403이다. 예외는 초대 코드 참여다. 초대 코드를 가진 사람은 참여하려는 사람이므로 409로 보관 상태를 알린다
- 프로젝트 안의 대상(업무·제출물 id 등)이 없는지는 보관 여부 다음에 판정할 수 있다. 보관된 프로젝트에서 없는 업무를 고치려 하면 404가 아니라 409일 수 있다

## 4. 응답

프로젝트 응답(`ProjectResponse`, 목록과 단건 공통)에 칸 두 개를 더한다.

| 필드 | 형식 | 의미 |
| --- | --- | --- |
| `archivedAt` | ISO-8601 UTC 시각 또는 `null` | 보관한 시각. `null`이면 보관되지 않은 프로젝트 |
| `archivedNotice` | 문자열 또는 `null` | 보관 중일 때 화면 상단에 보일 서버 문장. 3장의 409 `detail`과 같은 상수다. 보관되지 않았으면 `null` |

- 프로젝트 목록(`GET /api/projects`)은 보관된 프로젝트도 함께 돌려준다. 순서는 지금과 같다. 화면이 `archivedAt`으로 나눠 보여 준다
- 보관한 사람은 응답에 넣지 않는다. 화면에 필요해지면 더한다

## 5. DB

V41(A 작성):

- `projects.archived_at TIMESTAMPTZ NULL`, `projects.archived_by UUID NULL REFERENCES users(id)`
- 제약: 두 칸은 함께 있거나 함께 없다(`(archived_at IS NULL) = (archived_by IS NULL)`)
- 기존 프로젝트는 모두 보관되지 않은 상태(`NULL`)로 시작한다

## 6. 서버 구현의 경계

### A

- 쓰기 권한 검사(`ProjectAccessChecker.requireContributor`, `requireLeader`)가 보관된 프로젝트에서 409를 던진다. 쓰기 명령 대부분이 이 두 검사를 지나므로 한곳에서 막는다. 해제 명령만 보관 검사를 건너뛴다
- 이 두 검사를 지나지 않는 쓰기는 main(`217687f2`) 코드를 조사해 아래처럼 정한다. 외부에서 들어오는 웹훅은 없고(디스코드는 보내기만 한다), 스케줄러는 B 요청의 두 개뿐이다

| 경로 | 지금의 권한 확인 | 보관 중 | 담당 |
| --- | --- | --- | --- |
| 알림 읽음 표시(`NotificationService.markRead`) | 회원 검사 | 허용 | - |
| 데이터 수집 동의 변경(`ProjectService.recordConsent`) | 회원 검사 | 허용 | - |
| 프로젝트 나가기(`ProjectService.leaveProject`) | 회원 검사 | 409 | A |
| AI 실행 시작(`AgentRunner`) | 회원 검사 + 실행 종류별 역할 | 409 | A |
| AI 카드 수정·채택·거절(`ProposalService`) | 회원 검사 + `canContribute` | 409 | A |
| 최종본 확정·확정 취소(`DeliverableConfirmationService`) | 회원 검사 + 팀장 역할 비교 | 409 | A |
| 초대 코드 참여(`ProjectService.joinProject`) | 없음(초대 코드) | 409 | A |

- A의 경로는 가능하면 `requireContributor`·`requireLeader`를 쓰도록 바꿔 보관 검사를 함께 받게 하고, 그럴 수 없는 곳(나가기, 초대 코드 참여)에만 `requireNotArchived`를 직접 부른다
- 회의 액션 아이템 만들기(`MeetingService.createActionItem`)는 바깥에서 회원 검사만 하지만 안에서 `TaskService.createTask`의 `requireContributor`를 지나므로, 따로 고치지 않아도 보관 중 409다
- 보관 검사용 공개 메서드(`ProjectAccessChecker.requireNotArchived(Project)`)를 두어 같은 검사와 같은 오류를 쓸 수 있게 한다
- 보관 여부를 읽기만 하는 곳(스케줄러, 이메일 발송 직전 재확인)을 위해 `Project.getArchivedAt()`과 `Project.isArchived()`를 둔다. 이런 곳은 409를 던지지 말고 그 프로젝트를 건너뛴다. 이메일 발송 직전 재확인이 409를 밖으로 던지면 worker가 lease 회수와 재시도로 남기므로, 빈 자격으로 돌려 `SKIPPED`로 끝낸다

### B 요청

- 점수 재계산 스케줄러(`ScoreScheduler`)와 회의 10분 전 알림(`DiscordReminderScheduler`)에서 보관된 프로젝트를 뺀다
- 업무 처리 커밋 후 도는 비동기 재계산(`TaskWorkflowService` → `ScoreService.recalculateAsync` → `recalculate`)도 보관된 프로젝트면 저장과 경보 생성을 하지 않는다. 보관 직전에 권한 검사를 지난 쓰기가 보관 후에 재계산을 부를 수 있기 때문이다
- 이메일 발송 직전 재확인에서 보관된 프로젝트의 대기를 조건 소멸(`SKIPPED`)로 끝낸다. 보관 후에는 쓰기가 막혀 새 대기는 생기지 않지만, 보관 전에 쌓인 대기가 남을 수 있다

### 동시성

보관과 다른 쓰기가 같은 순간에 들어오면, 보관 전에 권한 검사를 지난 쓰기는 끝까지 실행될 수 있다. 보관 전에 시작한 AI 실행도 끝까지 돌아 카드를 만들 수 있지만, 그 카드는 보관 중에 채택할 수 없다. 소수 사용자 기준에서 문제가 되지 않아 프로젝트 행 잠금으로 직렬화하지 않는다.

## 7. 화면(C)

- 대시보드: 보관된 프로젝트를 접을 수 있는 "보관됨" 영역으로 나눈다
- 보관된 프로젝트 안: 상단에 `archivedNotice`를 그대로 보이고, 팀장에게는 "보관 해제" 버튼을 보인다. 409를 받기 전에도 안내가 보여야 하므로 프로젝트 응답에 서버 문장을 싣는다. 화면은 문장을 따로 만들지 않는다
- 프로젝트 설정: 팀장에게 "프로젝트 보관" 버튼과 확인 창을 둔다
- 버튼을 기능마다 끄지 않는다. 쓰기를 시도하면 서버의 409 `detail`을 그대로 보인다

## 8. 수용 테스트

1. 팀장이 보관하면 200과 `archivedAt`·`archivedNotice`, 다시 보관하면 같은 시각, 해제하면 둘 다 `null`, 팀원·관찰자는 403
2. 보관된 프로젝트에서 업무 만들기, 제출물 수정, 파일 업로드, 회의 액션 아이템 만들기, 최종본 확정·확정 취소, AI 실행(물어보기 포함), 카드 수정·채택·거절, 초대 코드 참여, 나가기가 409 `PROJECT_ARCHIVED`
3. 보관된 프로젝트에서 조회, 파일 내려받기, 교수용 PDF, 증빙 ZIP, 알림 읽음 표시, 동의 변경이 성공
4. 해제하면 같은 쓰기가 다시 성공
5. 회원이 아닌 사람은 보관 여부와 상관없이 지금과 같은 오류(409를 받지 않음), 관찰자의 쓰기는 지금처럼 403
6. V41: 기존 프로젝트의 `archived_at`이 `NULL`, 두 칸 중 하나만 있는 행은 제약 위반
7. (B) 점수 재계산 스케줄러·업무 처리 후 비동기 재계산·회의 10분 전 알림이 보관된 프로젝트를 건너뛰고, 보관 전에 쌓인 이메일 발송 대기는 `SKIPPED`로 끝난다

## 9. 합의 요청

- B: 6장의 B 요청 세 가지(두 스케줄러, 비동기 재계산, 이메일 발송 직전 재확인)와 담당 파일 변경
- C: 3장의 오류 응답, 4장의 `archivedAt`·`archivedNotice`, 7장의 화면 흐름
