## 1. 무엇을 약속하는가

제출물마다 검토 회차를 열고, 검토자가 회차마다 `승인` 또는 `수정 요청`을 결정한다. 회차는 열 때 고른 **파일 버전 하나**를 가리키며, 이후 파일이 바뀌어도 회차의 대상은 바뀌지 않는다.

- 회차는 파일 금고의 파일 버전 id를 직접 가리킨다. 제출물과 파일을 잇는 별도 연결은 만들지 않는다(결정안 3장)
- "같은 파일"은 파일 금고의 기준 그대로 같은 프로젝트의 같은 파일 이름이다. 승인 뒤 내용이 바뀌었는지는 그 이름의 최신 버전과 **해시**를 비교해 판단한다(3장)
- 최종 확정(`CONFIRMED`)과 제출 기록(`SUBMITTED`)은 K-20 범위다. 이 계약은 확정이 근거로 삼을 "지금 유효한 승인"까지만 정한다

## 2. 명령

기본 경로: `/api/projects/{projectId}/deliverables/{deliverableId}/reviews`. 모든 id는 UUID이고 기존 쿠키 인증을 쓴다.

| 명령 | 요청 | 성공 | 역할 |
| --- | --- | --- | --- |
| 회차 목록 | GET 기본 경로 | 200, 3장의 객체 | 팀장·팀원·관찰자 |
| 회차 열기 | POST 기본 경로, `{ "fileId": "…" }` 또는 `{ "fileId": null }` | 201, 회차 객체 | 팀장·팀원 |
| 결정 | PUT `/{reviewId}/decision`, `{ "decision": "APPROVED" }` 또는 `"CHANGES_REQUESTED"` | 200, 회차 객체 | 팀장·팀원 중 그 회차 파일을 올리지 않은 사람 |

### 회차 열기

- `fileId`는 같은 프로젝트의 파일 버전이어야 한다. 최신 버전이 아니어도 고를 수 있다. `null`이거나 생략하면 파일 없는 중간 검토다(CONTRACTS 3장 4항). 기존 요청들과 같이 생략과 `null`을 구분하지 않는다
- 회차 번호는 제출물 안에서 1부터 1씩 늘어난다
- 새 회차는 **언제든 열 수 있다.** 같은 파일 버전으로도 열 수 있고, 최신 회차가 아직 결정 전이어도 열 수 있다. 결정 없이 지나간 회차는 "결정 없음"으로 남는다. 회차를 취소하는 명령은 두지 않는다
- 새 회차가 열리면 그 제출물의 이전 승인은 더 이상 확정 근거가 아니다. 이전 승인을 되살리는 방법은 없고, 새 회차에서 다시 승인받아야 한다

### 결정

- **최신 회차에만** 결정할 수 있다. 지난 회차에 결정을 요청하면 409다
- 그 회차의 파일을 올린 사람은 결정할 수 없다(403). 파일 없는 회차는 팀장·팀원 누구나 결정할 수 있다
- `APPROVED`는 그 제출물의 **미해결 피드백이 0건**일 때만 된다. 1건 이상이면 409다. 미해결은 K-11의 `OPEN`과 `REFLECTION_PENDING`이다
- 결정은 회차마다 한 번이다. 이미 결정된 회차에 **같은 결정**을 다시 보내면 현재 회차 객체를 그대로 돌려주고(중복 클릭), **다른 결정**을 보내면 409다. 결정을 바꾸려면 새 회차를 연다
- 승인된 회차에는 코멘트 작성·해결·다시 열기를 막는다(K-11이 5장의 조회로 확인한다). 승인 뒤 추가 의견은 새 회차에서 받는다
- 승인 뒤에 **지난 회차의** 피드백을 다시 열면 미해결이 생길 수 있다. 승인 자체와 `currentBasis`는 그대로 두고, 확정(K-20)이 미해결 0건을 다시 검사하므로 확정은 막힌다(CONTRACTS 3장 8항). 그 피드백을 다시 해결하면 새 승인 없이 확정할 수 있다. 승인받은 파일 내용이 그대로이기 때문이다. CONTRACTS 3장 6항의 "판정은 다음 회차에서 검토자의 승인으로 한다"에 대한 예외이고, 그 항목에도 적었다. 내용을 고쳐야 해결되는 피드백이면 새 버전이 올라와 승인이 근거에서 빠지므로(3장) 새 회차가 필요하다. 화면은 `unresolvedCommentCount`로 알린다

### 제출물 상태

상태는 **저장하지 않고 회차에서 계산한다.** 회차와 따로 저장하면 두 값이 어긋날 수 있다.

| 조건 | `deliverableStatus` |
| --- | --- |
| 회차가 없다 | `DRAFT` |
| 최신 회차가 결정 전이다 | `IN_REVIEW` |
| 최신 회차가 `CHANGES_REQUESTED`다 | `DRAFT` (보완 중) |
| 최신 회차가 `APPROVED`다 | `IN_REVIEW` (확정 대기) |

`CONFIRMED`·`SUBMITTED`는 K-20이 확정·제출 기록을 저장하면서 이 표 앞에 추가한다. `IN_REVIEW → DRAFT` 보완 전환(CONTRACTS 3장 7항)은 따로 명령을 두지 않고 `수정 요청` 결정으로 일어난다.

| 필드 | 값 | 의미 |
| --- | --- | --- |
| `deliverableStatus` | `DRAFT`·`IN_REVIEW` | 2장의 표로 계산한 값 |
| `unresolvedCommentCount` | 0 이상 정수 | 제출물 전체의 미해결 피드백 수. K-11의 `countUnresolvedComments`와 같은 값. 승인 버튼을 막는 사유로 쓴다 |
| `rounds` | 배열 | `roundNo` 내림차순(최신이 먼저). 페이지 처리는 없다 |
| `latest` | 불리언 | 이 제출물의 가장 최근 회차인가. 새 코멘트 작성과 결정은 최신 회차에만 된다 |
| `file` | 객체 또는 `null` | 대상 파일 버전. 파일 없는 중간 검토면 `null`. 필드는 생략하지 않는다 |
| `file.shortHash` | 문자열 7자 | SHA-256의 앞 7자. 화면 표시용이다. 전체 해시는 파일 금고 API에서 본다 |
| `decision` | 객체 또는 `null` | 결정 전이면 `null`. 필드는 생략하지 않는다 |
| `decision.result` | `APPROVED`·`CHANGES_REQUESTED` | |
| `currentBasis` | 불리언 | 이 회차의 승인이 **지금 확정 근거인가**(아래) |
| 시각 | 시간대 포함 ISO-8601 | 기존 응답과 같은 형식 |

### 확정 근거 (`currentBasis`)

다음을 모두 만족할 때만 `true`다. 저장하지 않고 **조회할 때의 상태로만** 계산한다. 서버 한 곳에서 계산하고, K-20의 확정 검사도 같은 계산을 쓴다.

1. 결정이 `APPROVED`다
2. 최신 회차다(더 늦은 회차가 없다)
3. 파일이 있다. 파일 없는 회차의 승인은 확정 근거가 되지 않는다
4. 그 파일 이름의 **최신 버전이 이 회차의 파일과 내용(해시)이 같다.** 같은 내용을 다시 올려도 파일 금고는 버전을 올리므로, 버전 번호가 아니라 내용으로 비교한다. 최신 버전의 내용이 다르면 `false`다. 결정안(`docs/team/handoffs/A-10-20260930.md`)은 처음에 "더 높은 버전이 있는가"로 적었는데, 이 계약에서 내용 비교로 구체화하고 결정안과 CONTRACTS 3장 3항도 같은 기준으로 고쳤다

비교 대상은 그 이름의 **최신 버전 하나**다. 중간 버전은 보지 않는다. v1 승인 → 내용이 다른 v2 → v1과 같은 내용의 v3 순서로 올라오면 v2가 최신인 동안은 `false`이고 v3이 올라오면 다시 `true`다. 승인은 파일 내용에 대한 것이고, 지금 최신 내용이 승인받은 내용과 같기 때문이다. 승인된 회차에는 코멘트를 쓸 수 없으므로(2장) 그 사이에 이 회차에 쌓인 의견도 없다. 새 회차가 열렸다면 조건 2로 `false`이고 되살아나지 않는다.

**한계**: 다른 이름으로 올린 수정본은 같은 파일로 이어지지 않는다. 그 파일로 새 회차를 열기 전까지는 이전 승인이 근거로 남는다. 화면은 회차를 열 때 이전 회차와 파일 이름이 다르면 "같은 이름으로 올려야 새 버전으로 이어집니다"를 안내한다.

## 5. 다른 담당과 주고받는 것

도메인 사이에 서비스를 서로 주입하지 않도록 읽기 인터페이스로 나눈다(CONTRACTS 3장 12항).

### A가 제공: 회차 확인과 제출물 잠금

K-11·K-12의 쓰기 명령이 호출한다. 이름은 구현에서 바뀔 수 있고 의미는 아래로 고정한다.

```java
public interface ReviewRoundReader {
    // 프로젝트·제출물·회차가 서로 맞는지 확인한다. 맞지 않거나 없으면 NotFoundException
    ReviewRoundView get(UUID projectId, UUID deliverableId, UUID reviewId);

    // 같은 확인을 하되 제출물 행을 먼저 잠근다(쓰기 명령용). 같은 트랜잭션 안에서 호출한다
    ReviewRoundView lockForWrite(UUID projectId, UUID deliverableId, UUID reviewId);
}

public record ReviewRoundView(
        UUID reviewId, UUID deliverableId, UUID projectId, int roundNo,
        boolean latest,              // 최신 회차인가
        String decision,             // null · "APPROVED" · "CHANGES_REQUESTED"
        String deliverableStatus) {} // 2장의 표. K-20 이후 CONFIRMED·SUBMITTED 포함
```

호출하는 쪽이 사용자 권한(`requireContributor` 등)을 먼저 확인한다. 이 인터페이스는 권한을 보지 않는다.

### B가 제공: 미해결 피드백 수

```java
long countUnresolvedComments(UUID projectId, UUID deliverableId); // K-11 4장
```

A는 승인(이 계약)과 확정(K-20)에서 제출물 잠금을 잡은 뒤 이 조회를 부른다. 이 메서드를 가진 인터페이스는 부르는 쪽인 A의 검토 패키지에 선언하고, B-20이 구현을 등록한다. B-20이 병합되기 전에는 코멘트가 존재하지 않으므로, A-11은 0을 돌려주는 기본 구현으로 시작한다.

기본 구현이 실제 조회 누락을 가리지 않게 다음을 지킨다.

- 기본 구현은 조건 없이 등록하는 일반 빈으로 둔다. "다른 구현이 없을 때만 등록" 같은 조건부 등록을 쓰지 않는다
- B-20 PR이 실제 구현을 등록하면서 **같은 PR에서 기본 구현 파일을 지운다.** A 소유 파일이므로 A가 그 PR에서 확인한다
- 그러면 구현이 정확히 하나일 때만 서버가 뜬다. 둘 다 있거나 둘 다 없으면 시작 단계에서 실패하고, 0으로 승인 검사를 통과하는 경로는 남지 않는다. A의 승인 서비스는 이 인터페이스를 생성자에서 형식으로만 주입받는다(`@Primary`나 이름 지정을 쓰지 않는다)

### 동시 요청

회차 열기·결정·확정과 K-11·K-12의 쓰기 명령은 모두 **같은 제출물 행 잠금**을 먼저 잡는다. 그래서 같은 제출물에 대한 쓰기는 차례대로 처리되고, "승인 직전에 새 피드백이 끼어드는" 일이 없다. 회차 번호 중복은 DB 유일 제약으로도 막는다.

### 파일 업로드 (결정안 4장)

같은 이름으로 내용이 다른 파일을 올려도 `TAMPER` 경보를 만들지 않는다. 변경 기록(`tamper_detection_log`)과 업로드 응답의 `tamperDetected` 필드는 그대로 둔다. 기존 경보 정리는 B의 별도 작업이다.

## 6. DB (V21, A-11에서 작성)

```text

  project_id     UUID NOT NULL
  deliverable_id UUID NOT NULL
  round_no       INT  NOT NULL
  file_id        UUID NULL           -- 파일 없는 중간 검토는 NULL

  FOREIGN KEY (deliverable_id, project_id) → deliverables(id, project_id)
  FOREIGN KEY (file_id, project_id)        → file_vault(id, project_id)
  UNIQUE (deliverable_id, round_no)
  UNIQUE (id, deliverable_id, project_id)   -- K-11 코멘트의 복합 외래키용
```

## 7. 화면 (C)

- 목록 응답 하나로 검토 탭을 그릴 수 있다. 코멘트 내용은 K-11의 목록 API에서 회차별로 받는다
- 회차 열기 창의 파일 목록은 기존 `GET /api/projects/{projectId}/files`를 쓴다
- `currentBasis`가 `false`인 승인은 흐리게 표시하고 사유를 보여 준다. 사유는 응답만으로 정해진다: `latest`가 `false`면 "이후 새 회차가 열림", `file`이 `null`이면 "파일 없는 회차", 둘 다 아니면 "같은 이름의 최신 버전과 내용이 다름". 파일 목록을 다시 비교할 필요가 없다
- 승인 버튼은 `unresolvedCommentCount`가 0이 아니거나 본인이 올린 파일이면 비활성으로 두고 이유를 적는다
- fixture는 3장의 JSON에서 복사해 C가 관리한다. 실제 API로 바꾸는 시점은 A-11 병합 뒤다. #54의 임시 데이터 형식(`status`가 `OPEN`·`CLOSED`인 회차)은 이 계약과 달라 새로 맞춘다

## 10. 확인 결과와 정하지 않은 것

**손정협님(B)** — #69에서 세 차례 검토하고 0.2에 동의했다.

- 5장의 회차 확인·제출물 잠금 인터페이스는 K-11·K-12의 쓰기 검사에 충분하다. 승인된 회차의 코멘트 차단은 `decision == "APPROVED"`로 판단한다
- 승인 무효 기준(그 이름의 최신 버전과 내용 비교, 같은 내용으로 돌아오면 다시 근거), 기본 구현을 B-20 PR에서 지우는 방식, 다시 열었다 해결한 피드백의 예외에 동의했다

**손정효님(C)** — 검토 탭(#66)을 이 형식에 맞춰 브라우저로 확인하고 답했다.

- 3장 응답 하나로 검토 탭을 그릴 수 있고 빠진 값이 없다
- 회차를 언제든 열 수 있고 취소가 없는 흐름은 자연스럽다. 다만 사용자가 모르고 결정 전 회차를 버리지 않게, 화면은 회차 열기 창에서 "진행 중인 N회차는 결정 없이 남습니다"와 "새 회차를 열면 지금 승인은 확정 근거에서 빠집니다"를 보여 주고, 결정 없이 지나간 회차에는 "결정 없음"을 표시한다
- 제출물 상태를 이 응답에만 두는 것은 지금은 괜찮다

**정하지 않은 것**

- 결정에 의견(한 줄 사유)을 함께 남길지. 지금은 넣지 않았고, 의견은 K-11 코멘트로 남긴다
- 결정을 되돌리는 명령. 지금은 새 회차로만 바꾼다
- 제출물 목록 응답에 상태를 넣을지. 목록 카드에 상태를 보여 주게 되면 제출물마다 이 API를 부르게 되므로, 확정·제출 화면(K-20)을 만들 때 다시 정한다
- **팀장·팀원이 한 명뿐인 프로젝트.** 파일을 올린 사람은 결정할 수 없으므로(CONTRACTS 3장 3항) 혼자서는 파일이 있는 회차를 승인할 수 없고, 확정도 할 수 없다. 팀 과제를 전제로 한 규칙이라 그대로 두었지만, 1인 프로젝트를 허용할지는 K-20에서 함께 정한다. 정해지면 화면은 막힌 사람에게 다음 행동(팀원 초대 등)을 안내한다
