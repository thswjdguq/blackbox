# K-31 · 과제 안내문 공간과 빠졌거나 모호한 요구사항 찾기

- 버전: 0.3 / 상태: DRAFT (0.2에 B 검토(#162)를 반영했다: 바뀐 안내문의 근거 표시, 진척의 HTTP 검사. 마이그레이션 번호 V38. 0.3에 C 검토를 반영했다: 요구사항 근거의 원문, 오류 응답의 `code`와 칸, 계획 만들기의 안내문 재사용 알림)
- 생산자: 송승준(A) / 소비자: 손정효(C, 안내문 공간·제출물 연결·제안 카드 화면), 손정협(B, 요구사항이 바뀔 때의 진척 K-13)
- 기능: S2 / 작성일: 2026-11-08 (0.2와 0.3은 2026-11-09) / 기준 SHA: `5adea21`
- 근거: 주간 계획(#158) 정할 것 2, 중간발표 향후 일정의 "빠졌거나 모호한 요구사항 찾기(과제 안내문 저장)"
- 관련: K-14(요구사항 충족 확인), K-20(확정 뒤 잠금), K-30(실행과 제안 카드). K-30에서 바뀌는 것은 10장
- 범위: 1단계. 안내문 공간, 제출물 연결, 계획 만들기의 안내문 저장, 요구사항 찾기. PDF·HWP 등 파일에서 글자를 뽑는 기능은 없다

## 1. 무엇을 약속하는가

- **안내문은 프로젝트 단위로 둔다.** 하나의 안내문이 여러 제출물(발표자료, 보고서 등)을 요구할 수 있다. 멤버는 언제든 안내문 공간에서 본다
- **제출물에 안내문을 거는 것은 선택이다.** 구두로만 전달된 과제는 걸지 않는다. 한 제출물에 여럿(원래 안내문과 추가 공지)을 걸 수 있다
- **쓰이는 안내문은 지우지 않는다.** 걸린 제출물이나 검토 대기 중인 제안 카드가 있으면 삭제를 막고, 무엇이 쓰고 있는지 알린다(2.4)
- **AI의 지적에는 근거가 있다.** 카드의 문장마다 안내문의 문장 번호를 근거로 달고, 서버가 그 번호가 실제로 있는지 확인한다. 근거가 없는 지적은 카드가 되지 않는다(6장)
- **AI는 요구사항을 직접 바꾸지 않는다.** 결과는 제안 카드이고, 사람이 채택할 때 그 사람의 권한으로 바뀐다(K-30 1장)

## 2. 과제 안내문

기본 경로: `/api/projects/{projectId}/briefs`. 모든 id는 UUID다.

### 2.1 안내문 객체

```json
{
  "id": "…",
  "title": "웹 프로젝트 중간 과제",
  "body": "…",
  "sourceFile": { "id": "…", "fileName": "과제안내.pdf", "version": 1 },
  "createdBy": { "id": "…", "name": "김민지" },
  "createdAt": "2026-11-08T10:00:00+09:00",
  "updatedBy": { "id": "…", "name": "김민지" },
  "updatedAt": "2026-11-08T10:00:00+09:00",
  "bodyHash": "sha256 hex",
  "usage": {
    "deliverables": [ { "id": "…", "title": "중간 보고서", "status": "DRAFT" } ],
    "pendingProposals": 2
  },
  "locked": false
}
```

- `title`: 1~200자. `body`: 1~20000자(`app.agent.brief-max-length`와 같다). AI가 읽는 것은 `body`다
- `sourceFile`: 원본 파일(선택). 같은 프로젝트 파일 금고의 파일 버전이다. 화면은 내려받기 링크로만 쓴다
- `bodyHash`: `body`의 SHA-256. 카드의 근거가 만들어진 뒤 안내문이 바뀌었는지 가린다(6.4)
- `usage`: 이 안내문을 쓰는 곳. 삭제 가능 여부와 안내 문구는 이 값으로 정한다(2.4)
- `locked`: 걸린 제출물 중 확정(`CONFIRMED`) 또는 제출(`SUBMITTED`)된 것이 있으면 `true`. 고칠 수 없다(2.3)

### 2.2 명령

| 명령 | 요청 | 성공 | 역할 |
| --- | --- | --- | --- |
| 목록 | GET `/briefs` | 200, 안내문 배열(최근 수정이 먼저) | 팀장·팀원·관찰자 |
| 조회 | GET `/briefs/{briefId}` | 200, 안내문 | 팀장·팀원·관찰자 |
| 등록 | POST `/briefs`, `{ "title", "body", "sourceFileId"? }` | 201, 안내문 | 팀장·팀원 |
| 수정 | PUT `/briefs/{briefId}`, 등록과 같은 본문 | 200, 안내문 | 팀장·팀원 |
| 삭제 | DELETE `/briefs/{briefId}` | 204 | 팀장·팀원 |

### 2.3 수정

- `locked`인 안내문은 고칠 수 없다(409, `BRIEF_LOCKED`). 확정의 근거가 바뀌지 않게 하기 위해서다. 바뀐 내용은 추가 공지로 새로 등록해 아직 확정하지 않은 제출물에 건다
- 고치면 `bodyHash`가 바뀐다. 그 안내문을 근거로 만든 검토 대기 카드는 지우지 않고 "근거 안내문이 바뀜"으로 표시한다(6.4)

### 2.4 삭제

쓰는 곳이 있으면 지울 수 없다. 사용자가 직접 지우기 전까지 안내문은 남는다(채택하지 않은 안내문도 다시 계획을 세울 때 쓴다).

| 쓰는 곳 | 결과 | 응답 |
| --- | --- | --- |
| 걸린 제출물이 있다(상태와 관계없이) | 409, `BRIEF_IN_USE` | `usage.deliverables`를 담는다 |
| 검토 대기(`PENDING`) 제안 카드가 이 안내문을 근거로 한다 | 409, `BRIEF_IN_USE` | `usage.pendingProposals`를 담는다 |
| 없다 | 204 | |

- 화면은 누르기 전에 알린다. `usage`가 비어 있지 않으면 삭제 버튼을 비활성화하고, 무엇이 쓰는지와 바로가기(제출물, AI 도우미의 제안 탭)를 보여 준다
- 카드를 채택하면 제출물이 걸리고(4장), 거절하면 그 카드는 더 이상 막지 않는다

## 3. 제출물과 안내문 연결

| 명령 | 요청 | 성공 | 역할 |
| --- | --- | --- | --- |
| 걸기 | POST `/deliverables/{deliverableId}/briefs/{briefId}` | 200, 그 제출물의 안내문 요약 배열 | 팀장·팀원 |
| 떼기 | DELETE `/deliverables/{deliverableId}/briefs/{briefId}` | 200, 같은 배열 | 팀장·팀원 |

- 안내문 요약: `{ "id", "title", "bodyHash", "linkedAt" }`. 건 순서(오래된 것부터)
- 제출물 조회 응답(`DeliverableDtos`)에 같은 배열을 `briefs`로 더한다. 기존 칸은 바꾸지 않는다
- 확정·제출된 제출물에는 걸거나 뗄 수 없다(409, 기존 `lockEditable`과 같다)
- 이미 걸린 안내문을 다시 걸거나 걸리지 않은 것을 떼면 지금 배열을 그대로 돌려준다(중복 클릭)
- 안내문 화면에서도 같은 명령으로 뗀다. 잘못 건 안내문을 제출물마다 열지 않고 정리하게 한다
- 떼어도 그 안내문을 근거로 한 검토 대기 카드는 남고 채택할 수 있다. 근거 원문은 카드에 있다(7장)

## 4. 계획 만들기의 변경(`PLAN_FROM_BRIEF`)

`input`은 둘 중 하나다.

| `input` | 하는 일 |
| --- | --- |
| `{ "briefId": "…" }` | 저장된 안내문으로 계획을 만든다 |
| `{ "briefText": "…", "briefTitle"?: "…" }` | **실행 전에** 안내문 공간에 먼저 저장하고(제목이 없으면 "과제 안내문 yyyy-MM-dd"), 그 안내문으로 계획을 만든다. 실행은 입력을 남기지 않으므로 먼저 저장해야 나중에 비교할 수 있다 |

- 저장은 실행 가능 검사(동시 실행 409, 시간당 상한 429)를 통과한 뒤에 한다. 막힌 실행으로 안내문이 쌓이지 않게 하기 위해서다
- 같은 프로젝트에 본문이 같은(`bodyHash`가 같은) 안내문이 있으면 새로 만들지 않고 그것을 쓴다. 두 번 누르거나 같은 안내문을 다시 붙여 넣어도 중복이 생기지 않는다
- 실행이 모델 오류로 끝나도 저장한 안내문은 남는다. 화면은 그 안내문(`briefId`)으로 다시 실행하게 한다
- 이벤트 스트림의 첫 `step`에 쓴 안내문의 `briefId`, `briefTitle`, 새로 저장했는지(`briefCreated`)를 담는다. 화면은 새로 저장했으면 "안내문 공간에 저장했습니다", 본문이 같은 안내문을 썼으면 "기존 안내문 '…'을 썼습니다"를 알린다
- `DELIVERABLE_PLAN` 카드 `content`에 `briefId`를 더한다. 채택하면 만들어진 제출물에 그 안내문이 걸린다. 한 안내문에서 카드가 여러 장이면 모두 같은 안내문에 걸린다
- `briefText`만 받던 기존 화면은 그대로 동작한다(저장이 더해질 뿐이다)

## 5. 요구사항 찾기(`FIND_REQUIREMENT_GAPS`)

| `skill` | 하는 일 | `input` | 결과 | 역할 |
| --- | --- | --- | --- | --- |
| `FIND_REQUIREMENT_GAPS` | 한 제출물에 걸린 안내문들과 등록된 요구사항을 비교해 빠진 것과 모호한 것을 찾는다 | `{ "deliverableId": "…" }` | `REQUIREMENT_ADD`, `REQUIREMENT_REVISE` 카드. 찾은 것마다 한 장. 없으면 카드 없이 글로 답한다 | 팀장·팀원 |

- 걸린 안내문이 없으면 400(`NO_BRIEF`, "제출물에 과제 안내문을 먼저 걸어 주세요")
- 확정·제출된 제출물이면 409(고칠 수 없으므로 찾지 않는다)
- 걸린 안내문들의 `body` 합이 20000자를 넘으면 400(`BRIEFS_TOO_LONG`). 응답에 안내문별 글자 수를 담아 무엇을 뗄지 고르게 한다(모양은 8장)
- 이미 같은 문구(앞뒤 공백·대소문자 무시)의 요구사항이 있으면 `REQUIREMENT_ADD` 카드를 만들지 않는다
- 카드 하나는 지적 하나다. 따로 채택하고 거절할 수 있게 하기 위해서다

### 5.1 `REQUIREMENT_ADD`(빠진 요구사항)

채택하면 그 제출물에 요구사항이 추가된다(K-14의 요구사항 저장과 같은 검증). 카드를 만든 뒤 제출물이 확정됐으면 채택은 409다(기존 잠금).

### 5.2 `REQUIREMENT_REVISE`(모호한 요구사항)

| 칸 | 뜻 |
| --- | --- |
| 지금 문구 | 카드를 만들 때의 요구사항 문구(스냅숏) |
| 모호한 점 | 무엇이 모호한지 |
| 수정안 | 고친 문구. **안내문에 근거가 있을 때만** 낸다 |
| 확인 질문 | 교수님 등에게 물을 것 |

- **채택**: 요구사항이 수정안으로 바뀐다. 충족 확인이 있던 요구사항이면 기존 규칙대로 확인이 풀리고(문구가 달라지면 푼다), 결과에 `assessmentCleared: true`를 담는다
- **고치기**: K-30의 카드 수정으로 수정안을 다듬은 뒤 채택한다
- **질문만**: 안내문만으로 정할 수 없으면 수정안 없이 확인 질문만 낸다. 이 카드는 채택할 수 없고(409, `QUESTION_ONLY`) 거절로 닫는다. 화면은 "확인 필요"로 보인다
- 카드를 만든 뒤 그 요구사항의 문구가 바뀌었거나 요구사항이 지워졌으면 채택은 409(`REQUIREMENT_CHANGED`)다. 다시 찾게 한다. 제출물이 확정됐으면 409다(기존 잠금)

## 6. 문장 번호와 근거

### 6.1 문장 번호

- 서버가 걸린 안내문을 건 순서대로 `B1`, `B2`…로, 각 안내문의 문장을 `S1`, `S2`…로 번호 붙여 모델에 보낸다. 예: `[B1-S4] 보고서는 A4 10쪽 이내로 작성한다.`
- 문장 나누기: 줄바꿈마다 나누고, 한 줄 안에서는 마침표·물음표·느낌표 뒤의 공백에서 나눈다. 목록의 항목은 한 문장이다. 빈 줄은 번호를 받지 않는다
- 같은 안내문 본문이면 번호가 같다(같은 규칙, 같은 결과)
- 요구사항도 `R1`, `R2`…로 번호 붙여 보낸다

### 6.2 근거 달기

- 모델은 카드의 문장마다 근거 번호 배열을 단다. `REQUIREMENT_ADD`의 요구사항 문구와 이유, `REQUIREMENT_REVISE`의 모호한 점·수정안 각각이다
- `R` 번호는 `REQUIREMENT_REVISE`의 모호한 점에만 근거로 인정한다. 그 카드가 고치는 요구사항뿐 아니라 다른 요구사항도 가리킬 수 있다(예: "R2와 R3이 겹친다"). 겹침처럼 다른 요구사항을 보아야 드러나는 모호함이 있기 때문이다. 그 밖의 문장은 `B` 번호가 있어야 한다
- 확인 질문에는 근거를 요구하지 않는다(안내문에 없는 것을 묻는 문장이므로)
- 모델에게 문장을 옮겨 쓰게 하지 않는다. 옮기면서 글자를 바꾸거나 요약할 수 있기 때문이다. 원문은 서버가 번호로 찾아 넣는다

### 6.3 서버의 검사

아래 순서로 검사한다.

1. 근거 번호가 그 실행에 보낸 번호인지 확인한다. 없는 번호와 6.2에서 인정하지 않는 번호는 지운다
2. `REQUIREMENT_REVISE`의 수정안에 `B` 번호가 남지 않았으면 수정안을 빼고 질문만 카드로 바꾼다. 확인 질문도 없으면 카드를 만들지 않는다
3. 그 밖에 근거가 하나도 남지 않은 문장이 있으면 그 카드를 만들지 않는다
- 버린 카드 수는 실행의 마지막 글에 "근거를 확인할 수 없어 n건은 제외했습니다"로 알린다

### 6.4 저장과 표시

- 카드 `content.evidenceText`에 번호마다 안내문 id, 원문, 본문 안의 위치(`start`·`end`, 글자 단위), 그 안내문의 `bodyHash`를 저장한다
- 카드 `content.evidenceRequirements`에 카드가 쓴 `R` 번호마다 요구사항 id와 실행 때의 문구를 저장한다. 화면은 `R` 번호 옆에 이 문구를 보인다. 그 뒤 요구사항이 바뀌거나 지워졌으면 지금 요구사항 대신 이 문구를 "카드를 만들 때의 문구"로 보인다
- 근거 하나는 `briefId`, `bodyHash`, `start`·`end`로 가린다. 화면은 카드의 문장 옆에 근거 번호를 보이고, 누르면 안내문 공간에서 그 안내문을 연다. 화면이 문장을 직접 나누지 않는다
- 안내문의 지금 `bodyHash`가 카드에 저장된 것과 같을 때만 `start`~`end`를 강조한다
- `B1`·`B2`는 그 실행에서 건 순서로 붙인 이름이라 제출물마다 다를 수 있다. 안내문은 `briefId`로 가린다
- 다르면 지금 본문에 옛 위치를 쓰지 않는다. 글자가 밀려 다른 문장을 가리킬 수 있기 때문이다. 대신 카드에 저장된 원문을 "카드를 만들 때의 문장"으로 보이고 "근거 안내문이 바뀜"을 함께 보인다. 채택은 막지 않는다(사람이 판단한다)
- 근거 안내문이 삭제될 수 없으므로(2.4) 검토 대기 카드의 근거가 사라지는 일은 없다

## 7. 카드 `content`

```json
{
  "kind": "REQUIREMENT_ADD",
  "deliverableId": "…",
  "requirement": { "content": "보고서는 A4 10쪽 이내로 작성한다", "required": true, "evidence": ["B1-S4"] },
  "reason": { "text": "안내문의 분량 조건이 요구사항에 없다", "evidence": ["B1-S4"] },
  "evidenceText": { "B1-S4": { "briefId": "…", "text": "보고서는 A4 10쪽 이내로 작성한다.", "start": 120, "end": 141, "bodyHash": "…" } }
}
```

```json
{
  "kind": "REQUIREMENT_REVISE",
  "deliverableId": "…",
  "requirementId": "…",
  "currentContent": "보고서 제출",
  "issue": { "text": "형식과 분량이 정해지지 않았다", "evidence": ["R2", "B1-S4"] },
  "revision": { "content": "보고서는 PDF로, A4 10쪽 이내로 제출한다", "evidence": ["B1-S4", "B1-S7"] },
  "question": "표지와 참고문헌도 10쪽에 포함되는지 확인이 필요합니다",
  "evidenceText": { "B1-S4": { "…": "…" }, "B1-S7": { "…": "…" } },
  "evidenceRequirements": { "R2": { "requirementId": "…", "content": "보고서 제출" } }
}
```

- `revision`이 `null`이면 질문만 카드다(5.2)
- `R` 번호의 원문은 `evidenceText`가 아니라 `evidenceRequirements`에 둔다. 그 카드가 고치는 요구사항도 `R` 근거로 쓰였으면 여기에 들어가고, 내용은 `currentContent`와 같다
- 카드 수정(K-30)으로 바꿀 수 있는 칸은 `requirement.content`, `requirement.required`, `revision.content`, `question`이다. 근거와 원문은 바꿀 수 없다

## 8. 권한과 오류

오류는 기존 ProblemDetail(`status`, `detail`)에 확장 칸을 더한다. 아래 표에 이름이 있는 오류는 `code`에 그 이름을 담고, 화면은 `code`로 안내를 나눈다(걸기 유도, "다시 찾기" 버튼 등). `code`가 없는 오류는 지금처럼 `detail`만 보인다.

```json
{ "status": 409, "detail": "이 안내문을 쓰는 곳이 있어 지울 수 없습니다", "code": "BRIEF_IN_USE",
  "usage": { "deliverables": [ { "id": "…", "title": "중간 보고서", "status": "DRAFT" } ], "pendingProposals": 2 } }
```

```json
{ "status": 400, "detail": "걸린 안내문의 글자 수 합이 20000자를 넘습니다. 일부를 떼어 주세요", "code": "BRIEFS_TOO_LONG",
  "limit": 20000, "total": 23500, "briefs": [ { "id": "…", "title": "웹 프로젝트 중간 과제", "length": 15000 }, { "id": "…", "title": "추가 공지", "length": 8500 } ] }
```

- `BRIEF_IN_USE`의 `usage`는 2.1 안내문 객체의 `usage`와 같은 모양이다
- `BRIEFS_TOO_LONG`의 `briefs`는 걸린 순서(오래된 것부터)다

| 경우 | 응답 |
| --- | --- |
| 프로젝트 멤버가 아님 | 403 |
| 관찰자가 등록·수정·삭제·걸기·떼기·실행 | 403 |
| 다른 프로젝트의 안내문·제출물·파일 | 404 |
| 제목·본문 길이 초과 | 400 |
| 걸린 안내문 합계 초과 | 400 `BRIEFS_TOO_LONG` + `limit`, `total`, `briefs` |
| 확정된 제출물이 쓰는 안내문 수정 | 409 `BRIEF_LOCKED` |
| 쓰는 곳이 있는 안내문 삭제 | 409 `BRIEF_IN_USE` + `usage` |
| 확정·제출된 제출물에 걸기·떼기, 그 제출물로 요구사항 찾기 | 409 |
| 걸린 안내문 없이 요구사항 찾기 | 400 `NO_BRIEF` |
| 질문만 카드 채택 | 409 `QUESTION_ONLY` |
| 카드 뒤 요구사항 문구가 바뀌었거나 지워진 상태에서 수정 카드 채택 | 409 `REQUIREMENT_CHANGED` |
| 카드 뒤 제출물이 확정된 상태에서 채택 | 409 |

## 9. DB

마이그레이션 번호는 V38이다. 번호는 기능의 병합 순서대로 정했다: 확정 취소(#133) V36 → 기여도 집계 저장(K-40) V37 → 이 계약 V38. 병합도 이 순서로 한다. 서버의 Flyway는 이미 적용된 번호보다 낮은 번호를 받지 않는다. 순서를 바꿔야 하면 바뀌는 PR들이 모두 병합 전일 때 번호를 함께 바꾼다.

- `project_briefs`: `id`, `project_id`, `title`, `body`, `body_hash`, `source_file_id`(파일 금고, 선택), `created_by`, `created_at`, `updated_by`, `updated_at`. 프로젝트 쪽 외래 키는 기존 표와 같이 `CASCADE`다. 파일 금고에는 삭제 기능이 없으므로 `source_file_id`는 일반 외래 키다. 같은 프로젝트 안에서 `body_hash`로 찾을 수 있게 색인을 둔다(4장)
- `deliverable_briefs`: `deliverable_id`, `brief_id`, `linked_by`, `linked_at`. 기본 키는 두 id. 안내문 쪽 외래 키는 `NO ACTION`이다(걸린 안내문은 DB도 지우지 못한다). 검사를 문장 끝에 하므로, 프로젝트를 지울 때 제출물·연결·안내문이 한 문장 안에서 함께 지워지는 경우에도 지우는 순서와 관계없이 된다(PostgreSQL 16 임시 DB에서 걸린 안내문의 직접 삭제는 막히고 프로젝트 삭제는 되는 것을 확인). 제출물 쪽은 `CASCADE`다(제출물을 지우면 연결만 지워진다)
- `agent_proposal_briefs`: `proposal_id`, `brief_id`. 카드가 근거로 쓰는 안내문. 검토 대기(`PENDING`) 카드가 있으면 서비스가 삭제를 막는다. 채택·거절한 카드는 막지 않으므로 외래 키는 양쪽 모두 `CASCADE`다. 결정한 카드의 근거 원문은 카드 `content`에 남아 있다(6.4)

## 10. K-30에서 바뀌는 것

- 1장과 8장의 "안내문과 질문의 원문은 저장하지 않는다"를 "질문 원문은 저장하지 않는다. 안내문은 안내문 공간에 저장된 것만 남는다(K-31)"로 바꾼다
- 2장 실행 종류 표에 `FIND_REQUIREMENT_GAPS`를, 3장 종류별 `content`에 `REQUIREMENT_ADD`·`REQUIREMENT_REVISE`를 더하고, `PLAN_FROM_BRIEF`의 `input`을 4장대로 바꾼다
- 안내문은 지금도 모델에 보내고 있다(Bedrock). 저장한 안내문을 다시 보내는 것 말고 새로 보내는 자료는 없다. 안내문에 개인정보를 적지 말라는 안내를 안내문 공간에 둔다

## 11. 화면(C)

- 안내문 공간: 목록(제목, 쓰는 제출물, 수정 시각), 등록·수정(본문 붙여 넣기, 원본 파일 고르기), 삭제 버튼의 비활성 안내(2.4)
- 제출물 화면: 걸린 안내문 목록, 걸기·떼기, "요구사항 찾기" 버튼(걸린 안내문이 없으면 걸기를 안내)
- 제안 카드: 빠진 요구사항·수정안·질문만 세 모양. 문장 옆 근거 번호와 안내문 강조, 안내문이 바뀌었으면 강조 대신 저장된 원문과 "근거 안내문이 바뀜"(6.4), 채택 뒤 "충족 확인이 풀렸습니다"
- 계획 만들기: 저장된 안내문 고르기 또는 붙여 넣기. 붙여 넣으면 저장된다는 안내

## 12. 확인을 부탁하는 것

- 손정효님(답변, #162): 안내문 공간, 제출물 화면, 카드의 세 모양은 응답만으로 그려진다. 세 곳의 보완을 요청했고 반영했다: 바뀐 안내문의 근거 표시(6.4), 다른 요구사항을 가리키는 `R` 근거의 원문(`evidenceRequirements`, 6.2·6.4·7장), 오류의 `code`와 글자 수 초과 응답의 모양(8장). 계획 만들기의 안내문 재사용 알림(4장)도 더했다
- 손정협님(답변, #162): 진척(K-13)은 조회할 때 필수 요구사항의 전체·충족 수를 직접 세므로, 요구사항을 기존 저장 경로(`DeliverableService.saveRequirement`)로 추가·수정하면 따로 다시 계산할 것은 없다. 다만 13장의 진척 검사를 실제 HTTP 응답으로 확인한다. 바뀐 안내문의 근거는 옛 위치 대신 저장된 원문을 보인다(6.4에 반영)

## 13. 수용 테스트

- 안내문 하나를 두 제출물에 걸고, 각 제출물에서 요구사항 찾기가 그 안내문의 같은 문장에 같은 `S` 번호와 위치를 쓴다
- 걸린 제출물이 있거나 검토 대기 카드가 있으면 삭제가 409이고 `usage`가 맞다. 둘 다 없으면 지워진다
- 확정된 제출물에 걸린 안내문은 고칠 수 없고, 그 제출물에서는 걸기·떼기가 409다
- `briefText`로 계획을 만들면 실행 전에 안내문이 저장되고, 카드를 채택하면 만들어진 제출물에 걸린다
- 모델이 없는 근거 번호를 달면 그 번호는 지워지고, 근거가 남지 않은 카드는 만들어지지 않는다
- 수정안에 `B` 근거가 없으면 질문만 카드가 되고, 그 카드는 채택이 409다. 확인 질문도 없으면 카드가 만들어지지 않는다
- 수정 카드를 채택하면 충족 확인이 풀리고 `assessmentCleared: true`다. 카드 뒤 문구가 바뀌었으면 409다
- 안내문을 고치면 그 안내문을 근거로 한 카드에 "근거 안내문이 바뀜"이 보이고, 근거를 열면 지금 본문의 옛 위치를 강조하지 않고 저장된 원문을 보인다
- 진척(실제 DB에서 진척 조회 HTTP 응답, K-13)
  - 선택 요구사항(`required: false`)을 채택으로 더하면 `requiredRequirements.total`은 그대로다
  - 필수 요구사항을 채택으로 더하면 `requiredRequirements.total`이 1 늘고 `met`은 그대로다
  - 충족 확인된 필수 요구사항의 문구를 수정 카드로 바꾸면 `met`이 1 준다
  - 요구사항 카드를 채택해도 `tasks`(업무 수·완료 수)와 업무의 완료 승인은 바뀌지 않는다
- 같은 본문으로 계획 만들기를 두 번 하면 안내문은 하나다. 두 번째 실행의 첫 `step`은 `briefCreated: false`다. 실행이 409·429로 막히면 안내문이 저장되지 않는다
- 수정 카드가 다른 요구사항(`R3`)을 근거로 들면 `evidenceRequirements.R3`에 실행 때의 문구가 저장된다. 그 뒤 R3의 문구를 바꿔도 카드에는 실행 때의 문구가 남는다
- 안내문 삭제가 막히면 응답의 `code`가 `BRIEF_IN_USE`이고 `usage`가 2.1과 같은 모양이다. 걸린 안내문 합계가 넘으면 `code`가 `BRIEFS_TOO_LONG`이고 `briefs`의 글자 수 합이 `total`이다
- 안내문이 걸린 제출물이 있는 프로젝트도 프로젝트 삭제는 된다
