## 1. 무엇을 약속하는가

팀장이 제출물의 최종본을 확정하고, 학교에 낸 뒤 그 사실을 기록한다.

- 확정은 팀장의 명시 동작이다. 서버는 필수 요구사항 충족, 최신 회차의 승인, 미해결 피드백 0건을 그 자리에서 다시 검사한다(CONTRACTS 3장 8항)
- 확정본은 **승인된 회차가 가리키는 파일 버전**이다. 회차의 대상은 바뀌지 않으므로(K-10 1장) 이후 같은 이름의 새 버전이 올라와도 확정본이 무엇이었는지 남는다
- 확정하면 그 제출물의 요구사항, 연결 업무, 피드백, 회차는 더 이상 바뀌지 않는다(4장)
- 확정을 되돌리는 명령은 두지 않는다(CONTRACTS 3장 9항)
- 제출 기록은 사람이 학교 시스템 등에 낸 뒤 남기는 기록이다. 앱이 대신 제출하거나 접수를 확인하지 않는다(CONTRACTS 3장 10항)

## 2. 명령

기본 경로: `/api/projects/{projectId}/deliverables/{deliverableId}`. 모든 id는 UUID이고 기존 쿠키 인증을 쓴다.

| 명령 | 요청 | 성공 | 역할 |
| --- | --- | --- | --- |
| 확정 준비와 확정 정보 조회 | GET `/confirmation` | 200, 3장의 객체 | 팀장·팀원·관찰자 |
| 최종본 확정 | PUT `/confirmation`, `{ "reviewId": "…" }` | 200, 3장의 객체 | 팀장 |
| 제출 기록 | PUT `/submission`, `{ "channel": "…", "submittedAt": "…", "note": "…" }` | 200, 3장의 객체 | 팀장·팀원 |

세 명령 모두 같은 객체를 돌려준다. 확정이나 기록 뒤에 화면이 다시 조회하지 않아도 된다.

### 확정

- 요청의 `reviewId`는 **화면이 보여 준 확정 대상 회차**다(3장의 `candidate.reviewId`). 세 검사를 통과한 뒤 서버가 계산한 대상과 다르면 409다. 팀장이 화면에서 본 것과 다른 파일이 확정되는 일을 막는다. 그 사이 새 회차가 열렸다면 대조까지 가지 않고 검사 2의 사유가 나온다
- 서버는 제출물 행을 잠근 뒤(K-10 5장의 잠금) 이 순서로 처리한다: 이미 확정됐는지 확인 → 아래 세 검사 → `reviewId` 대조. 검사를 하나라도 통과하지 못하면 409이고 `detail`에 첫 번째로 막힌 이유를 적는다
  1. 필수 요구사항이 모두 충족 확인됐다. 필수 요구사항이 하나도 없으면 통과로 보되, `detail`은 "필수 요구사항이 없습니다"로 적는다. 빈 목록을 모두 확인한 것처럼 보이지 않게 한다(CONTRACTS 3장 2항)
  2. 최신 회차가 승인됐고 그 승인이 지금 확정 근거다(K-10 3장의 `currentBasis`). 파일 없는 회차의 승인, 이후 새 회차가 열린 승인, 최신 버전과 내용이 다른 승인은 통과하지 못한다
  3. 미해결 피드백이 0건이다(K-10 5장의 `countUnresolvedComments`). 지난 회차에서 다시 연 피드백도 센다
- 이미 확정된 제출물에 **같은 `reviewId`** 로 다시 요청하면 지금 객체를 그대로 돌려준다(중복 클릭). 다른 `reviewId`면 409다
- 확정을 취소하거나 다시 여는 명령은 없다. 고쳐야 하면 새 제출물로 다시 만든다

### 제출 기록

- 상태가 `CONFIRMED`일 때만 된다. 확정 전이면 409다
- `submittedAt`은 실제로 낸 시각이다. 필수이고, 서버 시각보다 5분 넘게 뒤면 400이다. 확정 시각보다 앞서도 받는다(먼저 내고 나중에 확정하는 팀도 있다)
- `channel`은 낸 곳이다(예: 학교 LMS 과제함). 500자까지. `null`이거나 생략하면 제출물의 제출 경로(`submissionMethod`)를 그대로 쓴다. 둘 다 비어 있으면 `null`로 남는다
- `note`는 증빙 메모다(접수 번호, 확인 메일 제목 등). 선택이고 1000자까지. `null`·생략·빈 문자열은 `null`로 저장한다
- 증빙 파일은 받지 않는다. 필요하면 파일 금고에 올리고 메모에 파일 이름을 적는다
- 기록은 한 번이다. 이미 기록된 제출물에 **같은 내용**을 다시 보내면 지금 객체를 돌려주고, 다른 내용이면 409다. 잘못 기록했을 때 고치는 명령은 이 계약 범위 밖이다

### 제출물 상태

K-10 2장의 표 앞에 두 줄이 더해진다. 위에서부터 먼저 맞는 것이 상태다.

| 조건 | 상태 |
| --- | --- |
| 제출 기록이 있다 | `SUBMITTED` |
| 확정 기록이 있다 | `CONFIRMED` |
| 회차가 없다 | `DRAFT` |
| 최신 회차가 결정 전이다 | `IN_REVIEW` |
| 최신 회차가 `CHANGES_REQUESTED`다 | `DRAFT` (보완 중) |
| 최신 회차가 `APPROVED`다 | `IN_REVIEW` (확정 대기) |

확정과 제출 기록은 저장되는 사실이고, 그 앞의 상태는 지금처럼 회차에서 계산한다.

### 제출물 응답에 상태 추가

제출물 목록과 단건 조회(`GET /api/projects/{projectId}/deliverables`, `…/{id}`) 응답에 두 필드를 더한다. 목록 카드, 업무 보드, 프로젝트 홈이 제출물마다 회차 API를 부르지 않아도 된다. 필드 추가라 기존 화면은 그대로 동작한다.

| 필드 | 값 | 의미 |
| --- | --- | --- |
| `status` | `DRAFT`·`IN_REVIEW`·`CONFIRMED`·`SUBMITTED` | 위 표의 값 |
| `latestDecision` | `null`·`APPROVED`·`CHANGES_REQUESTED` | 최신 회차의 결정. 회차가 없거나 결정 전이면 `null` |

`status`만으로는 회차가 없는 초안과 수정 요청을 받은 초안, 검토 중과 승인된 확정 대기가 구분되지 않는다. 프로젝트 홈의 단계 안내(C-30 3장)가 이 구분을 쓰므로 `latestDecision`을 함께 준다. `APPROVED`여도 그 뒤에 내용이 다른 새 버전이 올라왔을 수 있다. 확정할 수 있는지는 `GET /confirmation`만 답한다.

K-10의 회차 목록 응답의 `deliverableStatus`와 `ReviewRoundView.deliverableStatus`에도 `CONFIRMED`·`SUBMITTED`가 나온다(K-10 2장과 5장이 예고한 대로다).

| 필드 | 값 | 의미 |
| --- | --- | --- |
| `status` | `DRAFT`·`IN_REVIEW`·`CONFIRMED`·`SUBMITTED` | 2장의 표로 정한 값 |
| `canConfirm` | 불리언 | 세 검사를 모두 통과했고 아직 확정 전인가. 요청한 사람의 역할은 보지 않는다. 버튼을 누구에게 보여 줄지는 화면이 역할로 정한다 |
| `checks` | 배열 | 확정 전에는 항상 아래 세 항목이 이 순서로 들어 있다. 확정 뒤에는 빈 배열이다 |
| `checks[].code` | `REQUIRED_REQUIREMENTS`·`APPROVED_FILE`·`NO_UNRESOLVED_COMMENTS` | 어느 검사인가. 화면이 고칠 곳으로 가는 링크를 고를 때 쓴다 |
| `checks[].passed` | 불리언 | 통과했는가 |
| `checks[].detail` | 문자열 | 사람이 읽는 문장. 통과하지 못했으면 다음에 할 일을 알 수 있게 쓴다. 화면은 그대로 보여 준다 |
| `candidate` | 객체 또는 `null` | 지금 확정하면 확정본이 될 회차와 파일. `APPROVED_FILE`을 통과했을 때만 있다. `file`의 모양은 K-10 3장과 같다 |
| `soleContributor` | 불리언 | 팀장·팀원이 한 명뿐인가(5장) |
| `confirmation` | 객체 또는 `null` | 확정 전이면 `null`. 필드는 생략하지 않는다 |
| `confirmation.fileStillLatest` | 불리언 | 확정본이 지금도 그 파일 이름의 최신 내용인가. 확정 뒤에 내용이 다른 새 버전이 올라오면 `false`가 된다. 확정본은 바뀌지 않는다 |
| `submission` | 객체 또는 `null` | 기록 전이면 `null`. 필드는 생략하지 않는다 |
| 시각 | 시간대 포함 ISO-8601 | 기존 응답과 같은 형식 |

`APPROVED_FILE`이 통과하지 못했을 때의 `detail`은 K-10 7장의 사유와 같은 말을 쓴다: 회차가 없음, 최신 회차가 결정 전, 수정 요청을 받음, 파일 없는 회차, 최신 버전과 내용이 다름.

## 4. 확정 뒤에 막히는 것

`CONFIRMED`와 `SUBMITTED`에서는 아래 표대로다. 막는 것은 모두 409이고 `detail`은 "확정된 제출물은 변경할 수 없습니다"를 기본으로 한다. 화면은 같은 표로 버튼을 숨긴다.

| 대상 | 동작 | 확정 뒤 | 구현 |
| --- | --- | --- | --- |
| 제출물 | 수정, 삭제 | 409 | A |
| 요구사항 | 추가, 수정, 삭제 | 409 | A |
| 요구사항 | 충족 확인, 확인 해제 | 409 | A |
| 검토 회차 | 열기, 결정 | 409 | A |
| 피드백 | 작성, 해결, 다시 열기 | 409 (K-11이 이미 정함) | B |
| 피드백의 업무 전환 | 새 업무 만들기 | 409 (K-12가 이미 정함) | B |
| 피드백의 업무 전환 | 이미 연결된 업무가 있을 때의 재요청 | 200, 기존 업무 반환. 새로 쓰는 것이 없다 | B |
| 연결된 업무 | 수정, 상태 변경, 담당자 변경, 삭제 | 409 | B |
| 연결된 업무 | 다른 제출물로 이동, 연결 해제 | 409 | B |
| 업무 | 확정된 제출물에 새로 연결하거나 그 제출물로 새 업무 만들기 | 409 | B |
| 파일 금고 | 같은 이름의 새 버전 업로드 | 허용. 파일은 프로젝트에 속하고 확정본은 회차가 가리키는 버전으로 고정돼 있다 | - |
| 파일 금고 | 파일 버전 삭제 | 명령 없음. 파일 금고에는 지금도 삭제가 없고, 회차가 가리키는 버전은 DB가 삭제를 막는다(K-10 6장) | - |
| 확정 | 취소, 다시 확정 | 명령 없음 | - |
| 제출 기록 | 기록 | `CONFIRMED`에서 한 번 | A |
| 제출 기록 | 수정 | 명령 없음 | - |

연결되지 않은 업무와 다른 제출물은 영향을 받지 않는다.

**연결된 업무를 전부 읽기 전용으로 두는 이유**: 확정 시점의 기록을 그대로 남기려는 것이다. 끝나지 않은 업무가 있어도 확정은 되므로(업무 완료와 충족은 다르다, CONTRACTS 3장 1항), 그런 업무는 끝나지 않은 채로 남는다. 그래서 화면이 확정 전에 알린다(8장). 삭제까지 막는 것은 피드백에서 만든 업무를 지우면 그 피드백의 연결이 비워져(K-12) 확정된 검토 기록이 바뀌기 때문이다. 업무는 B 담당이라 이 줄들은 B의 확인이 필요하다(9장).

## 5. 권한과 오류

기존 ProblemDetail 형식이고 `detail`을 화면에 표시한다.

| 상황 | 응답 |
| --- | --- |
| 로그인하지 않음 | 401 |
| 프로젝트 참여자가 아님 | 403 |
| 팀원·관찰자가 확정 | 403 "최종본 확정은 팀장만 할 수 있습니다" |
| 관찰자가 제출 기록 | 403 |
| 다른 프로젝트의 제출물·회차 id, 없는 id | 404. 제목 등 추가 정보를 드러내지 않는다 |
| UUID 형식 오류, `reviewId` 생략, `submittedAt` 생략·형식 오류·미래 시각, 길이 초과 | 400 |
| 확정 조건을 통과하지 못함 | 409, 첫 번째로 막힌 검사의 `detail` |
| `reviewId`가 서버가 계산한 확정 대상과 다름 | 409 "확정하려는 대상이 바뀌었습니다. 새로고침해 다시 확인해주세요" |
| 이미 다른 회차로 확정됨 | 409 "이미 확정된 제출물입니다" |
| 확정 전에 제출 기록 | 409 "최종본을 확정한 뒤에 제출을 기록할 수 있습니다" |
| 이미 기록된 제출물에 다른 내용으로 기록 | 409 "이미 제출이 기록됐습니다" |
| 확정 뒤 4장의 막힌 동작 | 409 "확정된 제출물은 변경할 수 없습니다" |

### 팀장·팀원이 한 명뿐인 프로젝트

허용하지 않는다. 파일을 올린 사람은 자기 파일을 승인할 수 없으므로(K-10 2장) 혼자서는 확정 조건을 채울 수 없다. 이 제품은 2~4인 팀을 대상으로 한다(`docs/team/DEVELOPMENT_PLAN.md` 1장). 예외를 두지 않는 대신 `soleContributor`를 응답에 넣어, 화면이 "파일을 올리지 않은 팀원의 승인이 필요합니다"와 팀원 초대 링크를 보여 줄 수 있게 한다.

## 6. 다른 담당과 주고받는 것

### A가 제공: 제출물 상태 확인

B의 업무 명령이 "이 업무가 연결된 제출물이 확정됐는가"를 확인할 때 쓴다. 피드백 명령은 K-10의 `ReviewRoundReader`가 돌려주는 `deliverableStatus`를 그대로 쓰면 된다. 이름은 구현에서 바뀔 수 있고 의미는 아래로 고정한다.

```java
public interface DeliverableStatusReader {
    // DRAFT·IN_REVIEW·CONFIRMED·SUBMITTED. 프로젝트와 제출물이 맞지 않거나 없으면 NotFoundException
    String statusOf(UUID projectId, UUID deliverableId);

    // 같은 확인을 하되 제출물 행을 먼저 잠근다(쓰기 명령용). 같은 트랜잭션 안에서 호출한다
    String lockForWrite(UUID projectId, UUID deliverableId);
}
```

권한은 보지 않는다. 호출하는 쪽이 먼저 확인한다(K-10 5장과 같다).

### B가 제공: 미해결 피드백 수

K-10 5장의 `countUnresolvedComments`를 확정에서도 같은 방식으로 쓴다. 제출물 잠금을 잡은 뒤 부른다.

### 동시 요청

- 확정, 제출 기록, 4장의 A 담당 쓰기(제출물·요구사항·충족 확인·회차)는 모두 같은 제출물 행 잠금을 먼저 잡는다. 확정 직전에 충족 확인이 풀리거나 피드백이 다시 열리는 일이 끼어들지 못한다
- 확정과 제출 기록은 제출물마다 한 줄만 저장되도록 DB가 보장한다. 동시에 두 번 확정해도 하나만 남는다
- **파일 업로드는 이 잠금을 잡지 않는다.** 파일은 프로젝트에 속하기 때문이다. 확정과 같은 이름의 새 버전 업로드가 겹치면, 확정은 검사 시점의 최신 내용을 기준으로 통과하고 확정본은 `reviewId`의 회차가 가리키는 버전으로 고정된다. 확정 직후 올라온 새 버전은 확정본이 아니며 `fileStillLatest: false`로 드러난다
- 위 경우의 기준을 한 줄로 적으면 이렇다(B-22의 동시 요청 시나리오): **확정과 내용이 다른 업로드를 동시에 보내면 둘 다 성공한다. 확정본은 언제나 승인된 회차의 파일 버전이고, 업로드가 반영된 뒤 조회하면 `fileStillLatest`가 `false`다.** 업로드가 먼저 끝나 확정 검사가 새 버전을 봤다면 확정이 409다. "확정본이 확정 시점의 최신 버전이다"까지는 보장하지 않는다
- B의 업무 명령이 `lockForWrite`를 쓰면 확정과 차례대로 처리된다. `statusOf`만 쓰면 확정과 거의 동시에 들어온 업무 변경 하나가 확정 뒤에 반영될 수 있다. 업무는 확정 조건이 아니라서 확정의 근거가 깨지지는 않는다. 어느 쪽을 쓸지는 B가 정한다. 업무를 다른 제출물로 옮길 때처럼 두 제출물을 함께 잠가야 하면 id가 작은 것부터 잠근다(교착 방지)

## 7. DB (V23, A-20에서 작성)

```text
deliverable_confirmations
  deliverable_id UUID PK
  project_id     UUID NOT NULL
  review_id      UUID NOT NULL        -- 확정본은 이 회차가 가리키는 파일 버전이다
  confirmed_by   UUID NOT NULL → users(id)
  confirmed_at   TIMESTAMPTZ NOT NULL

  FOREIGN KEY (review_id, deliverable_id, project_id) → review_rounds(id, deliverable_id, project_id)

deliverable_submissions
  deliverable_id UUID PK → deliverable_confirmations(deliverable_id)   -- 확정된 제출물만 기록할 수 있다
  channel        VARCHAR(500) NULL
  submitted_at   TIMESTAMPTZ NOT NULL
  note           VARCHAR(1000) NULL
  recorded_by    UUID NOT NULL → users(id)
  recorded_at    TIMESTAMPTZ NOT NULL
```

- 제출물 테이블에는 열을 더하지 않는다. 상태는 두 테이블에 줄이 있는지와 회차에서 정한다
- 기본 키가 제출물 id라서 확정과 제출 기록은 제출물마다 하나다
- 확정 파일 버전은 따로 저장하지 않는다. 회차가 파일 버전을 고정하므로 회차 id가 곧 확정본이다. B-22에 적힌 "확정 기록에 파일 버전 ID를 저장하는 안"을 이것으로 바꾼다. 같은 값을 두 곳에 두면 어긋날 수 있어서다
- 승인 뒤 같은 내용이 다시 올라와 더 높은 버전이 있어도(K-10 3장) 확정본의 버전 번호는 회차가 가리키는 것이다. 내용은 같다
- 회차와 마찬가지로 연쇄 삭제를 두지 않는다. 확정된 제출물은 지울 수 없다
- 번호는 V23이다. V21·V22는 #91이 쓴다

## 8. 화면 (C)

- GET 응답 하나로 최종 제출 탭을 그릴 수 있다. 준비 목록은 `checks`의 `detail`을 그대로 보여 주고 `code`로 갈 곳을 고른다. 화면이 진척 수치로 확정 가능 여부를 따로 계산하지 않는다
- 확정 버튼은 팀장에게만 보이고 `canConfirm`이 `false`면 비활성이다. 확정 창에는 `candidate`의 파일과 4장의 표를 보여 준다. 요청에는 `candidate.reviewId`를 넣는다
- 끝나지 않은 연결 업무가 있으면 확정 창에서 "끝나지 않은 연결 업무 N건은 확정 뒤 바꿀 수 없습니다"를 알린다. 수는 K-13 진척 조회의 `tasks.total - tasks.completed`다. 이 계약은 업무 수를 따로 세지 않는다(CONTRACTS 3장 12항)
- `soleContributor`가 `true`면 팀원 초대 안내를 보여 준다
- 확정 뒤에는 `confirmation`으로 확정자·시각·확정본을 보여 주고, `fileStillLatest`가 `false`면 "확정 뒤에 새 버전이 올라왔습니다. 확정본은 N버전입니다"를 알린다
- 제출 기록 창의 기본값은 화면이 채운다: 채널은 제출물의 제출 경로, 시각은 지금
- 목록 카드, 업무 보드, 프로젝트 홈은 제출물 응답의 `status`와 `latestDecision`을 쓴다
- fixture는 3장의 JSON에서 복사해 C가 관리한다. 실제 API로 바꾸는 시점은 A-20 병합 뒤다

5. 끝나지 않은 연결 업무 수를 이 응답에 넣지 않고 K-13 진척 조회에서 읽는 것
