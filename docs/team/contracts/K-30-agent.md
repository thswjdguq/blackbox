# K-30 · AI 에이전트 실행과 제안 카드

- 버전: 0.1 / 상태: DRAFT (B·C 확인 전, 구현 전)
- 생산자: 송승준(A) / 소비자: 손정협(B, 점수·경보 자료와 기여도 반영), 손정효(C, 도우미 창과 제안 카드 화면)
- 기능: S2 / 작성일: 2026-10-09 / 기준 SHA: `1527927`
- 근거: `docs/team/handoffs/A-K30-proposal-20261007.md`(#92, 방향과 설계), CONTRACTS.md 3장 1항·12항
- 구현: A-30. 이 문서는 계약만 다룬다. Spring Boot 3.5(A-14)가 먼저 들어가야 한다
- 범위: 엑스포 1차. 계획 단계(안내문 → 제출물·요구사항·업무 제안)와 진행 단계(상태 요약, 위험, 다음 할 일). 검토·확정 단계의 도움, 스스로 보내는 주간 요약은 이 버전에 없다

## 1. 무엇을 약속하는가

에이전트는 프로젝트 기록을 읽고, 사람이 읽을 답을 만들고, 다음 행동을 **제안 카드**로 내놓는다.

- **에이전트는 쓰지 않는다.** 읽기 도구만 가진다. 제출물·요구사항·업무는 사람이 제안 카드를 채택할 때, 그 사람의 권한으로 만들어진다
- **요청한 사람이 볼 수 있는 것만 읽는다.** 도구는 요청한 사람의 권한으로 기존 조회를 부른다
- **판정은 규칙이 한다.** 늦었는지, 어느 단계인지는 서버가 계산하고 모델은 설명만 한다. 같은 기록이면 판정이 같다
- **AI가 꺼져도 나머지는 그대로다.** 모델이 설정되지 않았거나 실패해도 기존 기능에는 영향이 없다
- **AI가 만든 것은 남는다.** 누가 어떤 실행을 요청했고 모델이 무엇을 만들었고 사람이 어떻게 고쳐 채택했는지 저장한다. 안내문과 질문의 원문은 저장하지 않는다(8장)
- 화면은 이 문서의 응답 형식만 안다. 어느 모델을 쓰는지는 서버 설정이다

## 2. 명령

기본 경로: `/api/projects/{projectId}/agent`. 모든 id는 UUID이고 기존 쿠키 인증을 쓴다.

| 명령 | 요청 | 성공 | 역할 |
| --- | --- | --- | --- |
| 상태 조회 | GET `/status` | 200, 3장의 상태 객체 | 팀장·팀원·관찰자 |
| 실행 | POST `/runs`, `{ "skill": "…", "input": { … } }` | 200, 이벤트 스트림(4장) | 실행 종류마다 다름(아래 표) |
| 제안 카드 목록 | GET `/proposals?status=PENDING` | 200, 카드 배열(최신이 먼저) | 팀장·팀원·관찰자 |
| 제안 카드 조회 | GET `/proposals/{proposalId}` | 200, 카드 | 팀장·팀원·관찰자 |
| 제안 카드 수정 | PUT `/proposals/{proposalId}`, `{ "content": { … } }` | 200, 카드 | 팀장·팀원 |
| 채택 | POST `/proposals/{proposalId}/accept` | 200, 카드(`results` 포함) | 팀장·팀원 |
| 거절 | POST `/proposals/{proposalId}/reject` | 200, 카드 | 팀장·팀원 |

`status`를 생략하면 모든 상태를 돌려준다. 페이지 처리는 없고 최근 50건까지다.

### 실행 종류 (`skill`)

| `skill` | 하는 일 | `input` | 결과 | 역할 |
| --- | --- | --- | --- | --- |
| `PLAN_FROM_BRIEF` | 과제 안내문에서 제출물·요구사항·업무와 기한을 뽑는다 | `{ "briefText": "…" }` 1~20000자 | `DELIVERABLE_PLAN` 카드 1개 이상 | 팀장·팀원 |
| `BREAK_DOWN_TASKS` | 한 제출물의 요구사항을 업무로 나누고 완료 기준과 기한을 붙인다 | `{ "deliverableId": "…" }` | `TASKS` 카드 1개 | 팀장·팀원 |
| `STATUS_BRIEF` | 끝난 일, 진행 중인 일, 늦은 일, 위험을 요약한다 | `{}` | 글. 다음 할 일이 있으면 `TASKS` 카드 | 글은 누구나. 관찰자에게는 카드를 만들지 않는다 |
| `ASK` | 프로젝트에 대한 질문에 기록을 근거로 답한다 | `{ "question": "…" }` 1~1000자 | 글 | 팀장·팀원·관찰자 |

- 실행 종류는 "지시문, 쓸 수 있는 도구, 결과 형식"의 묶음으로 서버에 등록한다. 종류를 더해도 이 API의 모양은 바뀌지 않는다. 다만 종류마다 `input`이 다르므로 화면은 새 종류의 입력 칸을 따로 만들어야 한다
- 안내문과 질문은 모델에 **자료**로 넘긴다. 그 안에 지시문이 있어도 따르지 않게 지시문을 구성하고, 속더라도 결과는 사람이 보는 제안 카드에서 멈춘다(1장)
- 같은 사람이 같은 프로젝트에서 실행을 연달아 보내면 앞의 실행이 끝날 때까지 409다. 시간 상한(4장)을 넘긴 실행은 끝난 것으로 보므로, 서버가 중간에 죽어도 계속 막히지 않는다. 프로젝트마다 한 시간에 실행할 수 있는 횟수에 상한이 있고 넘으면 429다. 상한은 서버 설정이다

### 제안 카드의 일생

```text
PENDING ──(채택)──▶ ACCEPTED
   └────(거절)──▶ REJECTED
```

- 카드는 `PENDING`으로 만들어진다. 수정은 `PENDING`일 때만 된다
- **채택**: 카드의 지금 내용(`content`)대로 기존 서비스가 실제 기록을 만든다. 채택한 사람의 권한으로 만들고, 전부 만들어지거나 하나도 만들어지지 않는다. 만들어진 것의 id가 `results`에 남는다
- 이미 채택된 카드에 채택을 다시 보내면 지금 카드를 그대로 돌려준다(중복 클릭). 새로 만들지 않는다
- 거절한 카드는 지우지 않는다. 거절된 카드를 채택하거나 채택된 카드를 거절하면 409다
- 채택할 때 내용을 다시 검증한다. 제목이 비었거나 기한 형식이 틀리면 400이고 아무것도 만들지 않는다
- 채택과 거절을 되돌리는 명령은 없다. 만들어진 제출물과 업무는 기존 화면에서 고치거나 지운다

## 3. 응답

### 상태 객체

```json
{
  "available": true,
  "unavailableReason": null,
  "skills": [
    { "skill": "PLAN_FROM_BRIEF", "label": "과제 안내문으로 계획 만들기", "allowed": true },
    { "skill": "BREAK_DOWN_TASKS", "label": "요구사항을 업무로 나누기", "allowed": true },
    { "skill": "STATUS_BRIEF", "label": "지금 상태 살펴보기", "allowed": true },
    { "skill": "ASK", "label": "물어보기", "allowed": true }
  ],
  "stages": [
    { "deliverableId": "11111111-1111-4111-8111-111111111111", "title": "중간 보고서", "dueDate": "2026-10-18", "stage": "TASKS_IN_PROGRESS" }
  ],
  "pendingProposalCount": 2
}
```

| 필드 | 값 | 의미 |
| --- | --- | --- |
| `available` | 불리언 | 모델이 설정돼 있어 실행할 수 있는가. `false`면 화면은 에이전트 버튼을 숨긴다 |
| `unavailableReason` | 문자열 또는 `null` | 사람이 읽는 이유. 예: "AI 기능이 설정되지 않았습니다" |
| `skills[].allowed` | 불리언 | 요청한 사람의 역할로 실행할 수 있는가 |
| `stages[]` | 배열 | 제출물마다의 단계. 기한이 빠른 순. 제출물이 없으면 빈 배열 |
| `stages[].stage` | 아래 여섯 값 | 서버가 규칙으로 계산한 단계 |
| `pendingProposalCount` | 0 이상 정수 | 채택이나 거절을 기다리는 카드 수 |

단계는 프로젝트 홈의 "다음 할 일" 카드(#77)와 같은 순서로 판정한다. 위에서부터 먼저 맞는 것이 단계다.

| `stage` | 조건 |
| --- | --- |
| `NO_REQUIREMENT` | 요구사항이 없다 |
| `NO_TASK` | 연결된 업무가 없다. 다만 필수 요구사항이 하나 이상 있고 모두 확인됐으면 이 단계를 건너뛴다 |
| `UNCOVERED_REQUIREMENT` | 아직 확인 전인 필수 요구사항 중 업무가 없는 것이 있다 |
| `TASKS_IN_PROGRESS` | 끝나지 않은 연결 업무가 있다 |
| `UNCHECKED_REQUIREMENT` | 확인하지 않은 필수 요구사항이 있다 |
| `READY_FOR_REVIEW` | 위에 해당하는 것이 없다 |

제출물이 하나도 없는 프로젝트는 `stages`가 빈 배열이다(#77의 첫 단계 "제출물 없음"에 해당한다). 검토 회차(K-10)와 확정(K-20)이 들어오면 그 뒤 단계를 이 표에 더한다.

### 제안 카드

```json
{
  "id": "22222222-2222-4222-8222-222222222222",
  "runId": "33333333-3333-4333-8333-333333333333",
  "kind": "DELIVERABLE_PLAN",
  "status": "PENDING",
  "title": "중간 보고서 계획",
  "rationale": "안내문의 '10월 18일까지 중간 보고서 제출'과 평가 항목 세 가지에서 뽑았습니다.",
  "content": {
    "deliverable": { "title": "중간 보고서", "description": "문제 정의와 설계까지", "dueDate": "2026-10-18", "submissionMethod": "학교 LMS 과제함" },
    "requirements": [
      { "key": "r1", "content": "문제 정의와 대상 사용자를 적는다", "required": true },
      { "key": "r2", "content": "분량은 10쪽 안팎", "required": false }
    ],
    "tasks": [
      { "title": "문제 정의 초안 작성", "completionCriteria": "대상 사용자와 문제를 한 쪽으로 정리", "dueDate": "2026-10-13", "requirementKey": "r1" }
    ]
  },
  "edited": false,
  "requestedBy": { "userId": "55555555-5555-4555-8555-555555555555", "name": "송승준" },
  "createdAt": "2026-10-10T14:00:00+09:00",
  "decision": null,
  "results": null
}
```

채택된 카드는 `decision`과 `results`가 채워진다.

```json
{
  "status": "ACCEPTED",
  "edited": true,
  "decision": { "result": "ACCEPTED", "decidedBy": { "userId": "55555555-5555-4555-8555-555555555555", "name": "송승준" }, "decidedAt": "2026-10-10T14:05:00+09:00" },
  "results": {
    "deliverableId": "11111111-1111-4111-8111-111111111111",
    "requirementIds": ["66666666-6666-4666-8666-666666666661", "66666666-6666-4666-8666-666666666662"],
    "taskIds": ["77777777-7777-4777-8777-777777777771"]
  }
}
```

| 필드 | 값 | 의미 |
| --- | --- | --- |
| `kind` | `DELIVERABLE_PLAN`·`TASKS` | 카드 종류. `content`의 모양을 정한다 |
| `status` | `PENDING`·`ACCEPTED`·`REJECTED` | |
| `title` | 문자열 | 목록에 보일 한 줄 |
| `rationale` | 문자열 | 왜 이렇게 제안했는지. 기록이나 안내문의 어느 부분에서 나왔는지 적는다 |
| `content` | 객체 | 채택하면 만들어질 내용. 사람이 고칠 수 있다 |
| `edited` | 불리언 | 사람이 모델의 원본을 고쳤는가. 서버는 원본을 따로 보관한다 |
| `requestedBy` | 객체 | 실행을 요청한 사람 |
| `decision` | 객체 또는 `null` | 결정 전이면 `null`. 필드는 생략하지 않는다 |
| `results` | 객체 또는 `null` | 채택으로 만들어진 것의 id. 채택 전이나 거절이면 `null` |
| 시각 | 시간대 포함 ISO-8601 | 기존 응답과 같은 형식 |

### 종류별 `content`

**`DELIVERABLE_PLAN`** — 제출물 하나와 그 요구사항, 업무. 안내문에 제출물이 여러 개면 카드도 여러 장이다.

| 필드 | 규칙 |
| --- | --- |
| `deliverable.title` | 필수, 255자까지 |
| `deliverable.description` | 선택, 5000자까지 |
| `deliverable.dueDate` | 필수, `YYYY-MM-DD`. 안내문에 기한이 없으면 모델이 `null`로 두고, 사람이 채워야 채택된다 |
| `deliverable.submissionMethod` | 선택, 500자까지 |
| `requirements[].key` | 카드 안에서만 쓰는 이름표. 업무가 요구사항을 가리킬 때 쓴다 |
| `requirements[].content` | 필수, 1000자까지 |
| `requirements[].required` | 불리언 |
| `tasks[]` | 아래 `TASKS`의 항목과 같다. `requirementKey`로 같은 카드의 요구사항을 가리킨다 |

**`TASKS`** — 이미 있는 제출물에 붙일 업무 초안.

| 필드 | 규칙 |
| --- | --- |
| `deliverableId` | 선택. 있으면 같은 프로젝트의 제출물 |
| `tasks[].title` | 필수, 255자까지 |
| `tasks[].completionCriteria` | 선택, 2000자까지 |
| `tasks[].dueDate` | 선택, `YYYY-MM-DD` |
| `tasks[].requirementId` | 선택. 있으면 그 제출물의 요구사항 |

- 길이와 필수 여부는 기존 제출물·요구사항·업무 API와 같다. 채택은 그 API가 쓰는 검증을 그대로 지난다
- **담당자는 카드에 없다.** 에이전트는 사람을 배정하지 않는다(CONTRACTS 3장 1항). 만든 뒤 업무 보드에서 정한다
- 모델이 채우지 못한 칸은 `null`이나 "[작성 필요: 무엇]"으로 둔다. 기록에 없는 것을 지어내지 않는다

## 4. 실행의 이벤트 스트림

`POST /runs`의 응답은 `text/event-stream`이다. 이벤트는 아래 순서로 온다.

```text
event: step
data: {"label":"제출물과 요구사항 조회","tool":"list_deliverables"}

event: step
data: {"label":"업무 조회","tool":"list_tasks"}

event: text
data: {"text":"중간 보고서는 업무 5개 중 2개가 끝났습니다. …"}

event: proposal
data: { …3장의 제안 카드… }

event: done
data: {"runId":"33333333-3333-4333-8333-333333333333","proposalIds":["22222222-2222-4222-8222-222222222222"]}
```

| 이벤트 | 언제 | `data` |
| --- | --- | --- |
| `step` | 에이전트가 도구를 부를 때마다 | `label`은 사람이 읽는 말, `tool`은 5장의 도구 이름 |
| `text` | 답의 글이 만들어졌을 때. 여러 번 올 수 있고 화면은 이어 붙인다 | `text` |
| `proposal` | 카드가 저장됐을 때. 카드마다 한 번 | 3장의 제안 카드 |
| `done` | 정상 종료. 마지막 이벤트 | `runId`, 만들어진 카드의 id |
| `error` | 실행 중 실패. 마지막 이벤트 | `detail`은 화면에 그대로 보일 문장 |

- 스트림이 시작되기 전의 실패(권한, 입력 오류, 상한)는 이벤트가 아니라 6장의 HTTP 오류로 온다
- 글에 나오는 기록에는 그 화면으로 가는 링크가 붙는다. 링크는 Markdown의 `[이름](경로)`이고 경로는 `/projects/…`로 시작하는 화면 경로다
- 화면이 스트림을 끊으면 서버는 실행을 멈출 수 있다. 그때까지 저장된 카드는 남고 `GET /proposals`로 다시 받을 수 있다
- 중간의 프록시(nginx, 개발 서버)가 응답을 모아 두지 않게 서버가 응답 헤더로 알린다. 프록시 설정을 바꿔야 하면 A-30에서 함께 다룬다
- 실행 하나에는 시간 상한이 있다. 넘으면 `error`로 끝난다. 그때까지 저장된 카드는 남는다

## 5. 읽기 도구

모델이 부를 수 있는 것은 아래뿐이다. 모두 읽기이고, 요청한 사람의 권한으로 기존 조회를 부른다.

| 도구 | 돌려주는 것 | 자료의 출처 |
| --- | --- | --- |
| `get_project` | 프로젝트 이름·기간, 멤버의 이름과 역할, 오늘 날짜(한국 시간) | A |
| `list_deliverables` | 제출물과 요구사항, 충족 확인 여부, 단계(3장) | A |
| `get_progress` | 제출물의 업무 완료율과 필수 요구사항 충족률 | B (K-13) |
| `list_tasks` | 업무의 제목·상태·기한·완료 시각·담당자·연결된 제출물과 요구사항·완료 기준. 늦었는지는 서버가 계산해 붙인다(끝나지 않았고 기한이 한국 시간의 오늘보다 앞) | B |
| `list_alerts` | 경보(무임승차·과부하·이탈·변조)와 심각도 | B |
| `get_scores` | 멤버별 기여도 점수 | B |

- **이메일 같은 연락처와 파일 내용은 도구가 돌려주지 않는다.** 모델로 나가는 것은 이름, 역할, 위 표의 기록이다
- B의 자료는 지금 컨트롤러가 쓰는 조회 메서드(`TaskService.listTasks`, `AlertService.getAlerts`, `ScoreService.getScores`, 진척 조회)를 그대로 부른다. 권한 확인이 그 안에 있다. 에이전트가 B의 엔티티나 저장소에 직접 붙지 않는다
- 도구가 돌려주는 목록에는 건수 상한이 있다. 넘으면 잘렸다는 표시와 전체 건수를 함께 준다
- 검토 회차(K-10)와 피드백(K-11) 도구는 그 기능이 들어온 뒤에 더한다

## 6. 권한과 오류

기존 ProblemDetail 형식이고 `detail`을 화면에 표시한다.

| 상황 | 응답 |
| --- | --- |
| 로그인하지 않음 | 401 |
| 프로젝트 참여자가 아님 | 403 |
| 관찰자가 카드를 만드는 실행, 카드 수정·채택·거절 | 403 "관찰자는 제안을 만들거나 채택할 수 없습니다" |
| 다른 프로젝트의 카드·제출물 id, 없는 id | 404. 제목 등 추가 정보를 드러내지 않는다 |
| 모르는 `skill`, 입력 누락·길이 초과, UUID 형식 오류 | 400 |
| 채택할 내용이 검증에 걸림(제목 없음, 기한 없음 등) | 400, 어느 칸인지 `detail`에 적는다. 아무것도 만들지 않는다 |
| 결정된 카드를 수정, 거절된 카드를 채택, 채택된 카드를 거절 | 409 "이미 결정된 제안입니다" |
| 같은 사람의 실행이 아직 진행 중 | 409 "앞의 요청이 끝난 뒤 다시 시도해주세요" |
| 프로젝트의 실행 횟수 상한 초과 | 429 "잠시 뒤 다시 시도해주세요" |
| 모델이 설정되지 않음 | 503 "AI 기능이 설정되지 않았습니다". 3장의 `available`도 `false`다 |
| 모델 호출 실패·시간 초과·응답 형식 오류(스트림 시작 뒤) | `error` 이벤트 "AI 응답을 받지 못했습니다. 다시 시도해주세요" |
| 모델이 요청을 거절함 | `error` 이벤트 "이 요청은 처리할 수 없습니다" |

모델이 만든 내용이 카드 형식에 맞지 않으면 서버가 한 번 다시 요청하고, 그래도 맞지 않으면 `error`로 끝낸다. 형식에 맞지 않는 카드를 저장하지 않는다.

## 7. 다른 담당과 주고받는 것

### B에게 필요한 것

- 5장의 조회 메서드를 에이전트가 부르는 것. 메서드의 인자나 반환이 바뀌면 에이전트의 도구가 같이 바뀌므로, 바꿀 때 알려 주면 된다
- 채택이 업무를 만들 때 기존 `TaskService.createTask`를 채택한 사람으로 부르는 것. 업무 생성의 검증, 활동 기록, 알림이 화면에서 만들 때와 같게 동작한다. A가 B의 쓰기 메서드를 부르는 곳은 여기 하나다
- **기여도**: 채택으로 만들어진 업무는 채택한 사람이 만든 것으로 활동 기록에 남는다(기존 업무 생성과 같은 경로). 이것을 기여도에서 빼거나 따로 셀지는 B가 정한다. A는 "이 업무가 제안 카드에서 만들어졌는가"를 알려 주는 조회를 제공한다

```java
public interface AgentOriginReader {
    // 이 기록이 제안 카드의 채택으로 만들어졌는가. targetType은 "DELIVERABLE"·"REQUIREMENT"·"TASK"
    boolean createdFromProposal(UUID projectId, String targetType, UUID targetId);
}
```

### A가 지키는 것

- 모델을 부르는 코드는 한 곳에만 둔다. 도구, 제안 카드, 단계 판정은 Spring AI의 타입을 모른다
- 공급자와 모델 이름, 반복 횟수와 시간·횟수 상한, 입력 길이는 설정에 두고 지시문은 리소스 파일에 둔다
- 공급자 설정이 없으면(`spring.ai.model.chat=none`) 서버는 그대로 뜨고 `available`만 `false`가 된다

### 동시 요청

- 채택과 거절은 카드 행을 잠근 뒤 상태를 확인한다. 동시에 두 번 채택해도 기록은 한 번만 만들어진다
- 채택이 만드는 제출물·요구사항·업무는 한 트랜잭션이다. 중간에 실패하면 카드는 `PENDING`으로 남는다

## 8. DB (A-30에서 작성)

```text
agent_runs
  id            UUID PK
  project_id    UUID NOT NULL → projects(id)
  requested_by  UUID NOT NULL → users(id)
  skill         VARCHAR(40) NOT NULL
  status        VARCHAR(20) NOT NULL        -- RUNNING · DONE · FAILED
  error         VARCHAR(500) NULL
  started_at    TIMESTAMPTZ NOT NULL
  finished_at   TIMESTAMPTZ NULL

agent_proposals
  id            UUID PK
  project_id    UUID NOT NULL → projects(id)
  run_id        UUID NOT NULL → agent_runs(id)
  kind          VARCHAR(40) NOT NULL
  status        VARCHAR(20) NOT NULL        -- PENDING · ACCEPTED · REJECTED
  title         VARCHAR(255) NOT NULL
  rationale     TEXT NOT NULL
  content       JSONB NOT NULL              -- 지금 내용(사람이 고친 것 포함)
  original      JSONB NOT NULL              -- 모델이 만든 원본
  decided_by    UUID NULL → users(id)
  decided_at    TIMESTAMPTZ NULL
  created_at    TIMESTAMPTZ NOT NULL

agent_proposal_results
  proposal_id   UUID NOT NULL → agent_proposals(id)
  target_type   VARCHAR(20) NOT NULL        -- DELIVERABLE · REQUIREMENT · TASK
  target_id     UUID NOT NULL
  PRIMARY KEY (proposal_id, target_type, target_id)
```

- 안내문과 질문 원문은 저장하지 않는다. 실행 기록에는 종류와 결과만 남긴다
- 만들어진 기록이 나중에 지워져도 `agent_proposal_results`의 줄은 남는다(외래키를 걸지 않는다). 카드의 `results`에는 그대로 나오고, 화면이 열었을 때 없으면 "삭제됨"으로 보인다
- 마이그레이션 번호는 병합 순서대로 A가 정한다. 검토 회차 구현(#91)의 V21·V22 다음 번호를 쓰고, K-20 초안에 적은 V23은 실제 병합 순서에 맞춘다. **#91보다 먼저 병합하지 않는다.** 번호가 뒤바뀌면 이미 적용한 DB에서 마이그레이션이 실패한다

## 9. 화면 (C)

- **도우미 창**: 어느 화면에서든 연다. `GET /status`의 `available`이 `false`면 여는 버튼을 숨긴다. `skills` 중 `allowed`인 것을 버튼으로 보여 주고, `ASK`는 입력창이다
- **단계별 버튼**: 화면의 맥락에 맞는 실행을 바로 부른다. 예: 제출물이 없는 프로젝트의 "과제 안내문으로 계획 만들기", 업무가 없는 제출물의 "요구사항을 업무로 나누기"
- **진행 표시**: `step`이 올 때마다 한 줄씩 보여 준다. `text`는 이어 붙이고 Markdown 링크는 화면 이동으로 바꾼다
- **제안 카드**: `content`를 종류에 맞는 입력 칸으로 보여 주고 고칠 수 있게 한다. 고치면 `PUT`으로 저장한 뒤 채택한다. 채택하면 `results`의 제출물·업무로 가는 링크를 보여 준다
- AI가 만든 것임을 카드에 표시한다. `edited`가 `true`면 사람이 고쳤다는 것도 보여 준다
- 외부 AI 모델로 프로젝트 기록(이름, 역할, 제출물·업무 내용)이 나간다는 안내를 도우미 창에 둔다
- fixture는 3장과 4장의 예시에서 복사해 C가 관리한다. 실제 API로 바꾸는 시점은 A-30 병합 뒤다

## 12. 수용 테스트 (A-30에서)

모델은 매번 답이 달라지므로 두 가지로 나눠 확인한다.

**정해진 답을 돌려주는 가짜 모델로 (자동 테스트, 실제 DB·HTTP)**

| 조건 | 기대 |
| --- | --- |
| 모델 설정이 없을 때 상태 조회 / 실행 | `available: false` / 503 |
| 팀원이 `PLAN_FROM_BRIEF` 실행 | `step` → `proposal` → `done` 순서, 카드가 `PENDING`으로 저장 |
| 관찰자가 `PLAN_FROM_BRIEF` 실행 / `ASK` 실행 | 403 / 200 |
| 관찰자의 `STATUS_BRIEF` | 글은 오고 카드는 만들어지지 않는다 |
| 카드 수정 뒤 조회 | `content`가 바뀌고 `edited: true`, 원본은 그대로 |
| 채택 | 제출물·요구사항·업무가 만들어지고 `results`의 id로 조회된다. 업무가 요구사항에 연결돼 있다 |
| 같은 카드를 다시 채택 / 동시에 두 번 채택 | 200, 새로 만들지 않는다 / 한 번만 만들어진다 |
| 기한이 `null`인 `DELIVERABLE_PLAN` 채택 | 400, 아무것도 만들어지지 않는다 |
| 채택 도중 실패(세 번째 업무의 제목이 300자) | 400, 제출물과 앞의 업무도 만들어지지 않고 카드는 `PENDING` |
| 거절한 카드 채택, 채택한 카드 수정 | 409 |
| 다른 프로젝트의 카드 id | 404 |
| 다른 프로젝트의 `deliverableId`로 `BREAK_DOWN_TASKS` | 404 |
| 형식에 맞지 않는 모델 응답 두 번 | `error` 이벤트, 카드 없음 |
| 담당자가 있는 업무를 `list_tasks`로 조회 | 결과에 이름은 있고 이메일은 없다 |
| 실행 중에 같은 사람이 또 실행 | 409 |
| 단계 판정: 제출물 없음과 여섯 단계 | #77의 화면 판정과 같은 결과 |

**실제 모델로 (시연용 프로젝트를 고정해 두고)**

- 답에 나온 숫자가 DB와 같은가
- 기록에 없는 것을 지어내지 않았는가
- 제안이 형식에 맞고 채택하면 실제로 만들어지는가
- 권한 밖의 것을 보여 주지 않는가

같은 질문 세트를 Gemini와 Bedrock의 Sonnet에서 돌린다.
