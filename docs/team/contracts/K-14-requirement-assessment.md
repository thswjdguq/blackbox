## 1. 무엇을 약속하는가

사람이 요구사항 하나를 보고 "충족됐다"고 체크하거나 체크를 푸는 기능이다. 요구사항 문구가 바뀌면 체크는 저절로 풀린다.

**충족은 사람이 확인하는 행위다.** 연결된 업무가 모두 DONE이 돼도, AI가 판단해도 서버는 자동으로 체크하지 않는다(CONTRACTS §3-1).

상태는 두 가지다. **확인 전**과 **충족**. "봤는데 아직 부족하다"는 이 계약에서 기록하지 않는다. 부족한 점은 피드백(K-11)으로 남기고, 화면은 연결 업무의 진행 상황으로 이유를 보여준다(§6).

이 계약은 요구사항 한 건의 상태만 다룬다. 제출물 전체의 충족률은 K-13이 계산하고, 최종 확정 가능 여부는 K-20이 서버에서 다시 검사한다.

## 2. 체크 · 해제

```
PUT    /api/projects/{projectId}/deliverables/{deliverableId}/requirements/{requirementId}/assessment
DELETE /api/projects/{projectId}/deliverables/{deliverableId}/requirements/{requirementId}/assessment
```

요청 본문은 없다. PUT은 충족으로 체크하고, DELETE는 체크를 푼다. **둘 다 200과 함께 갱신된 요구사항(§3 형식)을 돌려준다.** 화면은 이 응답으로 다시 그린다.

두 요청 모두 여러 번 보내도 결과가 같다. 이미 체크된 요구사항에 PUT을 다시 보내면 확인자와 시각이 마지막 요청 기준으로 바뀐다. 체크되지 않은 요구사항에 DELETE를 보내도 200이다.

### 문구가 바뀌면 체크가 풀린다

요구사항 **문구(`content`)가 바뀌면** 서버가 체크를 푼다. 확인했던 문장과 다른 문장이 체크된 채로 남으면 안 되기 때문이다. 오타 수정과 실제 변경을 서버가 구분할 방법은 없으므로, 판단은 수정하는 사람에게 맡긴다(§6-1).

**필수 여부(`required`)만 바뀌면** 체크를 유지한다. 필수에서 선택으로 바뀐 요구사항은 K-13의 필수 개수에서 빠질 뿐이다.

## 3. 응답 — 기존 요구사항 객체에 필드 추가

새 조회 API를 만들지 않는다. 기존 제출물 목록(`GET .../deliverables`)과 요구사항 생성·수정 응답의 요구사항 객체에 `assessment`를 **추가**한다.

충족으로 체크된 요구사항:

```json
{
  "id": "55555555-5555-4555-8555-555555555555",
  "content": "출처 표기",
  "required": true,
  "assessment": {
    "assessedBy": { "userId": "11111111-1111-4111-8111-111111111111", "name": "송승준" },
    "assessedAt": "2026-10-02T14:30:00+09:00"
  }
}
```

확인 전인 요구사항:

```json
{
  "id": "55555555-5555-4555-8555-555555555555",
  "content": "출처 표기",
  "required": true,
  "assessment": null
}
```

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `assessment` | 객체 또는 `null` | 체크되면 객체, 확인 전이면 `null`. 필드 자체는 생략하지 않는다 |
| `assessment.assessedBy` | 객체 | 체크한 사람 |
| `assessment.assessedAt` | 시각 문자열 | 시간대 포함 ISO-8601. 기존 `TaskResponse`의 시각 필드와 같은 형식 |

## 4. 권한과 오류

기존 요구사항 쓰기와 같은 권한이다(`requireContributor`). 팀장·팀원은 체크·해제, 관찰자와 비회원은 불가. 조회 권한은 기존과 같다.

**권한 범위는 리뷰에서 확정한다.** 기본안은 팀장·팀원 모두다. 2~4명 팀에서 팀장만 체크할 수 있으면 팀장이 병목이 된다. 대신 자기 업무를 자기가 체크할 수 있다는 약점이 있어서, 누가 체크했는지를 항상 보여주는 것으로 보완한다(§6-2). 팀장만 허용하자는 의견이 있으면 이 절만 바꾸면 된다.

401·403·404와 오류 본문(ProblemDetail)은 기존 요구사항 API와 같다. 404는 다른 프로젝트 자원의 존재 여부를 드러내지 않는다.

**경로의 UUID 형식 오류는 아직 400을 약속하지 않는다.** 현재 예외 처리가 이 경우를 500으로 바꿀 가능성이 있어 A-02에서 실제 요청으로 확인한 뒤 확정한다.

동시에 두 요청이 오면 나중에 저장된 쪽이 남는다.

**알려진 한계:** 저장 시 행 전체를 다시 쓰기 때문에, 한 사람이 요구사항 수정 화면을 연 사이에 다른 사람이 체크하면, 앞 사람이 필수 여부만 바꿔 저장해도 그 체크가 지워진다. 막으려면 버전 기반 잠금이 필요한데 현재 저장소 어디에도 없고 업무·제출물도 같은 한계를 가진다. 확정·제출의 동시 요청을 잠금이나 버전으로 검증해야 하는 K-20(CONTRACTS §3-11)에서 함께 도입한다.

## 5. B가 읽을 방법 · DB

K-13의 `met`에는 **필수이면서 체크된 요구사항 수**를 쓴다. A가 `DeliverableService`에 읽기 전용 메서드를 제공한다.

```java
@Transactional(readOnly = true)
public long countMetRequiredRequirements(Deliverable deliverable)
```

필수 요구사항 총수(`countRequiredRequirements`)와 짝을 이룬다. 이 계약이 구현되면 K-13의 `assessmentAvailable`은 `true`가 되고 `met`·`percent`에 실제 값이 들어간다. 그 전환은 B가 K-13에서 한다.

마이그레이션 번호 **V20을 이 계약에 예약한다.** 작성일 기준 모든 원격 브랜치의 최대 번호는 V19다. `deliverable_requirements`에 열 두 개를 추가한다.

| 열 | 타입 | 의미 |
| --- | --- | --- |
| `assessed_by` | UUID, `REFERENCES users(id)` | 체크한 사람. 확인 전이면 NULL |
| `assessed_at` | TIMESTAMPTZ | 체크한 시각. 확인 전이면 NULL |

`assessed_at`에 값이 있으면 충족이다. 기존 행은 두 열 모두 NULL(확인 전)로 시작한다. 기존 V1~V19는 수정하지 않는다. 체크 이력은 남기지 않고 마지막 상태만 저장한다.

## 6. 권장 화면 동작 (C)

서버 변경 없이 화면에서 할 수 있는 것들이다. 구현 방식은 C가 정한다.

1. **체크된 요구사항의 문구를 저장하기 전에 알린다.** 예: "문구를 바꾸면 송승준님의 충족 확인이 풀립니다. 계속할까요?" 체크가 조용히 사라지면 확인했던 팀원은 이유를 모른다.
2. **누가 언제 체크했는지를 항상 보여준다.** 예: "송승준 · 3일 전". §4의 권한 약점을 이것으로 보완한다.
3. **확인 전인 요구사항 옆에 연결 업무의 진행 상황을 보여준다.** 업무는 `requirementId`로 요구사항에 연결돼 있고(V19), 제출물 화면은 이미 업무 목록을 불러온다. 빈 체크박스만 있으면 "아직 안 봤다"인지 "봤는데 부족하다"인지 알 수 없다.
4. **연결 업무가 모두 끝났는데 확인 전이면 다음 행동을 알린다.** 예: "업무가 모두 끝났습니다. 충족 여부를 확인하세요." 서버는 자동으로 체크하지 않고, 화면이 사람에게 확인을 권한다.
5. **관찰자에게는 체크박스를 비활성으로 보여주고 이유를 적는다.** 예: "관찰자는 확인할 수 없습니다." 제출물 화면이 이미 역할로 편집 가능 여부를 계산하고 있어 서버 필드는 필요 없다. 관찰자가 403을 보게 하지 않는다.

```
☐ 출처 표기           연결 업무 1/2 완료 · 자료조사(진행 중)
☐ 결론 3쪽 이상        연결 업무 2/2 완료 → 충족 여부를 확인하세요
☑ 표지 양식 준수       송승준 · 3일 전
```
