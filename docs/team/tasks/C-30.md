# C-30 · 최종 확정·제출 기록 화면

- 상태: READY 전 (화면 설계만. K-20 계약이 아직 없어 구현하지 않음)
- 담당: 손정효 / 검토: 송승준(K-20), 손정협(B-22 확정 경계)
- 주차: 4주차 (10/12~18) 계획. 3주차 계획(#79)에서 검토 흐름 확인이 한 주 밀려 4주차 범위는 다음 주 계획에서 다시 본다
- 의존: K-20(A, 미작성), A-20 확정 API, K-10(#69 AGREED)·K-11·K-12, C-20(#66)

이 문서는 K-20을 쓰기 전에 화면이 무엇을 보여 주고 무엇이 필요한지 정리한 것이다. K-20은 A가 생산자로 작성하고, 여기의 "K-20에 바라는 것"은 소비자 요청이다. 계약에 맞지 않는 부분은 K-20 리뷰에서 맞춘다. 화면 코드에 가짜 데이터는 넣지 않는다(DEVELOPMENT_PLAN 6장: mock 시연은 완료가 아니다).

## 근거

| 영역 | 근거 | 상태 |
| --- | --- | --- |
| 업무 완료 ≠ 충족 ≠ 제출 | CONTRACTS 3장 1항 | 확정 |
| 상태 `DRAFT → IN_REVIEW → CONFIRMED → SUBMITTED` | CONTRACTS 3장 7항, K-10 2장 | 확정 |
| 확정은 팀장 명시 동작, 서버가 필수 충족·최신 회차 승인·미해결 0을 재검증 | CONTRACTS 3장 8항 | 확정 |
| 강제 확정·재개 없음 | CONTRACTS 3장 9항 | 확정 |
| SUBMITTED는 사용자가 학교에 낸 뒤 남기는 기록. 자동 접수로 표현하지 않음 | CONTRACTS 3장 10항 | 확정 |
| 확정 근거 `currentBasis`, 미해결 수 `unresolvedCommentCount` | K-10 3장 | AGREED |
| 확정 URL·본문·응답·잠금 범위·제출 기록 필드 | K-20 | 없음 |

## 화면

### 1. 제출물 상세 "최종 제출" 탭

지금은 "준비 중"으로 막혀 있는 탭이다. 상태별로 보여 준다.

**확정 전 (DRAFT·IN_REVIEW)**

- 확정 준비 목록. 항목마다 충족 여부, 이유, 고칠 화면 링크
  1. 필수 요구사항 충족 확인 n/m → 요구사항·업무 탭
  2. 최신 회차가 승인됐고 그 승인이 지금 확정 근거인가(`currentBasis`). 확정할 파일 이름·버전·짧은 해시·올린 사람 → 검토 탭
     - 근거가 아니면 K-10 7장의 사유를 그대로: "이후 새 회차가 열림" / "파일 없는 회차" / "같은 이름의 최신 버전과 내용이 다름"
  3. 미해결 피드백 0건 → 검토 탭 (지난 회차에서 다시 연 피드백도 센다, K-10 2장)
- 목록은 안내다. 확정 가능 여부는 서버 판단을 그대로 보여 주고, 화면이 진척 수치로 따로 계산하지 않는다(CONTRACTS 3장 8항)
- "최종본 확정" 버튼은 팀장에게만. 준비 목록이 다 차지 않으면 비활성 + 첫 번째로 막힌 이유. 팀원에게는 "팀장이 확정합니다", 관찰자에게는 버튼 없이 상태만
- 확정 확인 창
  - 확정할 파일 버전(이름·버전·짧은 해시)
  - 확정하면 막히는 것: K-20이 정하는 잠금 범위를 그대로 나열(파일·요구사항·연결 업무·피드백·회차)
  - "확정은 되돌릴 수 없습니다. 고쳐야 하면 새 제출물로 다시 만들어야 합니다" (강제 재개 없음, 9항). 문구는 K-20의 실제 정책에 맞춘다
  - 확인 버튼을 누르면 처리 중에는 다시 누를 수 없다. 중복 방지는 서버가 한다(11항)

**확정 후 (CONFIRMED)**

- 확정자·시각·확정 파일 버전(다운로드 링크)
- 다른 탭과 업무 보드가 읽기 전용이 된다는 안내
- 제출 기록 입력 (아래 2)

**제출 기록 후 (SUBMITTED)**

- 제출 채널·제출 시각·기록자·증빙 메모
- "이 기록은 팀이 직접 남긴 것으로, 학교 시스템의 접수 여부를 확인하지 않습니다" (10항)

### 2. 제출 기록 입력

학교 시스템에 낸 뒤 사람이 남기는 기록이다. 버튼 이름은 "제출했다고 기록"처럼 기록임을 드러낸다. "제출하기"처럼 앱이 대신 제출하는 것으로 읽히는 말은 쓰지 않는다.

| 입력 | 화면 기본값 | 비고 |
| --- | --- | --- |
| 제출 채널 | 제출물의 "제출 경로"(`submissionMethod`) | 예: 학교 LMS 과제함 |
| 제출 시각 | 지금 | 미래 시각은 막는다(서버도) |
| 증빙 메모 | 비움 | 접수 번호·확인 메일 제목 등. 선택 |
| 증빙 파일 | 없음 | K-20에서 받을지 정함. 받는다면 파일 금고와 따로 둘지도 |

### 3. 확정 뒤 다른 화면

| 화면 | 확정(CONFIRMED·SUBMITTED) 뒤 |
| --- | --- |
| 제출물 상세 헤더 | 수정·삭제 숨김, 상태 배지 |
| 요구사항·업무 탭 | 요구사항 추가·수정·삭제, 충족 체크, 업무 연결·추가 숨김 |
| 검토 탭(#66) | 이미 확정 제출물은 읽기 전용으로 그림(K-11 409) |
| 업무 보드 | 확정된 제출물에 연결된 업무 카드를 읽기 전용으로(#63의 관찰자 읽기 전용과 같은 방식). 잠금 범위는 K-20 |
| 파일 금고 | 확정 파일 버전 삭제·같은 이름 새 버전 업로드를 어떻게 할지 K-20 |
| 제출물 목록 | 카드에 상태 배지 |
| 프로젝트 홈 "다음 할 일"(#77) | 검토 요청 이후 단계 추가: 검토 중 → 수정 요청 받음 → 확정 대기 → 제출 기록 대기 → 제출 기록됨 |

### 4. 막히는 경우의 안내

- 팀장·팀원이 한 명뿐인 프로젝트: 파일을 올린 사람은 승인할 수 없어 확정까지 갈 수 없다(K-10 10장, K-20에서 허용 여부 결정). 허용하지 않으면 "파일을 올리지 않은 팀원의 승인이 필요합니다"와 팀원 초대(프로젝트 설정) 링크
- 확정 직전에 다른 사람이 새 회차를 열거나 피드백을 다시 열어 409: 서버 사유를 보여 주고 준비 목록을 다시 불러온다
- 확정 정보 조회가 실패하면 "확정할 수 없음"으로 보이지 않게 오류와 다시 시도를 보여 준다(C-31 기준)

## K-20에 바라는 것 (C 소비자 요청)

1. **확정 준비 조회를 서버가 한 번에 준다.** 위 1의 세 항목 각각의 통과 여부, 막힌 이유, 확정할 파일 버전을 주면 화면이 따로 계산하지 않는다. K-10 회차 응답(`GET .../reviews`)에 붙여도 되고 따로 둬도 된다. 확정 명령이 쓰는 검사와 같은 코드면 좋겠다(K-10의 `currentBasis`처럼)
2. **제출물 응답에 상태를 넣는다.** K-10 10장에서 미룬 질문이다. 목록 카드·업무 보드·프로젝트 홈이 제출물마다 회차 API를 부르지 않게, 제출물 목록·단건 응답에 `status`를 넣어 주면 좋겠다
3. **확정 결과에 확정 파일 버전과 확정자·시각을 남긴다.** 이후 같은 이름의 새 버전이 올라와도 확정본이 무엇이었는지 보여야 한다
4. **잠금 범위를 표로.** 파일·요구사항·충족 확인·연결 업무(수정·상태 변경·이동·삭제 각각)·피드백·회차·제출물 수정·삭제마다 확정 뒤 허용/409를 적어 주면 화면에서 같은 표로 버튼을 숨긴다
5. **제출 기록 필드와 규칙.** 채널·시각(미래 허용 여부)·기록자·증빙(메모·파일), 누가 기록하는지(팀장만/팀장·팀원), 두 번째 기록 요청은 409인지 기존 기록 반환인지, 잘못 기록했을 때 정정 방법(1차 범위 밖이면 그렇게 명시)
6. **409·403의 `detail`은 사용자가 다음 행동을 알 수 있는 문장으로.** 화면은 서버 사유를 그대로 보여 준다(예: "미해결 피드백 2건을 해결해야 확정할 수 있습니다")
7. **1인 프로젝트 허용 여부.** 위 4의 안내 문구가 달라진다

## 구현 순서 (K-20 합의 뒤)

1. `types/review.ts`에 확정·제출 타입, `lib/api/review.ts`(또는 새 파일)에 요청 함수
2. "최종 제출" 탭: 준비 목록 → 확정 창 → 확정 후 → 제출 기록
3. 잠금 반영: 제출물 상세·업무 보드·파일 금고·목록 배지
4. 프로젝트 홈 "다음 할 일" 단계 추가
5. 브라우저 확인: 팀장·팀원·관찰자, 실제 서버로 초안 → 검토 → 수정 → 재검토 → 승인 → 확정 → 제출 기록, 확정 뒤 쓰기 차단, 확정 경쟁 409, 작은 화면(390px)

## 완료 기준

- K-20 AGREED와 A-20 병합 뒤 실제 API로 위 5의 흐름을 브라우저로 확인하고 결과를 이 문서에 남긴다
- 화면이 확정 가능 여부를 스스로 계산하지 않는다(서버 응답만)
- 확정 뒤 잠긴 동작의 버튼이 보이지 않거나, 보이면 서버 사유를 보여 준다
