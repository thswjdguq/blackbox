## 발견 경위

- 손정효가 4주차 보고에서 "`start-local.ps1`로 띄우면 화면의 API 호출이 실패한다"고 보고했다. 코드로 확인했다.
- A-01 이후 Windows에서 `scripts/verify-db.sh`가 검사용 DB를 띄우지 못하는 경우가 있었다.

## 사실

1. `frontend/src/lib/api.ts`는 `baseURL: "/api"`로 요청하고, `frontend/next.config.mjs`는 `NEXT_DEV_BACKEND`가 있을 때만 `/api/*`를 백엔드로 넘긴다. `start-local.ps1`의 화면 명령(`$frontendCmd`)은 이 값을 넘기지 않는다. `frontend/.env.local`에 따로 적어 두지 않았다면 개발 서버에 `/api` 경로가 없어 화면의 모든 API 호출이 실패한다. 이 스크립트는 예시 파일이 없는 `.env.local`이 있어야만 실행되고, 4월에 만들어진 뒤 수정된 적이 없으며 CI·배포에서 쓰지 않는다.
2. Docker 설정(`frontend/Dockerfile`, `docker-compose*.yml`)은 `NEXT_PUBLIC_API_URL`을 넘기지만 화면 코드는 이 값을 읽지 않는다. README 환경 변수 표와 `frontend/.env.example`은 이 값만 안내하고, 로컬 개발에 필요한 `NEXT_DEV_BACKEND`는 어디에도 적혀 있지 않다.
3. 검사용 DB 포트 55432는 Windows(Hyper-V·WinNAT)가 예약하는 구간(예: 55386~55485)에 들어가 "ports are not available"로 실패할 수 있다. 개발 DB 컨테이너(`blackbox_db`)와는 관계없다. 이 100개 단위 구간은 동적 포트 범위(49152~65535) 안에서 부팅마다 바뀐다. 그 아래에는 낱개 예약만 있고 25432는 예약되어 있지 않다.
4. 포트를 바꾸는 `BB_TEST_DB_PORT`는 `scripts/verify-db.sh`에만 적용되고 `docker-compose.test-db.yml`과 테스트 설정에는 적용되지 않는다(작업 중 확인).

## 할 일

1. `start-local.ps1`·`start-local.bat`을 지운다. 처음에는 화면 명령에 `NEXT_DEV_BACKEND`를 넣어 고치려 했지만, 사실 1대로 쓰이지 않는 스크립트라 삭제로 바꿨다. 손정협이 만든 파일이므로 PR에서 삭제 동의를 받는다.
2. 스크립트가 하던 일을 README 6장에 옮긴다: 로컬 개발 명령 세 개(DB, 백엔드, `NEXT_DEV_BACKEND`를 준 화면)와 업로드 폴더(`FILE_UPLOAD_DIR`) 지정. 7장 환경 변수 표의 `NEXT_PUBLIC_API_URL` 행은 "현재 화면 코드가 읽지 않음"으로 고친다. Docker 설정은 배포 경로라 이 Task에서 바꾸지 않는다.
3. 검사용 DB 포트를 25432로 바꾼다: `docker-compose.test-db.yml`, `scripts/verify-db.sh` 기본값, `backend/src/test/resources/application-test.yml`(설명·기본 URL), A-01 작업서·인수인계의 포트 표기. 세 설정이 모두 `BB_TEST_DB_PORT`를 따르게 한다.
4. `frontend/.env.example`은 C 소유라 고치지 않고, 같은 내용을 PR 후속 작업으로 손정효에게 넘긴다.

## 금지 범위

화면 코드(`frontend/**`)와 CI 워크플로(검사용 DB 포트를 쓰지 않음)는 바꾸지 않는다. 개발 DB(`docker-compose.yml`, 5432)는 건드리지 않는다. 일반 검증에서 `docker compose down -v`를 쓰지 않는다.
