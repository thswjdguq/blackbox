# A-72 · 이메일 주소 인증

- 담당: 송승준 / 검토: 손정협
- 기능: C5 (알림)
- 상태: IN_REVIEW
- 기준 SHA: `3e206b14`(#224 병합, SMTP 발송 어댑터 포함)
- 근거: K-41 0.5 9·10장(#221 병합), #221 승인 리뷰에서 A가 맡은 V40·인증 API·가용 상태 조회

## 목표

업무 메일은 수신 동의와 현재 주소 인증을 모두 마친 사용자에게만 보낸다(K-41 0.5). 가입 흐름은 바꾸지 않고, 로그인한 본인이 프로필에서 확인 메일을 요청해 주소를 인증한다. B의 수신 설정 API와 발송 worker가 읽을 인증 상태와 가용 상태를 제공한다.

## 구현

- **V40**: `users.email_verified_at`(NULL이면 미확인, 기존 계정은 모두 미확인), 확인 토큰 표 `email_verification_tokens`(SHA-256만 저장, 발급할 때의 주소, 만료·사용 시각), B의 수신 설정 표 `email_notification_preferences`(행이 없으면 꺼짐, 켜면 `enabled_at` 필수)
- **API**(로그인한 본인만)
  - `POST /api/auth/email-verification/request`: 202 발송 요청(`message` 포함), 204 이미 확인한 주소, 429 재요청 제한(`Retry-After` 초), 503 사용 불가
  - `POST /api/auth/email-verification/confirm` `{ "token": "..." }`: 204 확인, 400 사용할 수 없는 링크(없는 토큰·다른 계정의 토큰·이미 쓴 토큰을 구분하지 않음), 410 만료, 409 주소 변경
  - 실패 응답의 `detail`은 K-41 9장 표의 사용자 문장이다. `EmailVerificationService`의 상수 하나로 관리한다
- **토큰**: 32바이트 무작위 값(base64url), 15분 만료, 한 번만 사용. 확인 링크는 `{FRONTEND_BASE_URL}/email/verify#token=…`로 토큰을 fragment에만 싣는다. 확인에 성공해도 로그인이나 다른 권한을 주지 않는다
- **요청 제한**: 계정별 60초 간격과 시간당 5회, 서비스 전체 하루 100회(서비스 Gmail의 하루 발송 한도를 업무 메일과 나눠 쓴다). 요청 제한의 검사와 토큰 발급은 advisory lock 하나로 직렬화해, 서로 다른 사용자가 동시에 요청해도 서비스 하루 상한을 넘지 않는다(#228 B 리뷰에서 99건 상태의 동시 두 요청이 101건이 되는 것을 재현). 보내지 못한 요청도 횟수에 넣는다
- **발송 경로**: 확인 메일은 V39 발송 큐를 거치지 않는다. 발송 큐는 이벤트 종류가 업무·검토 요청 둘뿐이고, 수신자와 행위자가 같으면 안 되며(본인 요청), 업무·검토 대상 id가 필수다. 토큰 발급을 커밋한 후 요청 처리 안에서 A-71 어댑터로 바로 보내고, 토큰 행 id를 발송 id(Message-ID)로 쓴다. 발급은 `REQUIRES_NEW`로 호출자의 트랜잭션과 따로 커밋하므로, 호출자에게 트랜잭션이 있어도 메일을 보낼 때 토큰이 이미 다른 연결에서 보이고 호출자가 롤백해도 보낸 링크의 토큰이 사라지지 않는다(#228 B 리뷰에서 재현). SMTP 동안 잠금을 잡지 않는다
- **가용 상태**: `EmailVerificationService.availability(User)`는 `MAIL_ENABLED`, 수신 허용 목록, SMTP 어댑터, 메일 링크 출처가 모두 갖춰졌는지를 돌려주고, 불가하면 503과 같은 문장을 함께 준다. B의 `verificationAvailable`·`verificationUnavailableReason`이 이 값을 그대로 쓴다. SMTP에 접속하지 않는다
- **인증 상태**: B는 `User.getEmailVerifiedAt()`을 읽는다. 엔티티에서는 읽기 전용이라, 확인 전에 읽은 엔티티를 저장해도 확인 시각을 지우지 않는다. 이미 확인된 주소를 다시 확인하면 처음 확인 시각을 유지한다
- **허용 목록 판정**: B의 `EmailNotificationPolicy`에 `allowsAddress(email)`를 추가해 업무 메일과 같은 주소 정규화로 판단한다
- 계정 이메일은 지금 바꿀 수 없다(가입 때만 정함). 그래도 토큰에 발급 주소를 묶어, 주소 변경 기능이 생기면 옛 주소의 링크는 409로 거절된다

## 검사

- HTTP 테스트 9건(`EmailVerificationHttpTest`, 실제 PostgreSQL·인증, SMTP만 mock): 발송·확인·재사용 거절, 60초 간격과 시간당 상한의 429·`Retry-After`, 서비스 하루 예산, 꺼짐·허용 목록 밖·SMTP 실패·발송 예외의 503, 다른 계정·잘못된·만료·옛 주소 토큰, 로그인 필수. 발급이 따로 커밋되므로 테스트 트랜잭션으로 감싸지 않고, 만든 사용자를 테스트마다 지운다
- B 리뷰 회귀 2건: 하루 상한 99건에서 서로 다른 두 사용자의 동시 요청은 한 건만 발급, 호출자 트랜잭션 안에서 불러도 메일 발송 시점에 다른 연결에서 토큰이 보이고 호출자 롤백 후에도 남음. 두 수정을 되돌리면 두 테스트가 실패하는 것을 확인했다
- DB 마이그레이션 테스트 1건(`MainMigrationCompatibilityTest`): V39에서 V40으로 올릴 때 기존 계정 미확인, 토큰 해시 중복·만료·사용 시각 제약, 수신 설정의 `enabled_at` 제약과 `updated_at` 트리거
- 빈 DB 마이그레이션 검사가 최신 버전을 숫자(39)로 고정해, 마이그레이션을 추가할 때마다 손으로 올려야 했다(V38·V39 때도 갱신). Flyway가 읽은 파일 중 가장 높은 버전까지 적용됐는지 보도록 바꿨다. 고정값이 막던 "이름을 잘못 쓴 파일을 Flyway가 조용히 건너뛰는 경우"는 테스트의 Flyway 설정에 `validateMigrationNaming`을 켜서 실패하게 했다. 임시 `V41__probe.sql`은 수정 없이 통과하고, `V41_probe.sql`은 실패하는 것을 확인한 뒤 두 파일을 지웠다
- 백엔드 전체 565건 통과(건너뜀 5건은 실제 모델·메일 테스트), 새 검사용 DB 사용

## 남은 것

- B: 수신 설정 API(K-41 8장, V40의 `email_notification_preferences` 사용), 발송 worker의 `EmailDeliveryAuthorization` 실제 구현
- C: 프로필 수신 설정·인증 안내, 확인 링크 화면과 로그인 후 복귀
- 오래된 토큰 행은 지우지 않는다. 계정별 시간당 5건, 서비스 하루 100건이 상한이라 쌓이는 양이 작다
