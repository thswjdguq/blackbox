# A-81 · 자동 최신화한 PR의 워크플로 실행 승인 대기 해소

- 담당: 송승준 / 검토: 손정협(저장소 관리자, Secret 등록), 손정효
- 기능: M5 (개발 운영)
- 상태: IN_REVIEW
- 기준 SHA: `63ead3fd`(#234 병합)
- 근거: #230 후속 코멘트(2026-11-25), 손정협님의 `PR_UPDATE_TOKEN` 등록(같은 날)

## 문제

#230은 main이 바뀌면 `GITHUB_TOKEN`으로 열린 PR 브랜치를 갱신하고, 그 push로는 CI가 실행되지 않는다고 보고 `workflow_dispatch`로 CI를 따로 실행했다. 실제로는 GitHub의 동작 변경(2026-06-11 공지) 후 봇의 push로 시작된 CI 워크플로가 "Approve workflows to run" 승인을 기다려, 필수 상태 검사 세 개가 "Expected"로 남아 병합이 막혔다(#203, #231, #234). `workflow_dispatch`로 실행한 CI는 PR 병합 커밋에 붙지 않아 필수 상태 검사를 채우지 못했다(#230 손정협님 코멘트).

## 변경

- `update-pr-branches.yml`
  - 갱신은 저장소 Secret `PR_UPDATE_TOKEN`(이 저장소의 Contents·Pull requests 쓰기만 가진 fine-grained 토큰)으로 한다. push가 봇이 아닌 토큰 소유자의 것으로 기록되어 CI가 승인 없이 바로 실행된다
  - job은 `github.ref`가 main일 때만 돈다. 수동 실행에서 다른 브랜치를 골라 그 브랜치의 스크립트가 Secret을 받는 일을 막는다
  - checkout은 실행을 일으킨 main 커밋(`github.sha`)으로 고정하고 `persist-credentials: false`로 git 설정에 토큰을 남기지 않는다. PR 브랜치의 코드는 내려받지도 실행하지도 않는다
  - `GITHUB_TOKEN` 권한은 `contents: read`만 남긴다(`pull-requests`, `actions` 쓰기 제거)
- `update-pr-branches.sh`: CI를 따로 부르던 부분과 head가 바뀌기를 기다리던 부분을 뺐다. update-branch만 부르고, 422(이미 최신이거나 충돌)는 건너뛰며 그 밖의 실패는 실패로 끝낸다. 토큰이 비어 있으면 gh를 부르기 전에 실패한다
- `ci.yml`: `workflow_dispatch` 우회를 뺐다
- `WORKFLOW.md`: 갱신 방식, 다시 실행하는 법, 토큰 만료 시 재등록을 고쳤다

## 검사

- `scripts/test-update-pr-branches.sh`(mock `gh`, CI의 backend job에서 실행) 4가지: head 조건으로 갱신하고 검사를 따로 부르지 않음, 422는 건너뛰고 성공, 422가 아닌 실패는 실패로 끝나되 나머지 PR은 처리, 토큰이 없으면 gh를 부르기 전에 실패
- 422를 실패로 보게 바꾸면 2건, 실패를 무시하게 바꾸면 1건이 실패하는 것을 확인했다
- 실제 동작은 main에 병합된 후에만 확인할 수 있다. 병합 후 첫 main 병합에서 확인할 것: 열린 PR에 토큰 소유자 이름의 병합 커밋이 생기는지, 그 PR의 필수 상태 검사 세 개가 승인 없이 실행되는지, 승인이 그대로 남아 병합할 수 있는지

## 남은 확인

- main ruleset의 `require_extra_approval_for_unattributed_changes`가 토큰 소유자 이름의 병합 커밋에 승인을 더 요구하는지. 찾은 자료로는 Copilot 코딩 에이전트가 연 PR에 승인을 하나 더 요구하는 설정으로 보이지만 GitHub 공식 문서에서 이름을 확인하지 못했다. 병합 후 실제 동작으로 확인한다
