# A-73 · main 변경 시 열린 PR 브랜치 자동 최신화

- 담당: 송승준 / 검토: 손정협
- 기능: M5 (운영과 배포)
- 상태: IN_REVIEW
- 기준 SHA: `3e206b14`(#224 병합)

## 문제

main 보호 규칙이 "병합 전 최신 상태 요구"라, PR 하나가 병합될 때마다 열린 PR마다 최신 main을 손으로 병합(update-branch)하고 CI를 다시 기다려야 했다. 11주차에만 이 작업을 여러 번 반복했다. GitHub의 merge queue는 조직 소유 저장소에서만 쓸 수 있어, 개인 소유인 이 저장소에는 적용할 수 없다.

## 구현

- `.github/workflows/update-pr-branches.yml`: main push마다(실패한 실행은 손으로도) `scripts/update-pr-branches.sh`를 실행한다
  - 연달아 병합되면 앞 실행을 취소하고 마지막 main 기준으로 한 번만 갱신한다
  - 이미지 빌드(`images.yml`)와 분리했다. 배포 실패와 PR 갱신이 서로 영향을 주지 않는다
- `scripts/update-pr-branches.sh`
  - Draft가 아니고 같은 저장소 브랜치인, base가 main인 열린 PR마다 update-branch API를 부른다. `expected_head_sha`를 넘겨, 그사이 작성자가 push한 PR은 갱신하지 않는다. 이미 최신이거나 충돌이 나면 API가 422로 거절하므로 갱신하지 않는다
  - update-branch는 비동기라 브랜치 head가 바뀔 때까지(최대 60초) 기다린다
  - CI를 실행할지는 "이번에 갱신했는가"가 아니라 "그 PR의 지금 head에 `ci.yml` 실행 기록이 있는가"로 정한다. 갱신한 PR은 새 head에 기록이 없어 실행하고, 앞선 실행에서 CI 요청이 실패한 PR은 다시 돌릴 때 이미 최신이어도 기록이 없어 실행되며, pull_request로 이미 돈 head는 중복 실행하지 않는다
  - 조회 실패, 갱신 대기 초과, CI 요청 실패가 하나라도 있으면 실행이 실패(종료 1)로 끝난다. 한 PR이 실패해도 나머지 PR은 처리한다
  - 처음에는 CI 요청 결과를 보지 않아, 요청이 실패해도 실행이 성공으로 끝나고 다시 돌려도 422에서 건너뛰어 복구되지 않았다(#230 B 리뷰에서 재현). 위 규칙으로 고쳤다
- `ci.yml`: `workflow_dispatch` 추가. `GITHUB_TOKEN`으로 만든 push는 `pull_request` 실행을 만들지 않으므로(GitHub의 재귀 실행 방지 규칙), 갱신한 브랜치의 필수 검사를 이 방법으로 다시 돌린다. 같은 커밋에 같은 이름의 검사가 GitHub Actions 앱으로 붙어 필수 검사를 채운다. 개인 토큰(PAT)이 필요 없다
- `docs/team/WORKFLOW.md`: 자동 갱신 동작과, 이어서 push하기 전에 `git pull`이 필요하다는 점을 추가했다

## 유지한 것

- "최신 상태 요구"는 끄지 않았다. 각 PR이 혼자서는 통과해도 합치면 깨지는 경우(같은 마이그레이션 번호, 바뀐 공용 메서드 등)를 병합 전 CI가 잡게 하기 위해서다
- 병합은 자동으로 하지 않는다. 승인과 병합은 지금처럼 사람이 한다

## 검사

- 두 워크플로의 YAML 구문과 스크립트의 bash 구문을 확인했다
- `scripts/test-update-pr-branches.sh`(CI의 backend 작업에서 실행): 가짜 `gh`로 5개 경우를 검사한다. 갱신 후 CI 실행, 이미 최신이고 CI가 있으면 실행 안 함, CI 요청 실패 시 종료 1과 다시 실행했을 때의 복구, head가 바뀌지 않으면 CI 미실행과 종료 1, 한 PR이 실패해도 나머지 처리. 예전 스크립트에 이 검사를 돌리면 5건이 실패한다
- Draft·fork 제외 필터는 실제 GitHub API의 PR 목록으로 확인했다(Draft PR 2건 제외)
- 실제 동작(병합 커밋 생성, workflow_dispatch로 붙은 검사가 필수 검사를 채우는지)은 이 PR이 main에 들어간 후 다음 병합에서 확인한다
