## 목표

1단계(`fbbb3cb`)의 제출물 화면 기능을 모두 유지하면서 목록과 상세를 분리하고, K-13 진척과 K-14 충족 확인을 붙인다.

## 1단계 기능 유지 확인

1단계 화면은 목록과 상세를 한 페이지에 두었다. 분리하면서 아래 기능을 모두 옮겼다.

| 1단계 기능 | 현재 위치 |
|------|------|
| 제출물 등록 (이름·기한·담당자·제출 경로·설명) | 목록 > 제출물 추가 |
| 제출물 수정·삭제 (삭제 확인 창) | 상세 헤더 |
| 제출 기한·담당자·제출 경로 표시 | 상세 헤더 |
| 요구사항 추가·수정·삭제 (삭제 확인 창, 필수 기본값) | 상세 > 요구사항 |
| 이 요구사항의 업무 만들기, 업무 추가 | 상세 (업무 보드와 같은 TaskModal) |
| 기존 미연결 업무를 이 제출물에 연결 | 상세 > 연결 업무 |
| 연결 업무의 상태·담당자·마감·완료 기준, 보드의 해당 업무로 이동 (`board?task=`) | 상세 > 연결 업무 |
| 저장 성공 안내, 미연결 업무 수 안내, 프로젝트 홈 이동 | 목록·상세 |

## 추가한 것

- K-13 진척 현황: 실제 `GET .../progress`. 업무 완료율과 필수 요구사항 충족률을 따로 표시
- K-14 6장
  - 1번: 충족 확인된 요구사항의 문구를 바꾸려 할 때만 저장 전에 "저장하면 ○○님의 충족 확인이 풀립니다"
  - 2번: 확인자·시각 표시
  - 3번: 확인 전 요구사항 옆에 아직 끝나지 않은 연결 업무 표시
  - 4번: 연결 업무가 모두 끝났는데 확인 전이면 확인 권유
  - 5번: 관찰자는 체크 비활성 + 이유 표시
- 충족 확인 체크는 낙관적 업데이트, 실패 시 해당 요구사항만 원복 + 안내, 처리 중 연타 방지
- 요구사항 추가·수정·삭제, 충족 확인, 업무 추가·연결 후 진척 재조회
- 탭 구조: 요구사항·업무(구현) / 검토·최종 제출(준비 중)
- 상세는 단건 조회(`GET /deliverables/{id}`, #56). 404 는 서버 detail 표시
- 보드 링크 `board?deliverable=<id>` 는 그 제출물로 필터된 보드를 연다

## 저장 요청은 전체 교체

서버 `PUT /deliverables/{id}`, `PUT .../requirements/{id}` 는 보내지 않은 필드를 null·false 로 저장한다. 화면은 수정할 때도 모든 필드를 보낸다 (`SaveDeliverablePayload`, `SaveRequirementPayload`).

## K-13 진척 표시

| 조건 | 화면 |
|------|------|
| `tasks.total === 0` | "연결 업무 없음" (0% 로 표시하지 않음) |
| `requiredRequirements.total === 0` | "필수 요구사항 없음" |
| 그 외 | `met/total (percent%)` — 서버 값 그대로 |
| API 실패 | 가짜 0% 대신 오류 + 다시 시도. 재조회 성공 시 해제 |

## 오류 안내

| 동작 | 실패 시 |
|------|---------|
| 제출물·요구사항 삭제 409 | 삭제 확인 창 안에 서버 detail (예: "이 요구사항에 연결된 업무를 먼저 변경해주세요") |
| 저장·삭제 기타 오류 | 서버 detail (`apiError`) 또는 기본 문구 |
| 충족 확인·해제 실패 | 해당 요구사항 원복 + 안내 |
| 업무 연결 실패 | 상단 안내 |
