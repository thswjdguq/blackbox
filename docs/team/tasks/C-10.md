## 구현 단위 (이 순서대로)

### 단계 1: 타입 정의 (의존 없음, 먼저 가능)

`frontend/src/types/deliverable.ts` 신규:

```typescript
// CONTRACTS.md 1항 현재 약속 기준
export interface Requirement {
  id: string;
  content: string;
  required: boolean;
}

export interface Deliverable {
  id: string;
  projectId: string;
  title: string;
  description: string | null;
  dueDate: string;            // "YYYY-MM-DD"
  submissionMethod: string | null;
  ownerId: string | null;
  ownerName: string | null;
  requirements: Requirement[];
}

export interface CreateDeliverablePayload {
  title: string;
  dueDate: string;
  description?: string;
  submissionMethod?: string;
  ownerId?: string;
}

export interface CreateRequirementPayload {
  content: string;
  required: boolean;
}

// K-13 진척 응답 (DRAFT — fixture 사용)
export interface DeliverableProgress {
  deliverableId: string;
  tasks: { total: number; completed: number; percent: number };
  requiredRequirements: {
    total: number;
    met: number | null;
    percent: number | null;
    assessmentAvailable: boolean;
  };
}
```

`frontend/src/types/task.ts`에 추가할 필드:

```typescript
// 기존 Task 인터페이스에 아래 필드 추가
deliverableId: string | null;
requirementId: string | null;
completionCriteria: string | null;
```

`CreateTaskPayload`에 추가:
```typescript
deliverableId?: string;
requirementId?: string;
completionCriteria?: string;
clearDeliverable?: boolean;
clearRequirement?: boolean;
```

### 단계 2: K-13 fixture (의존 없음)

`frontend/src/__fixtures__/deliverable-progress/`에 3개 파일:

- `with-tasks.json` — 연결 업무 있는 경우 (K-13 §2 현행 예시)
- `empty.json` — total=0인 경우 (K-13 §2 빈 상태 예시)
- `future-met.json` — assessmentAvailable=true 미래 예시 (실제 노출 금지, 개발 참고용)

### 단계 3: API 래퍼 (`frontend/src/lib/api/deliverable.ts`)

기존 `lib/api.ts` axios 인스턴스를 import해서 사용. `/api/api` 중복 안 됨.

```typescript
import api from "@/lib/api";
export const getDeliverables = (projectId: string) =>
  api.get<Deliverable[]>(`/projects/${projectId}/deliverables`);
// ... 목록·생성·수정·삭제·요구사항 CRUD·진척 조회
```

진척 조회는 K-13 AGREED 전까지 fixture를 반환하는 mock 함수로 구현.
fixture를 사용할 때 콘솔에 `[MOCK] K-13 progress` 로그 출력.
실제 연동 전환 기준: K-13 계약 AGREED + B-10 서버 병합 완료.

### 단계 4: 제출물 목록 페이지

`/projects/[projectId]/deliverables/page.tsx`

- 상단: 제목 + 팀장·팀원만 "제출물 추가" 버튼
- 카드 목록: 제목·기한·요구사항 수·업무 완료율(K-13 fixture)
- 로딩: 스켈레톤 카드
- 0건: 빈 상태 안내
- 삭제 시 409: "연결된 업무를 먼저 해제하세요" 안내
- 오류: 에러 배너 + 재시도

### 단계 5: 제출물 상세 페이지

`/projects/[projectId]/deliverables/[deliverableId]/page.tsx`

탭: **요구사항·업무** | `검토 (준비 중)` | `최종 제출 (준비 중)`

**요구사항·업무 탭**
- 요구사항 목록 (필수/선택 구분)
- 진척 섹션: 업무 완료율 + 요구사항 충족률 별도 행
  - total=0 → "연결 업무 없음" / "필수 요구사항 없음"
  - met=null → "충족 확인 기능 준비 중"
  - 진척 API 실패 → "정보를 불러올 수 없습니다" (가짜 0% 금지)
- 연결 업무 목록 (status badge + 제목)

**검토 탭** — `className="opacity-40 cursor-not-allowed"` 비활성. 클릭 시 "검토 기능 준비 중입니다" 안내.

**최종 제출 탭** — 동일하게 비활성.

### 단계 7: TaskModal 제출물 연결 섹션

기존 필드(제목·설명·우선순위·담당자·기한) 아래에 접을 수 있는 섹션 추가:

- 제출물 선택 드롭다운 (getDeliverables 호출)
- 요구사항 선택 드롭다운 (선택한 제출물의 requirements)
- 완료 기준 텍스트 입력
- 연결 해제 버튼 (clearDeliverable·clearRequirement)
- 제출물 목록 로딩 실패 시 섹션 숨김 (모달 전체 블로킹 금지)

## 검증 시나리오 (수동)

1. 프로젝트 홈 → 사이드바 "제출물" 클릭 → 목록 로드
2. "제출물 추가" → 제목·기한 입력 → 저장 → 목록에 추가됨
3. 제출물 클릭 → 상세 이동 → 요구사항 추가·삭제
4. 업무 보드에서 업무 클릭 → 모달에서 제출물 선택·저장
5. 제출물 상세에서 연결 업무 표시 확인
6. 관찰자 계정(있다면): 추가·수정 버튼 없음, 목록 읽기만 가능
