# A-03 · 프로젝트 삭제를 막는 외래키 조사와 처리안

- 담당: 송승준 / 검토: 손정협(점수·활동 로그 소유자로서 필수)
- 기능: M5 (환경·데이터 검증)
- 상태: READY — **조사·제안까지만. 구현은 팀 결정 후 별도 Task.**
- 기준 SHA: `fbbb3cb`
- 예상: 2시간

## 발견 경위

A-01 DB 검증(`scripts/verify-db.sh`)에서 실제 PostgreSQL로 프로젝트 삭제를 시도하다 발견했다.
mock 기반 단위 테스트로는 드러나지 않는 종류다.

## 사실

`projects`를 참조하는 FK 14개 중 **8개에 연쇄 삭제가 없다**(NO ACTION):
`activity_logs`, `alerts`, `contribution_scores`, `file_vault`, `manual_work_reports`,
`peer_reviews`, `weight_change_log`, `weight_configs`.

V9 트리거가 **업무 생성 시 `contribution_scores` 행을 자동 생성**하므로,
업무가 하나라도 있는 프로젝트는 `ProjectService.deleteProject`(`projectRepository.delete` 단순 호출)로 삭제되지 않는다.
현재는 `fbbb3cb`가 추가한 핸들러 덕에 500 대신 409가 나가지만 삭제 자체는 실패한다.
V19가 추가한 `deliverables`는 정상적으로 CASCADE다.

## 할 일

1. 실제 재현: 업무 있는 프로젝트 삭제 요청 → 응답 코드·메시지·로그 기록.
2. 8개 테이블 각각에 대해 **보존 요구**를 판단한다. 점수·활동 로그·파일 금고는
   "프로젝트가 사라져도 남겨야 하는 기록"일 수 있어 단순 CASCADE가 정답이 아닐 수 있다.
3. 처리안 3개를 장단점과 함께 제시한다.
   - (가) 새 migration으로 FK에 `ON DELETE CASCADE` 부여 — 간단하지만 기록이 함께 사라진다.
   - (나) 서비스에서 연관 행을 명시적으로 선삭제 — 삭제 범위를 코드에서 통제, 트랜잭션 주의.
   - (다) 실제 삭제 대신 보관 상태로 전환(soft delete) — 기록 보존에 가장 안전, 범위가 가장 크다.
4. 파일 금고는 해시 불변성 원칙(DEVELOPMENT.md)과 충돌하는지 확인한다.
