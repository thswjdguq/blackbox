# A-67 · 운영 백업 복원 시험

- 담당: 송승준 / 검토: 손정협
- 기능: M5 (운영과 배포)
- 상태: DONE
- 기준 SHA: `470348a2`(#205 병합)
- 근거: 11주차 계획(#203) A 할 일 3, 개발 계획 9주차 A 항목

## 목표

서버 자동 갱신(`scripts/ec2-update.sh`)이 만든 DB 덤프와 업로드 볼륨으로 서비스를 복원할 수 있는지 확인한다.

## 절차

1. 서버의 최신 자동 덤프(`auto-20261117-110040.dump`, 384KB, 11/17 갱신 직전 생성)와 업로드 볼륨(`/data/uploads`)의 압축본을 SSH로 PC에 받았다. 업로드 볼륨은 자동 갱신이 백업하지 않으므로, 백엔드 컨테이너 안에서 `tar`로 압축해 SSH 출력으로 바로 받아 서버에 파일을 남기지 않았다
2. 받은 파일은 저장소 밖의 PC 폴더(권한 700)에 두었다
3. 덤프를 검사용 DB 컨테이너(25432)의 새 DB에 `pg_restore --no-owner --no-privileges --exit-on-error`로 복원했다
4. 업로드 압축본을 풀고, `file_vault`의 모든 행에 대해 파일의 SHA-256과 크기를 DB 기록과 대조했다
5. 복원한 DB 위에 main 서버를 띄워 테스트용 시드 계정(`@chajara.example`)으로 로그인하고, 그 계정의 프로젝트에서 파일 목록과 교수용 PDF를 요청했다
6. 시험 서버를 끄고 임시 DB와 PC 사본(덤프, 업로드, 압축본, PDF)을 삭제했다

## 알게 된 점

- 파일의 `storage_path`는 `/data/uploads/...` 절대 경로로 저장된다. 다른 환경에 복원할 때는 업로드를 같은 경로(`/data/uploads`)에 두어야 서버가 파일을 읽는다. 운영 Compose는 볼륨을 이 경로에 붙이므로 서버 재구축 시에는 문제가 없다. 이번 시험은 PC에 이 경로를 만들지 않아, 서버를 통한 파일 내려받기 대신 위의 SHA-256 대조로 파일을 확인했다
- 서버의 자동 덤프 파일 권한이 `-rw-r--r--`(644)다. 덤프에는 계정 정보(비밀번호 해시 포함)가 있다. 서버 사용자는 `ec2-user` 하나라 지금 위험은 낮지만, 자동 갱신 스크립트가 덤프를 600으로 만들도록 바꾸는 것이 맞다
- 업로드 볼륨은 자동 백업 대상이 아니다. 11주차 계획대로 이번에는 수동 압축으로 시험했고, 자동 백업 추가는 하지 않는다
