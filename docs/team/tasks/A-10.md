## 목표

검토 회차를 만들고, 검토자가 회차마다 `승인` 또는 `수정 요청`을 결정하는 API 계약을 쓴다. 규칙의 큰 줄기는 1부에서 정했다. 2부는 그것을 URL·필드·상태 코드·DB 컬럼으로 옮기고, 아직 정하지 않은 **파일–제출물 연결**을 결정한다. 구현은 다음 주 A-11이다.

## 사실 (9/29 확인)

1. `file_vault`(V6)는 프로젝트에만 속하고 제출물과 연결되지 않는다.
2. 파일 버전은 **같은 프로젝트의 같은 파일 이름**으로 매긴다(`FileVaultService.upload`). 이름이 다르면 새 파일 1버전이 되고, 같은 이름·같은 내용이면 중복으로 보고 버전만 올린다.
3. 같은 이름으로 **내용이 다른 파일을 올리면 "변조 의심"으로 기록하고 경보를 만든다.** 검토 흐름에서는 수정본 업로드가 정상 동작이므로, 지금 방식 그대로면 수정본을 올릴 때마다 변조 경보가 뜬다.
4. `file_vault`에는 수정·삭제를 막는 트리거가 있다. 트리거를 끄지 않는 한 기존 행에 나중에 제출물 id를 채울 수 없고, 파일 금고의 불변 원칙 때문에 트리거를 끄는 방법은 쓰지 않는다. 열 추가(`ALTER TABLE ... ADD COLUMN`)는 행을 수정하지 않으므로 가능하다.
5. 제출물에는 아직 상태 필드(`DRAFT → IN_REVIEW → CONFIRMED → SUBMITTED`)가 없다(CONTRACTS 3장 7항).

## 할 일

1. **파일–제출물 연결 방식 결정안**: 아래 선택지를 장단점과 함께 비교하고 A 권고를 낸다.
   - (가) `file_vault`에 `deliverable_id` 열 추가 — 새 업로드부터 제출물을 지정. 기존 파일은 제출물 없음
   - (나) 별도 연결 테이블(제출물, 파일 버전, 제출물 안의 버전 번호) — 기존 파일도 나중에 연결 가능, 파일 금고는 그대로
   - (다) 회차가 파일 버전 id를 직접 가리키고, 제출물과 파일은 회차를 통해서만 이어진다 — 새 테이블·열이 없어 가장 작다. 다만 "새 파일 버전이 올라오면 이전 승인은 무효"를 판단하려면 제출물의 최신 파일을 알아야 하는데, 회차 없이 올라온 파일은 제출물에 속하는지 알 수 없다
   - 공통으로 정할 것: 수정본의 기준(같은 이름인가, 같은 제출물인가), 수정본 업로드를 변조 경보에서 제외하는 조건. 변조 판정은 파일 금고(A) 코드에 있지만 경보는 B의 경보 체계로 들어가므로 B와 합의한다
2. **K-10 계약 초안** `docs/team/contracts/K-10-review-round.md`
   - 회차 생성(대상 파일 버전 지정, 파일 없는 중간 검토 허용 여부), 회차 목록, 결정(`승인`/`수정 요청`) API
   - 검토자 자격: 그 파일 버전을 올린 사람을 뺀 팀장·팀원. 관찰자 403, 본인 버전 승인 거절
   - 승인 조건: 미해결 피드백 0건(K-11의 읽기 메서드 호출 지점). 승인된 회차 이후의 코멘트 차단은 K-11과 맞춤
   - 제출물 상태 전환 중 K-10 범위(`DRAFT ↔ IN_REVIEW`), 새 파일 버전·새 회차가 이전 승인을 무효로 하는 규칙
   - 동시 요청(같은 제출물에 회차 두 개 동시 생성 등)을 서버에서 막는 방법(CONTRACTS 3장 11항)
   - 요청·응답 JSON 예시, null 규칙, 오류 표, DB 컬럼표
3. V21(K-10), V22(K-11 피드백 SQL. WORKFLOW "DB·데이터·비밀값" 장에 따라 B 엔티티의 SQL은 A가 쓴다) 번호를 계약에 예약한다.
4. B의 K-11 초안과 회차 참조(회차 id, 승인 후 차단) 부분을 서로 검토한다.
