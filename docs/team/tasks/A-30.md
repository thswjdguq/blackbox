- 담당: 송승준 / 검토: 손정협(점수·경보 자료, 기여도 반영), 손정효(도우미 창과 제안 카드 화면)

## 목표

K-30의 엑스포 1차 범위를 서버에 구현한다. 과제 안내문에서 계획을 뽑는 장면과 진행 상태를 살피는 장면이 실제 DB와 HTTP로 동작하게 한다. 에이전트는 읽기만 하고, 제출물·요구사항·업무는 사람이 제안 카드를 채택할 때 만들어진다.

## 할 일

1. DB: `agent_runs`, `agent_proposals`, `agent_proposal_results` 테이블과 제약, 엔티티와 저장소
2. 모델 호출 경계: Spring AI를 감싼 한 곳. 공급자 설정이 없으면 서버는 그대로 뜨고 "쓸 수 없음"만 알린다. 테스트는 정해진 답을 돌려주는 가짜 모델을 쓴다
3. 읽기 도구 여섯 개(K-30 5장). 요청한 사람의 권한으로 기존 조회를 부르고 이메일은 내보내지 않는다
4. 단계 판정(K-30 3장)
5. 실행 종류 네 가지와 실행기, 이벤트 스트림(K-30 2장·4장)
6. 제안 카드의 조회·수정·채택·거절. 채택은 기존 제출물·요구사항·업무 서비스를 채택한 사람으로 부르고 한 트랜잭션으로 묶는다
7. K-30 12장 수용 조건을 가짜 모델로 실제 DB와 HTTP에서 확인한다
8. 실제 모델(Gemini)로 시연용 프로젝트에서 질문 세트를 돌린다. 키가 준비된 뒤에 한다

## 금지 범위

화면 코드(`frontend/**`)는 바꾸지 않는다. 점수·경보·업무의 코드(B 소유)는 부르기만 하고 고치지 않는다. 기존 회의록 요약의 AI 코드(`AiService`, `ClaudeService`, `OpenAiService`)는 건드리지 않는다. 기존 V1~V20은 수정하지 않는다. 검토·확정 단계의 실행 종류와 스스로 보내는 주간 요약은 범위 밖이다. 비밀값(모델 키)은 커밋하지 않는다.

## 설계 메모

늘어날 것과 고정할 것을 나눠 둔다. 구현하면서 이 기준을 지킨다.

| 구분 | 무엇 | 어떻게 |
| --- | --- | --- |
| 등록으로 늘어남 | 실행 종류(`skill`), 카드 종류(`kind`), 채택이 만드는 대상 종류(`target_type`), 읽기 도구 | 문자열로 저장하고 값 목록을 DB 제약이나 열거형에 박아 두지 않는다. 종류 하나는 "지시문, 쓸 수 있는 도구, 결과 형식"이나 "검증, 채택" 묶음 하나로 더한다 |
| 고정 | 실행의 상태(`RUNNING`·`DONE`·`FAILED`), 카드의 상태(`PENDING`·`ACCEPTED`·`REJECTED`) | 열거형과 DB 제약으로 묶는다. 상태는 엔티티의 메서드로만 바뀐다(`AgentRun.finish`·`fail`, `AgentProposal.edit`·`accept`·`reject`) |
| 바깥에 닿는 곳 | 모델 호출 | Spring AI를 감싼 한 곳에만 둔다. 나머지는 Spring AI의 타입을 모른다 |
| 다른 도메인과의 연결 | 제출물·요구사항·업무 | 카드는 내용을 JSON으로만 갖고 대상은 id로만 가리킨다. 에이전트의 엔티티가 그쪽 엔티티를 참조하지 않는다 |
| 설정으로 뺌 | 목록 건수, 실행의 시간·횟수 상한, 입력 길이 | 저장소는 값을 인자로 받고, 값은 설정에 둔다 |
| 마이그레이션에 적지 않음 | 늘어나는 값의 목록, 병합 순서 같은 한때의 사정 | 마이그레이션은 병합 뒤 고칠 수 없다. 바뀔 내용은 이 작업서와 계약에 적는다 |

## 진행 기록

- 1번(DB, 엔티티, 저장소): 작성. 실제 DB의 저장소 테스트 7건과 DB 없이 도는 상태 전환 테스트 5건이 통과하고 전체 테스트는 101건이다. JSON 내용의 저장과 재조회, 원본이 바뀌지 않는 것, 채택 결과를 대상으로 찾는 것, 버려진 실행과 끝난 실행을 "도는 중"으로 보지 않는 것, 제약 다섯 가지의 거절, 카드 목록이 조회 두 번으로 끝나는 것, 결정된 카드를 고치거나 다시 결정할 수 없는 것을 확인했다
- 2번(모델 호출 경계): 작성. Spring AI 1.1.8의 두 공급자를 넣고 기본 공급자를 `none`으로 두었다. 모델을 부르는 코드는 `agent/model/SpringAiAgentModel` 한 곳이고, 나머지는 `AgentModel`과 `AgentTool`만 안다. 가짜 모델로 지시문·자료·도구가 넘어가는 것, 중괄호가 든 글이 그대로 전달되는 것, 공급자의 실패가 우리 예외로 바뀌는 것, 공급자 설정 없이 서버가 뜨고 에이전트만 꺼지는 것을 확인했다
- 실제 Gemini 확인: 모델이 우리 도구를 부르고 그 결과로 답하는 반복이 동작한다(`AgentModelLiveTest`, 세 번 실행 모두 통과, 호출 한 번에 약 6초). 이 테스트는 `SPRING_AI_GOOGLE_GENAI_API_KEY`가 있을 때만 돌고 평소 빌드에서는 건너뛴다
- 모델 이름은 설정에 둔다(`spring.ai.google.genai.chat.options.model`, 기본 `gemini-3.5-flash`). Spring AI 1.1.8이 기본으로 쓰는 `gemini-2.0-flash-001`은 폐기돼 404가 난다. 10/9에 잰 응답 시간은 3.5 Flash 약 2.5초, 3.1 Flash Lite 약 1.5초였고, 3.8 Flash는 30~100초에 503이 섞였다. 시연 전에 다시 재고 필요하면 `GEMINI_MODEL`로 바꾼다
- 5번에서 볼 것: Spring AI의 재시도 기본값이 10회, 2초부터 5배씩이다(`spring.ai.retry.*`). Gemini의 503에 실제로 걸리는지는 확인하지 못했다. 실행의 시간 상한을 둘 때 함께 정한다
- 공급자를 켜는 법: `SPRING_AI_MODEL_CHAT=google-genai`와 `GEMINI_API_KEY`(Docker), 또는 `SPRING_AI_GOOGLE_GENAI_API_KEY`(직접 실행). Bedrock은 `SPRING_AI_MODEL_CHAT=bedrock-converse`와 `SPRING_AI_BEDROCK_AWS_REGION`, AWS 자격 증명이다
- 3번(읽기 도구): 작성. 도구 하나는 `agent/tool`의 `ProjectTool` 빈 하나다. 이름, 화면에 보일 말, 모델이 읽는 설명, 인자 형식, 조회를 한 클래스에 두고, `AgentToolbox`가 이름으로 찾아 실행(프로젝트와 요청한 사람)에 묶는다. 도구를 더할 때 다른 코드는 고치지 않는다. 조회는 기존 서비스(`ProjectService`, `DeliverableService`, `DeliverableProgressService`, `TaskService`, `AlertService`, `ScoreService`)를 요청한 사람으로 부르고, 응답에서 이름·역할·기록만 골라 담는다
- 3번의 확인(실제 DB 테스트 7건, 설정 테스트 2건): 여섯 도구의 값, 이메일이 어디에도 없는 것(이메일을 내보내게 고쳐 보면 테스트가 실패하는 것도 확인), 참여자가 아닌 사람으로는 아무것도 읽지 못하는 것, 다른 프로젝트의 제출물 id와 잘못된 인자가 이유만 돌려주는 것, 예상하지 못한 실패는 모델에 넘기지 않는 것, 이름이 겹치면 서버가 뜨지 않는 것, 목록이 상한에서 잘리는 것, 설정이 빠지거나 틀리면 서버가 뜨지 않는 것. 인자가 있는 도구를 실제 Gemini가 인자를 채워 부르는 것도 확인했다
- 3번에서 정한 것
  - 모델이 잘못 부른 것(없는 id, 인자 오류, 권한 없음)은 실행을 끝내지 않고 `{"error": 이유}`를 돌려준다. 그 밖의 실패는 이유를 모델에 넘기지 않고 실행을 끝낸다
  - 건수 상한은 도구가 아니라 도구함이 건다. 도구가 목록을 돌려주면 `{items, total, truncated}`로 나간다. 전부 읽은 뒤 `app.agent.tool-list-limit`(100)에서 자른다
  - `list_tasks`에는 인자를 두지 않았다
  - "오늘"과 "늦음"의 시간대는 `app.agent.zone`이고 `AgentProperties.today()` 한 곳에서 구한다
- 3번에서 남긴 것: `list_deliverables`의 단계는 4번에서 붙인다. 도구를 부를 때마다 보내는 `step` 이벤트는 5번에서 도구함에 연결한다
- 4번(단계 판정): 작성. `DeliverableStage.of`가 제출물의 요구사항과 연결 업무로 여섯 단계를 정한다. 화면의 판정(`frontend/src/components/project/NextStepCard.tsx`의 `nextStepFor`)과 조건과 순서가 같다. `DeliverableStages.read`가 제출물을 기한 순으로 읽어 단계를 붙이고, `list_deliverables`가 이것을 쓴다. 상태 조회의 `stages[]`도 5번에서 이것을 쓴다. 제출물이 없으면 빈 목록이다
- 4번의 확인: 화면의 판정 함수를 그대로 돌려 만든 기준표 1,361가지(요구사항 0~2개, 업무 0~2개의 모든 조합)와 서버의 결과가 전부 같다(`DeliverableStageTest`, 기준표는 `backend/src/test/resources/agent/stage-cases.txt`). 규칙 하나를 일부러 바꾸면 테스트가 실패하는 것도 확인했다. 화면의 판정이 바뀌면 기준표를 다시 만들어야 한다. 만드는 스크립트는 저장소에 없고(로컬 `.claude/g1/stage-cases.cjs`), 화면 함수를 TypeScript로 변환해 조합마다 부른 뒤 안내 제목을 단계 이름으로 옮긴 것이다
- 4번에서 정한 것: 단계의 뜻은 `DeliverableStage`에 있고 `list_deliverables`의 설명이 거기서 만들어진다. 단계를 더하면 설명도 따라 바뀐다. 업무가 끝났는지는 `TaskStatus.isDone` 한 곳에서 본다
- 5번 앞부분(실행 종류, 카드 종류, 실행기): 작성. HTTP와 이벤트 스트림, 시간 상한의 강제는 뒷부분에서 한다
  - 실행 종류는 `agent/skill`의 `AgentSkill` 빈이다. 이름, 화면의 말, 팀장·팀원만 실행하는지, 쓸 도구, 만들 수 있는 카드 종류, 입력 검증을 한 클래스에 둔다. 지시문은 `resources/agent/skills/{이름}.md`다. 화면에 보이는 순서는 `@Order`다
  - 역할의 규칙은 한 곳에 둔다. 누가 기록을 만들 수 있는지는 `ProjectAccessChecker.canContribute`가 정하고(기존 `requireContributor`도 이것을 쓴다), 관찰자의 실행이 카드를 만들지 않는 것은 실행기가 정한다. 실행 종류는 역할의 이름을 모른다
  - 카드 종류는 `agent/proposal`의 `ProposalKind` 빈이다. 내용 검증은 기존 API의 요청 객체(`SaveRequest`, `RequirementRequest`, `CreateTaskRequest`)에 붙은 검증을 그대로 쓴다. 길이 제한을 따로 적지 않았다. 검증을 지난 내용은 그 종류가 아는 칸만 남겨 저장한다. 모델이나 사람이 덧붙인 칸(예: 담당자)은 저장되지 않는다. 모델에 알려 줄 형식은 `resources/agent/kinds/{이름}.md`다
  - 지시문은 `AgentInstructions`가 공통 규칙(`common.md`), 실행 종류, 답의 형식, 카드 종류 순서로 조립한다. 등록된 종류의 파일이 없으면 서버가 뜨지 않는다. 안내문과 질문은 지시문에 섞지 않고 자료 표시(`material.md`) 안에 넣어 넘긴다. 글이 표시를 흉내 내 바깥으로 나오지 못하게 표시와 같은 글자는 지운다. 표시의 글자는 리소스에만 있다
  - 실행기(`agent/run/AgentRunner`)는 둘로 나뉜다. `prepare`는 스트림 전에 볼 것(참여자, 실행 종류, 역할, 입력, 모델 설정, 같은 사람의 실행 중, 시간당 횟수)을 확인하고 실행 기록을 만든다. `execute`는 모델을 부르고 `AgentEvents`로 알린다. 예외를 던지지 않고 `done`이나 `error`로 끝낸다
  - 형식에 맞지 않는 답은 어디가 틀렸는지 적어 도구 없이 한 번만 다시 요청한다. 그래도 틀리면 아무것도 저장하지 않고 실패로 끝낸다. 실패의 이유는 실행 기록과 로그에만 남고 화면에는 정해진 문장만 나간다
  - `BREAK_DOWN_TASKS`의 카드에는 서버가 고른 제출물의 id를 채운다. 모델이 빠뜨리거나 다른 값을 적어도 바뀌지 않는다
  - 설정: `app.agent.run-time-limit`(120초), `runs-per-hour`(30), `brief-max-length`(20000), `question-max-length`(1000)

  - Gemini 클라이언트를 Spring AI 대신 우리가 만든다(`agent/model/GoogleGenAiClientConfig`). 공급자가 `google-genai`일 때만 쓰인다. Spring AI가 설정을 바꾸는 방법으로 주는 것은 공급자마다 다르다. OpenAI나 Anthropic처럼 Spring의 HTTP 클라이언트를 쓰는 공급자는 `RestClientCustomizer`나 `spring.http.client.*`로, Bedrock은 `spring.ai.bedrock.aws.*`의 설정 키로 시간 제한을 준다. Gemini는 Google의 SDK를 그대로 쓰고, 이 공급자에는 그런 설정 키도 커스터마이저도 없다(자동 설정의 코드와 2.0.1 문서에서 확인). 자동 설정이 클라이언트 빈을 "없을 때만" 만들게 돼 있어, `@Configuration`에서 빈을 직접 내놓는 것이 이 공급자의 정해진 확장 방법이다. 우리 것은 API 키 방식만 다룬다
  - **`enable-cached-content`를 끈 이유**: Spring AI는 이 기능의 조건을 따지면서 모델 빈을 설정이 읽히기도 전에 만든다. 우리 클라이언트가 `AgentProperties`를 받게 되자 그 객체가 값이 빈 채로 굳어 서버가 뜨지 않았다. 쓰지 않는 기능이라 꺼서 모델 빈이 제때 만들어지게 했다. 이 문제는 실제 모델 테스트(키가 있을 때만 도는)에서만 드러났다. 그래서 가짜 키로 Gemini를 골라 띄워 보는 `GeminiWiringTest`를 더했고, 이 설정을 다시 켜면 이 테스트가 실패하는 것을 확인했다
  - 모델을 부를 때마다 모델 이름, 걸린 시간, 입출력 토큰 수를 한 줄 남긴다(`SpringAiAgentModel`). 실행 한 번은 입력 3천 토큰, 출력 4백~7백 토큰쯤이다. 서버가 뜰 때 어떤 모델 구현을 쓰는지도 한 줄 남긴다
  - 확인: 우리가 띄운 가짜 서버로 응답 없는 요청이 시간 제한에서 끝나는 것, 503은 정한 횟수만큼만 다시 보내는 것, 429는 다시 보내지 않는 것(`GoogleGenAiClientConfigTest`). 도구 호출 상한(`AgentToolboxTest`). 설정은 실제 `application.yml`을 읽어 확인한다(`AgentPropertiesTest`, 빠진 키가 있으면 실패). 실제 Gemini로 세 건이 새 기본 모델과 우리 클라이언트로 통과

  - 하지 않은 것: 한도 초과를 다른 실패와 구분해 알리는 것(지금은 같은 문장), 답을 JSON으로만 받게 하는 모델 설정(형식이 틀리면 다시 요청하는 것으로 충분했다), compose로 Bedrock의 지역과 모델을 넘기는 것(배포 환경이 정해지면)
