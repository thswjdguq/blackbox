## 배경

`fbbb3cb`에서 업무·제출물 쓰기는 `requireContributor`로 바뀌어 관찰자가 차단됐다. 그러나 다른 기능은 여전히 `requireMember`라서 **관찰자가 파일 업로드·회의 수정·노션 동기화를 할 수 있다.** DEVELOPMENT.md 4번("관찰자는 읽기만 가능하다")과 절반만 일치하는 상태다.

또한 `DataIntegrityViolationException` 핸들러가 모든 무결성 위반을 409로 바꾸면서 "연결된 데이터가 변경되었습니다. 새로고침 후 **연결 관계를** 확인해주세요"라는 제출물 전용 문구를 쓴다. 제출물과 무관한 위반(멤버 중복, NOT NULL 등)에도 같은 안내가 나가고, 로그를 남기지 않아 원인을 찾을 수 없다.

마지막으로 형식이 틀린 경로 값, 깨진 JSON, 빠진 파라미터나 파일, 지원하지 않는 메서드와 Content-Type이 모두 **500**으로 나간다. `b02057a`(예외 처리 통일)에서 넣은, 모든 예외를 받는 핸들러가 Spring의 기본 4xx 처리를 먼저 가로채기 때문이다. K-13 검토 답변과 K-14 계약에서 이 문제를 A-02에서 확인하기로 했다.

## 범위

1. `FileVaultService`의 **쓰기 기능**(업로드)을 `requireContributor`로 바꾼다. 다운로드·목록·이력 조회는 `requireMember`를 유지한다. 파일 금고에는 삭제 기능이 없다.
2. 무결성 오류 문구를 어떤 충돌에도 맞는 문구로 바꾼다(예: "요청한 변경이 다른 데이터와 충돌합니다. 새로고침 후 다시 시도해주세요"). `log.warn`으로 예외를 남기되 **SQL 원문·내부 메시지는 응답에 넣지 않는다.**
3. `ResponseStatusException`이 5xx일 때 `reason`을 응답에 넣지 않는다. 4xx는 그대로 둔다.
4. 관찰자 차단이 적용되지 않은 나머지 기능 목록을 PR 설명에 후속 작업으로 남긴다. 담당과 경로를 적어 B가 자기 Task로 가져갈 수 있게 한다.
5. `GlobalExceptionHandler`가 `ResponseEntityExceptionHandler`를 상속해 표준 MVC 오류를 올바른 4xx로 응답하게 한다. 사용자가 볼 수 있는 문구는 `messages.properties`에 한국어로 두고, 화면이 읽는 검증 실패의 `errors` 필드는 그대로 유지한다.
