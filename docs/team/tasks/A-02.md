# A-02 · 관찰자 쓰기 차단 일관성과 무결성 오류 처리

- 담당: 송승준 / 검토: 손정협
- 상태: READY
- 기능: M5 (권한 검증)
- 기준 SHA: `fbbb3cb` (+ A-01 병합 후 최신 main)
- 예상: 3시간
- 계약: 변경 없음. 외부 API 경로·응답 형식은 그대로 두고 권한 판정과 오류 문구만 바꾼다.

## 배경

`fbbb3cb`에서 업무·제출물 쓰기는 `requireContributor`로 바뀌어 관찰자가 차단됐다.
그러나 다른 도메인은 여전히 `requireMember`라서 **관찰자가 파일 업로드·회의 수정·노션 동기화를 할 수 있다.**
DEVELOPMENT.md 4번("관찰자는 읽기만 가능하다")과 절반만 일치하는 상태다.

또한 `DataIntegrityViolationException` 핸들러가 모든 무결성 위반을 409로 바꾸면서
"연결된 데이터가 변경되었습니다. 새로고침 후 **연결 관계를** 확인해주세요"라는 제출물 전용 문구를 쓴다.
제출물과 무관한 위반(멤버 중복, NOT NULL 등)에도 같은 안내가 나가고, 로그를 남기지 않아 원인 추적이 안 된다.

## 금지 파일

`TaskService`·`MeetingService`·`Score*`·`Notion*`(B 소유), `frontend/**`(C 소유), migration, 빌드 설정.
**회의·노션 쪽 관찰자 차단은 B 소유라 이 Task에서 건드리지 않는다.** 필요한 변경은 이 PR 설명의 후속 작업 항목으로 적어 B에게 넘긴다.

## 범위

1. `FileVaultService`의 업로드·삭제 등 **쓰기 경로**를 `requireContributor`로 바꾼다. 조회는 `requireMember` 유지.
2. 무결성 오류 문구를 중립화한다(예: "요청한 변경이 다른 데이터와 충돌합니다. 새로고침 후 다시 시도해주세요").
   `log.warn`으로 예외를 남기되 **SQL 원문·내부 메시지는 응답에 넣지 않는다**(기존 테스트가 이를 검증한다).
3. `ResponseStatusException` 핸들러가 5xx의 `reason`을 그대로 노출하지 않도록 한다. 4xx는 현행 유지.
4. 관찰자 차단이 적용되지 않은 나머지 경로 목록을 PR 설명에 후속 작업으로 남긴다. 담당과 경로를 명시해 B가 자기 Task로 가져갈 수 있게 한다.
