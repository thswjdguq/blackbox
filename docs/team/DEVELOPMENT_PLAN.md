# 3인 개발 일정 및 업무 분배

작성일: 2026-09-21 · 계획 기간: 2026-09-21~2026-11-29 (10주) · 송승준(A), 손정협(B), 손정효(C).

## 1. 공동 목표와 범위

2~4인 대학생 팀이 전공과 관계없이 `제출물 등록 → 요구사항 → 업무 분담 → 초안 검토 → 수정·재검토 → 최종본 확정 → 실제 제출 기록`을 끝까지 수행한다. 기여도·AI·외부 연동은 이 흐름을 보조한다.

### 우선순위

| 구분 | 범위 | 완료 판단 |
| --- | --- | --- |
| 필수 M1 | 기존 제출물·요구사항·업무 연결 완성, 진척 조회 | 새로고침 후 보존, 타 프로젝트 접근 거절 |

M1~M6 등은 참고 문서와 연결하기 위한 기능 ID다. 구현 Task는 `A-00`, `B-10`, `C-20`처럼 별도로 발급한다. 최종본 PDF/ZIP의 제출물별 확장은 M3 이후 추가 작업으로 분리하고, 미구현이면 기존 프로젝트 단위 기능으로 명시한다.

## 2. 현재 출발점

09/21 로컬 확인: V19, DeliverableController/Service/DTO, 제출물 화면, 업무 연결 필드와 테스트 파일이 이미 존재한다. 모두 GitHub에 반영되었는지는 확인되지 않았다. 09/15 기록에는 타입 검사·빌드·관련 17개 단위 테스트 통과가 있으며, 실제 DB·브라우저 통합 검증은 미완료다. 오늘 재실행한 결과로 오해하지 않는다.

**첫 일정은 재개발이 아니라 기존 코드의 공유·검증이다.** 파일 소유권도 A-00 기준선 공유 후 적용한다. 현재 Java 코드는 `service/`, `entity/`, `repository/` 식의 계층형 구조이므로 존재하지 않는 `deliverable/` 패키지를 전제로 일을 나누지 않는다.

## 3. 10주 마감과 시간 운영

사용자 목표: **10주 안에 구현·통합·검증을 마치고 실제 시연 가능 상태로 완성한다.** 기존 시작일 2026-09-21을 유지한다. 12월 과목 발표·포트폴리오는 개발 기간에 포함하지 않는다.

- 8주차 말 **11/15 기능 동결**, 9주차 말 **11/22 릴리스 후보**, 10주차 말 **11/29 최종 시연 검수 완료**.
- 시간 가정: 화~일 개인 2시간, 월요일 공동 2시간. 이론 개발량 10×3×12=360인시. 월요일 60인시는 회의·검수로 별도다.
- 참고안의 단축 주 가정에 따른 차감: 1주차 18, 3주차 6, 5주차 18인시. 추가 시험·일정 불확실성 30인시를 확보하면 계획 용량은 288인시다. 학교 일정은 확인 전 가정이다.
- 1~8주차 216인시: 핵심 구현·지속 검증 168 + 모바일·AI 최소 범위 24 + 미배정 버퍼 24. 9~10주차 72인시는 통합·결함 수정·시연에 전용한다.
- 위 숫자는 확정 견적이 아닌 예산 상한이다. 2주차 실측으로 재산정하고 개인별 주 12시간을 넘겨 배정하지 않는다. 실제 가용 시간이 줄면 범위를 줄인다.
- 테스트·문서·PR 리뷰는 위 용량에 포함한다. Task는 2~6시간, 개인 진행 중 작업은 1개를 기본으로 한다.
- 6주차 핵심 게이트 미통과 시 신규 확장을 중단한다. 모바일·AI는 최소 범위를 정하고 일정 초과 시 범위 변경을 기록한다. 후반 검증 시간을 신규 기능에 사용하지 않는다.

### 최종 완료 체크리스트

- [ ] 검수한 커밋/태그와 안내로 다른 팀원 컴퓨터에서 기동한다.
- [ ] 실제 DB에 제출물·요구사항·업무를 저장하고 새로고침 후 재조회한다.
- [ ] 초안→검토→피드백 업무→수정본→재검토 버전 기록이 유지된다.
- [ ] 최종 확정→제출 기록까지 이어지고 확정 후 잘못된 수정이 차단된다.
- [ ] 비회원·관찰자 쓰기·타 프로젝트 ID·중복 요청을 검증한다.
- [ ] 선정한 모바일·AI 범위를 검수하며 AI 장애로 기본 PMS가 멈추지 않는다.
- [ ] 실제 API로 전체 시나리오를 두 번 연속 완주하고 시연 데이터 복구를 연습한다.
- [ ] 핵심 흐름 중단·데이터 손실·권한 침해 결함이 0건이다. 기타 결함은 영향·우회 방법을 기록한다.
- [ ] 시연 담당·순서·데이터·실행 안내·녹화본을 준비한다. 녹화본이 실제 검증을 대체하지 않는다.

11/30 이후는 과목 제출 자료·개인 포트폴리오 정리 기간이다. 필수 기능의 개발 완료를 이 기간으로 넘기지 않는다.

## 5. 첫 작업의 인수인계

| Task | 담당·검토 | 산출물·완료 기준 | 의존성·대기 중 대체 |
| --- | --- | --- | --- |
| A-00 | A / B 검토 | 기존 변경을 명시적 경로로 검토·커밋 후보 분리, 기준 SHA·기동 절차·V19 적용 결과 | 먼저 시작. 실패 원인과 미검증 항목을 기록 |
| A-01 | A / B 검토 | PR 대상 CI 추가, 깨끗한 DB와 기존 DB 업그레이드 검증, 보호 설정 확인 | A-00 후. CI 설계는 미리 가능 |
| B-00 | B / A 검토 | 기존 업무 연결 테스트 목록, 권한·null·0건 예시, B-10 계약 PR | 공유 코드 전에는 문서·데이터 설계 |
| C-00 | C / B 검토 | 빈 상태·오류·다음 행동 점검표, C-10 화면 작업서 | 공유 코드 전에는 화면 명세 |
| B-10 | B / A 검토 | 진척 API·경계 테스트·계약 예시 | M1 기준선. 리뷰 모듈 완료를 기다리지 않음 |
| A-10 | A / B 검토 | Review·ReviewComment 공동 데이터 계약 및 A/B 생성 파일 목록 | B·C가 각각 저장소 mock·화면 mock 작업 시작 가능 |
| C-10 | C / B 검토 | 제출물→업무 실제 연결 검수, 팀원 관리 화면 | 기존 API 사용. 서버 변경 요청은 계약 PR로 분리 |

A-00/A-01은 팀장에게 모든 구현을 몰아주는 업무가 아니다. B는 테스트 입력과 회귀 결과, C는 실제 화면 검수 결과를 제공한다. A는 그것을 다시 작성하지 않고 공통 기준선과 환경만 통합한다.

## 6. 지연·완료 기준

- 30분 이상 외부 의존성으로 막히면 Issue에 필요한 계약/파일/응답과 대체 작업을 적는다. 상대는 다음 작업 시간, 목표 24시간 이내에 응답한다. 응답이 없다고 허락으로 간주하지 않는다.
- 1일 대기: mock·단위 테스트·자기 문서로 진행. 2일 대기: 범위 축소 또는 소유권 임시 이전을 Issue에 명시하고 양측 확인 후 작업.
- 예상 시간이 주간 용량을 넘으면 ‘필수 오류 수정 → 핵심 흐름 → 모바일·AI → 기타 확장’ 순서로 남긴다. 테스트와 데이터 보호는 절단하지 않는다.
- G1~G6은 캘린더가 아니라 완료 조건이다. 미통과 상태에서 다음 도메인 전체를 완료 처리하지 않는다. 독립 작업은 계속 가능하다.
- 기능 완료 = 담당 PR 병합 + 필요한 의존 PR 병합 + 실제 API/DB 검수 + 문서 갱신. ‘내 컴퓨터에서 코드 작성’, ‘mock 시연’, ‘단위 테스트 통과’는 각각 별도 상태다.
- 주간 진행률은 이번에 확정한 Task 완료 수/전체 Task 수와 게이트 상태로 보고한다. PR 개수·코드 줄 수를 기여도나 제품 완성도로 사용하지 않는다.
