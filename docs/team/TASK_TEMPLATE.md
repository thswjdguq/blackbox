# 작업지시·인수인계 양식

이 파일을 복사해서 `docs/team/tasks/<Task-ID>.md`로 저장한다. 서로 다른 AI에도 같은 작업서를 전달한다. 빈 소유권·계약·완료 기준을 AI가 임의로 채워 구현하지 않도록 한다.

## 1. 작업서

```markdown
# B-21 · 피드백을 업무로 전환
상태: READY / IN_PROGRESS / BLOCKED / IN_REVIEW / MERGED / VERIFIED 중 하나
기능 ID: M2
작성자: 손정협
검토자: 송승준
기준 브랜치/SHA: main / 실제 SHA 입력
예상 시간: 구현 3h + 검사/문서 2h + 리뷰 대응 1h
계약: K-12 v1, AGREED PR 링크
의존성: 필요한 선행 PR과 병합 여부

## 목표
사용자가 피드백에서 업무를 생성하고 해당 업무로 이동한다.

## 수정 허용 파일
- 실제 경로와 허용 메서드/영역을 적는다.
- 새 파일은 예정 경로를 적는다.

## 수정 금지
- A 소유 ReviewService·migration·공통 권한 설정
- frontend 전체
- 관계없는 리팩토링·포맷팅·의존성 교체

## 입력·출력·권한
계약 링크와 중요한 예시를 적는다. 추측으로 새 URL을 만들지 않는다.

## 완료 조건
- 한 피드백의 재요청에도 업무가 중복 생성되지 않는다.
- 타 프로젝트·관찰자·확정 후 수정 요청을 거절한다.
- 생성 업무에 제출물·피드백 연결이 유지된다.
- 실패 시 일부 데이터만 저장되지 않는다.

## 검사
- 실제 테스트 클래스/명령과 수동 시나리오를 적는다.
- 테스트 데이터·필요 환경·미검증 범위를 적는다.

## 병합 순서 및 독립 작업
- 선행 PR 대기 중 할 수 있는 mock/단위 테스트를 적는다.
- 선행 PR 없이는 노출하면 안 되는 경로를 적는다.

## 결과
- 변경 파일:
- 수행 검사·결과:
- 미수행 검사·이유:
- 계약 변경: 없음 / 별도 PR
- PR·커밋:
- 남은 위험과 다음 Task:
```

예시의 B-21은 실제 작업 배정 시 허용 파일·SHA·계약을 채워야 READY다. 계약이 DRAFT면 구현 전체 대신 계약·테스트 설계만 먼저 수행한다.

## 2. 각자 AI에 붙여 넣을 시작 프롬프트

```text
Team Blackbox 저장소에서 아래 Task 하나만 진행해줘.
나는 [송승준/손정협/손정효]이고 작업 ID는 [ID], 기준 커밋은 [SHA]야.
먼저 AGENTS.md, DEVELOPMENT.md, docs/team/README.md,
OWNERSHIP.md, WORKFLOW.md, 해당 Task와 계약 파일을 읽어줘.
현재 git 상태와 파일 존재 여부를 확인하고 다른 사람의 변경은 보존해줘.

허용된 파일 안에서만 구현하고 서버/화면 계약을 임의로 바꾸지 마.
현재 코드에 있는 기능은 다시 만들지 말고 필요한 차이만 수정해줘.
타인 파일이나 계약 변경이 필요하면 필요한 변경을 기록하고,
독립적으로 할 수 있는 테스트·mock·문서 작업은 계속해줘.
실제로 실행한 검사와 실행하지 못한 검사를 구분해서 보고해줘.
자동으로 원격 push·merge·배포하지 말고 검토 가능한 diff와 PR 설명을 준비해줘.
별도로 원격 작업을 요청하면 그때 지정 범위에서 수행해줘.

작업서: [docs/team/tasks/ID.md 또는 전체 내용]
계약: [docs/team/contracts/K-XX.md]
```

## 5. 상태 사용법

- READY: 소유 범위·계약·완료 조건이 합의됨.
- IN_PROGRESS: 자기 영역 구현 중.
- BLOCKED: 외부 입력이 필요함. 대체 작업을 함께 기록.
- IN_REVIEW: PR과 검사 근거 제출.
- MERGED: main에 합쳐졌으나 실제 연동 검증이 남을 수 있음.
- VERIFIED: 필요한 의존 변경까지 합쳐 실제 시나리오 확인.

개인 업무 완료와 제품 기능 완료를 구분한다. 예를 들어 C의 mock 화면 PR이 MERGED여도 M2 전체는 서버와 함께 VERIFIED 되기 전까지 미완료다.
