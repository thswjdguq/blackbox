# API·도메인 계약 기준

여기서 ‘계약’은 서버와 화면이 공유하는 URL·데이터·권한·오류·상태 전환의 약속이다. 현재 구현과 향후 설계를 구별한다. 향후 항목은 기능 구현이 완료되었다는 뜻이 아니다.

## 1. 현재 구현을 유지할 항목

09/21 로컬 DTO 및 코드 확인 기준이다. 원격 반영 여부·DB 통합 결과는 A-00에서 확인한다.

| 항목 | 현재 약속 |
| --- | --- |
| 기본 경로 | `/api/projects/{projectId}/deliverables` |
| 제출물 목록·생성 | GET/POST 기본 경로 |
| 수정·삭제 | PUT/DELETE `/{deliverableId}` |
| 요구사항 생성 | POST `/{deliverableId}/requirements` |
| 요구사항 수정·삭제 | PUT/DELETE `/{deliverableId}/requirements/{requirementId}` |
| 제출물 필드 | `id, projectId, title, description, dueDate, submissionMethod, ownerId, ownerName, requirements` |
| 필수 생성값 | `title`, `dueDate` |
| 요구사항 필드 | `id, content, required` |
| 업무 연결 | `deliverableId`, `requirementId`, `completionCriteria` |
| 업무 수정 해제 | `clearDeliverable`, `clearRequirement`; 생략은 유지 |
| 날짜 | `dueDate`는 `YYYY-MM-DD`. 참고안의 `due_at`으로 임의 변경 금지 |
| 권한 | 팀장/팀원 쓰기, 관찰자 읽기. 모든 경로에 프로젝트 범위 검증 |
| 삭제 충돌 | 업무가 연결된 제출물/요구사항은 409 |
| 오류 | 기존 ProblemDetail 형태. `detail` 또는 검증 `errors`를 화면에 표시 |

프론트 API 인스턴스는 `/api` 기반 경로 처리를 이미 갖고 있으므로 새 래퍼에서 `/api/api`가 되지 않게 현재 설정을 확인한다. 인증 방식은 현재 구현을 사용하며 AI가 임의로 바꾸지 않는다.

## 2. 새 기능의 계약 분리

아래 URL은 계획안이다. 최종 필드·상태 코드는 해당 계약 파일을 리뷰해 확정한 뒤 구현한다.

| 계약 ID / 작성자 | 예정 경로·책임 | 소비자 |
| --- | --- | --- |
| K-10 / A | `/deliverables/{id}/reviews` 회차·파일 버전·검토 상태 | B 피드백, C 검토 탭 |
| K-11 / B | `/deliverables/{id}/reviews/{reviewId}/comments` 피드백·반영 확인 | A 최종 확인, C 검토 탭 |
| K-12 / B | `.../comments/{commentId}/task` 피드백→업무 | C 업무 이동 |
| K-13 / B | `/deliverables/{id}/progress` 읽기 전용 진척 | C 홈·제출물 화면, A 확정 안내 |
| K-14 / A | `/deliverables/{id}/requirements/{requirementId}/assessment` 요구사항 충족 확인·해제 | B 진척(K-13 `met`), C 제출물 화면 |
| K-20 / A | `/deliverables/{id}/confirmation`, `/submission` 확정·제출 기록 | B 수정 차단, C 최종 제출 탭 |
| K-30 / A+B | AI 호출 인터페이스(A) / PM 브리핑 API(B) | C AI 화면 |

외부 HTTP 경로에는 위 공통 `/api/projects/{projectId}`를 붙인다. A의 기존 `DeliverableDtos`에 B 응답을 계속 추가하는 대신 B의 별도 조회 DTO를 쓴다. 프론트는 도메인별 호출 래퍼를 구성하고 페이지에서 URL·응답 변환을 중복 작성하지 않는다.

## 3. 공통 의미 — 세 모델이 다르게 구현하지 않도록

1. **업무 DONE ≠ 요구사항 충족 ≠ 최종 제출 완료.** 업무가 끝나면 ‘검토 가능’ 상태를 계산할 수 있지만 사람이 충족/반영 여부를 확인한다. AI도 자동 승인하지 않는다.
2. 진척은 `(완료 업무 수 / 연결 업무 수)`와 `(충족한 필수 요구사항 수 / 필수 요구사항 수)`를 따로 표시한다. 분모 0이면 수치 0과 `total: 0`을 반환하고 화면에는 ‘항목 없음’으로 표시한다. 빈 목록을 100% 완료로 표시하지 않는다.
3. 검토 회차는 검토 당시 특정 파일 버전 ID를 가리킨다. 이후 최신 파일이 바뀌어도 회차의 대상을 갈아끼우지 않는다. 전체 해시는 저장·검증용, 짧은 해시는 화면 표시용이다.
4. 중간 검토의 파일 생략 허용 여부는 K-10에서 명시한다. 파일이 없다면 화면에 ‘파일 없음’. 최종본 확정에는 같은 프로젝트의 실제 파일 버전이 필요하다.
5. 피드백→업무 전환은 중복 클릭/재시도에도 하나의 업무만 연결되도록 설계한다. 트랜잭션과 고유 제약/잠금 전략, 중복 시 기존 업무 반환 또는 409 중 하나를 K-12에 고정한다.
6. 업무 DONE 후 피드백은 ‘반영 확인 대기’가 된다. 검토자가 반영 확인하고 재오픈 가능 여부를 계약에 적는다. 자동 해결로 표시하지 않는다.
7. 제안 상태는 `DRAFT → IN_REVIEW → CONFIRMED → SUBMITTED`. `IN_REVIEW → DRAFT` 보완 전환은 허용하며 이전 회차 기록을 유지한다. 구체적 전환 명령·권한은 K-10/K-20에 작성한다. 기존 1단계에는 이 상태 필드가 없다.
8. 최종 확정은 팀장 명시 동작으로 계획한다. 필수 요구사항, 최종 검토 결과, 미해결 피드백, 최종 파일을 서버에서 재검증한다. `CONFIRMED`부터 파일·요구사항·연결 업무·코멘트 수정 차단 범위를 A/B가 함께 정의한다. 진척 조회 결과만 믿고 확정하지 않는다.
9. 강제 확정/재개는 초기 범위 밖으로 두고 별도 계약 없이는 우회 버튼을 만들지 않는다. 필요하면 권한·사유·감사 기록·기존 확정본 보존을 포함해 변경한다.
10. `SUBMITTED`는 사용자가 학교 시스템 등에 제출한 후 남기는 기록이다. eClass 자동 업로드나 실제 접수 확인 기능으로 표현하지 않는다. 채널·시각·기록자·증빙은 K-20에서 고정한다.
11. 최종 확정·중복 제출·검토 회차 증가의 동시 요청은 서버에서 잠금/버전/고유 제약으로 검증한다. 버튼 비활성화만으로 처리하지 않는다.
12. 도메인 간 무한 서비스 참조를 만들지 않는다. 권한·읽기 전용 조회 인터페이스는 별도로 두고, 트랜잭션 책임은 명령 서비스 한 곳에 둔다. B가 A 파일을 수정해야 할 때는 최소 읽기 API 요청 PR로 분리한다.

위 1·6·9는 참고안의 자동 충족/자동 반영/강제 확정과 다른 이번 계획의 결정이다. 팀이 다른 정책을 선택하면 양쪽 구현을 따로 바꾸지 말고 계약 변경부터 한다.

## 4. 계약 PR에 들어갈 내용

파일: `docs/team/contracts/K-XX-주제.md`. 상태는 `DRAFT → AGREED → IMPLEMENTED`.

```text
계약 ID / 버전 / 상태:
서버 생산자 / 소비자 / 리뷰한 PR:
요청 method·URL·인증·역할:
path/query/body 필드, 타입, 필수, null/생략/빈값 의미:
응답 성공 코드와 실제 JSON 예시:
실패 코드와 예시: 400 / 401 / 403 / 404 / 409 중 해당 항목
날짜: 날짜만인지, 시간대 포함 시각인지:
정렬·페이지 처리·빈 목록:
상태 전환 전제·중복 요청·동시 요청 처리:
트랜잭션 책임·다른 도메인 호출 서명:
DB 컬럼·제약·migration 예약 Task:
프론트 fixture 위치·실제 API 전환 기준:
기존 소비자 영향·하위호환·병합 순서:
완료 테스트와 미확정 항목:
```

fixture는 C가 `frontend`의 개발/테스트 영역에 관리한다. 계약 PR의 예제에서 복사한 뒤 서버 응답과 비교한다. mock 기본값이 운영 빌드에 남아 저장 성공처럼 보이지 않게 한다. 타입 자동 생성 도구는 아직 도입하지 않았으므로 도입 전까지 생산자·소비자 리뷰가 필수다.
