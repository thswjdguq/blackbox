## 1. 문제와 범위

세 사람이 서로 다른 AI로 작업할 때 과한 추상화·추측 구현·불필요한 정리가 검토 비용을 늘릴 수 있다. 코드 줄 수 자체보다 요구사항 충족·읽기 쉬움·유지보수·검증 가능한 동작을 기준으로 한다.

현행 WORKFLOW에는 최소 수정, 소유권, 검증, PR 분리 기준이 이미 있다. 새로운 지침 파일을 여러 개 만들지 않고 공통 규칙에 부족한 문장만 보완한다. 이 제안의 병합은 아래 규칙의 활성화나 린터 설치가 아니다.

## 2. 추가할 기준 초안

1. 작업 전에 현재 선언·호출·계약·성공 기준을 확인한다. 의사결정에 영향을 주는 가정은 기록하고, 경계가 불명확하면 담당자에게 확인한다. 이미 합의된 범위의 구현은 계속한다.
2. 요구사항을 충족하는 가장 단순한 구현을 선택한다. 예정되지 않은 기능·설정·추상화·범용 프레임워크를 추가하지 않는다. 단순성은 권한·트랜잭션·오류 처리·기록 보존을 생략하는 근거가 아니다.
3. 코드 정리는 요청 범위 안에서 한다. 별도 리팩토링·삭제는 기능 변경과 다른 Task/PR로 나눈다. 테스트 삭제로 검사를 통과시키지 않는다.
4. 삭제 전에 호출부, DI 자동 등록, JPA 매핑, 설정·스케줄러·reflection, API 소비자, 진행 중인 PR의 의존성을 확인하고 근거를 남긴다. 검색 결과가 없다는 이유만으로 삭제하지 않는다. 타인 담당 파일, 기존 마이그레이션, 실제 데이터·파일·볼륨은 임의 삭제하지 않는다.
5. 완료 보고는 실제 실행한 명령·종료 결과·검사 범위를 근거로 작성한다. 단위/mock, DB, 인증 HTTP, 브라우저 검증을 구별한다. 환경·선행 계약 때문에 실행하지 못한 검사는 사유와 다음 조치를 적는다.
6. 실패하면 원인을 해결하고 재검증한다. 무한 반복하거나 권한·테스트·CI를 약화해 통과시키지 않는다. 담당 경계나 환경 문제로 진행할 수 없으면 원인을 기록하고 독립 작업을 이어 간다.
7. 사용자 답변은 결과·주요 변경·실제 검사·남은 의존을 먼저 간결하게 쓴다. PR 설명과 보고서의 재현 근거, 주석의 권한·동시성·업무 규칙은 생략하지 않는다. 현행 주석 기준을 유지한다.
