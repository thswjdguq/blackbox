## 2. 왜 이 방향인가

- 엑스포 시연에서 지금 제품은 임팩트가 약하다. 제출물·요구사항·업무·검토는 기록하고 확인하는 도구라 눈에 띄는 장면이 적다.
- 학생 팀에는 프로젝트 매니저 역할을 맡는 사람이 따로 없다. 조장이 다른 일과 함께 떠맡거나 아무도 하지 않는다. 에이전트가 들어갈 자리가 여기다.
- 지금 제품은 기록하고 확인하는 부분은 갖췄지만, 먼저 살피고 알려 주고 다음 일을 제안하는 능동적인 부분은 사람에게 맡겨져 있다.
- 기업용 제품의 에이전트는 쌓인 기록에서 배운다. 우리 에이전트는 프로젝트 매니저의 지식을 가져와 빈 프로젝트를 채운다. 3장의 일곱 묶음이 그 지식이다.

## 3. 근거 요약

### 프로젝트 매니저가 하는 일 (상세는 부록 A)

여러 직무 자료와 표준에 공통으로 나오는 것은 일곱 가지다.

| 묶음 | 내용 | 팀 과제에서의 모습 |
| --- | --- | --- |
| 범위 | 요구사항과 목표를 정한다 | 과제가 요구하는 것을 빠짐없이 파악하고 무엇을 낼지 정한다 |
| 일정 | 마감을 맞추도록 계획하고 변경을 관리한다 | 마감에서 거꾸로 중간 목표를 잡고 늦어지는 일을 알아챈다 |
| 자원 | 필요한 사람을 파악하고 역할을 배정한다 | 누가 무엇을 맡을지 나누고 한 사람에게 몰리지 않게 한다 |
| 진행 추적·보고 | 마일스톤을 살피고 상태를 보고한다 | 진행 상황을 공유하고 교수에게 중간 보고를 한다 |
| 위험 | 문제를 미리 찾고 대응한다 | 무임승차, 연락 두절, 막판 몰아치기 |
| 품질 | 기준에 맞는지 확인하고 납품한다 | 요구사항을 충족했는지 확인하고 서로 검토한다 |
| 소통 | 회의를 잡고 진행하고 문서를 배포한다 | 회의를 잡고 정리한다 |

원가, 조달, 채용은 팀 과제에 거의 해당하지 않아 뺐다.

### 기존 제품의 AI 기능 (상세는 부록 B)

아홉 개 제품의 기능은 네 가지로 모인다.

1. 한 줄에서 계획으로: 목표나 모호한 요청을 업무 목록으로 풀어 준다
2. 상태 요약과 보고서: 흩어진 진행 상황을 읽을 글로 만든다
3. 위험 알림: 늦어질 조짐을 찾아 등급을 매기고 알린다
4. 부르지 않아도 움직임: 정해진 시간이나 조건에 스스로 실행한다

우리가 차별화할 자리는 두 곳이다. 기록이 없는 팀의 시작을 돕는 것, 그리고 "무엇을 내야 하고 그것이 요구를 충족했는가"라는 제출물 관점이다.

| 가져올 것 | 버릴 것 |
| --- | --- |
| 한 줄에서 계획으로. 입력은 과제 안내문으로 바꾸고 결과에 제출물과 요구사항을 넣는다 | 과거 패턴에 기대는 기능(자동 배정, 자동 분류). 기록이 없다 |
| 상태 요약과 단순한 위험 등급(낮음·중간·높음) | 담당자 자동 배정. 학생 팀에서는 민감해 근거만 보여 주고 사람이 정한다 |
| "검토 대기"로 돌아오는 결과 | 에이전트가 업무를 대신 수행하는 것. 수업 과제에서는 조사와 초안 보조까지만 한다 |
| 정해진 시간에 오는 주간 요약과 마감 임박 알림 | 여러 프로젝트를 한꺼번에 보는 분석 |

## 4. 에이전트가 맡을 일

개입 수준은 세 가지다.

- **자동**: 에이전트가 만들어 바로 보여 준다(읽을거리)

- **근거만**: 판단 재료만 보여 주고 결정은 사람이 한다

순위는 엑스포 기준이다. 1차는 꼭, 2차는 가능하면, 이후는 엑스포 뒤다.

### 1차 범위가 만드는 시연 장면

- **빈 프로젝트를 채우는 장면**: 안내문을 붙여 넣으면 제출물, 요구사항, 업무, 기한이 제안된다(계획 단계의 세 가지)
- **진행 중인 프로젝트를 살피는 장면**: 상태를 요약하고, 위험을 등급과 함께 짚고, 다음 할 일을 제안한다(진행 단계의 세 가지)

두 장면 모두 쌓인 기록 없이 동작한다. 첫 장면은 안내문만 있으면 되고, 둘째 장면은 시연용 데이터로 충분하다. 1차는 지금 서버에 있는 제출물·요구사항·업무·경보만으로 가능하다. 검토 단계의 항목은 피드백 구현(B-20)이 들어온 뒤에야 재료가 생겨 2차로 뒀다.

표의 "초안" 항목은 모두 같은 제안 카드를 쓴다. 열여덟 가지 중 아홉 가지가 그렇다. 제안 카드와 채택이 가장 중요한 부품이다.

## 5. 지켜야 할 원칙

### 제품 원칙

1. 승인, 충족 확인, 담당자 배정은 사람이 한다. 에이전트는 제안만 한다. `docs/team/CONTRACTS.md` 3장 1항과 `docs/team/DEVELOPMENT_PLAN.md`의 "자동 승인 금지"를 따른다
2. 기록에 없는 내용은 지어내지 않는다. 빈 곳은 "[작성 필요: 무엇]"처럼 표시해 사람이 채울 것을 알려 준다
3. AI가 만든 것은 표시하고 활동 기록에 남긴다. 수업에 따라 AI 사용에 제한이 있을 수 있고, 누가 무엇을 했는지 남기는 것이 이 제품의 주제다
4. AI가 만든 것은 기여도에 넣지 않는다. 버튼을 누른 사람이 그만큼 기여한 것으로 집계되면 안 된다
5. AI가 멈춰도 나머지 기능은 그대로 동작한다. 키가 없으면 버튼을 숨기고, 실패하면 안내만 띄운다
6. 에이전트는 요청한 사람의 권한으로만 조회한다. 관찰자가 볼 수 없는 것은 에이전트도 그 사람에게 보여 주지 않는다
7. 늦었는지와 쏠렸는지 같은 판정은 규칙으로 계산하고, 모델에는 설명만 맡긴다. 실행할 때마다 결과가 달라지지 않게 한다

### 설계 원칙

확장성을 두고 외부 변경이 코드에 직접 번지지 않게 한다. 하드코딩과 높은 결합도를 피한다. 이 원칙은 에이전트뿐 아니라 앞으로의 구현 전체에 적용한다.

1. 외부에 닿는 곳은 한 군데로 모은다. 모델을 부르는 코드는 Spring AI를 감싼 한 곳에만 둔다. 도구, 제안 카드, 단계 판단은 Spring AI의 타입을 모르고 우리 타입만 쓴다. Spring AI의 API가 바뀌어도 그 한 곳만 고치면 된다
2. 값은 코드 밖에 둔다. 공급자, 모델 이름, 응답 길이와 반복 횟수 상한은 설정에, 지시문은 리소스 파일에 둔다
3. 도구는 도메인의 읽기 인터페이스를 거친다. K-10의 회차 확인 인터페이스(`ReviewRoundReader`)와 같은 방식이다. 에이전트가 엔티티나 저장소에 직접 붙지 않는다. 업무나 피드백의 내부 구조가 바뀌어도 에이전트 쪽은 그대로다
4. 새 종류는 등록으로 더한다. 단계별 도움과 제안 카드의 종류는 "지시문, 쓸 수 있는 도구, 결과 형식"의 묶음으로 정의한다. 하나를 더할 때 기존 코드를 고치지 않는다
5. 화면은 K-30의 응답 형식만 안다. 어떤 모델을 쓰는지 모른다
6. 바뀔 일이 없는 내부 코드까지 추상화하지는 않는다. 경계는 외부에 닿는 곳에만 둔다

## 6. 설계

### 세 가지 동작

에이전트는 단계가 달라도 세 가지만 한다.

1. **살핀다**: 프로젝트가 지금 어느 단계이고 무엇이 막혀 있는지 진단한다
2. **알린다**: 진단을 사람이 읽을 요약이나 경고로 만든다
3. **제안한다**: 다음 행동을 초안으로 내놓고 사람의 승인을 기다린다

### 구성 요소

| 구성 요소 | 하는 일 |
| --- | --- |
| 읽기 도구 | 프로젝트 기록을 조회한다. 쓰기 도구는 두지 않는다 |
| 단계 판정 | 프로젝트가 어느 단계인지 규칙으로 계산한다 |
| 에이전트 실행기 | 모델과 도구를 반복 실행하고 진행 과정을 화면에 실시간으로 보낸다 |
| 제안 카드 | 제안을 저장하고 상태를 가진다. 모든 쓰기가 여기를 지난다 |
| 화면 | 어디서든 여는 도우미 창과 단계별 버튼 |
| 기록과 안전장치 | AI 표시, 활동 기록, 기여도 제외, 반복 횟수와 비용 상한, 실패 안내 |

### 단계 판정

프로젝트 홈의 "다음 할 일" 카드(#77, C, 병합 전)가 같은 판단을 화면에서 하고 있다. 그 순서를 서버의 기준으로 삼는다.

1. 제출물이 없다
2. 요구사항이 없다
3. 연결된 업무가 없다
4. 업무가 없는 필수 요구사항이 있다
5. 끝나지 않은 업무가 있다
6. 확인하지 않은 필수 요구사항이 있다
7. 모두 끝났다(검토를 요청할 준비)

검토 회차(K-10)와 확정(K-20)이 들어오면 그 뒤 단계를 잇는다. 화면과 서버가 같은 기준을 쓰도록 계약에서 한 곳으로 모은다.

### 제안 카드의 일생

1. 에이전트가 제안을 만든다. 종류는 제출물·요구사항 초안, 업무 초안, 문서 초안, 계획 변경 등이다
2. 서버가 저장한다. 상태는 "대기"다. 누가 요청했고 어떤 근거로 만들었는지 함께 남긴다
3. 사람이 내용을 고칠 수 있다
4. 사람이 채택하면 기존 API(제출물 생성, 업무 생성 등)가 그 사람의 권한으로 실제로 만든다. 상태는 "채택"이 되고 만들어진 것에 AI 표시가 남는다
5. 거절하면 "거절"로 남는다. 지우지 않는다

에이전트가 직접 쓰는 길은 없다. 피드백이나 파일 내용에 섞인 지시문에 모델이 속더라도 피해가 "틀린 제안"에서 멈추고, 그 제안은 사람이 본다.

### 들어가는 길

- **단계별 버튼**: 화면마다 그 단계에 맞는 버튼을 둔다. 예를 들어 요구사항이 없는 제출물에는 "과제 안내문으로 요구사항 만들기"
- **도우미 창**: 어디서든 열어 물을 수 있다

둘 다 같은 실행기를 부른다. 버튼은 목적이 정해진 요청을 대신 넣어 주는 것이다.

### 진행 표시

에이전트가 도구를 부를 때마다 화면에 한 줄씩 보여 준다("제출물 조회", "늦은 업무 확인"). 기다리는 동안 무엇을 하는지 보이고, 답이 어떤 기록에서 나왔는지 알 수 있다. 답의 항목은 해당 화면으로 가는 링크를 붙인다.

### 능동성

- 1차: 사람이 부를 때만 동작한다
- 2차: 정해진 시간에 스스로 살펴 주간 요약과 마감 임박 알림을 보낸다. "먼저 챙긴다"는 인상은 여기서 나온다

### 평가

모델의 응답은 매번 달라지므로 눈으로 보고 판단하지 않는다. 시연용 프로젝트를 고정해 두고, 정답이 정해진 질문 세트로 확인한다.

- 답에 나온 숫자가 DB와 일치하는가
- 기록에 없는 것을 지어내지 않았는가
- 제안이 형식에 맞고 채택하면 실제로 만들어지는가
- 권한 밖의 것을 보여 주지 않는가

같은 질문 세트를 Gemini와 Bedrock의 Sonnet 양쪽에서 돌린다.

### 시연 대비

엑스포 현장의 네트워크와 외부 API에 기대게 된다. 시연용 데이터를 고정하고, 실패할 때 보여 줄 녹화본을 준비한다. 녹화본이 실제 검증을 대체하지는 않는다(`docs/team/DEVELOPMENT_PLAN.md` 최종 완료 체크리스트).

## 7. 기술 방향

### 공급자와 구현 방식

- 로컬 개발: Gemini
- AWS 배포: Bedrock의 Sonnet. 비용은 학교 지원
- 구현: Spring AI. 공급자 교체가 의존성과 설정 변경으로 끝나게 한다

### Spring AI 버전과 Spring Boot (2026-10-08 확인)

**지금의 Spring Boot 3.3.5로는 Spring AI를 쓸 수 없다.** 어느 계열을 쓰든 Boot를 먼저 올려야 한다.

| Spring AI 계열 | 확인한 버전 | 지원하는 Spring Boot |
| --- | --- | --- |
| 2.0.x (현재 안정판) | 2.0.1 | 4.0.x, 4.1.x |
| 1.1.x | 1.1.8 | 문서는 3.4.x와 3.5.x, 저장소 안내는 3.5.x |
| 1.0.x | 1.0.9 | 3.4.x, 3.5.x |

Spring Boot 쪽의 지원 상태는 다음과 같다. 3.5는 무료 지원이 2026년 6월에 끝났고 마지막 버전은 3.5.16이다. 4.0은 2026년 12월까지, 4.1은 2027년 7월까지 무료 지원된다. 지금 쓰는 3.3은 이미 지원이 끝난 버전이다.

올리는 길은 둘이다.

| 길 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| 가 | Boot 3.5.x + Spring AI 1.1.x | 같은 3 계열 안의 이동이라 기존 코드에 미치는 영향이 작다 | Boot 3.5의 무료 지원이 끝났고 Spring AI도 이전 계열이다 |
| 나 | Boot 4.x + Spring AI 2.0.x | 지금 유지되는 조합이다 | 주 버전이 바뀐다. 보안, DB 연동 등 기존 기능 전체에 영향이 갈 수 있어 확인할 범위가 크다 |

A의 권고는 **가**다. 이 프로젝트는 11월 말에 끝나고, 남은 기간에 주 버전을 올리는 위험을 질 이유가 적다. 5장 설계 원칙대로 모델 호출을 한 곳에 모아 두면 나중에 2.0.x로 옮길 때 고칠 곳도 그 한 곳이다. 어느 길이든 정하는 것은 11장의 "정할 것"이다.

Boot를 올리는 일은 에이전트 구현과 섞지 않고 별도 PR로 먼저 한다. 올린 뒤에는 자동 테스트, DB 검증 스크립트(`scripts/verify-db.sh`), 화면 확인으로 기존 기능을 다시 본다. 3.5의 변경 중 우리와 닿는 것으로, 내장 서버가 파일 업로드 요청의 조각 수와 머리말 크기에 제한을 두기 시작했다. 파일 금고의 업로드를 따로 확인해야 한다.

### 공급자별 모듈 (2026-10-08 확인)

| 공급자 | 의존성 | 주요 설정 | 도구 호출 | 실시간 전송 |
| --- | --- | --- | --- | --- |
| Gemini (API 키) | `spring-ai-starter-model-google-genai` | `spring.ai.google.genai.api-key` | 지원 | 지원 |
| Bedrock | `spring-ai-starter-model-bedrock-converse` | `spring.ai.bedrock.aws.region`, 모델 이름 | 지원 | 지원 |

- 두 모듈 모두 1.1.x와 2.0.x 문서에 있다. 도구는 메서드에 표시를 붙여 정의하고 ChatClient에 넘기는 방식이 같다
- 모델 이름을 넣는 설정 키가 계열마다 다르다. Bedrock은 1.1.x에서 `spring.ai.bedrock.converse.chat.options.model`, 2.0.x에서 `spring.ai.bedrock.converse.chat.model`이다. 설정 키를 코드에 흩어 두지 않아야 하는 이유다
- Bedrock의 모델 이름은 Anthropic API의 이름과 형식이 다르다. 문서의 예는 `us.anthropic.claude-haiku-4-5-20251001-v1:0`처럼 지역 접두어와 버전이 붙는다. 우리가 쓸 Sonnet의 정확한 이름은 계정과 리전에서 확인한다

### 공급자를 바꿀 때 새는 것

Spring AI가 호출 형식은 통일해 주지만 모델의 행동까지 같게 해 주지는 않는다.

- 같은 지시문에 대한 반응이 다르다. Gemini에서 잘 되던 도구 호출과 출력 형식이 Sonnet에서는 다르게 나올 수 있다. 6장의 질문 세트를 양쪽에서 돌려야 하는 이유다
- Bedrock 확인을 마지막으로 미루지 않는다. 뼈대가 서면 바로 Bedrock의 Sonnet으로 한 번 돌려 본다
- 공급자마다 다른 설정과 제약이 있다. 이런 차이는 모델을 감싼 한 곳에서 흡수한다

### Sonnet에 대해 알아 둘 것 (2026-10 기준, 구현 전에 다시 확인)

Anthropic의 API 문서 기준이다. Bedrock과 Spring AI를 거치면 달라질 수 있다.

- 현재 Sonnet은 Claude Sonnet 5.5(`claude-sonnet-5-5`)다. Bedrock에서 쓰는 정확한 모델 이름은 계정과 리전에서 확인한다
- 특정 도구를 강제로 부르게 하는 옵션을 받지 않는다. 도구 선택은 모델에 맡기고 지시문으로 유도한다
- 안전 분류기가 요청을 거절하는 경우가 있다. 응답이 정상 코드로 오면서 중단 사유가 거절로 표시된다. 화면에 안내하는 처리가 필요하다
- 생각 과정을 끄는 예전 설정을 받지 않는다(오류가 난다). 기본으로 켜져 있어 응답 시간과 비용에 반영된다
- Anthropic 직접 API의 가격은 입력 100만 토큰당 2달러, 출력 10달러다. Bedrock의 가격은 따로 정해진다

### 지금 있는 AI 코드와의 관계

- 회의록 요약과 할 일 추출이 이미 있다. `AiService`가 `LlmClient` 구현 중 키가 설정된 첫 번째를 쓴다. 순서는 `ClaudeService`, `OpenAiService`다. 둘 다 Spring AI가 아니라 HTTP를 직접 호출한다
- 설정은 `backend/src/main/resources/application.yml`의 `external.claude.*`, `external.openai.*`이고 키는 `CLAUDE_API_KEY`, `OPENAI_API_KEY`다. 모델은 `claude-sonnet-4-6`, `gpt-4o-mini`로 적혀 있다
- 호출하는 곳은 `MeetingController`(요약, 할 일 추출)와 `GoogleCalendarService`다
- 이번에는 이 코드를 건드리지 않는다. 에이전트가 자리 잡은 뒤 같은 경계로 옮길지 정한다. 옮기면 회의록 요약이 에이전트의 "소통" 단계로 들어온다

## 8. 지금 코드와 데이터

### 에이전트가 읽을 수 있는 기록

| 기록 | 들어 있는 것 |
| --- | --- |
| 프로젝트, 멤버 | 이름, 기간, 역할(팀장·팀원·관찰자), 동의 항목 |
| 제출물, 요구사항 | 제목, 설명, 기한, 제출 경로, 담당자, 요구사항 문구와 필수 여부, 충족 확인자와 시각 |
| 업무 | 제목, 설명, 완료 기준, 상태, 우선순위, 기한, 완료 시각, 담당자, 연결된 제출물과 요구사항 |
| 회의 | 제목, 날짜, 목적, 내용, 결정 사항, AI 요약, 출석 |
| 파일 금고 | 파일 이름, 버전, 해시, 올린 사람 |
| 검토 회차 | 회차, 대상 파일, 결정(#91에서 구현) |
| 피드백 | 내용, 해결 정보, 연결 업무(테이블은 #91의 V22, 기능은 B-20 예정) |
| 기여도, 경보 | 점수, 경보(무임승차·과부하·이탈·변조) |
| 활동 기록 | 출석, 회의 참석, 업무 생성, 업무 완료, 파일 등록, 파일 재업로드 여섯 가지뿐이다 |

### 없는 기록

- 계획: 중간 목표, 일정의 기준선
- 위험 목록과 대응 기록
- 계획 변경 이력
- 회고
- 과제 안내문. 지금은 제출물의 설명 칸뿐이다

없는 기록은 에이전트가 만든 제안을 저장하면서 생긴다. 예를 들어 채택된 계획 제안이 일정의 기준선이 된다.

### 이미 있는 것 중 쓸 수 있는 것

- 멤버의 동의 항목에 `consent_ai_analysis`가 이미 있다. 다만 지금은 저장하고 멤버 응답에 내보낼 뿐, 서버 어디에서도 이 값을 검사하지 않고 화면도 쓰지 않는다. 회의록 요약도 동의를 확인하지 않고 내용을 외부 모델로 보낸다. 에이전트에서 이 항목을 실제 동의로 쓸지 11장에서 정한다
- 백엔드는 Spring MVC로 동작하고, 외부 호출용으로 WebFlux 의존성도 들어 있다. 진행 과정을 실시간으로 보내는 방식은 구현할 때 정한다
- 권한 확인(`ProjectAccessChecker`)과 오류 응답 형식(ProblemDetail)은 기존 것을 그대로 쓴다

### 환경

### AI와의 관계

PMI 커뮤니티에서 쓰는 구분은 세 가지다.

- 자동화: 보고서 생성, 데이터 분석처럼 단순한 일
- 보조: 초안 작성, 위험 분석처럼 사람이 다듬고 검증해야 하는 일
- 증강: 전략적 판단처럼 사람이 주도하고 AI는 통찰을 보태는 일

실제 쓰임으로는 회의록 요약, 상태 보고 작성, 일정과 우선순위에 대한 제안, 병목과 위험의 조기 경고가 꼽힌다. 4장의 개입 수준(자동, 초안, 근거만)은 이 구분을 우리 제품에 맞게 옮긴 것이다.

## 부록 C. 이후 단계의 장면 상세

1차 범위는 아니지만 검토한 내용이라 남긴다.

### 문서 초안 작성

제출물 상세에서 시작해 세 단계로 진행한다.

1. 넣을 내용 제안: 요구사항과 기록을 읽고 목차를 제안한다. 항목마다 어떤 요구사항에 대응하는지, 쓸 자료가 얼마나 있는지 보여 준다. 사용자가 항목을 빼거나 더하고 메모를 붙인다
2. 진행 상황 요약: 끝난 일, 진행 중인 일, 늦어진 일, 담당자별로 한 일, 회의에서 정한 것, 남은 일과 위험을 정리한다. 보고서의 한 장으로도 들어간다
3. 초안 작성: 확정한 목차대로 장마다 쓴다. 문단마다 근거(어느 업무, 어느 회의)를 표시한다. 기록에 없는 부분은 빈칸으로 둔다

마지막에 "파일 금고에 올리고 검토 요청"을 누르면 초안이 1버전으로 올라가고 검토 회차가 열린다. 올린 사람은 자기 파일을 결정할 수 없으므로(K-10) 다른 팀원이 검토하게 된다. 이후 피드백을 반영한 수정본 초안까지 가면 초안 → 검토 → 수정이 에이전트와 한 바퀴 돈다.

단계가 고정이고 단계마다 사람이 확인하므로, 자유롭게 움직이는 에이전트보다 정해진 순서로 진행하는 편이 맞다. 결과물은 처음에는 화면에 표시하고 내려받는 정도로 충분하다. 한글·워드 서식까지 맞추는 것은 범위가 크다.

### 묻고 답하기

도우미 창에서 "금요일까지 중간보고서를 낼 수 있어?"처럼 물으면, 에이전트가 제출물·요구사항·피드백·회차를 조회해 근거와 함께 답하고 지금 할 일을 업무 초안으로 제안한다. 9장 순서 1의 뼈대가 서면 이 장면은 따로 만들지 않아도 나온다.
