## 1. 결론

**프로젝트는 만든 뒤 첫 점수 계산이 돌고 나면 삭제되지 않는다.** 점수 스케줄러가 앱 시작 직후와 이후 30분마다 모든 프로젝트의 모든 멤버에게 점수 행을 만들고, 그 행이 프로젝트 삭제를 막는다. 프로젝트를 만든 사람이 곧 멤버이므로 사실상 모든 프로젝트가 해당된다.

화면(대시보드)에는 삭제 버튼이 있고, 누르면 409와 "연결된 데이터가 변경되었습니다. 새로고침 후 연결 관계를 확인해주세요"가 나온다. 사용자가 이 안내를 보고 할 수 있는 일은 없다.

**정정:** A-01 인수인계, A-03 작업서, `verify-db.sh` 출력 문구, #46 PR 본문에 "V9 트리거가 업무를 만들 때 점수 행을 만든다"고 적었는데 틀렸다. V9에는 `updated_at` 갱신 트리거만 있다. 점수 행은 애플리케이션의 `ScoreService`가 만든다. 영향 범위도 "업무가 있는 프로젝트"가 아니라 "첫 점수 계산이 지난 모든 프로젝트"다.

## 2. 재현 (실제 API)

`main`(`fbbb3cb`) 코드를 검사용 DB에 띄우고 가입·로그인 후 요청을 보냈다.

| 순서 | 요청 | 결과 |
| --- | --- | --- |
| 1 | 프로젝트 생성 직후 `DELETE /api/projects/{id}` | **204**, 삭제됨 |
| 2 | 다른 프로젝트 생성 → `POST .../scores/recalculate`(스케줄러가 한 번 도는 것과 같음) → `DELETE` | **409**, 프로젝트가 남음 |
| 3 | 2의 프로젝트에 파일 업로드 → SQL로 `file_vault` 행 삭제 시도 | `file_vault 레코드는 수정/삭제할 수 없습니다`로 거절 |

2의 응답 본문은 다음과 같다.

```json
{"type":"about:blank","title":"Conflict","status":409,"detail":"연결된 데이터가 변경되었습니다. 새로고침 후 연결 관계를 확인해주세요"}
```

서버 로그에는 Hibernate가 `contribution_scores_project_id_fkey` 위반을 ERROR로 남겼다. 원인은 로그로 추적할 수 있지만, 우리 예외 처리기는 아무것도 남기지 않았다(A-02에서 경고 로그를 추가했다).

## 4. 처리안

| | (가) 외래키에 연쇄 삭제 | (나) 서비스에서 먼저 삭제 | (다) 삭제 대신 보관 | (라) 삭제를 막고 정확히 안내 |
| --- | --- | --- | --- | --- |
| 방법 | 새 migration으로 8개 외래키를 `ON DELETE CASCADE`로 변경 | `deleteProject`가 점수·로그·알림을 먼저 지운 뒤 프로젝트 삭제 | 프로젝트에 보관 시각 열을 두고, 보관된 프로젝트를 목록·접근·점수 계산에서 제외 | 삭제 전에 기록이 있는지 확인해 409와 "기록이 쌓인 프로젝트는 삭제할 수 없습니다"로 안내 |
| 파일이 있는 프로젝트 | **여전히 실패.** 트리거가 연쇄 삭제를 막는다. 이 오류는 무결성 위반으로 분류되지 않아 500이 될 가능성이 높다 | **여전히 실패.** 같은 트리거 | 가능(아무것도 지우지 않음) | 삭제 불가를 정확히 안내 |
| 기록 보존 | 전부 사라짐 | 전부 사라짐 | 전부 남음 | 전부 남음 |
| 담당 경계 | A가 B의 테이블 규칙을 바꿈 | A가 B의 데이터를 지움 | 점수 스케줄러의 제외 처리는 B, 화면은 C | A만 |
| 작업량 | 2시간 | 3시간 + B 협의 | 6~8시간(A 서버·DB, B 스케줄러, C 화면) | 1시간 |

(가)와 (나)는 파일이 있는 프로젝트를 끝내 지우지 못한다. 트리거를 풀면 가능하지만 파일 불변 원칙을 깨는 일이라 선택지로 두지 않았다.

## 5. 권고

**지금은 (라), 이후 (다)를 3단계 "종료·재개" 기능으로 만든다.**

- (라)는 A 혼자 1시간 안에 할 수 있고, 사용자가 받는 안내가 사실과 맞게 된다. 화면의 삭제 버튼을 둘지는 C와 정한다.
- (다)는 DEVELOPMENT.md의 단계별 범위 중 3단계 "통합본 검토·확정, 제출 기록, 종료·재개"의 "종료"와 같은 기능이다. 따로 만들 이유가 없다. 기록과 파일을 모두 지키면서 사용자 목록에서 치울 수 있는 유일한 방법이기도 하다.
- (가)와 (나)는 권하지 않는다. 파일이 있는 프로젝트를 해결하지 못하고 기록만 지운다.

## 7. 확인하지 않은 것

- 점수 스케줄러가 30분마다 도는 것은 코드(`fixedRate`)로 확인했다. 재현에서는 재계산 API로 같은 상황을 만들었다.
- 활동 로그와 알림이 쌓인 프로젝트는 따로 재현하지 않았다. 점수 행 하나로 이미 막히기 때문이다.
- 화면에서 삭제 버튼을 누르는 확인은 하지 않았다. API 응답이 같으므로 화면은 그 문구를 보여줄 것이다.
- (가)를 적용했을 때 파일 금고 트리거의 오류가 500이 된다는 것은 예외 분류로 추정한 것이고 실행해보지 않았다.
