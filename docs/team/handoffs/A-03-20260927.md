## 1. 결론

**프로젝트는 만든 뒤 첫 점수 계산이 돌고 나면 삭제되지 않는다.** 점수 스케줄러가 앱 시작 직후와 이후 30분마다 모든 프로젝트의 모든 멤버에게 점수 행을 만들고, 그 행이 프로젝트 삭제를 막는다. 프로젝트를 만든 사람이 곧 멤버이므로 사실상 모든 프로젝트가 해당된다.

화면(대시보드)에는 삭제 버튼이 있다. 누르면 서버는 409와 "연결된 데이터가 변경되었습니다. 새로고침 후 연결 관계를 확인해주세요"를 돌려주지만, **화면은 이 오류를 표시하지 않고 대화상자만 닫는다.** 프로젝트는 목록에 그대로 남아, 사용자는 삭제가 왜 안 됐는지 알 수 없다.

**정정:** A-01 인수인계, A-03 작업서, `verify-db.sh` 출력 문구, #46 PR 본문에 "V9 트리거가 업무를 만들 때 점수 행을 만든다"고 적었는데 틀렸다. V9에는 `updated_at` 갱신 트리거만 있다. 점수 행은 애플리케이션의 `ScoreService`가 만든다. 영향 범위도 "업무가 있는 프로젝트"가 아니라 "첫 점수 계산이 지난 모든 프로젝트"다.

## 2. 재현 (실제 API)

`main`(`fbbb3cb`) 코드를 검사용 DB에 띄우고 가입·로그인 후 요청을 보냈다.

| 순서 | 요청 | 결과 |
| --- | --- | --- |
| 1 | 프로젝트 생성 직후 `DELETE /api/projects/{id}` | **204**, 삭제됨 |
| 2 | 다른 프로젝트 생성 → `POST .../scores/recalculate`(스케줄러가 한 번 도는 것과 같음) → `DELETE` | **409**, 프로젝트가 남음 |
| 3 | 2의 프로젝트에 파일 업로드 → SQL로 `file_vault` 행 삭제 시도 | `file_vault 레코드는 수정/삭제할 수 없습니다`로 거절 |

2의 응답 본문은 다음과 같다.

```json
{"type":"about:blank","title":"Conflict","status":409,"detail":"연결된 데이터가 변경되었습니다. 새로고침 후 연결 관계를 확인해주세요"}
```

서버 로그에는 Hibernate가 `contribution_scores_project_id_fkey` 위반을 ERROR로 남겼다. 원인은 로그로 추적할 수 있지만, 우리 예외 처리기는 아무것도 남기지 않았다(A-02에서 경고 로그를 추가했다).

## 5. 권고

**지금은 (라)를 적용하고, 이후 (다)를 3단계 "종료·재개" 기능으로 만들자고 권한다.**

- (라)는 A 혼자 할 수 있고, 서버가 돌려주는 안내가 사실과 맞게 된다. 다만 **사용자에게 보이려면 화면이 이 안내를 표시해야 한다(C).** 데이터와 스키마를 바꾸지 않아 어떤 결정이 나도 버릴 코드가 아니므로 이 브랜치에서 바로 구현했다(6장). 화면의 삭제 버튼을 둘지는 C와 정한다.
- (다)는 DEVELOPMENT.md의 단계별 범위 중 3단계 "통합본 검토·확정, 제출 기록, 종료·재개"의 "종료"와 같은 기능이다. 따로 만들 이유가 없다. 기록과 파일을 모두 지키면서 사용자 목록에서 치울 수 있는 유일한 방법이기도 하다.
- (가)와 (나)는 권하지 않는다. 파일이 있는 프로젝트를 해결하지 못하고 기록만 지운다.

## 6. (라) 구현과 확인

`ProjectService.deleteProject`가 삭제를 `flush()`로 즉시 DB에 반영해보고, 무결성 위반이 나면 409와 "기록 보존을 위해 이 프로젝트는 삭제할 수 없습니다"를 돌려준다. B 소유 테이블의 Repository를 하나씩 조회하지 않아도 점수·활동 기록·알림·파일 금고를 한 번에 처리한다.

안내 문구를 "기록이 쌓인 프로젝트"가 아니라 "기록 보존을 위해"로 정한 이유가 있다. 아무 활동도 하지 않은 프로젝트도 점수 스케줄러가 점수 행을 만들어 삭제되지 않는다. "기록이 쌓인"이라고 하면 아무것도 하지 않은 사용자가 이해할 수 없다.

같은 방식으로 실제 앱을 띄워 확인했다.

| 경우 | 결과 |
| --- | --- |
| 방금 만든 프로젝트 | 204, 삭제됨 |
| 점수 계산 후 | 409, 새 안내 문구, 프로젝트 유지 |
| 파일 업로드 후 | 409, 새 안내 문구, 프로젝트 유지 |

단위 테스트(`ProjectDeleteTest`)는 기록이 없으면 삭제하고, 무결성 위반이 나면 409와 안내 문구로 바뀌는지 확인한다.

**이 변경은 API 응답만 바꾼다.** 화면이 오류를 표시하지 않아 사용자가 보는 것은 아직 그대로다. 화면 수정은 C의 몫이다(7장 2번).

## 7. 팀이 정할 것

1. (다) 보관을 3단계 "종료·재개" 기능으로 만들지
2. 대시보드가 삭제 실패를 표시하게 할지(C). 지금은 오류를 삼키고 대화상자만 닫는다. 화면에 이미 있는 `lib/apiError.ts`로 서버 안내(`detail`)를 꺼내 보여줄 수 있다. 버튼 자체를 숨길지도 함께 정한다
3. (다)를 3단계 일정에 넣을 때 점수 스케줄러가 보관된 프로젝트를 건너뛰는 처리(B)
4. 쓰이지 않는 네 테이블(`manual_work_reports`, `peer_reviews`, `weight_configs`, `weight_change_log`)은 점수 체계 재설계 유예(`DEFERRED.md`)와 함께 정리할지

## 8. 확인하지 않은 것

- 점수 스케줄러가 30분마다 도는 것은 코드(`fixedRate`)로 확인했다. 재현에서는 재계산 API로 같은 상황을 만들었다.
- 활동 로그와 알림이 쌓인 프로젝트는 따로 재현하지 않았다. 점수 행 하나로 이미 막히기 때문이다.
- 화면에서 삭제 버튼을 직접 눌러보지는 않았다. 대시보드 코드(`dashboard/page.tsx`의 `handleDelete`)를 읽어 오류를 표시하지 않는다는 것을 확인했다.
- (가)를 적용했을 때 파일 금고 트리거의 오류가 500이 된다는 것은 예외 분류로 추정한 것이고 실행해보지 않았다.
