# 송승준 · A-20 · 2026-10-11 최종 확정과 제출 기록 구현 인수인계

최종 확정·제출 기록 계약(K-20 v0.1)을 서버에 구현했다. 브랜치 `feat/A-20-confirmation`, 기준 main `5aa2877`에 검토 회차 구현(#91)을 합친 것.

## 들어간 것

| 구분 | 내용 |
| --- | --- |
| DB | V24 `deliverable_confirmations`, `deliverable_submissions`. 기존 테이블은 바꾸지 않았다 |
| API | `GET`·`PUT /api/projects/{projectId}/deliverables/{deliverableId}/confirmation`, `PUT …/submission`. 세 명령이 같은 객체를 돌려주고 모양은 K-20 3장과 같다 |
| 기존 API 변경 | 제출물 목록·단건·생성·수정 응답에 `status`, `latestDecision` 추가 |
| 기존 API 변경 | 회차 목록의 `deliverableStatus`와 `ReviewRoundView.deliverableStatus`에 `CONFIRMED`·`SUBMITTED`가 나온다 |
| 기존 API 변경 | 확정된 제출물의 수정·삭제, 요구사항 추가·수정·삭제, 충족 확인·해제, 회차 열기·결정은 409 "확정된 제출물은 변경할 수 없습니다" |
| 다른 담당용 | `DeliverableStatusReader`(제출물 상태 확인과 잠금) |

확정과 제출 기록은 활동 기록과 알림에 남기지 않는다. 계약이 정하지 않아 넣지 않았다.

## 계약에 없어 구현에서 정한 것

- `PUT /confirmation`의 `reviewId`가 이 제출물의 회차가 아니면(다른 프로젝트의 회차, 없는 id) 다른 확인보다 먼저 404다. 이 제출물의 다른 회차면 확정 전에는 409 "확정하려는 대상이 바뀌었습니다", 확정 뒤에는 409 "이미 확정된 제출물입니다"
- 제출 기록의 낸 곳과 메모는 공백만 있으면 빈 것으로 보고, 앞뒤 공백을 떼고 저장한다
- 제출 기록이 "같은 내용"인지는 낸 곳(비웠으면 제출물의 제출 경로로 채운 뒤), 낸 시각, 메모로 본다. 낸 시각은 시간대 표기가 달라도 같은 순간이면 같다
- 확정 뒤에는 회차에 같은 결정을 다시 보내도 409다. 확정 전에는 지금 상태를 돌려준다
- 확정 시각, 낸 시각, 기록 시각은 UTC, 마이크로초로 나간다(예: `2026-10-10T16:42:39.943208Z`). 저장 직후의 응답과 이후의 조회가 글자까지 같다. 다른 응답의 시각 형식은 바꾸지 않았다

## 손정효님(C)이 이어받을 것

1. **최종 제출 탭(#99)**: 이 PR이 병합되면 위 세 API에 연결할 수 있다. `candidate`·`confirmation`·`submission`은 값이 없어도 생략하지 않고 `null`로 온다. 확정 뒤 `checks`는 빈 배열이다
2. **확정 요청**: 본문에 `candidate.reviewId`를 넣는다. 409면 `detail`을 그대로 보여 주면 된다. 세 검사 가운데 처음 막힌 사유가 온다
3. **중복 클릭**: 같은 확정, 같은 내용의 제출 기록을 다시 보내면 200과 처음의 객체가 온다
4. **제출 기록**: `submittedAt`은 서버 시각보다 5분 넘게 뒤면 400이다. `channel`을 비우면 서버가 제출물의 제출 경로로 채운다
5. **목록 카드와 프로젝트 홈**: 제출물 응답의 `status`와 `latestDecision`을 쓴다
6. **확정 뒤의 버튼**: 위 표의 쓰기는 모두 같은 문구의 409다. 같은 이름의 새 파일 업로드는 막지 않는다. 내용이 다른 파일을 올리면 `confirmation.fileStillLatest`가 `false`가 되고, 같은 내용을 다시 올린 것이면 `true` 그대로다

## 손정협님(B)이 이어받을 것

1. **제출물 상태 확인**: `com.blackbox.service.DeliverableStatusReader`를 주입받아 쓴다. `statusOf(projectId, deliverableId)`는 상태를 돌려주고, `lockForWrite`는 같은 값을 돌려주되 제출물 행을 먼저 잠근다. 프로젝트와 제출물이 맞지 않거나 없으면 `NotFoundException`이다. 권한은 보지 않으므로 먼저 확인한 뒤 부른다
2. **`lockForWrite`는 쓰기 명령의 트랜잭션 안에서만** 부를 수 있다. 밖에서 부르면 `IllegalTransactionStateException`이 난다. 잠금이 바로 풀리는 실수를 막으려는 것이다
3. **같은 문자열을 다시 적지 않게** 인터페이스에 세 가지를 뒀다: 상태 상수, `DeliverableStatusReader.isConfirmed(status)`(확정됐거나 제출까지 기록된 상태인가), `CONFIRMED_DETAIL`(409 문구). 피드백 명령은 `ReviewRoundReader`가 돌려주는 `deliverableStatus`에 `isConfirmed`를 쓰면 된다
4. **잠금**: #91과 같은 제출물 행 잠금이다. 확정, 제출 기록, 제출물·요구사항·충족 확인·회차의 쓰기가 모두 이것을 먼저 잡는다. 업무 명령이 `lockForWrite`를 쓰면 확정과 차례대로 처리된다. 두 제출물을 함께 잠가야 하면 id가 작은 것부터 잠근다(K-20 6장)
5. **미해결 피드백 수**: `UnresolvedCommentCounter` 구현을 등록하면 확정 검사가 그대로 쓴다. 확정은 제출물을 잠근 뒤에 부른다
6. **확정 뒤 업무와 피드백의 차단**은 이 PR에 없다. K-20 4장의 B 담당 줄이다

## 검증

### 실제 DB (`bash scripts/verify-db.sh`, 전체 통과)

- 깨끗한 DB에 V1~V22와 V24 적용, 엔티티와 스키마 일치. V23은 이 브랜치에 없다(AI 에이전트 #102가 쓴다)
- V22 시점의 제출물과 승인된 회차가 V24 적용 뒤에도 그대로이고, 확정·제출 기록은 비어 있음
- 확정·제출 기록 제약: 같은 제출물 두 번 확정, 다른 제출물의 회차로 확정, 프로젝트를 다르게 적은 확정, 확정 없는 제출 기록, 확정에 쓰인 회차 삭제, 제출 기록 두 번, 제출 기록이 있는 확정 삭제를 DB가 거절

### 자동 테스트 (`./gradlew clean build`, 137건 통과)

- `DeliverableConfirmationHttpTest`(21건): K-20 11장의 조건을 실제 DB와 HTTP로 본다. 준비 조회, 확정, 제출 기록, 확정 뒤의 차단, 제출물 응답의 상태
- `DeliverableConfirmationConcurrencyTest`(4건): 커밋된 자료와 실제 스레드로 동시 요청을 본다. 겹친 확정은 한 줄, 확정과 충족 확인 해제는 한쪽만, 확정과 새 버전이 겹쳐도 확정본은 승인된 회차의 버전, 모든 쓰기가 제출물 줄부터 잠금
- `DeliverableStatusesTest`(3건), `DeliverableConfirmationRepositoryTest`(4건): 상태 표, 읽기 인터페이스, 제약, 저장 형태
- 단계마다 규칙을 일부러 틀리게 바꿔 테스트가 실패하는 것을 확인했다. 내용은 작업서(`docs/team/tasks/A-20.md`)의 진행 기록에 있다
