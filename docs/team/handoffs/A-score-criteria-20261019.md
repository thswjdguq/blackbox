# 송승준 · 기여도 점수 기준 논의 안건 (A → B·C)

- 대상: 기여도 점수(`ScoreService`)와 경보(`AlertService`). 둘 다 손정협(B) 담당이다
- 제안자: 송승준(A, 제출물·검토 회차·확정 담당)
- 날짜: 2026-10-19 · 기준 SHA: `5e28837`(main)
- 결론: **점수에 무엇을 넣을지 정한 기준이 없다.** 처음 만든 네 항목이 그대로 남아 있고, 그 뒤에 만든 기능은 계약마다 "합의 전에는 점수에 넣지 않는다"로 미뤄 두었는데 그 합의를 하지 않았다. 원칙을 먼저 정하고, 기존 항목의 결함을 고친 뒤, 제출물 쪽 활동을 원칙에 맞춰 넣자는 안이다. 아래 6장의 안건을 정하고, 빠진 항목이 있으면 7장대로 코멘트를 남겨 주세요

## 1. 왜 지금 정해야 하는가

- 제품의 핵심 흐름(제출물 → 요구사항 → 업무 → 검토 → 확정 → 제출 기록)에서 한 일이 점수에 하나도 들어가지 않는다. 검토와 확정만 맡은 팀원은 "미참여"로 나오고, 같은 판정으로 무임승차 경보를 받는다
- 점수는 기여도 화면, 교수용 PDF, AI 도우미의 점수 도구(`get_scores`), 경보(Discord 알림 포함)가 모두 같이 쓴다. 기준이 틀리면 한 곳만 고쳐서는 안 된다
- 새 기능을 만들 때마다 "점수에 넣을까"를 따로 묻게 된다. 원칙이 있으면 그 자리에서 정해진다

## 2. 지금 점수가 세는 것

항목마다 "했다/안 했다"만 본다. 양과 질은 재지 않는다.

| 항목 | 판정 | 코드 |
| --- | --- | --- |
| 업무 완료 | 담당한 업무 중 완료(DONE)가 1개 이상 | `TaskAssigneeRepository.countDoneByProjectAndUser` |
| 회의 참석 | 프로젝트의 전체 회의 수 대비 체크인 50% 이상. 회의가 없으면 미참여 | `MeetingAttendeeRepository.countCheckedInByProjectAndUser` |
| 파일 업로드 | 파일 금고에 1개 이상 | `FileVaultRepository.countByProjectAndUploader` |
| 액션 아이템 | 회의에서 나온 업무 중 완료가 1개 이상. 업무 설명에 `[Action item from meeting:`이 들어 있는지로 가린다 | `TaskAssigneeRepository.countDoneActionItemsByProjectAndUser` |

- 네 개 모두면 전체참여(`FULL`), 2~3개면 부분참여(`PARTIAL`), 0~1개면 미참여(`NONE`)
- 다시 계산하는 때: 30분마다(스케줄러), 업무가 완료될 때, 기여도 화면의 "재계산" 버튼. 체크인과 파일 업로드 뒤에는 경보 해제만 다시 보고 점수는 바로 바뀌지 않는다
- 프로젝트의 모든 참여자를 계산한다. 관찰자도 들어간다

## 3. 지금 세지 않는 것

| 기능 | 기록이 남는 곳 | 점수에서 빠진 근거 |
| --- | --- | --- |
| 제출물 등록·수정 | 제출물 테이블만 | 정한 문서 없음 |
| 요구사항 작성, 충족 확인 | 요구사항 테이블(확인한 사람·시각) | 정한 문서 없음 |
| 검토 회차 열기, 승인·수정 요청 | 회차 테이블(연 사람, 결정한 사람·시각) | 정한 문서 없음 |
| 피드백 작성·해결·다시 열기·업무 전환 | 활동 기록(`FEEDBACK_*`) | K-11 3장: "신규 actionType의 기여도 영향은 별도 합의 전 점수 계산에 추가하지 않는다" |
| 최종 확정, 제출 기록 | 확정·제출 기록 테이블 | K-20 9장: "실행자와 시각으로만 남기고 기여도 점수는 주지 않는다. 활동 기록에 넣는 것은 따로 정한다" |
| AI 제안 채택 | 제안 테이블 | K-30 7장: 채택 자체에는 점수를 주지 않고, 만들어진 업무는 기존 기준대로 센다 |
| 회의록 작성 | 회의 테이블만 | 정한 문서 없음. 회의를 만든 사람은 자동으로 체크인 처리되어 "회의 참석"에는 들어간다 |
| 업무 만들기 | 활동 기록(`TASK_CREATE`) | 정한 문서 없음 |

`DEVELOPMENT_PLAN.md`는 "기여도 계산 개선"을 10주 범위 밖(S1)으로 두었다. 그래서 위 기능들은 점수를 정하지 않은 채로 만들어졌다.

## 4. 경보와 어긋나는 곳

경보 셋 가운데 둘은 점수를 쓰고 하나는 활동 기록을 쓴다. 그래서 같은 행동이 경보마다 다르게 세진다.

| 경보 | 판정 | 어긋나는 곳 |
| --- | --- | --- |
| 무임승차(`FREE_RIDE`) | 참여 수준이 `NONE` | 2장의 네 항목만 본다. 가입 직후에도 바로 나온다 |
| 과부하(`OVERLOAD`) | `FULL`이 한 명이고 나머지가 두 명 이상 | 2장의 네 항목만 본다 |
| 이탈(`DROPOUT`) | 가입 2주가 지났고 최근 2주 활동 기록이 없음 | 활동 기록의 모든 종류를 본다. 그래서 피드백을 쓴 사람은 이탈은 피하지만 무임승차는 받는다. 검토·요구사항 확인·확정만 한 사람은 활동 기록이 없어 둘 다 받는다 |

## 5. 기존 항목의 결함

원칙과 상관없이 고칠 것들이다.

| 결함 | 영향 |
| --- | --- |
| 관찰자(교수·조교)도 계산하고 경보를 만든다 | 교수가 PDF에 "미참여"로 찍히고, 2주 뒤 이탈 경보가 생긴다. Discord를 연동한 프로젝트면 알림도 나간다 |
| 회의 참석의 분모가 가입 전 회의까지 포함한다 | 늦게 들어온 팀원은 체크인을 다 해도 50%를 못 넘을 수 있다 |
| 액션 아이템을 업무 설명의 글자로 가린다 | 설명을 고치면 액션 아이템이 아니게 된다 |
| 액션 아이템 완료가 "업무 완료"로도 세진다 | 한 번 한 일이 두 항목을 채운다 |
| 무임승차 경보에 가입 유예가 없다 | 이탈은 가입 2주를 기다리는데, 무임승차는 가입 직후 첫 계산에서 나온다 |
| 체크인·업로드 뒤 점수가 바로 바뀌지 않는다 | 방금 체크인한 팀원이 기여도 화면에서 여전히 ✗를 본다. "재계산" 버튼이 사람이 누르면 바뀌는 값처럼 보이게 한다 |
| 업무 보드가 점수 응답에 없는 칸(`totalScore`)을 읽는다 | 보드의 업무 카드에 점수가 나오지 않고, 보드 위쪽의 "기여도 점수 재계산" 버튼은 재계산만 돌리고 보여 주는 것이 없다(`board/page.tsx`, `TaskCard.tsx`) |
| 쓰지 않는 옛 점수 칸이 남아 있다 | `ContributionScore`의 가중치·점수 칸(`gitScore`, `totalScore`, `weight*` 등)은 0이나 기본값 그대로다. 점수 목록을 `totalScore`로 정렬해 순서가 정해지지 않는다 |

## 6. 정할 것

### 6.1 원칙

후보 셋이다. 어느 쪽이든 "양과 질은 재지 않는다"는 지금처럼 둔다. 그래서 어느 후보든 항목마다 한 번씩만 하면 채워진다. 마음먹고 채우려는 사람은 막지 못한다는 한계를 화면과 PDF에서 숨기지 않는다.

| 후보 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 흐름 단계별 | 제품 흐름의 단계마다 한 일이 하나 이상인가. 예: 계획(제출물·요구사항·업무 만들기), 실행(업무 완료·파일), 검토(회차·결정·피드백), 마무리(확정·제출 기록), 소통(회의 참석·회의록) | 새 기능이 어느 단계인지만 정하면 끝난다. 검토만 맡은 사람도 드러난다 | 항목 수와 판정(몇 개면 전체참여인가)을 새로 정해야 한다. 화면·PDF의 표가 바뀐다 |
| B. 지금 넷 + 검토 | 지금 네 항목을 두고 "검토 참여"(회차 결정, 피드백 작성·해결, 요구사항 충족 확인 중 하나 이상)를 더한다 | 바꾸는 양이 가장 적다 | 확정·제출 기록, 회의록 같은 다음 기능이 오면 또 정해야 한다 |
| C. 활동 기록 하나로 | 점수와 경보 모두 활동 기록의 종류를 항목에 묶어 판정한다. 항목 구성은 A나 B를 따른다 | 4장의 어긋남이 사라진다. 기록하는 곳만 늘리면 된다 | 지금 기록하지 않는 행동(회차, 요구사항 확인, 확정 등)을 먼저 기록해야 한다 |

**제안**: C의 방식(활동 기록 하나로)에 B의 항목(지금 넷 + 검토)으로 시작한다. 판정 근거가 한 곳에 모여 경보와 어긋나지 않고, 항목은 작게 늘린다. 확정·제출 기록처럼 팀장 한 명이 하는 행동은 개인 점수에 넣지 않고 기록으로만 남긴다(K-20 9장 유지).

### 6.2 활동 기록의 범위

C를 고르면 지금 기록하지 않는 행동을 기록해야 한다.

- 무엇을 기록할지: 회차 열기, 승인·수정 요청, 요구사항 작성·충족 확인, 제출물 등록, 확정, 확정 취소, 제출 기록, 회의록 저장
- 누가 쓰는지: 기록하는 호출은 각 기능의 담당이 넣고(제출물·회차·확정은 A, 회의는 B), 활동 기록의 형식(`actionType` 이름, 메타데이터)은 B가 정한다
- 기존 자료: 이미 있는 회차·요구사항 확인·확정은 테이블에 사람과 시각이 있다. 활동 기록으로 옮길지(마이그레이션), 앞으로의 것만 셀지

### 6.3 결함 수정의 순서와 담당

5장의 결함은 6.1과 상관없이 먼저 고칠 수 있다. 관찰자 제외, 회의 분모, 무임승차 유예, 액션 아이템 판정은 B, 기여도 화면의 "재계산" 버튼과 업무 보드의 점수 표시·재계산 버튼은 C다. 옛 점수 칸을 지울지는 마이그레이션 번호를 함께 정한다(시연 브랜치 통합이 V26~V30, 확정 취소가 V31을 쓴다).

### 6.4 화면과 PDF의 표기

항목이 바뀌면 기여도 화면(C), PDF 리포트(A), AI 도우미의 점수 도구 설명(A)을 같이 고친다. 표의 칸 이름과 "전체참여·부분참여·미참여" 기준 문구를 한 곳에서 정해 세 곳이 같은 말을 쓰게 한다.

### 6.5 언제 하는가

엑스포 시연은 지금 기준으로 한다. 5장의 관찰자 제외는 시연에서 교수가 "미참여"로 보이므로 엑스포 전에 고치는 것이 좋다. 나머지는 엑스포 뒤에 한다.
