# 송승준 · A-11 · 2026-10-07 검토 회차 구현 인수인계

검토 회차 계약(K-10 v0.2)을 서버에 구현했다. 브랜치 `feat/A-11-review-rounds`, 기준 main `ca7c7ad`.

## 들어간 것

| 구분 | 내용 |
| --- | --- |
| DB | V21 `review_rounds`. `file_vault`에는 `(id, project_id)` 유일 제약만 추가(기존 행 변경 없음) |
| API | `GET`·`POST /api/projects/{projectId}/deliverables/{deliverableId}/reviews`, `PUT …/reviews/{reviewId}/decision`. 응답은 K-10 3장과 같다 |
| 다른 담당용 | `ReviewRoundReader`(회차 확인·제출물 잠금), `UnresolvedCommentCounter`(미해결 피드백 수)와 기본 구현 `NoCommentsYet` |
| 기존 API 변경 | 회차가 있는 제출물 삭제는 409 "검토 기록이 있는 제출물은 삭제할 수 없습니다" |
| 파일 업로드 | 같은 이름으로 내용이 다른 파일을 올려도 `TAMPER` 경보를 만들지 않는다. 변경 기록(`tamper_detection_log`)과 응답의 `tamperDetected`는 그대로다 |

회차 열기와 결정은 활동 기록에 남기지 않는다. 계약에 없어 넣지 않았다.

## 손정협님(B)이 이어받을 것

1. **회차 확인과 잠금**: `com.blackbox.service.ReviewRoundReader`를 주입받아 쓴다. 조회는 `get`, 쓰기 명령은 `lockForWrite`를 **쓰기 명령의 트랜잭션 안에서** 부른다. 돌려주는 값은 `ReviewRoundReader.ReviewRoundView`(회차·제출물·프로젝트 id, 회차 번호, `latest`, `decision`, `deliverableStatus`)다. 권한은 보지 않으므로 먼저 확인한 뒤 부른다
2. **미해결 피드백 수**: `com.blackbox.service.UnresolvedCommentCounter`를 구현한 빈을 등록하고, **같은 PR에서 `backend/src/main/java/com/blackbox/service/NoCommentsYet.java`를 지운다.** 둘 다 있거나 둘 다 없으면 서버가 뜨지 않는다. 이 동작은 `ReviewRoundServiceTest`가 확인하며, 그 테스트는 `NoCommentsYet`을 가리키지 않으므로 파일만 지우면 된다
3. **잠금의 성질**: 제출물 행을 `for no key update`로 잠근다. 같은 잠금끼리는 차례를 기다리고, 그 제출물에 업무를 새로 연결하는 일반 삽입은 막지 않는다
4. **V22**: K-11 5장과 K-12대로 A가 다음에 쓴다. `review_comments`는 `review_rounds`의 `(id, deliverable_id, project_id)` 유일 제약을 참조한다
5. **기존 `TAMPER` 경보**: 새로 생기지 않을 뿐 이미 있는 경보는 그대로다. 정리는 결정안대로 B의 별도 작업이다. 보고서의 "변조" 표기(`ReportService`)도 기존 경보를 위해 남겨 두었다

## 손정효님(C)이 이어받을 것

1. **검토 탭(#66)**: 이 PR이 병합되면 위 세 API에 연결할 수 있다. 필드 이름과 null 규칙은 K-10 3장 그대로다(아래 HTTP 확인에서 대조함)
2. **파일 금고 화면 문구**: 업로드 응답의 `tamperDetected`는 내용이 바뀌면 여전히 `true`지만 이제 경보는 생기지 않는다. `frontend/src/app/projects/[projectId]/vault/page.tsx`의 "변조" 문구를 "파일 변경"에 맞추면 좋겠다
3. **제출물 삭제**: 회차가 있으면 409와 새 사유가 온다. 화면은 지금처럼 `detail`을 보여 주면 된다

## 검증

### 실제 DB (`bash scripts/verify-db.sh`, 전체 통과)

- 깨끗한 DB에 V1~V21 적용, 엔티티와 스키마 일치
- V20 데이터(파일 2건 포함) 위에 V21 적용: 기존 업무·사용자·파일 보존
- 회차 제약: 같은 프로젝트 파일로 여는 회차와 파일 없는 회차는 들어가고, 다른 프로젝트의 파일, 프로젝트 id가 섞인 회차, 겹치는 회차 번호, 결정자 없는 결정, 정해지지 않은 결정 값, 회차가 있는 제출물 삭제는 DB가 거절

### 실제 HTTP (검사용 PostgreSQL의 임시 DB, 계정 5개, 39건 모두 기대와 일치)

| 흐름 | 결과 |
| --- | --- |
| 회차 없는 목록 | 200, `DRAFT`, `rounds: []` |
| 팀원이 파일로 열기 → 목록 | 201, `roundNo` 1, 파일 요약(이름·버전·짧은 해시 7자) → `IN_REVIEW` |
| 파일을 올린 사람·관찰자의 결정, 관찰자의 열기, 비회원의 목록 | 403 |
| 로그인 없이 목록 | 401 |
| `decision` 생략·값 오류, UUID 형식 오류(경로, 본문) | 400 |
| 없는 회차·없는 제출물, 다른 프로젝트 경로, 다른 프로젝트의 파일 | 404 |
| 수정 요청 → 목록 | 200 → `DRAFT` |
| 같은 결정 다시 / 다른 결정 다시 / 지난 회차에 결정 | 200 / 409 / 409 |
| 파일 없이 열기(`null`, 생략) | 201, `file: null` |
| 파일 없는 회차 승인 | 200, `currentBasis: false` |
| 수정본으로 새 회차 → 다른 팀원이 승인 | 201 → 200, `currentBasis: true` |
| 승인 뒤 같은 내용 재업로드 / 다른 내용 업로드 / 승인한 내용으로 되돌림 | `true` / `false` / `true` |
| 같은 이름으로 네 번 다시 올린 뒤(내용이 바뀐 것 세 번) `TAMPER` 경보 수, 변경 기록 | 0건, 변경 기록은 남음(3건 이상) |
| 승인 뒤 새 회차 | 이전 승인 `currentBasis: false` |
| 같은 제출물에 회차 열기 6건 동시 | 모두 201, 회차 번호 1~6 |
| 회차가 있는 제출물 삭제 / 없는 제출물 삭제 | 409 / 204 |

### 자동 테스트 (`./gradlew test`, 101건 통과)

- `ReviewRoundRepositoryTest`: 실제 DB에서 매핑, 회차 목록의 조회 한 번, 잠금·파일 조회의 프로젝트 범위
- `ReviewRoundServiceTest`: 상태 계산, 회차 번호, 권한, 최신 회차에 한 번만 결정, 확정 근거, 읽기 인터페이스. 실제 요청으로 만들 수 없던 두 경우도 여기서 본다 — 미해결 피드백이 있을 때 승인 409, 미해결 수 구현이 없거나 둘일 때 시작 실패

## 확인하지 않은 것과 남은 것

- 화면에서의 확인. 검토 탭이 연결된 뒤 손정효님과 한다
- 미해결 피드백이 실제로 있을 때의 HTTP 요청. 피드백 구현(B-20) 뒤에 한다
- K-10 문서의 상태 줄에 "구현 전"이 남아 있다. 그 문서는 #69에 있어 이 브랜치에서 고칠 수 없다. #69가 병합되면 고친다
- "그 파일 이름의 최신 버전" 조회에 인덱스를 두지 않았다. 지금 업로드 코드와 같은 조회이고 과제 규모에서는 문제가 없다
