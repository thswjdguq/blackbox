## 2. 로컬에서 켜기

기본은 꺼져 있다. Docker로 띄울 때는 `.env`에 아래 세 줄을 넣고 서버를 다시 띄운다. 서버를 직접 실행할 때는 환경 변수 `SPRING_AI_MODEL_CHAT=google-genai`와 `SPRING_AI_GOOGLE_GENAI_API_KEY`를 준다.

```text
SPRING_AI_MODEL_CHAT=google-genai
GEMINI_API_KEY=(Google AI Studio에서 받은 키)
GEMINI_MODEL=gemini-3.5-flash-lite
```

- 켜지지 않았으면 `GET /status`가 `available: false`를 주고 실행은 503이다. 나머지 기능은 그대로다
- **무료 등급의 한도**: Flash-Lite는 분당 15번, 하루 500번이다. 실행 한 번이 요청을 2~3번 쓴다. Flash 계열(3.5, 3.6, 3.8)은 하루 20번이라 쓰지 않는다
- **무료 등급으로 보낸 내용은 Google의 제품 개선에 쓰인다.** 지어낸 프로젝트로만 시험한다. 실제 팀의 기록은 넣지 않는다
- 모델을 켜지 않고 화면만 만들 때는 K-30 3·4장의 예시를 fixture로 쓴다

## 3. 화면이 부르는 순서

| 언제 | 부르는 것 | 쓰는 것 |
| --- | --- | --- |
| 프로젝트 화면을 열 때 | GET `/status` | `available`이 `false`면 도우미를 숨긴다. `skills[].allowed`로 버튼을 정하고 `pendingProposalCount`로 대기 카드 수를 보인다 |
| 버튼을 누르거나 질문을 보낼 때 | POST `/runs` | 응답이 이벤트 스트림이다(4장). `step`마다 한 줄, `text`는 글, `proposal`은 카드 |
| 대기 카드를 볼 때 | GET `/proposals?status=PENDING` | 최신이 먼저, 50건까지 |
| 카드를 고칠 때 | PUT `/proposals/{id}` `{ "content": {…} }` | 보낸 `content`가 통째로 대신한다. 응답의 카드로 화면을 바꾼다 |
| 채택·거절 | POST `/accept`, `/reject` | 응답의 `results`로 만들어진 제출물·업무에 링크를 건다 |

## 4. 실행 스트림 읽기

`EventSource`는 POST를 보내지 못하므로 `fetch`로 읽는다. 아래는 제안이고, 실제로 받은 스트림을 통째로·7글자씩·한 글자씩 쪼개 넣어 같은 결과가 나오는 것을 확인했다.

```ts
export async function runAgent(
  projectId: string, skill: string, input: object,
  on: (event: "step" | "text" | "proposal" | "done" | "error", data: any) => void,
) {
  const res = await fetch(`/api/projects/${projectId}/agent/runs`, {
    method: "POST",
    credentials: "include",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ skill, input }),
  });
  // 스트림이 시작되기 전의 실패(400·403·404·409·429·503)는 JSON으로 온다
  if (!res.ok) {
    const problem = await res.json().catch(() => ({}));   // 401은 본문이 없다
    throw new Error(problem.detail ?? "요청을 처리할 수 없습니다");
  }

  const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = "";
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += value;
    let end: number;
    while ((end = buffer.indexOf("\n\n")) >= 0) {        // 이벤트 하나는 빈 줄로 끝난다
      const block = buffer.slice(0, end);
      buffer = buffer.slice(end + 2);
      let event = "", data = "";
      for (const line of block.split("\n")) {
        if (line.startsWith("event:")) event = line.slice(6).trim();
        else if (line.startsWith("data:")) data += line.slice(5).trim();
      }
      if (event) on(event as any, JSON.parse(data));     // 첫 줄의 주석(:start)은 event가 없어 건너뛴다
    }
  }
}
```

- 서버는 `event:step`, `data:{…}`처럼 콜론 뒤에 공백 없이 보낸다. K-30 4장의 예시에는 공백이 있다. 둘 다 받게 `trim()`한다
- 공용 클라이언트(`lib/api.ts`)는 401이면 토큰을 갱신하고 다시 보낸다. `fetch`에는 그 처리가 없으므로, 401이면 `/auth/refresh`를 부르고 한 번 다시 보내는 것을 화면에서 넣어야 한다
- 스트림은 `done`이나 `error` 중 하나로 끝난다. `error`의 `detail`은 그대로 보인다
- 실행은 길어도 120초다. 넘으면 `error`가 온다
- 화면이 연결을 끊어도 서버는 끝까지 간다. 만들어진 카드는 목록에서 다시 받는다

10/10에 이 브랜치의 서버를 임시로 띄우고 Gemini 3.5 Flash-Lite로 받은 것이다. 길어서 줄인 곳은 `…`로 표시했다.

**실행** (안내문으로 계획 만들기, 줄 앞은 요청 뒤 지난 초)

```text

  2.6 | event:step
  2.6 | data:{"label":"프로젝트와 멤버 조회","tool":"get_project"}
  2.7 | event:step
  2.7 | data:{"label":"제출물과 요구사항 조회","tool":"list_deliverables"}
  3.0 | event:text
  3.0 | data:{"text":"제공된 과제 안내문을 바탕으로 중간 보고서 제출에 대한 계획 카드를 만들었습니다. …"}
  3.1 | event:proposal
  3.1 | data:{"id":"4bdc2ac6-…","runId":"2b158558-…","kind":"DELIVERABLE_PLAN","status":"PENDING","title":"중간 보고서 제출 계획", …}
  3.1 | event:proposal
  3.1 | data:{"id":"9ef2a8ce-…","runId":"2b158558-…","kind":"DELIVERABLE_PLAN","status":"PENDING","title":"최종 발표 계획", …}
```

응답 헤더는 `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`다.

**카드의 `content`** (업무 넷 중 하나, 요구사항 넷 중 둘만 옮겼다. 다른 카드인 최종 발표는 안내문에 날짜가 "추후 공지"여서 `dueDate`가 `null`로 왔다)

```json

  "tasks": [
    { "title": "문제 정의 작성", "dueDate": "2026-10-18", "requirementKey": "r1", "completionCriteria": "문제 정의 초안 작성 완료" }
  ],
  "deliverable": { "title": "중간 보고서", "dueDate": "2026-10-24", "description": "문제 정의, 대상 사용자, 시스템 설계가 포함된 중간 보고서", "submissionMethod": "LMS 과제함에 PDF 제출" },
  "requirements": [
    { "key": "r1", "content": "문제 정의가 반드시 들어가야 한다.", "required": true },
    { "key": "r4", "content": "분량은 10쪽 안팎을 권장한다.", "required": false }
  ]

```

**채택한 뒤**

```json
{
  "status": "ACCEPTED",
  "decision": { "result": "ACCEPTED", "decidedBy": { "userId": "fbb04c1d-…", "name": "김팀장" }, "decidedAt": "2026-10-10T19:37:26.806565077+09:00" },
  "results": { "deliverableId": "88f24e15-…", "requirementIds": ["9f6a7b01-…", "aa33f094-…", "ba767574-…", "6abe0d16-…"], "taskIds": ["0fd23fe9-…", "10717650-…", "53af15d1-…", "5ba58e8f-…"] }

```

채택 뒤 `GET /status`의 `stages`에 그 제출물이 `TASKS_IN_PROGRESS`로 나왔고, 기존 업무 API에서 업무 네 개가 제출물과 요구사항에 연결돼 담당자 없이 보였다.

**오류** (기존 오류 응답과 같은 형식이고 `status`와 `detail`만 옮겼다. 차례로 기한이 빈 카드의 채택, 관찰자의 채택, 채택한 카드의 거절이다)

```text
{ "status": 400, "detail": "제안의 내용을 확인해주세요 (deliverable.dueDate: must not be null)" }
{ "status": 403, "detail": "관찰자는 제안을 만들거나 채택할 수 없습니다" }
{ "status": 409, "detail": "이미 결정된 제안입니다" }
```

## 6. 화면에서 챙길 것

- **400의 `detail`**: 괄호 안이 `경로: 이유`이고 여러 개면 쉼표로 이어진다. 이유의 말은 브라우저의 언어를 따른다(`Accept-Language`가 한국어면 "공백일 수 없습니다", 없으면 영어). 그대로 보이기보다 경로(`deliverable.dueDate`, `requirements[0].content`, `tasks[1].title`)로 어느 칸인지 찾아 표시하는 편이 낫다
- **시각**: 같은 필드가 `…Z`로 올 때도 있고 `…+09:00`로 올 때도 있다(방금 만든 것은 서버의 시간대, DB에서 읽은 것은 UTC). 같은 순간이므로 `new Date()`로 읽는다. 문자열을 잘라 쓰지 않는다
- **`content`의 칸 순서**는 정해져 있지 않다. 이름으로 읽는다
- **수정하면 표에 없는 칸은 사라진다.** 화면이 덧붙인 칸을 서버에 맡기지 않는다
- **"[작성 필요: …]"와 `null`**: 모델이 채우지 못한 칸이다. `null`로 남은 기한(`deliverable.dueDate`)은 서버가 채택을 막는다(400). "[작성 필요: …]" 글자가 남은 칸은 서버가 막지 않으므로 화면이 표시해 사람이 채우게 한다
- **카드가 없는 답이 정상이다.** 안내문에서 제출물을 찾지 못했거나 만들 업무가 없으면 `text`만 오고 `done`의 `proposalIds`가 비어 있다
- **글의 링크**는 `/projects/{projectId}/deliverables/{id}`와 `/projects/{projectId}/board` 두 가지다. 모델이 쓰는 것이라 붙지 않을 때도 있다
- **한도에 걸리면** 화면에는 "AI 응답을 받지 못했습니다. 다시 시도해주세요"만 간다. 분당 한도는 1분 뒤에 풀린다

## 7. 손정협님께

- 에이전트의 읽기 도구는 `TaskService.listTasks`, `AlertService.getAlerts`, `ScoreService.getScores`, `DeliverableProgressService.get`을 요청한 사람으로 부른다. 채택은 `TaskService.createTask`를 채택한 사람으로 부른다. 고치지 않았다
- 이 메서드들의 인자나 반환이 바뀌면 `agent/tool`의 도구와 `agent/proposal`의 카드 종류가 같이 바뀐다. 바꾸실 때 알려 주시면 된다
- 채택으로 만들어진 업무인지는 `AgentOriginReader`로 묻는다. 기여도에서 쓸지는 손정협님이 정한다

```java
@Autowired AgentOriginReader origin;
boolean fromProposal = origin.createdFromProposal(projectId, "TASK", taskId);   // "DELIVERABLE"·"REQUIREMENT"도 된다
```

- 채택으로 만들어진 업무는 채택한 사람이 만든 것으로 활동 기록에 남고(`TASK_CREATE`), 담당자는 비어 있다

## 8. 확인한 것과 못 한 것

확인한 것
- `./gradlew clean build`: 테스트 148건 중 146건 통과, 2건은 실제 모델 테스트라 평소에는 건너뛴다
- `bash scripts/verify-db.sh` 통과. #91을 합친 상태에서도 통과하고 테스트 160건 통과
- 실제 서버를 임시로 띄워 쿠키 로그인으로 상태 조회, 실행, 카드 수정, 채택, 거절과 오류 응답을 차례로 불렀다(5장)
- **Next 개발 서버의 프록시(`NEXT_DEV_BACKEND`)를 거쳐도 이벤트가 하나씩 온다.** 프록시를 거쳐 상태 요약을 실행했을 때 `:start` 0.1초, `step` 1.8~2.0초, `text`와 `done` 3.4초에 도착했다
- 실제 Gemini의 질문 세트 19개 항목 통과(작업서 8번)

못 한 것
- nginx를 거친 스트림. 개발용 nginx 컨테이너가 꺼져 있었다. `/api/`의 읽기 시간 제한이 기본 60초라 이벤트 사이가 60초를 넘으면 끊긴다. 설정은 바꾸지 않았다
- Bedrock. AWS 자격 증명이 없다
- 화면. 브라우저에서 스트림을 읽는 것은 해 보지 않았다. 4장의 코드는 받은 스트림을 Node에서 넣어 확인한 것이다
