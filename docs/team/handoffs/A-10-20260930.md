## 1. 결론

1. **파일–제출물 연결: (다) 회차가 파일 버전을 직접 가리킨다.** 새 연결 테이블이나 `file_vault` 열을 만들지 않는다. 제출물과 파일은 검토 회차를 통해서만 이어지고, "같은 파일의 새 버전"은 파일 금고가 이미 쓰는 **같은 이름 버전 사슬**로 판단한다.
2. **수정본 경보: (ㄷ) 같은 이름의 재업로드에서 해시가 바뀌면 새 버전으로만 기록하고 `TAMPER` 경보는 만들지 않는다.** 변경 기록(`tamper_detection_log`)은 그대로 남긴다. 경보는 B, 경보를 보여 주는 화면은 C 담당이라 두 사람의 동의가 필요하다.

## 3. 파일–제출물 연결 방식 비교

| 기준 | (가) `file_vault`에 `deliverable_id` 열 | (나) 별도 연결 테이블 | (다) 회차가 파일 버전을 직접 가리킴 |
| --- | --- | --- | --- |
| 새로 만드는 것 | 열 1개, 업로드 API에 제출물 인자, `@Immutable` 엔티티 수정 | 테이블 1개, "제출물에 파일 붙이기" API | `file_vault`에 유일 제약 1개(행은 바꾸지 않음). 검토 회차 테이블은 어느 안이든 필요 |
| 기존 파일 | 제출물 없음으로 남는다. 트리거 때문에 나중에 채울 수 없다 | 나중에 붙일 수 있다 | 회차를 열 때 고르면 된다 |
| "새 버전"의 기준 | 이름 사슬과 제출물 소속이 따로 있어 기준이 둘이 된다 | 연결 테이블의 순번과 파일 금고의 버전 번호가 따로 있어 기준이 둘이 된다 | 파일 금고의 이름 사슬 하나 |
| 이전 승인 무효 판정 | 같은 제출물의 더 늦은 파일이 있는가 | 연결 테이블에 더 늦은 순번이 있는가 | 같은 이름의 최신 버전이 승인한 회차의 파일과 내용이 다른가, 또는 더 늦은 회차가 있는가 |
| 다른 이름으로 올린 수정본 | 같은 제출물이면 새 버전으로 본다 | 붙이면 새 버전으로 본다 | 같은 파일로 보지 않는다. 새 회차를 열며 그 파일을 고르면 된다 |
| 파일 금고 불변성 | 스키마·엔티티를 바꾼다 | 그대로 | 그대로 |
| 화면 영향 | 업로드 화면에 제출물 선택 추가 | 제출물 화면에 파일 붙이기 추가 | 검토 탭에서 회차를 열 때 파일 선택 |

**(다)를 권하는 이유**

- 계약이 요구하는 것(회차가 특정 파일 버전을 가리키고, 최종본은 같은 프로젝트의 실제 파일)을 새 테이블 없이 만족한다.
- 버전의 기준이 파일 금고의 이름 사슬 하나로 유지된다. (가)·(나)는 기준이 둘이 되어 "어느 쪽이 최신인가"를 따로 맞춰야 한다.
- **한계**: 다른 이름으로 올린 수정본은 기존 버전 사슬에 이어지지 않는다. 그래서 그 파일로 새 회차를 열기 전까지는 이전 승인이 자동으로 무효가 되지 않는다. 새 회차가 열리면 그 제출물의 이전 승인은 확정 근거에서 빠진다("더 늦은 회차가 있으면 무효"). 이 한계를 K-10 계약에 적고, 화면은 회차를 열 때 "이전 회차와 다른 파일입니다. 같은 이름으로 올려야 새 버전으로 이어집니다"를 안내한다. 확정(K-20)도 사람이 고른 최종 파일 버전에 대해 "최신 회차 승인"을 검사한다.
- 나중에 "제출물에 속한 파일 목록"이 필요해지면, 그때 (나)를 더해도 (다)의 회차 데이터는 그대로 쓸 수 있다.

**K-10에 옮길 DB 윤곽** (V21, 컬럼 이름은 계약 초안에서 확정)

- 검토 회차: 제출물, 프로젝트, 회차 번호, 대상 파일 버전(중간 검토는 비어 있어도 됨), 결정(`승인`/`수정 요청`/미결정), 결정자, 결정 시각, 연 사람, 연 시각
- 제출물–프로젝트 일치: V19와 같은 방식으로 `(deliverable_id, project_id)` 복합 외래키
- 파일–프로젝트 일치: `file_vault`에 `UNIQUE (id, project_id)`를 추가하고 `(file_id, project_id)` 복합 외래키. 두 외래키가 같은 `project_id`를 쓰므로 회차의 제출물과 파일이 같은 프로젝트임을 DB가 보장한다
- 같은 제출물의 회차 번호 중복 방지: `UNIQUE (deliverable_id, round_no)`. 동시에 회차를 두 개 여는 요청은 이 제약으로 한쪽이 실패한다

## 4. 수정본 업로드와 변조 경보

검토 흐름에서는 "수정 요청 → 같은 이름으로 수정본 업로드 → 새 회차"가 정상 경로다. 지금 방식이면 수정본을 올릴 때마다 프로젝트 홈에 "파일 변조" 심각 경보가 뜬다(사실 4·6).

| 안 | 내용 | 판단 |
| --- | --- | --- |
| (ㄱ) 그대로 둔다 | 수정본마다 `TAMPER` 경보 | 정상 동작이 심각 경보로 보여 경보를 믿지 않게 된다 |
| (ㄴ) 회차에 걸린 파일의 재업로드만 경보에서 뺀다 | 조건부 제외 | 규칙이 복잡하고, 회차 밖의 재업로드는 여전히 "변조"로 보인다 |
| (ㄷ) 재업로드의 해시 변경은 새 버전으로만 기록하고 경보는 만들지 않는다 | `tamper_detection_log` 기록과 파일 금고 화면의 "파일 변경 내역"은 유지 | **권고.** 사실 5·7대로 지금 `TAMPER`는 재업로드에서만 생기고, 재업로드는 이미 정상 편집(`FILE_EDIT`)으로 다룬다. 재업로드는 기존 기록을 바꾸지 않고 새 버전을 더하는 것이라 "변조"로 부를 근거가 없다. 디스크에 저장된 파일이 바뀌는 진짜 변조는 지금 감지하지 않는다(아래 마지막 항목) |

(ㄷ)을 택하면 바뀌는 것:

- A: `FileVaultService.upload`에서 `createTamperAlert` 호출을 뺀다(A-11 범위). README의 Hash Vault 설명을 "재업로드 시 변경 이력 기록"으로 고치고, 보고서(`ReportService`, A 소유)에서 재업로드 기록을 "파일 변경 이력"으로 구분해 적는다
- B: 재업로드로 생긴 기존 `TAMPER` 경보는 지우지 않는다. 경보 생성 중단을 적용한 뒤 해결 시각과 "재업로드 정책 변경에 따른 기존 경보 해제" 사유를 남겨 닫는다. 적용 전에 대상 건수와 그 경보가 재업로드(`REUPLOAD`)에서 생긴 것인지 확인하고, 실제 처리는 별도 작업으로 한다. `TAMPER` 종류는 나중의 파일 무결성 검사용으로 남겨 두되, 지금 그런 검사가 구현된 것처럼 적지 않는다
- C: 프로젝트 홈의 "파일 변조" 심각 표시와 분석 화면 문구를 정리한다
- 저장된 파일이 해시와 달라지는 진짜 변조는 예약 검사를 만들 때 그때 경보로 다룬다. 이번 범위가 아니다

## 5. 요청

- 손정협: 4장 (ㄷ)에 동의하는지, 열린 `TAMPER` 경보를 어떻게 닫을지. K-11 초안에서 피드백이 가리킬 회차 id는 3장 윤곽대로 잡아도 된다
- 손정효: 검토 탭에서 회차를 열 때 프로젝트 파일 목록에서 대상 파일을 고르는 흐름이 가능한지, 파일 없는 중간 검토를 화면에서 어떻게 보일지

## 6. 확인하지 않은 것

- 제약 추가는 임시 DB에서 SQL로만 확인했다. JPA 엔티티(`@Immutable`, `ddl-auto=validate`)와의 관계와 기존 데이터가 있는 DB의 업그레이드는 A-11에서 V21을 쓸 때 `verify-db.sh`로 확인한다
- 이미 운영 DB에 쌓인 `TAMPER` 경보의 개수는 조회하지 않았다

## 7. 리뷰에서 정한 것 (#58)

손정협님과 손정효님이 (다)와 (ㄷ)에 모두 동의했다. 아래는 리뷰에서 나온 요청이며 K-10 계약 초안에 옮긴다.

- 화면 문구 정리(손정효님)는 A-11에서 경보 생성을 빼고 기존 경보 처리가 정해진 뒤에 한다. 먼저 바꾸면 남아 있는 경보가 이름 없이 보인다
