# 송승준 · K-13 진척 조회 계약 검토 (A 답변)

- 대상: [K-13 v0.1 DRAFT](../contracts/K-13-progress.md) · 작성 손정협(B)
- 검토자: 송승준(A, 제출물·요구사항·권한 담당)
- 날짜: 2026-09-21 · 기준 SHA: `fbbb3cb`
- 결론: **세 가지 확인 요청은 모두 확인했고, 두 가지를 바꾸자고 제안한다.** 아래 반영 후 AGREED로 올리면 B-10에 들어가도 된다.

## 1. 요청하신 세 가지에 대한 답

### (1) 기존 조회 메서드를 읽기 전용으로 재사용하는 방향 — 확인

- `ProjectAccessChecker.getProject(projectId)` → 없으면 `NotFoundException`(404). `requireMember(project, user)` → 비회원이면 `ForbiddenException`(403). 계약의 403·404 구분과 그대로 맞는다.
- `DeliverableService.find(project, deliverableId)` → 없거나 다른 프로젝트 것이면 404. 타 프로젝트 제출물 ID를 404로 처리하겠다는 계약과 맞다. 이 메서드를 그대로 호출하면 된다.
- 세 메서드 모두 A가 유지 책임을 진다. 시그니처를 바꿔야 할 일이 생기면 B에게 먼저 알린다.

### (2) 충족 확인 데이터 계약 — A가 낸다 (K-14)

[A-04](../tasks/A-04.md)로 등록했고 이번 주에 초안을 낸다. 현재 정한 방향은 다음과 같다. 확정은 K-14 리뷰에서 한다.

- **충족은 사람이 확인하는 행위다.** 업무 DONE이나 AI 판단으로 자동 승인하지 않는다(CONTRACTS §3-1).
- 확인자와 확인 시각을 저장한다. 확인 해제도 가능하게 한다.
- **요구사항 내용이 수정되면 기존 확인은 초기화한다.** 확인했던 문장과 다른 문장이 확인된 상태로 남으면 안 된다.
- 확인 권한은 팀장·팀원. 관찰자는 불가.
- `assessmentAvailable`이 `true`로 바뀌는 시점은 K-14 구현이 병합된 다음이다. 그전까지 B는 1차 구현을 그대로 둔다.

B가 엔티티나 SQL을 먼저 만들 필요는 없다. 읽을 방법은 K-14에서 A가 제공한다.

### (3) `assessmentAvailable=false`와 null 정책 — 확인

`met=null`, `percent=null`로 두는 방향에 동의한다. 없는 데이터를 0으로 채우면 '미지원'이 '모두 미충족'으로 보인다는 판단에 동의한다.

다만 계약에 한 문장을 추가해 달라. **화면은 `percent`를 다시 계산하지 말고 서버 값을 그대로 쓴다.** 프런트가 `met / total`을 직접 나누면 분모 0에서 NaN이 되거나 null이 0으로 바뀐다.

## 2. 바꾸자고 제안하는 것

### (가) 필수 요구사항 개수는 A가 메서드로 제공한다

계약 §4에 `DeliverableRequirementRepository.findByDeliverableOrderByCreatedAtAsc`를 읽어 필터하겠다고 적혀 있다. 동작은 하지만 두 가지가 걸린다. 요구사항 전체 행을 불러와 개수만 쓰는 것이고, B의 서비스가 A의 저장소를 직접 들여다보게 된다(CONTRACTS §3-12).

**A가 `DeliverableService`에 개수만 돌려주는 읽기 전용 메서드를 추가하겠다.** B는 그것만 호출하면 된다. 이름과 시그니처는 B가 원하는 형태로 맞춰줄 테니 알려달라. 기본안은 다음과 같다.

```java
@Transactional(readOnly = true)
public long countRequiredRequirements(Deliverable deliverable)
```

**이 PR에 함께 넣었다.** `DeliverableRequirementRepository.countByDeliverableAndRequiredTrue`로 개수만 세고, 요구사항 행을 읽지 않는다. 이 PR이 병합되면 B-10에서 바로 호출하면 된다.

**다만 지금 A 쪽도 같은 일을 하고 있다.** `DeliverableService`는 B 소유인 `TaskRepository`를 직접 주입받아 `existsByDeliverable`·`existsByRequirement`를 호출한다(`fbbb3cb`). A→B는 저장소를 직접 부르면서 B→A만 서비스 메서드를 거치라고 하면 규칙이 한쪽에만 적용된다. 지적하지 않고 넘어가는 게 맞지 않아 같이 적는다.

둘 중 하나로 정하자.

1. **서로 저장소 직접 호출을 허용한다.** 그러면 위 메서드는 선택 사항이 되고, B는 `countByDeliverableAndRequiredTrue`를 직접 불러도 된다. A 쪽도 지금 코드를 그대로 둔다.
2. **양쪽 다 좁은 읽기 메서드로 통일한다.** B가 "이 제출물/요구사항에 연결된 업무가 있는가"를 돌려주는 읽기 메서드를 내주고, A의 `DeliverableService`가 그것을 쓰도록 바꾼다.

A 의견은 2번이다. 상대 저장소 메서드의 이름이나 의미가 바뀌면 컴파일 에러로만 드러나고 계약 문서에는 아무 기록이 남지 않기 때문이다. 다만 2번은 B의 파일을 바꿔야 하므로 합의 후 별도 Task로 한다. **그때까지 B-10은 어느 쪽으로 구현해도 막지 않는다.** 이 결정 때문에 진척 API를 늦추지 말자.

### (나) 400(UUID 형식 오류)은 지금 코드에서 보장되지 않는다

계약 §3에 UUID 형식 오류를 400으로 적었는데, **현재 예외 처리로는 500이 나갈 가능성이 높다.** `GlobalExceptionHandler`에 `@ExceptionHandler(Exception.class)`가 있어서 경로 변수 타입 변환 실패(`MethodArgumentTypeMismatchException`)까지 잡아 500으로 바꾼다. 이 예외를 따로 받는 핸들러는 없다.

아직 실제 요청으로 확인하지는 못했다. **A가 [A-02](../tasks/A-02.md)에서 실제 요청으로 확인하고, 500이 맞으면 400 핸들러를 추가하겠다.** 그때까지 계약의 400 행에는 "A-02에서 확인 후 확정"이라고 표시해두자. 없는 동작을 계약에 적어두면 C가 그 응답을 전제로 화면을 만든다.

## 3. 그대로 가면 되는 것 (확인만)

- 401은 현재 `SecurityConfig`가 `anyRequest().authenticated()`라 인증 없이는 컨트롤러에 도달하지 않는다. 계약의 "실제 필터 반환은 통합 확인 필요"라는 단서도 맞다.
- 경로 `/api/projects/{projectId}/deliverables/{deliverableId}/progress`는 A의 `DeliverableController`(`/api/projects/{projectId}/deliverables`)와 겹치지 않는다. 별도 컨트롤러로 만들어도 매핑 충돌은 없다.
- 404에서 다른 프로젝트의 제목이나 존재 여부를 노출하지 않는다는 규칙에 동의한다. `find`가 `findByIdAndProject`를 쓰므로 자연히 지켜진다.
- 진척 조회를 확정의 근거로 쓰지 않는다는 문장(§4)에 동의한다. 확정은 A가 서버에서 다시 검사한다(CONTRACTS §3-8).
- 읽기 전용 트랜잭션, 여러 담당자가 붙은 업무를 1건으로 세는 것, 소수 둘째 자리 HALF_UP 모두 동의한다.
