# 송승준 · AI 도우미 화면 흐름과 개발 기준 (A → C)

- 대상: K-30의 화면(도우미 창, 제안 카드, 화면마다의 버튼, "AI 제안" 표시)
- 작성: 송승준(A) / 받는 사람: 손정효(C)
- 날짜: 2026-10-11 · 기준: main `998b5dd`, 서버 `feat/A-30-agent`(#102), 계약 K-30 v0.5(#98)
- 상태: 제안. 화면 코드는 손정효님 소유다. 이 문서는 무엇을 어떤 순서로 보여 주고 어떤 API를 부르는지를 정하고, 컴포넌트를 어떻게 나누고 어떻게 꾸밀지는 정하지 않는다
- 결론: **에이전트를 창 하나로 만들지 않는다.** 어디서든 여는 도우미 창, 화면마다 그 단계에 맞는 버튼, 사람이 결정할 제안 카드, 만들어진 기록의 출처 표시 네 가지가 같은 서버 위에서 함께 움직이게 한다. 시연용 화면이 아니라 서비스에서 계속 쓰는 화면이다

## 0. 이 문서의 쓰임

이 문서만 읽고 화면을 만들 수 있게 필요한 것을 모두 옮겼다. 응답 형식과 오류는 K-30과 같은 내용이고, 서로 다르면 K-30이 맞다.

| 알고 싶은 것 | 볼 곳 |
| --- | --- |
| 무엇을 만드나 | 1장 |
| 어기면 안 되는 것 | 2장 |
| 화면의 구성과 창의 모양 | 3장 |
| 누르면 무슨 일이 일어나나(흐름마다) | 4장 |
| 역할, 오류, 가장자리 상황 | 5장 |
| 타입과 그대로 쓸 수 있는 코드 | 6장 |
| 화면에 쓸 문구 | 7장 |
| 파일 배치와 만드는 순서 | 9장 |
| 다 됐는지 확인하는 목록 | 10장 |
| 서버가 아직 하지 않는 것 | 11장 |

**서버를 띄우는 방법**

- #102가 병합되기 전에는 `feat/A-30-agent` 브랜치의 서버를 띄운다
- 기본은 AI가 꺼져 있다. 켜려면 `.env`에 아래 세 줄을 넣고 서버를 다시 띄운다. 키는 Google AI Studio에서 받는다

```text
SPRING_AI_MODEL_CHAT=google-genai
GEMINI_API_KEY=(받은 키)
GEMINI_MODEL=gemini-3.5-flash-lite
```

- 무료 등급으로 보낸 내용은 Google의 제품 개선에 쓰인다. **지어낸 프로젝트로만 시험한다.** 한도는 분당 15번, 하루 500번이고 실행 한 번이 2~3번을 쓴다
- 키 없이 화면만 만들 때는 6장의 예시를 fixture로 쓴다. 꺼진 상태(`available: false`)의 화면도 만들어야 하므로 키 없는 서버도 그대로 쓸모가 있다
- 개발 서버의 프록시(`NEXT_DEV_BACKEND`)는 응답이 30초 동안 조용하면 스트림을 끊고 화면 쪽 연결을 열어 둔다. `frontend/next.config.mjs`의 `nextConfig`에 `experimental: { proxyTimeout: 150_000 }`을 넣으면 풀린다(#102의 코멘트)

## 1. 한눈에 보기

에이전트는 세 가지를 한다. 프로젝트를 **살피고**, 사람이 읽을 글로 **알리고**, 다음 행동을 **제안**한다. 만드는 것은 언제나 사람이 채택할 때다.

### 화면 요소 네 가지

| 요소 | 어디에 | 하는 일 | 쓰는 API |
| --- | --- | --- | --- |
| 도우미 창 | 프로젝트의 모든 화면. 오른쪽에서 열린다 | 실행을 고르고, 진행과 답을 보고, 제안 카드를 다룬다 | `GET /status`, `POST /runs`, 카드 API 전부 |
| 화면마다의 버튼 | 프로젝트 홈, 제출물 목록, 제출물 상세, 업무 보드 | 그 화면의 단계에 맞는 실행을 도우미 창에서 바로 시작한다 | `GET /status`의 `stages`, `skills` |
| 제안 카드 | 도우미 창의 실행 결과 안, 도우미 창의 "제안" 탭 | 내용을 보고, 고치고, 채택하거나 거절한다 | `GET·PUT /proposals`, `/accept`, `/reject` |
| "AI 제안" 표시 | 업무 카드·목록, 요구사항 줄, 제출물 | 채택으로 만들어진 기록임을 알린다 | `GET /origins` |

### 사용자가 만나는 순서

프로젝트가 진행되는 동안 같은 창이 단계에 맞는 도움을 내놓는다.

| 프로젝트의 상황 | 화면이 내놓는 도움 | 실행 종류 | 결과 |
| --- | --- | --- | --- |
| 제출물이 없다 | "과제 안내문으로 계획 만들기" | `PLAN_FROM_BRIEF` | 제출물마다 카드 한 장(제출물·요구사항·업무) |
| 요구사항은 있는데 업무가 없거나 모자란다 | "요구사항을 업무로 나누기" | `BREAK_DOWN_TASKS` | 업무 카드 한 장 |
| 업무가 진행 중이다 | "지금 상태 살펴보기" | `STATUS_BRIEF` | 요약 글. 할 일이 있으면 업무 카드 |
| 언제든 | "물어보기" | `ASK` | 기록을 근거로 한 답 |

검토·확정 단계의 실행 종류는 아직 서버에 없다(12장). 서버에 종류가 늘어도 창의 틀은 그대로이고, 종류 하나에 대한 등록만 더하게 만든다(3.4).

### 한 번의 실행

```text
버튼이나 질문 ──▶ POST /runs ──▶ step(무엇을 살피는지 한 줄씩)
                                 ──▶ text(답의 글)
                                 ──▶ proposal(카드, 0장 이상)
                                 ──▶ done 또는 error
카드 ──▶ (고치면 PUT) ──▶ 채택 ──▶ 제출물·요구사항·업무가 만들어짐 ──▶ 그 화면으로 가는 링크
      └─▶ 거절 ──▶ 기록으로 남음
```

## 2. 화면이 지켜야 할 것

제품 원칙과 계약에서 온 것이라 화면의 선택으로 바꾸지 않는다.

1. **스스로 실행하지 않는다.** 화면을 열었다고 실행을 보내지 않는다. 사람이 버튼을 누르거나 질문을 보낼 때만 `POST /runs`를 부른다. 실행에는 횟수 한도가 있다
2. **스스로 만들지 않는다.** 제출물·요구사항·업무는 사람이 채택을 누를 때만 만들어진다. 채택 버튼에는 무엇이 몇 개 만들어지는지 적는다
3. **AI가 꺼져도 나머지 화면은 그대로다.** `GET /status`가 실패하거나 `available`이 `false`여도 오류 창을 띄우지 않고 AI 버튼만 감춘다. 이미 있는 카드와 "AI 제안" 표시는 꺼진 상태에서도 보인다(4.1)
4. **AI가 만든 것은 표시한다.** 답의 글, 제안 카드, 채택으로 만들어진 기록 모두에 표시가 있다
5. **모델이 쓴 글을 HTML로 넣지 않는다.** 글자 그대로 그리고 링크만 바꾼다. 링크는 이 프로젝트의 화면 경로일 때만 만든다(6.6)
6. **역할은 서버의 값으로 정한다.** 실행 버튼을 보일지는 `skills[].allowed`로, 카드의 고치기·채택·거절 버튼을 보일지는 `canDecide`로 정한다. 화면이 멤버 목록을 읽어 역할을 계산하지 않는다. 관찰자는 `canDecide`가 `false`이고 읽기만 한다
7. **담당자는 화면에서도 정하지 않는다.** 카드에 담당자 칸을 두지 않는다. 만든 뒤 업무 보드에서 정한다고 알린다
8. **외부로 나간다는 것을 알린다.** 도우미 창에 "프로젝트 기록(이름, 역할, 제출물·업무 내용)이 외부 AI 모델로 전송됩니다"가 늘 보인다
9. **카드는 서버의 것이 기준이다.** 수정·채택·거절의 응답으로 받은 카드로 화면을 바꾼다. 화면이 내용을 따로 고쳐 들고 있지 않는다
10. **답의 글은 서버에 남지 않는다.** 남는 것은 카드뿐이다. 새로 고치면 답은 사라지고 카드는 "제안" 탭에 있다. 이것을 창에서 알린다

## 3. 화면 구성

### 3.1 여는 버튼

- 큰 화면: 사이드바의 프로젝트 이름 아래. 글자는 "AI 도우미", 대기 카드가 있으면 숫자를 붙인다(`pendingProposalCount`)
- 작은 화면: 상단 바의 오른쪽. 아이콘과 숫자
- 프로젝트 화면(`/projects/{projectId}/…`)에서만 보인다. 내 프로젝트 목록, 프로필에는 없다
- 보이는 조건: `available`이 `true`이거나 `pendingProposalCount`가 1 이상. 둘 다 아니면 감춘다(4.1)
- 사이드바는 화면마다 다시 그려지므로 버튼은 저장소(3.4)의 값을 읽기만 한다

### 3.2 창의 틀

창은 화면을 옮겨 다녀도 닫히지 않아야 한다. 답의 링크를 누르면 업무 보드나 제출물로 가는데, 그때 답이 계속 보여야 하기 때문이다. 그래서 창은 화면 하나에 넣지 않고 `app/layout.tsx`(`AuthProvider` 안)에 한 번만 둔다.

| 화면 너비 | 모양 | 뒤 화면 |
| --- | --- | --- |
| 1280px 이상 | 오른쪽에 붙은 420px 칸 | 그대로 쓸 수 있다. 본문이 창만큼 왼쪽으로 줄어든다 |
| 768~1279px | 오른쪽에 붙은 420px 칸이 본문 위를 덮는다. 어두운 배경은 없다 | 가려지지 않은 부분은 그대로 쓸 수 있다 |
| 768px 미만 | 화면 전체 | 쓸 수 없다. 업무 창(`TaskModal`)과 같은 방식 |

- 큰 화면에서 창은 대화 상자가 아니라 옆 칸이다(`<aside aria-label="AI 도우미">`). 작은 화면에서만 `role="dialog"`와 `aria-modal`을 쓴다
- 본문을 줄이는 것은 화면마다 고치지 않고 한 곳에서 한다. 창이 열리면 `<html>`에 표시를 달고 `globals.css`에서 `main`의 오른쪽 여백을 준다
- 업무 창(`z-50`)이 도우미 창 위에 열린다. 도우미 창은 그보다 낮게 둔다
- 닫기: 닫기 버튼, 창 안에 초점이 있을 때의 Escape. 닫아도 내용과 진행 중인 실행은 그대로다(3.4)

### 3.3 창 안

탭은 둘이다. **도우미**(실행과 답)와 **제안**(카드 목록).

```text
AI 도우미                                   [닫기]
[ 도우미 ] [ 제안 2 ]
──────────────────────────────────────────────
(처음)
  지금 단계에 맞는 도움
    중간 보고서 · 기한 10월 18일
    요구사항 4개에 연결된 업무가 없습니다
    [ 요구사항을 업무로 나누기 ]

  할 수 있는 일
    [ 과제 안내문으로 계획 만들기 ]
    [ 요구사항을 업무로 나누기 ]
    [ 지금 상태 살펴보기 ]

──────────────────────────────────────────────
[ 프로젝트에 대해 물어보세요            ] [보내기]
프로젝트 기록(이름, 역할, 제출물·업무 내용)이 외부 AI 모델로
전송됩니다. 답은 새로 고치면 사라지고 제안은 남습니다.
```

실행을 하면 "처음"의 자리에 실행 기록이 위에서 아래로 쌓인다. 실행 하나는 아래 모양이다.

```text
지금 상태 살펴보기                          송승준 · 방금
  ✓ 프로젝트와 멤버 조회
  ✓ 업무 조회
  ✓ 경보 조회
  AI 답변
  중간 보고서는 업무 5개 중 2개가 끝났습니다.
  - API 설계 문서 는 기한이 지났습니다. 담당 이팀원     ← 링크
  …
  ┌ 제안 · 업무 3개 ─────────────────────────┐
  │ 이번 주에 끝낼 업무                        │
  │ 근거: 기한이 이번 주인 요구사항 두 개에 …   │
  │ [ 열기 ]                                   │
  └────────────────────────────────────────────┘
```

- 실행 기록은 대화처럼 보이지만 **앞의 답을 기억하지 않는다.** 질문마다 따로 답한다. 입력 칸의 안내 문구로 알린다(7장)
- "지금 단계에 맞는 도움"은 `stages`의 첫 제출물(기한이 가장 빠른 것)로 정한다. 맞는 실행이 없으면 이 구역을 그리지 않는다(4.9의 표)
- "할 수 있는 일"의 버튼 글자는 서버가 준 `skills[].label`을 쓴다. `allowed`가 `false`인 것은 그리지 않는다. `ASK`는 버튼이 아니라 아래의 입력 칸이다
- 실행이 하나라도 있으면 "처음"의 두 구역은 접어서 위에 "다른 도움 보기"로 남긴다

### 3.4 상태를 두는 곳

창의 상태는 컴포넌트가 아니라 저장소에 둔다(`zustand`, 지금 `lib/store/authStore.ts`와 같은 방식). 이유는 세 가지다.

- 화면을 옮기면 사이드바와 본문은 다시 그려진다. 창의 내용이 거기에 있으면 사라진다
- 실행은 길면 2분이다. 그동안 화면을 옮겨도 스트림을 계속 읽어야 한다. 읽는 루프를 저장소의 동작으로 두면 컴포넌트가 사라져도 계속 돈다
- 화면마다의 버튼(4.9)이 창을 열고 실행을 시작하려면 창 밖에서 부를 수 있어야 한다

저장소가 가진 것(모양은 6.4):

| 값 | 설명 |
| --- | --- |
| 열림 여부, 고른 탭 | 화면을 옮겨도 유지 |
| 프로젝트별 상태 객체 | `GET /status`의 응답 |
| 프로젝트별 실행 기록 | 요청, 단계, 글, 카드 id, 끝난 모양. 새로 고치면 없어진다 |
| 카드 | id로 찾는 표 하나. 실행 기록과 "제안" 탭이 같은 카드를 본다. 한 곳에서 채택하면 다른 곳도 바뀐다 |
| 프로젝트별 출처 객체 | `GET /origins`의 응답. 화면들이 같이 쓰고 채택할 때 다시 부른다(4.10) |
| 기록이 바뀐 횟수 | 채택할 때마다 1씩 늘린다. 뒤 화면이 이것을 보고 다시 읽는다(4.11) |

**실행 종류의 등록**: 실행 종류마다 다른 것은 "입력을 어떻게 받는가"뿐이다. 종류 하나를 아래 표의 한 줄로 등록하고, 창은 이 표만 보고 그린다. 서버가 화면이 모르는 종류를 주면 그리지 않는다.

| `skill` | 입력을 받는 방법 | 보내는 `input` |
| --- | --- | --- |
| `PLAN_FROM_BRIEF` | 긴 글 입력 칸(1~20000자) | `{ "briefText": "…" }` |
| `BREAK_DOWN_TASKS` | 제출물 고르기. 화면의 버튼에서 왔으면 이미 정해져 있다 | `{ "deliverableId": "…" }` |
| `STATUS_BRIEF` | 없음. 누르면 바로 시작 | `{}` |
| `ASK` | 창 아래의 입력 칸(1~1000자) | `{ "question": "…" }` |

카드 종류(`kind`)도 같다. `DELIVERABLE_PLAN`과 `TASKS`의 보기·고치기 모양을 종류별로 등록하고, 모르는 종류는 제목과 근거만 보여 주며 수정·채택 버튼을 두지 않는다(거절은 된다).

## 4. 흐름

경로는 모두 `/api/projects/{projectId}/agent` 아래다.

### 4.1 상태 조회와 창 열기

| 언제 | 하는 일 |
| --- | --- |
| 프로젝트 화면에 들어올 때 | `GET /status`. 같은 프로젝트에서 30초 안에 다시 부르지 않는다 |
| 창을 열 때, 실행이 끝났을 때, 채택·거절한 뒤 | `GET /status`를 다시 부른다(대기 카드 수와 단계가 바뀐다) |

| 상태 | 여는 버튼 | 창 |
| --- | --- | --- |
| `available: true` | 보임 | 전부 |
| `available: false`, 대기 카드 있음 | 보임 | "제안" 탭만. "도우미" 탭에는 `unavailableReason`을 한 줄로 보인다 |
| `available: false`, 대기 카드 없음 | 감춤 | 없음 |
| `GET /status` 실패 | 감춤 | 없음. 오류를 띄우지 않는다 |

이미 만들어진 카드는 AI가 꺼진 뒤에도 채택할 수 있어야 한다. 그래서 대기 카드가 있으면 창을 열 수 있게 했다. K-30 9장도 0.5에서 이렇게 고쳤다.

### 4.2 실행 공통

1. **시작**: 저장소의 `run(projectId, skill, input)`을 부른다. 실행 기록 한 줄이 "진행 중"으로 생기고 `POST /runs`가 나간다
2. **진행 중**: 실행을 시작하는 모든 버튼과 입력 칸을 끈다. 한 사람이 한 프로젝트에서 한 번에 하나만 실행할 수 있다(서버는 409). 지난 시간을 초로 보인다
3. **`step`**: 올 때마다 `label`을 한 줄 더한다. 같은 말이 여러 번 올 수 있다. 끝나면 줄들을 접어 "기록 n가지를 살펴봤습니다"로 남기고 누르면 펼친다
4. **`text`**: 올 때마다 이어 붙여 6.6대로 그린다. 위에 "AI 답변" 표시를 둔다
5. **`proposal`**: 카드를 저장소에 넣고 실행 기록에 붙인다
6. **`done`**: "진행 중"을 끈다. 카드가 없고 글만 있는 것이 정상인 경우가 있다(안내문에서 제출물을 찾지 못함, 만들 업무가 없음)
7. **`error`**: `detail`을 그 실행 기록 안에 붉은 한 줄로 보이고 "다시 시도" 버튼을 둔다. 그때까지 온 단계·글·카드는 지우지 않는다. 카드는 서버에 저장된 것이다
8. 끝나면(성공·실패 모두) `GET /status`를 다시 부른다

**취소는 없다.** 서버는 화면이 연결을 끊어도 실행을 끝까지 한다. 그래서 "취소" 버튼을 두지 않는다. 대신 진행 중에 "창을 닫거나 다른 화면으로 가도 계속 진행됩니다"를 보인다.

스트림이 시작되기 전의 실패는 HTTP 오류로 온다. 실행 기록을 "실패"로 바꾸고 `detail`을 보인다(5.2).

### 4.3 과제 안내문으로 계획 만들기 (`PLAN_FROM_BRIEF`)

1. 버튼을 누르면 창에 입력 칸이 열린다. 여러 줄, 20000자까지, 지금 글자 수를 보인다
2. 안내: "과제 안내문을 그대로 붙여 넣으세요. 원문은 저장하지 않습니다"
3. "계획 만들기"를 누르면 실행한다. 빈 글이면 버튼을 끈다
4. 결과: 제출물마다 `DELIVERABLE_PLAN` 카드가 한 장씩 온다. 안내문에 제출물이 둘이면 카드도 둘이다
5. 안내문에 날짜가 없는 제출물은 카드의 기한이 `null`이다. 그 카드는 채택이 막혀 있고 "기한을 채워야 채택할 수 있습니다"가 보인다(4.7)
6. 제출물이 이미 있는 프로젝트에서도 쓸 수 있다. 과제가 추가됐을 때다. 같은 안내문을 두 번 넣으면 같은 제출물의 카드가 또 생길 수 있으므로, 이미 있는 제출물과 제목이 같은 카드에는 "같은 제목의 제출물이 이미 있습니다"를 보인다(막지는 않는다)

### 4.4 요구사항을 업무로 나누기 (`BREAK_DOWN_TASKS`)

1. 제출물 상세나 프로젝트 홈의 버튼에서 오면 제출물이 정해져 있으므로 바로 실행한다
2. 창의 "할 수 있는 일"에서 오면 제출물을 고르게 한다. 목록은 `stages`(제목, 기한)를 쓴다. `stage`가 `NO_REQUIREMENT`인 제출물은 고를 수 없게 하고 "요구사항이 없습니다"를 붙인다
3. 결과: `TASKS` 카드 한 장. 업무마다 제목, 완료 기준, 기한, 연결할 요구사항이 있다
4. 만들 업무가 없으면 카드 없이 글만 온다

### 4.5 지금 상태 살펴보기 (`STATUS_BRIEF`)

1. 입력 없이 바로 실행한다
2. 결과: 끝난 일, 진행 중인 일, 늦은 일, 위험을 요약한 글. 글 안의 업무와 제출물 이름은 링크일 수 있다
3. 다음 할 일이 있으면 `TASKS` 카드가 함께 온다. 관찰자에게는 글만 온다

### 4.6 물어보기 (`ASK`)

1. 창 아래의 입력 칸. 1000자까지. Enter로 보내고 Shift+Enter로 줄을 바꾼다
2. 실행 기록의 제목 자리에 질문을 그대로 보인다
3. 결과는 글이다. 기록에 없는 것을 물으면 없다고 답한다
4. 처음 쓰는 사람을 위해 실행 기록이 비어 있을 때 예시 질문 세 개를 누를 수 있게 둔다(7장). 누르면 입력 칸에 들어가고, 보내는 것은 사람이 한다

### 4.7 제안 카드

카드는 접힌 모양, 펼친 모양, 고치는 모양 세 가지다.

**접힌 모양** (목록과 실행 기록 안)

```text
[제출물 계획] 중간 보고서 계획                       대기
요구사항 4 · 업무 4 · 기한 10월 18일   송승준 · 5분 전
```

**펼친 모양**

```text
[제출물 계획] 중간 보고서 계획          AI 제안 · 사람이 고침
근거  안내문의 "10월 18일까지 중간 보고서 제출"과 평가 항목 …

제출물   중간 보고서
기한     2026-10-18
제출     학교 LMS 과제함
설명     문제 정의와 설계까지

요구사항 4
  [필수] 문제 정의와 대상 사용자를 적는다
  [선택] 분량은 10쪽 안팎
업무 4
  문제 정의 초안 작성 · 10월 13일
    완료 기준: 대상 사용자와 문제를 한 쪽으로 정리
    요구사항: 문제 정의와 대상 사용자를 적는다

[ 채택 — 제출물 1 · 요구사항 4 · 업무 4 만들기 ]  [ 고치기 ]  [ 거절 ]
담당자는 만든 뒤 업무 보드에서 정합니다.
```

| 칸 | 값 |
| --- | --- |
| 종류 | `DELIVERABLE_PLAN`은 "제출물 계획", `TASKS`는 "업무" |
| 표시 | 늘 "AI 제안". `edited`가 `true`면 "사람이 고침"을 더한다 |
| 근거 | `rationale` |
| 요청한 사람과 시각 | `requestedBy.name`, `createdAt` |
| `TASKS`의 제출물 | `content.deliverableId`로 제출물 목록에서 제목을 찾는다. 없으면 "제출물 연결 없음", 찾지 못하면 "삭제된 제출물" |
| `TASKS`의 요구사항 | `tasks[].requirementId`로 그 제출물의 요구사항에서 내용을 찾는다 |
| `DELIVERABLE_PLAN`의 요구사항 | `tasks[].requirementKey`로 같은 카드의 `requirements[].key`에서 찾는다. `key`는 화면에 보이지 않는다 |

**채워야 할 칸**

- `DELIVERABLE_PLAN`의 `deliverable.dueDate`가 `null`이면 채택 버튼을 끄고 "기한을 채워야 채택할 수 있습니다"를 보인다. "고치기"를 누르면 기한 칸에 초점이 간다
- 값에 "[작성 필요"가 들어 있는 칸은 눈에 띄게 표시하고, 버튼 위에 "채워야 할 칸이 n개 남았습니다"를 보인다. 채택은 막지 않는다(서버도 막지 않는다)

**고치기**

- 입력 칸은 지금의 제출물 입력(`DeliverableFormModal`)과 업무 입력(`TaskModal`)의 칸과 같은 이름, 같은 길이 제한을 쓴다

| 종류 | 칸 | 규칙 |
| --- | --- | --- |
| 제출물 계획 | 제출물 제목 | 필수, 255자 |
| | 기한 | 날짜. 비워도 저장은 된다. 채택에는 있어야 한다 |
| | 제출 방법 | 500자 |
| | 설명 | 5000자 |
| | 요구사항(줄 더하기·지우기) | 내용 필수 1000자, 필수 여부 |
| | 업무(줄 더하기·지우기) | 제목 필수 255자, 완료 기준 2000자, 기한(선택), 연결할 요구사항(없음 또는 이 카드의 요구사항) |
| 업무 | 제출물 | 고치지 않는다. 제목만 보인다 |
| | 업무(줄 더하기·지우기) | 위와 같다. 연결할 요구사항은 그 제출물의 요구사항에서 고른다. 업무는 한 줄 이상 남아야 한다 |

- 요구사항 줄을 새로 더하면 화면이 `key`를 만든다. 카드 안에서 겹치지 않으면 된다(예: `n1`, `n2`)
- 요구사항 줄을 지우면 그 `key`를 가리키던 업무의 `requirementKey`를 `null`로 바꿔 보낸다. 그대로 두면 서버가 400으로 거절한다
- "저장"은 `PUT /proposals/{id}`에 `{ "content": { … } }`를 보낸다. **보낸 내용이 통째로 대신한다.** 고치지 않은 칸도 모두 보낸다. 응답의 카드로 화면을 바꾸고 펼친 모양으로 돌아간다
- 고치는 모양에는 채택 버튼이 없다. 저장한 뒤 펼친 모양에서 채택한다. 화면에 보이는 내용과 만들어지는 내용이 늘 같게 하려는 것이다
- 저장하지 않고 닫으려 하면 묻는다(업무 창과 같은 방식)
- 400이면 `detail`에서 칸을 찾아 그 칸 아래에 이유를 보인다(6.5). 찾지 못한 것은 폼 위에 모아 보인다

**채택**

1. `POST /proposals/{id}/accept`. 버튼을 끄고 기다린다
2. 200이면 응답의 카드(`status: "ACCEPTED"`, `results`)로 바꾼다. 카드는 아래 모양이 된다

```text
[제출물 계획] 중간 보고서 계획                  채택됨 · 송승준 · 방금
[ 제출물 열기 ]  [ 업무 4개 보기 ]
담당자는 업무 보드에서 정하세요.
```

| 카드 | 링크 |
| --- | --- |
| 제출물 계획 | "제출물 열기" → `/projects/{projectId}/deliverables/{results.deliverableId}`, "업무 n개 보기" → `/projects/{projectId}/board?deliverable={results.deliverableId}` |
| 업무, 제출물 있음 | "업무 n개 보기" → `/projects/{projectId}/board?deliverable={content.deliverableId}` |
| 업무, 제출물 없음 | "업무 보드 열기" → `/projects/{projectId}/board` |
| 업무가 하나뿐일 때 | "업무 열기" → `/projects/{projectId}/board?task={taskIds[0]}` |

3. 저장소의 "기록이 바뀐 횟수"를 올리고(4.11) `GET /status`와 `GET /origins`를 다시 부른다
4. 400이면 카드를 그대로 두고 고치는 모양으로 열어 칸을 표시한다. 아무것도 만들어지지 않은 것이다
5. 다른 사람이 먼저 채택했으면 200으로 그 카드가 온다. 그대로 채택됨으로 보인다

**거절**

1. 되돌릴 수 없으므로 한 번 묻는다. 카드 안에서 "이 제안을 거절할까요? 되돌릴 수 없습니다 [거절] [취소]"
2. `POST /proposals/{id}/reject`. 200이면 "거절됨 · 이름 · 시각"으로 바꾼다. 지우지 않는다
3. 409("이미 결정된 제안입니다")면 `GET /proposals/{id}`로 다시 받아 지금 상태로 바꾼다

### 4.8 "제안" 탭

- 탭 이름 옆의 숫자는 `pendingProposalCount`
- 걸러 보기 셋: 대기(처음), 채택됨, 거절됨. 각각 `GET /proposals?status=PENDING` · `ACCEPTED` · `REJECTED`
- 최신이 먼저 오고 50건까지다. 50건이면 아래에 "최근 50건만 보입니다"를 둔다
- 카드는 접힌 모양으로 나열하고 누르면 펼친다
- 프로젝트 전체의 카드다. 다른 사람이 요청한 카드도 보이고, 팀장·팀원은 누구의 카드든 고치고 결정할 수 있다
- 비어 있을 때: "기다리는 제안이 없습니다. 도우미에게 계획이나 다음 할 일을 물어보세요"
- 탭을 열 때마다 다시 부른다. 따로 주기적으로 부르지 않는다

### 4.9 화면마다의 버튼

모두 같은 동작이다. 저장소의 `openWith(skill, input)`을 불러 창을 열고 실행을 시작한다. 입력이 필요한 종류는 입력 칸을 연 채로 기다린다. 버튼은 `available`이 `true`이고 그 실행의 `allowed`가 `true`일 때만 그린다.

| 화면 | 자리 | 조건 | 버튼 | 실행 |
| --- | --- | --- | --- | --- |
| 프로젝트 홈 | "다음 할 일" 카드(`NextStepCard`) 안, 기존 링크 옆 | 제출물이 없다 | 과제 안내문으로 계획 만들기 | `PLAN_FROM_BRIEF` |
| | | 카드가 보여 주는 제출물의 `stage`가 `NO_TASK`·`UNCOVERED_REQUIREMENT`. `stages`에서 순서가 아니라 `deliverableId`로 찾는다 | 요구사항을 업무로 나누기 | `BREAK_DOWN_TASKS`, 그 제출물 |
| | | `stage`가 `TASKS_IN_PROGRESS` | 지금 상태 살펴보기 | `STATUS_BRIEF` |
| 제출물 목록 | 빈 상태의 "제출물 등록하기" 옆 | 제출물이 없다 | 과제 안내문으로 계획 만들기 | `PLAN_FROM_BRIEF` |
| | 목록 위 "제출물 추가" 옆 | 늘 | 과제 안내문으로 계획 만들기 | `PLAN_FROM_BRIEF` |
| 제출물 상세 | "요구사항·업무" 탭의 "연결 업무" 제목 옆 | 요구사항이 하나 이상이고 제출물이 확정 전(#104가 더하는 `status`가 `CONFIRMED`·`SUBMITTED`가 아님) | 요구사항을 업무로 나누기 | `BREAK_DOWN_TASKS`, 이 제출물 |
| 업무 보드 | 보드 위 도구 줄 | 늘 | 지금 상태 살펴보기 | `STATUS_BRIEF` |

- 도우미 창의 "지금 단계에 맞는 도움"도 프로젝트 홈과 같은 규칙을 쓴다. 규칙은 한 곳(예: `lib/agent/suggest.ts`)에 두고 둘이 같이 쓴다
- `stage`가 `NO_REQUIREMENT`, `UNCHECKED_REQUIREMENT`, `READY_FOR_REVIEW`이거나 화면이 모르는 값이면 버튼을 그리지 않는다. 요구사항만 만들어 주는 실행은 서버에 없다(11장)
- "다음 할 일" 카드의 문구와 기존 링크는 그대로 둔다. 버튼만 더한다. 카드가 단계를 화면에서 계산하던 것을 `stages`로 바꾸는 일은 이 작업과 따로 해도 된다
- AI 버튼은 기존 버튼보다 덜 눈에 띄게 한다(테두리만 있는 버튼). 기존 방법이 먼저이고 AI는 돕는 길이다

### 4.10 "AI 제안" 표시

- 업무 보드, 업무 목록 보기, 제출물 상세, 제출물 목록을 열 때 `GET /origins`를 부른다. 응답은 저장소에 두고 화면들이 같이 쓴다. AI가 꺼져 있어도 온다
- 응답의 `taskIds`·`requirementIds`·`deliverableIds`에 id가 있는 기록에 작은 표시 "AI 제안"을 붙인다
- 뜻은 "AI가 제안했고 사람이 채택해 만들어졌다"이다. 사람이 그 뒤에 고쳤어도 계속 붙는다. 설명 글(`title`)에 "AI가 제안하고 팀원이 채택해 만든 기록입니다"를 둔다
- 실패하면 표시 없이 그린다. 오류를 띄우지 않는다

### 4.11 채택한 뒤 뒤 화면

큰 화면에서는 창 뒤의 화면이 보인다. 제출물 목록을 보면서 계획 카드를 채택하면 목록에 새 제출물이 바로 나와야 한다.

- 저장소의 "기록이 바뀐 횟수"를 프로젝트 홈, 제출물 목록, 제출물 상세, 업무 보드가 읽고, 값이 바뀌면 자기 자료를 다시 부른다. 지금 있는 불러오기 함수의 실행 조건에 이 값을 더하면 된다
- 업무 보드는 주소의 `?task=`와 `?deliverable=`를 처음 한 번만 읽는다(`KanbanBoard`). 보드를 보고 있을 때 창의 링크를 누르면 주소만 바뀌고 반응하지 않는다. 주소 인자를 `useSearchParams`로 읽게 바꿔야 한다

### 5.3 가장자리 상황

| 상황 | 동작 |
| --- | --- |
| 실행 중에 창을 닫음 | 저장소가 계속 읽는다. 다시 열면 이어서 보인다. 여는 버튼에 진행 중 표시를 둔다 |
| 실행 중에 다른 화면으로 감 | 같다 |
| 실행 중에 새로 고침 | 화면은 실행을 잃는다. 서버는 끝까지 가고 카드는 "제안" 탭에 생긴다. 2분 안에 다시 실행하면 409가 올 수 있다 |
| 실행 중에 다른 프로젝트로 감 | 실행은 처음 프로젝트의 기록에 계속 쌓인다. 창은 지금 프로젝트의 기록을 보인다 |

| 같은 카드를 두 사람이 고침 | 나중에 저장한 것이 남는다. 서버에 충돌 검사가 없다(11장) |
| 채택으로 만든 기록을 누가 지움 | 카드의 링크가 가리키는 것이 없다. 제출물 목록에 그 id가 없으면 링크 대신 "삭제됨"을 보인다 |
| 카드가 50건을 넘음 | 오래된 것은 목록에 나오지 않는다 |
| 서버가 모르는 `stage`·`skill`·`kind`를 줌 | 그리지 않거나 읽기 전용으로 보인다(3.4). 오류로 다루지 않는다 |
| 시각이 `…Z`로도 `…+09:00`로도 옴 | 같은 순간이다. `new Date(...)`로 읽는다. 문자열을 잘라 쓰지 않는다 |

## 6. 자료와 코드

코드는 제안이다. 이 장의 코드 블록을 그대로 뽑아 화면 프로젝트의 타입 검사에 넣었고 오류가 없었다. 6.3·6.5·6.6의 함수는 가짜 응답으로 돌려 확인했다: 스트림을 통째로·7글자씩·한 글자씩 넣어 같은 결과, 시작 전 오류(409), 끝 이벤트 없이 끊김, 401 뒤 갱신하고 다시 보내기. 브라우저와 실제 서버로는 아직 돌리지 않았다.

### 6.3 실행 스트림

`EventSource`는 POST를 보내지 못하므로 `fetch`로 읽는다. 서버는 `event:step`처럼 콜론 뒤에 공백 없이 보내고, 표준은 공백이 있어도 같게 읽으므로 둘 다 받는다. 첫 줄 `:start`는 건너뛴다.

```ts
// lib/agent/run.ts
import api from "@/lib/api";
import type { AgentEvent } from "@/types/agent";

/** 스트림이 시작되기 전의 실패, 또는 끝 이벤트 없이 끊긴 것(status 0) */
export class AgentRunError extends Error {
  constructor(public status: number, detail: string) { super(detail); }
}

// 서버의 실행 시간 상한(120초)보다 조금 길게 기다린다
const GIVE_UP_MS = 130_000;

/** 받은 글 덩어리에서 이벤트를 하나씩 꺼낸다. 덩어리가 어디서 잘려 와도 된다 */
export function createEventParser(on: (e: AgentEvent) => void) {
  let buffer = "";
  return (chunk: string) => {
    buffer += chunk;
    let end: number;
    while ((end = buffer.indexOf("\n\n")) >= 0) {      // 이벤트 하나는 빈 줄로 끝난다
      const block = buffer.slice(0, end);
      buffer = buffer.slice(end + 2);
      let event = "", data = "";
      for (const line of block.split("\n")) {
        if (line.startsWith("event:")) event = line.slice(6).trim();
        else if (line.startsWith("data:")) data += line.slice(5).trim();
      }
      if (event) on({ event, data: JSON.parse(data) } as AgentEvent);
    }
  };
}

export async function runAgent(projectId: string, skill: string, input: object, on: (e: AgentEvent) => void) {
  const giveUp = new AbortController();
  const timer = setTimeout(() => giveUp.abort(), GIVE_UP_MS);
  const send = () => fetch(`/api/projects/${projectId}/agent/runs`, {
    method: "POST",
    credentials: "include",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ skill, input }),
    signal: giveUp.signal,
  });
  try {
    let res = await send();
    if (res.status === 401) {                           // fetch는 공용 클라이언트의 자동 갱신을 타지 않는다
      await api.post("/auth/refresh");
      res = await send();
    }
    if (!res.ok) {
      const problem = await res.json().catch(() => ({}));
      throw new AgentRunError(res.status, problem.detail ?? "요청을 처리할 수 없습니다");
    }
    let ended = false;
    const feed = createEventParser((e) => {
      if (e.event === "done" || e.event === "error") ended = true;
      on(e);
    });
    const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
    for (;;) {
      const { value, done } = await reader.read();
      if (done) break;
      feed(value);
    }
    if (!ended) throw new AgentRunError(0, "연결이 끊겼습니다. 만들어진 제안은 제안 탭에 있습니다");
  } catch (e) {
    if (giveUp.signal.aborted) throw new AgentRunError(0, "응답이 오지 않습니다. 잠시 뒤 다시 시도해주세요");
    throw e;
  } finally {
    clearTimeout(timer);
  }
}
```

### 6.5 400의 `detail`에서 칸 찾기

카드의 수정·채택이 400이면 `detail`의 괄호 안에 `경로: 이유`가 쉼표로 이어져 온다. 이유의 말은 브라우저의 언어를 따른다.

```text
제안의 내용을 확인해주세요 (deliverable.dueDate: must not be null)
제안의 내용을 확인해주세요 (deliverable.title: 공백일 수 없습니다, tasks[1].title: 크기가 0에서 255 사이여야 합니다)
```

```ts
/** { "deliverable.dueDate": "must not be null", "tasks[1].title": "…" }. 괄호가 없으면 빈 객체 */
export function fieldProblems(detail: string): Record<string, string> {
  const inside = detail.match(/\((.*)\)\s*$/)?.[1];
  if (!inside) return {};
  const out: Record<string, string> = {};
  for (const part of inside.split(/,\s*(?=[A-Za-z][\w.\[\]]*:)/)) {
    const at = part.indexOf(":");
    if (at > 0) out[part.slice(0, at).trim()] = part.slice(at + 1).trim();
  }
  return out;
}
```

경로는 `deliverable.title`, `deliverable.dueDate`, `requirements[0].content`, `requirements[0].key`, `tasks[1].title`, `tasks[1].requirementKey`, `tasks[1].requirementId`, `deliverableId`, `tasks` 같은 모양이다. 입력 칸에 같은 이름을 붙여 두면 바로 찾는다.

### 6.6 답의 글 그리기

글에 쓰이는 표기는 줄바꿈, 줄 맨 앞의 `- `(목록), 링크 `[이름](경로)` 세 가지뿐이다. 모델이 다른 표기(굵게, 제목)를 쓰면 글자 그대로 보이게 둔다.

```ts
export type AnswerPart = string | { label: string; href: string };
export interface AnswerLine { bullet: boolean; parts: AnswerPart[] }

/** 줄마다 목록인지와 조각(글자 또는 링크)을 돌려준다. 이 프로젝트의 화면 경로가 아니면 링크로 만들지 않는다 */
export function parseAnswer(text: string, projectId: string): AnswerLine[] {
  const inApp = `/projects/${projectId}/`;
  return text.split("\n").map((raw) => {
    const bullet = raw.startsWith("- ");
    const line = bullet ? raw.slice(2) : raw;
    const parts: AnswerPart[] = [];
    let last = 0;
    for (const m of line.matchAll(/\[([^\]]+)\]\(([^)\s]+)\)/g)) {
      if (m.index! > last) parts.push(line.slice(last, m.index));
      parts.push(m[2].startsWith(inApp) ? { label: m[1], href: m[2] } : m[1]);
      last = m.index! + m[0].length;
    }
    if (last < line.length) parts.push(line.slice(last));
    return { bullet, parts };
  });
}
```

- 조각이 글자면 글자로, 링크면 `next/link`로 그린다. `dangerouslySetInnerHTML`을 쓰지 않는다
- 서버가 쓰는 경로는 세 가지다: `/projects/{projectId}/deliverables/{id}`, `/projects/{projectId}/board?task={id}`, `/projects/{projectId}/board`

## 8. 접근성과 작은 화면

- 창을 열면 초점이 창 안으로 간다. 닫으면 여는 버튼으로 돌아온다
- 큰 화면의 창은 옆 칸이라 초점을 가두지 않는다. 작은 화면의 전체 화면 창은 업무 창처럼 가둔다
- 단계와 답이 더해지는 구역은 `aria-live="polite"`다. 오류는 `role="alert"`다
- 진행 중 표시는 색만으로 알리지 않는다. 글자가 있다
- 카드의 상태와 "AI 제안" 표시는 글자다. 아이콘만 두지 않는다
- 채택·거절·저장 버튼은 요청 중에 꺼지고, 끝나면 초점이 결과(채택됨 줄이나 오류)로 간다
- 작은 화면에서 고치는 모양의 줄 더하기·지우기 버튼은 44px 이상이다
- 밝은 테마와 어두운 테마 모두 지금의 색 이름(`bb-surface`, `bb-border`, `bb-text2` 등)만 쓴다

| 카드 목록의 페이지 | 50건을 넘으면 오래된 것이 안 보인다 | 페이지를 더한다 |
| 파일로 안내문 넣기 | 글로 붙여 넣어야 한다 | 파일 금고의 파일을 고르는 입력을 더한다 |

## 12. 정하지 않은 것

- 검토·확정 단계의 실행 종류(피드백을 업무로, 확정이 막힌 이유). 서버에 생기면 3.4의 표에 한 줄씩 더하고, 검토 탭과 최종 제출 탭에 버튼을 둔다
- 스스로 살펴서 보내는 주간 요약과 마감 임박 알림. 알림 화면과 함께 정한다
- 대화 이어가기. 지금은 질문마다 따로다
- 모델로 나가는 내용에 대한 동의 절차. 지금은 안내만 둔다
- "다음 할 일" 카드가 단계를 `stages`로 읽게 바꾸는 시점
