## 문제와 수정

검토 발송 전 판정이 A 생산자의 `REVIEW_REQUESTED:{reviewId}`를 다시 조립해 비교하고 있었다. 생산자 형식이 바뀌면 유효한 요청도 조용히 제외될 수 있고, fixture도 같은 형식을 조립해 초기 검사로는 이를 잡기 어려운 구조였다. 운영에서 누락을 관측한 사고는 아니다.

업무 요청은 같은 task의 여러 요청을 시각으로 구분하지만, 검토는 회차 자체가 고유 id다. ReviewRoundReader.get에 전달한 reviewId와 latest·미결정 상태가 같은 요청인지 이미 구분하므로 키 문자열 비교를 제거했다. A 조회가 보장한 프로젝트/제출물 관계의 중복 비교도 제거했다. 현재 멤버·행위자·연 사람·파일 업로더 판정은 유지한다. 저장 시 event_key와 중복 제약은 그대로이며 접근 권한 검사를 제거한 것이 아니다.

잘못된 키를 거절하던 assertion은 도메인 규칙에 맞춰 제거하고, 생산자 키 형식이 달라도 유효한 검토가 허용되는 검사로 대체했다. 실제 ReviewRoundService.open이 DB에 저장한 알림을 재조립 없이 guard에 넘기는 검사도 추가했다. fixture는 키 규약을 복제하지 않는 불투명 합성 값만 사용한다.
