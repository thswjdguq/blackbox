# 송승준 · K-11 피드백 반영 확인 권한 변경 제안 (A → B)

- 대상: K-11 피드백·반영 확인 계약 (작성 예정 · 손정협(B))
- 제안자: 송승준(A, 검토 회차 K-10·확정 K-20 담당)
- 날짜: 2026-09-28 · 기준 SHA: `1488f69`
- 결론: **피드백 해결은 누구나 하고 다시 열 수 있게, 관문은 검토자의 다음 회차 승인으로 옮기자.** CONTRACTS §3-3·§3-6·§3-8을 같은 PR에서 고쳤다. B가 동의하면 K-11을 이 기준으로 쓰면 된다.

## 1. 무엇을 바꾸자는가

| 항목 | 지금 CONTRACTS | 제안 |
| --- | --- | --- |
| 반영 확인 주체 | 검토자가 반영 확인 (§3-6) | 관찰자를 뺀 팀장·팀원 누구나 해결 처리, 다시 열기 가능 |
| 반영 확인의 의미 | 관문 | 관문 아님. 목록 정리용 표시 |
| 관문 | (§3-8 "최종 검토 결과"로 모호) | 최종 파일 버전에 대한 **검토자의 승인** (K-10) |
| 검토 결정 | 정해지지 않음 | 회차마다 `승인` / `수정 요청`. 업로더는 자기 버전 승인 불가 |
| 새 파일 버전 | 정해지지 않음 | 이전 승인은 이어지지 않고 새 회차 필요 |

## 2. 왜 바꾸자는가

기존 PMS의 공통 방식을 따랐다.

- **GitHub PR**: 코멘트 해결은 코멘트 작성자가 아니라 PR 작성자나 쓰기 권한자가 한다. 병합 가능 여부는 해결 표시가 아니라 리뷰어 승인으로 정한다. 자기 PR은 승인할 수 없고, 새 커밋이 올라오면 기존 승인을 무효로 하는 설정이 있다.
- **Google Docs**: 접근 권한이 있으면 댓글을 해결할 수 있고 다시 열 수 있다.
- **Asana·Wrike**: 지정된 검토자가 승인·수정 요청·반려를 명시적으로 결정한다.

우리 팀 규모에서 보면 이렇다.

- **"검토자만 반영 확인"은 2~4명 팀에서 병목이 된다.** 피드백을 쓴 사람이 바쁘면 수정이 끝나도 목록이 계속 미해결로 남는다.
- **대신 자기 승인은 막아야 한다.** 해결 표시는 누구나 할 수 있어도, 다음 회차에서 업로더가 아닌 사람이 승인해야 확정으로 넘어간다.
- **검토자 지정은 선택으로 둔다.** 대형 팀 도구처럼 지정을 필수로 하면 사람을 고르는 단계에서 흐름이 멈춘다.

## 3. K-11에 담아 달라는 것

1. 해결·다시 열기 권한: 팀장·팀원(`requireContributor`). 관찰자는 403이 아니라 화면에서 비활성으로 보이게 한다(K-14 §6-5와 같은 방식).
2. 해결자와 해결 시각을 저장한다. 다시 열면 둘 다 지우는지, 이력으로 남기는지 정한다.
3. 상태: `열림 → 반영 확인 대기(연결 업무 DONE) → 해결`. 업무 DONE이 자동으로 `해결`을 만들지 않는다(§3-6 유지).
4. **미해결 피드백 개수 읽기 메서드**를 A에게 제공한다. K-20 확정 검사가 이것만 호출한다(§3-12). 기본안은 다음과 같다.

```java
@Transactional(readOnly = true)
public long countUnresolvedComments(Deliverable deliverable)
```

5. `CONFIRMED` 이후 코멘트 작성·해결·다시 열기를 막는 범위(§3-8). A의 K-20과 맞춘다.

## 4. A가 K-10·K-20에서 맡는 것

- 검토 회차의 `승인` / `수정 요청` 결정, 업로더의 자기 승인 거절, 새 파일 버전 이후 새 회차 요구.
- 확정 검사: 필수 요구사항 충족(K-14) + 최종 파일 버전의 승인된 회차(K-10) + 미해결 피드백 0건(K-11).

## 5. B에게 부탁하는 것

1. 이 방향에 동의하는지, 또는 반대 의견을 이 PR에 달아 달라.
2. 동의하면 K-11 초안을 위 §3 기준으로 쓴다. 메서드 이름과 시그니처는 B가 정하면 A가 맞춘다.
3. 반대하면 CONTRACTS 변경을 되돌리고, 다음 월요일 회의에서 같이 정한다.
