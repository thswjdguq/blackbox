# Team Blackbox 고도화 기획안 v2
## 대학 수업의 공동 결과물을 반복 검토하고 제출까지 완수하는 팀 프로젝트 PMS

작성일: 2026-09-14

이 문서는 기존 코드 분석을 바탕으로 제품의 사용자, 핵심 문제, 동작 규칙과 구현 범위를 구체화한 개발 기획이다. 신규 기능은 제안이며 사용자 수요와 개선 효과는 아직 검증되지 않았다. 기존 v1의 진단은 유지하되, 제품 방향과 우선순위는 본 문서를 기준으로 한다.

## 1. 제품 정의

**Team Blackbox는 한 학기 수업에서 공동 보고서·발표자료·작품을 제출하는 3~6인 대학생 팀이, 제출 조건을 업무로 나누고 작업 중간부터 서로 검토하며 최종 제출본을 확정하도록 돕는 PMS다.**

핵심 약속은 하나다.

> “교수님이 요구한 결과물을 기준으로, 지금 누가 무엇을 해야 하고 무엇을 고쳐야 하며 무엇이 제출 준비를 마쳤는지 알 수 있다.”

제품의 중심 단위는 **제출물**이다. 업무, 회의, 피드백, 버전은 각각 어떤 제출물을 완성하는 데 필요한 기록인지 연결한다.

예: ‘최종 보고서’라는 제출물 아래에 자료조사·인터뷰 분석·본문 작성·참고문헌 확인 업무가 있고, 각 업무의 중간 결과와 피드백이 모인다. 팀장은 마지막에 승인된 내용으로 만든 통합 보고서 버전을 별도로 검토하고 제출본으로 확정한다.

## 2. 확실한 사용자층

### 2.1 첫 사용자

다음 조건을 갖춘 **수업 과제형 팀 프로젝트**를 첫 대상으로 한다.

- 3~6명이 수 주에서 한 학기 동안 함께 수행한다.
- 보고서, 발표자료, 디자인 시안, 영상, 소프트웨어 시연 자료 등 공동 결과물을 제출한다.
- 제출 기한과 요구사항이 있으며, 작업을 나눠 맡은 뒤 합쳐야 한다.
- 초안 공유, 팀원 검토 또는 교수 피드백에 따른 수정이 발생한다.
- 전문 프로젝트 관리 경험이 적어 복잡한 설정 없이 사용할 수 있어야 한다.

‘모든 대학생’이 아니라 **분업한 결과를 합쳐 수업에 제출하는 팀**을 대상으로 한다. 초기에는 개인 과제, 장기 연구실 운영, 기업 프로젝트, 동아리 전체 운영을 지원 범위에 넣지 않는다.

### 2.2 핵심 역할

| 역할 | 가장 필요한 것 | 사용하는 순간 | 주요 행동 |
|---|---|---|---|
| 팀장·제출 담당자 | 제출일까지 빠진 내용 없이 결과를 모으기 | 시작, 주간 확인, 제출 직전 | 제출 조건 입력, 업무 조율, 통합본 검토 요청, 제출 기록 |
| 팀원 | 자신의 작업 범위와 완료 기준을 알기 | 작업 시작, 초안 공유, 수정 | 내 업무 확인, 중간 결과 등록, 의견 요청, 수정 반영 |
| 검토 담당자 | 어떤 버전의 무엇을 확인해야 하는지 알기 | 검토 요청 수신 | 기준별 확인, 보완 요청 또는 승인 |
| 교수자 | 제출물과 피드백 반영 결과를 확인하기 | 중간 지도, 최종 평가 | 기존 수업 채널로 자료 확인; 추후 선택적 열람 기능 |

검토 담당자는 별도 직책이 아니라 업무 또는 제출물마다 지정되는 팀원이다. 팀장에게 모든 검토가 몰리지 않도록 분담한다. 교수자가 계정을 만들거나 매일 접속하지 않아도 학생들의 전체 흐름이 작동해야 한다.

### 2.3 다른 학과도 사용하는 이유

전공별 작업 도구는 다르지만, ‘요구사항 확인 → 분담 → 초안 → 피드백 → 수정 → 통합 → 제출’은 공통으로 적용할 수 있다는 가설이다.

| 과제 예시 | 제출물 | 중간 검토 대상 | 확정 기준 예시 |
|---|---|---|---|
| 경영학 마케팅 과제 | 시장분석 보고서·발표자료 | 조사 근거, 전략 초안 | 조사 출처 포함, 전략 근거 확인, 분량 충족 |
| 디자인 과제 | 최종 시안·작품 설명서 | 스케치, 시안 v1 | 지정 규격 충족, 피드백 반영, 출력본 확인 |
| 인문사회 조사 과제 | 조사 보고서 | 인터뷰 정리, 분석 초안 | 인용 출처 확인, 질문별 분석, 필수 항목 포함 |
| 소프트웨어 과제 | 실행물·시연 영상·설명서 | 화면 시안, 기능 구현 결과 | 시연 시나리오 통과, 실행 방법 포함 |

이 표는 적용 예시이며 실제 이용 사례가 아니다. 특정 전공의 도구를 내장하는 대신 파일·링크·텍스트 설명을 동일한 제출물 흐름에 연결한다. 영상·실물 작품은 외부 링크나 사진과 설명으로 검토하며 실물 배송 자체를 관리하지 않는다.

## 3. 왜 필요한가

검증할 문제 가설은 다음 세 가지로 제한한다.

1. **분담한 일과 제출 조건이 분리된다.** 각자 작업을 끝냈는데 교수님이 요구한 항목이 빠지거나 통합 담당자가 다시 작업한다.
2. **중간 의견이 수정 작업으로 이어지지 않는다.** 메신저나 구두로 받은 피드백에 담당자·기한·반영 여부가 없어 같은 지적이 반복된다.
3. **마지막 제출본을 확정하는 책임과 근거가 불명확하다.** 파일이 여러 곳에 있고 어느 버전이 검토됐는지 몰라 제출 직전 확인을 반복한다.

제품의 존재 이유는 이 세 문제를 하나의 연결된 기록으로 해결하는 데 있다. 기존 채팅과 문서 편집기는 계속 사용한다. 학생이 작성 도구를 바꾸지 않아도, PMS에서 ‘이 결과가 어떤 제출 조건을 충족하고 어떤 피드백을 반영했는지’ 확인할 수 있어야 한다.

고유성은 기능 개수로 주장하지 않는다. **대학생 팀이 별도 설계 없이 제출물·업무·반복 검토·확정본을 연결해서 사용하는 경험**을 차별화 가설로 두고 실제 과제로 검증한다.

## 4. 제품의 기본 구조

### 4.1 제출물에서 업무로 내려가는 구조

프로젝트 → 제출물 → 요구사항·검토 기준 → 연결 업무 → 결과물 버전 → 검토·수정 기록 → 확정 제출본.

- 프로젝트: 한 수업의 한 팀 과제.
- 제출물: 교수님께 내야 하는 단위. 예: 중간발표 자료, 최종보고서.
- 요구사항: 제출물에 반드시 들어가야 하는 조건. 필수 여부와 사람이 확인할 기준을 기록한다.
- 업무: 해당 제출물을 만들기 위한 작업. 담당자 한 명을 책임자로 두고 공동 작업자를 추가할 수 있다.
- 결과물 버전: 작업 중 또는 통합 과정에서 등록한 파일·링크·설명.
- 검토: 특정 버전과 기준에 대한 의견, 수정 요청, 승인.
- 제출 기록: 확정본, 제출 담당자, 제출 경로, 제출 시각, 확인 근거.

하나의 업무는 첫 버전에서 주 제출물 하나에 연결한다. 복잡한 다대다 관계 대신 다른 제출물에 필요한 경우 참조 링크를 남긴다. 제출 조건에 따라 한 프로젝트에 중간·최종 등 여러 제출물을 둘 수 있다.

### 4.2 두 가지 흐름을 구분한다

**프로젝트 전체 흐름:** 과제 설정 → 준비·수행 → 제출물 통합 → 제출 → 종료.

**수행 중 반복 흐름:** 작업 → 중간 공유 → 의견·수정 → 다시 작업 → 검토 → 보완 또는 승인.

검토는 프로젝트 마지막에만 하는 단계가 아니다. 시작 직후의 계획안, 자료조사 초안, 중간발표 자료, 최종 통합본에서 모두 반복할 수 있다. 프로젝트 단계가 바뀌어도 업무 수정과 검토는 계속 가능하다.

## 5. 실제 사용 흐름과 소프트웨어 동작

### 단계 1. 교수님의 과제 조건을 프로젝트에 옮긴다

**사용자:** 팀장. **시점:** 팀 구성 직후.

과목·과제명, 팀원, 최종 기한을 입력한다. ‘보고서·발표·작품·직접 설정’ 중 시작 양식을 선택한다. 양식은 기본 입력 항목만 제공하며 요구사항은 팀이 과제 안내문에 맞게 수정한다.

제출물마다 이름, 기한, 제출 경로, 필수 파일·형식, 내용 체크리스트, 제출 담당자, 최종 검토자를 기록한다. 과제 안내문은 파일이나 링크로 첨부할 수 있다. 최종 검토자는 다른 팀원으로 지정하는 것을 기본으로 한다.

**다음 행동:** 제출물별 업무 나누기.

**완료 조건:** 제출물 한 개 이상, 제출 기한, 제출 담당자, 필수 기준이 정해짐. 교수자의 LMS 연결이나 외부 서비스 연동은 필요하지 않다.

### 단계 2. 제출 조건을 업무로 나눈다

**사용자:** 팀장과 팀원. **시점:** 첫 회의 또는 계획 수립.

제출물 상세에서 필요한 업무를 만든다. 업무에 ‘무엇을 만들 것인지’, 책임자, 기한, 완료 기준을 입력한다. 중간 검토 예정일과 검토자는 필요하면 추가한다. 계획만 잡힌 업무의 담당자를 비워둘 수 있지만 홈에서 ‘미배정’으로 보여준다.

예: ‘자료조사’ 대신 ‘경쟁 사례 3개를 출처와 비교표로 정리’로 등록한다.

회의 기록에서 결정사항을 업무로 만들 수도 있다. 회의 기능이나 AI를 사용하지 않고 직접 등록해도 같은 구조로 저장된다.

**다음 행동:** 각 팀원의 내 업무 확인.

**완료 조건:** 이번 작업 주기의 필수 업무에 책임자와 기한이 있고, 어느 제출물을 위한 일인지 연결됨.

### 단계 3. 작업 중간부터 공유하고 검토한다

**사용자:** 업무 담당자와 검토자. **시점:** 초안이 생겼거나 방향 확인이 필요할 때.

진행 중인 업무에서 파일·링크·텍스트를 중간 결과로 등록한다. ‘중간 의견 요청’을 누르고 “조사 방향이 맞는지 확인해주세요”처럼 질문과 응답 희망일을 남긴다. 업무는 계속 진행 중이다.

검토자는 특정 버전에 의견을 남긴다. 단순 의견은 댓글로, 반드시 고칠 내용은 ‘수정 항목’으로 등록한다. 수정 항목은 담당자와 기한을 갖는다. 작성자는 반영 버전과 설명을 연결하고, 요청자는 반영 확인으로 닫는다. 반영하지 않기로 하면 이유와 확인자를 남긴다.

**다음 행동:** 수정 반영 또는 작업 지속.

**완료 조건:** 의견 요청이 응답됐고 필수 수정 항목마다 처리 결과가 남음. 이 시점에 업무 전체를 완료할 필요는 없다.

### 단계 4. 업무 완료를 검토한다

**사용자:** 업무 담당자 → 지정 검토자. **시점:** 완료 기준을 충족했다고 판단할 때.

담당자는 결과 버전을 지정해 ‘완료 검토 요청’을 보낸다. 검토자는 기준을 확인하여 승인하거나 보완을 요청한다. 승인 시 업무 완료, 보완 요청 시 진행 중으로 돌아간다. 검토 대상·결과·사유·시각을 남긴다.

새 버전을 올려도 기존 승인이 자동으로 새 버전에 적용되지 않는다. 완료 후 내용이 바뀌면 업무를 다시 열어 새 버전 검토를 받는다.

**다음 행동:** 승인된 업무 결과를 제출물 통합에 사용.

**완료 조건:** 지정 검토자가 대상 버전을 승인하고 필수 수정 항목이 해소됨.

### 단계 5. 중간 제출·교수 피드백을 다시 작업으로 돌린다

**사용자:** 팀장 또는 피드백을 받은 팀원. **시점:** 중간발표, 지도, 수업 피드백 이후.

교수님이 기존 수업 채널에서 준 피드백을 제출물에 기록한다. 작성자는 ‘교수 피드백을 학생이 기록한 내용’으로 표시하고 가능하면 원본 파일·링크를 첨부한다. 교수자가 직접 승인한 것으로 표시하지 않는다.

각 피드백에서 수정 항목 또는 후속 업무를 만든다. 담당자, 기한, 반영 결과를 연결한다. 완료 업무라도 수정이 필요하면 다시 열거나 후속 업무를 만든다.

**다음 행동:** 단계 3~4 반복.

**완료 조건:** 피드백의 반영 여부와 근거, 또는 미반영 합의 이유를 확인할 수 있음.

### 단계 6. 개별 결과를 최종 제출물로 통합하고 다시 검토한다

**사용자:** 제출 담당자와 최종 검토자. **시점:** 제출 기한 전.

승인된 업무 결과를 바탕으로 작성 도구에서 통합본을 만든 후 ‘제출 후보 v1’로 등록한다. PMS가 보고서·영상·디자인 파일을 자동 합성하지는 않는다.

제출물 화면에서 필수 내용 누락, 필수 업무 미완료, 미해결 수정 항목, 파일 형식·파일 수, 최종 검토 여부를 확인한다. 형식·수량은 가능한 범위에서 시스템이 점검하고 내용 품질은 사람이 체크한다.

최종 검토자가 통합본의 목차, 연결성, 형식, 내용 기준을 확인한다. 보완이 있으면 후보 v2를 만들어 재검토한다. **개별 업무가 전부 완료되어도 통합본 승인 전에는 제출 준비 완료가 아니다.**

**다음 행동:** 승인된 통합 버전을 제출본으로 확정.

**완료 조건:** 필수 기준 확인, 필수 수정 해결, 통합본 승인, 제출 파일 선택 완료.

### 단계 7. 교수님께 제출하고 기록한다

**사용자:** 제출 담당자. **시점:** 제출본 확정 후.

PMS에서 확정 파일과 제출 목록을 다운로드한다. 제출 담당자가 학교 LMS·이메일 등 지정 경로로 직접 제출한다. 이후 제출 경로, 시각, 제출 파일 버전, 접수 화면이나 확인 링크 등 근거를 기록한다.

다운로드만 했을 때는 ‘제출 준비 완료’이며 ‘제출 기록 완료’로 자동 변경하지 않는다. 외부 접수 여부를 시스템이 확인하지 못했다면 ‘담당자 제출 기록’으로 표시한다. 접수 근거가 있어도 교수자의 평가·승인과 구분한다.

대용량 영상이나 실물 제출은 지정된 외부 경로 및 제출 근거를 기록한다. 파일 패키지에는 링크 목록을 넣을 수 있지만 외부 파일 자체를 보관했다는 의미는 아니다.

**다음 행동:** 남은 제출물이 있으면 수행을 계속하고, 모두 끝났으면 프로젝트 종료 확인.

**완료 조건:** 확정본과 실제 제출 기록이 연결됨.

### 단계 8. 프로젝트를 종료하고 보관한다

모든 필수 제출물에 제출 기록이 있는지 확인한다. 팀장이 종료하면 프로젝트를 읽기 중심으로 보관하고 결과물·검토·변경 기록을 다시 열람할 수 있게 한다.

제출 후 수정 요구가 오면 프로젝트를 재개하고 새 제출 버전을 만든다. 이전 제출 기록을 덮어쓰지 않는다. 중간 제출 완료만으로 전체 프로젝트를 종료하지 않는다.

## 6. 상태와 검토 규칙

### 6.1 업무 상태

`할 일 → 진행 중 → 완료 검토 중 → 완료`

- 중간 의견 요청은 진행 중 상태 안에서 처리한다.
- 완료 검토에서 보완 요청을 받으면 진행 중으로 돌아간다.
- 완료 후 수정은 다시 열기로 처리하고 사유를 기록한다.
- ‘막힘’은 별도 표시로 두고 원인·도움 요청 대상을 기록한다.

### 6.2 제출물 상태

`준비 중 → 통합본 검토 중 → 제출 준비 완료 → 제출 기록 완료`

- 통합본 보완 또는 새 후보 등록 시 검토가 다시 필요하다.
- 제출 후 수정본은 새로운 제출 차수로 기록한다.
- 별도로 프로젝트 상태는 준비·수행·종료로 두어 여러 제출물이 동시에 진행될 수 있게 한다.

### 6.3 검토의 최소 규칙

1. 검토는 대상 업무 또는 제출물과 특정 버전에 연결한다.
2. 댓글, 필수 수정 요청, 승인을 구분한다.
3. 필수 수정은 요청자 또는 지정 대체 검토자가 반영 결과를 확인한다.
4. 승인 대상 버전이 바뀌면 재검토한다. 이전 승인은 이력으로 남긴다.
5. 검토자 교체는 팀장이 사유를 남겨 처리한다. 마지막 제출 검토를 제출 담당자 혼자 승인하지 않도록 한다.
6. 미해결 필수 수정이 있으면 일반 확정을 차단한다. 촉박한 마감 때문에 예외 제출이 필요하면 팀장이 미해결 목록과 사유를 확인해 ‘미해결 항목 포함 제출’로 기록한다. 정상 승인으로 표시하지 않는다.
7. 링크의 내용은 외부에서 바뀔 수 있다. 파일은 업로드 버전으로, 링크는 접근 시점·설명·가능한 버전 식별자로 구분한다. 내용 고정이 필요한 최종 자료는 파일로 첨부한다.

## 7. 사용자가 실제로 보는 화면

메뉴는 **홈 / 제출물 / 내 업무·팀 업무 / 회의·결정 / 기록·보고 / 설정**으로 구성한다.

### 홈: 지금 무엇을 해야 하는가

- 다음 제출물과 마감일.
- 나에게 온 중간 의견·완료 검토 요청.
- 오늘 할 업무와 반영할 수정 항목.
- 제출을 막고 있는 미배정 업무·미해결 수정·통합본 검토 대기.

팀장은 전체 누락을, 팀원은 자기 행동을 먼저 본다. ‘기여도 순위’와 ‘외부 연동 개수’는 홈의 중심에 두지 않는다.

### 제출물 상세: 무엇을 내야 하고 얼마나 준비됐는가

요구사항 체크리스트, 연결 업무, 결과물 버전, 피드백, 통합 후보, 확정본, 제출 기록을 한 화면의 탭으로 묶는다. ‘업무 8/10 완료’와 ‘제출 기준 3/5 확인’을 별도로 표시하여 업무 개수만으로 제출 완성도를 오해하지 않게 한다.

### 업무 상세: 무엇을 만들고 누구의 확인을 받아야 하는가

목적, 연결 제출물, 담당자, 마감일, 완료 기준, 작업 결과, 의견 요청, 수정 항목, 완료 검토, 변경 이력을 보여준다. 작업 중에는 ‘중간 의견 요청’, 결과가 준비되면 ‘완료 검토 요청’을 제공한다.

### 기록·보고: 이미 한 일을 다시 쓰지 않게 한다

기간별 업무·검토·수정 내용을 모아 주간보고 초안을 제공한다. 필수 제출물에 주간보고서가 있다면 해당 제출물로 연결하고 같은 검토·확정 과정을 따른다. 보고서에는 원본 업무와 산출물 출처를 남긴다.

## 8. 기존 프로젝트에서 무엇을 고도화하는가

| 기존 자산 | 고도화 결정 | 사용자에게 생기는 변화 |
|---|---|---|
| 프로젝트 생성 | 과제 제출물·요구사항 설정 추가 | 시작부터 끝내야 할 결과가 명확해짐 |
| 칸반 업무 | 제출물 연결, 완료 기준, 검토 상태 추가 | 업무를 끝냈다는 의미가 명확해짐 |
| 회의록·AI 액션아이템 | 회의 결정과 업무를 ID로 연결 | 회의에서 정한 일의 실행 결과를 확인 |
| Hash Vault | 결과물 버전과 제출본 보관 구조로 확장 | 어느 버전이 검토·제출됐는지 확인 |
| 참여도·경보 | 활동 근거, 지연 업무, 미해결 수정 중심으로 변경 | 사람 평가보다 다음 조치를 찾음 |
| PDF·ZIP | 선택된 확정 버전과 제출 목록 내보내기 | 다른 버전을 잘못 제출할 가능성을 줄임 |
| 외부 연동 | 선택 기능으로 유지 | 연동 설정 없이 첫 과제를 시작 |

제품에서 ‘Hash Vault’는 ‘결과물·버전’처럼 학생이 이해할 수 있는 용어로 바꾼다. 해시는 파일 변경 확인을 위한 내부 기술로 사용한다.

## 9. 핵심 기능 요구사항과 개발 우선순위

### P0 — 시연 및 첫 파일럿에 반드시 필요한 범위

| ID | 기능 | 구현 완료 조건 |
|---|---|---|
| F01 | 제출물·요구사항 설정 | 프로젝트에 복수 제출물, 기한, 제출 담당자, 필수 기준 저장 |
| F02 | 제출물 기반 업무 분담 | 업무에서 제출물 이동, 담당자·기한·완료 기준 확인 |
| F03 | 파일·링크·설명 버전 등록 | 이전 버전을 유지하고 특정 버전 선택 가능 |
| F04 | 중간 의견과 수정 항목 | 진행 중 의견 요청, 담당자 배정, 반영 버전과 확인 기록 |
| F05 | 완료 검토 | 승인·보완·재검토·권한 검사 및 이력 보존 |
| F06 | 통합본 검토와 확정 | 개별 업무 완료와 별개로 제출 후보 검토 및 필수 누락 확인 |
| F07 | 제출·종료 기록 | 다운로드와 제출 구분, 제출 차수 보존, 전체 제출 후 종료 |
| F08 | 행동 중심 홈 | 내 업무·검토 요청·수정 항목·다음 제출물에 직접 이동 |

### P1 — 핵심 흐름이 동작한 뒤 고도화

- 기존 회의·AI 기능을 제출물과 연결하고 생성 전 확인·중복 방지 적용.
- 교수 피드백의 독립 입력 화면. P0에서는 제출물 수정 항목에 출처를 기록해 처리.
- 기간별 주간보고서 초안과 PDF. P0에서는 기존 내보내기를 활용하되 최종 파일 목록을 명확히 구분.
- 알림 기한과 담당자 변경 알림, 외부 연동 안정화.

### 제외

자동 성적·기여 순위 산정, 모든 학과 전용 도구 내장, 문서·영상 공동 편집기, 교수자 수업 운영 시스템, LMS 자동 업로드, 채팅·화상회의, 신규 외부 서비스 대량 연동.

AI 없이도 P0가 동작해야 한다. AI를 개발 성과의 중심으로 삼기보다 회의 정리 등 입력 부담을 줄이는 보조 기능으로 사용한다.

## 10. 적용 기술과 설계 변경

기존 Next.js·TypeScript·Tailwind 화면, Spring Boot·Java 서버, PostgreSQL·JPA·Flyway, 파일 저장소, OpenPDF·ZIP 생성, Docker·Nginx를 유지한다. 기술 교체보다 관계와 상태 규칙 구현에 집중한다.

신규 데이터 단위:

- Deliverable: 프로젝트의 제출물, 기한, 경로, 담당자, 검토자.
- Requirement: 제출물별 필수·선택 기준과 확인 기록.
- Task 확장: 제출물, 완료 기준, 검토자, 상태.
- ArtifactVersion: 업무 또는 제출물에 연결한 결과 버전, 파일 참조·URL·설명.
- ReviewRequest: 중간 의견/완료/통합본 검토 유형, 대상 버전, 요청자·검토자·결과.
- RevisionItem: 수정 내용, 필수 여부, 담당자·기한, 반영 버전, 확인자.
- SubmissionRecord: 제출 차수, 확정 버전, 시각·경로·기록자·확인 근거.
- ActivityEvent: 상태 변경 및 예외 처리 이력.

버전과 검토 결과는 서버에서 연결하고 승인 직후 버전이 바뀌는 동시 수정 충돌을 검사한다. 동일 요청 재전송으로 제출 차수나 업무가 중복 생성되지 않게 한다. 프로젝트 경계와 역할 권한을 API에서 검증한다.

기존 파일은 프로젝트 공용 자료로 보존하고 사용자가 업무·제출물에 연결하게 한다. 기존 완료 업무에는 ‘이전 완료 기록·검토 없음’을 표시한다. 기존 이력을 신규 승인으로 소급 변환하지 않는다.

## 11. 개발 및 스터디 계획

4인·12주 가정. 실제 일정과 담당은 팀 합의 후 확정한다.

| 기간 | 학습·작업 | 시연 가능한 결과 |
|---|---|---|
| 1~2주 | 서로 다른 전공 학생 인터뷰, 제출 사례 분석, 흐름·ERD 설계 | 한 과제의 시작부터 제출까지 화면 시나리오 |
| 3~4주 | 제출물·요구사항·업무 관계, 내 업무 화면 | 과제 설정과 업무 분담 |
| 5~6주 | 버전·중간 의견·수정 항목·권한 | 초안 검토와 수정 반영 |
| 7~8주 | 완료 검토·통합본 승인·동시 수정 처리 | 업무 결과를 통합본으로 확정 |
| 9~10주 | 제출 기록·종료·기존 데이터 이전 | 제출 패키지와 실제 제출 기록 연결 |
| 11~12주 | 파일럿, 권한·상태 검증, 사용성 보완 | 전공이 다른 팀의 과제 수행 결과와 발표 |

P1은 P0 전 과정이 연결되고 검증된 뒤 남은 일정에서 선택한다.

담당 제안(기존 명단 기준): 송병철—제출물·업무·권한·일정 관리, 송승준—파일 버전·검토·제출 기록·DB, 손정협—수정 항목·현황 집계·기존 회의/보고 기능 연결, 손정효—사용 흐름·공통 화면·핵심 UI. 기능별 화면 연결은 백엔드 담당자도 분담하고 손정효가 공통 UI를 검토한다. 전원은 자신의 기능을 전체 시나리오에서 검증한다.

## 12. 이 기획이 맞는지 검증하는 방법

첫 검증은 서로 다른 전공의 3개 팀, 팀당 3~6명, 최소 2주 사용을 목표로 한다. 모집과 참여 의사는 아직 확보하지 않았다. 개발 전에 각 팀의 과제 안내문과 기존 진행 방식을 확인한다.

확인 질문:
- 과제 요구사항 중 빠진 항목을 보통 언제 발견하는가?
- 초안 피드백은 어디에 남고, 누가 반영을 확인하는가?
- 최종 파일과 제출 담당자는 어떻게 정하는가?
- 이 PMS를 사용하면서 추가 기록 부담이 더 커지는 구간은 어디인가?

| 검증 목표 | 측정 방법 | 성공 기준 제안 |
|---|---|---|
| 전공과 무관한 이해 | 실제 과제로 설정·업무·검토·제출 시나리오 수행 | 3개 팀 모두 개발자용 용어 설명 없이 핵심 흐름 완주 |
| 반복 검토의 정착 | 초안→피드백→수정→확인 기록 관찰 | 팀별 최소 2회 순환 완료 |
| 다음 행동 발견 | 내 업무 또는 검토 요청 찾기 | 참여자 80% 이상 별도 설명 없이 성공 |
| 제출 상태의 명확성 | 파일을 다운로드만 한 상황 질문 | 제출 준비와 실제 제출 기록을 구별 |
| 정리 부담 감소 | 유사 과제의 검토·최종본 찾기 시간 비교 | 기존 방식 대비 중앙값 30% 감소 목표 |

수치는 목표이며 결과가 아니다. 기존 방식 비교 시 과제 복잡도와 학습 효과를 함께 기록한다. ‘좋다’는 만족도보다 실제로 반복 사용했는지, 누락·재확인·추가 입력이 줄었는지를 본다.

기술 검증 시나리오: 타 프로젝트 접근 차단, 비검토자 승인 차단, 검토 중 새 버전 등록, 필수 수정 미해결, 검토자 부재·교체, 파일 업로드 실패, 제출 중복 요청, 제출 후 재개, 기존 완료 이력 보존.

## 13. 교수님께 설명할 기획 요약

“저희의 대상은 한 학기 수업에서 공동 결과물을 제출하는 3~6인 대학생 팀입니다. 이런 팀은 전공과 관계없이 일을 나누고, 중간 결과에 피드백을 주고, 여러 작업을 합쳐 제출해야 합니다. 기존 프로젝트에서는 업무·회의·파일이 따로 관리되어 이 과정이 이어지지 않았습니다.

이번 고도화에서는 제출물을 중심으로 요구사항과 업무를 연결하고, 작업 중간에도 검토와 수정을 반복할 수 있도록 하겠습니다. 개별 업무 완료 후에는 통합본을 다시 검토하고, 승인된 버전의 제출과 제출 기록까지 이어지게 합니다. 핵심 성과는 기능 개수가 아니라 한 팀이 과제 시작부터 최종 제출까지 실제로 완주할 수 있는지로 검증하겠습니다.”

발표에서 강조할 세 문장:
1. 대상은 분업한 공동 결과물을 수업에 제출하는 대학생 팀이다.
2. 검토는 마지막 단계가 아니라 작업 중 반복되는 행동이다.
3. 업무 완료, 제출 준비 완료, 실제 제출 기록 완료를 구분한다.

팀명은 기존 Team Blackbox, 프로젝트명은 Team Blackbox를 유지하는 제안이다. 목표 산업은 교육·협업 소프트웨어이며 EXPO 희망 여부는 팀 합의 전까지 미정으로 둔다. 업로드 자료에는 확정 담당자를 기입한다.
