# Team Blackbox 대학생 팀 프로젝트 PMS 고도화 기획안

작성일: 2026-09-14

분석 범위: 현재 저장소의 화면 코드, 데이터 모델, 회의·참여도·알림 서비스, 기존 기획서 및 발표 정보 문서. 실제 서비스 화면을 실행한 사용성 평가나 사용자 인터뷰 결과는 아니다. 교수님의 발언 원문이 없으므로 지적 이유는 코드에 근거한 가설로 제시한다. 아래 신규 기능과 일정은 제안이며 구현 완료를 의미하지 않는다.

## 1. 진단: 기능은 있지만 프로젝트를 끝내는 흐름이 약하다

현재 서비스에는 프로젝트 관리, 칸반, 회의록, AI 액션아이템, 일정 조율, 파일 보관, 참여도, PDF/ZIP 내보내기가 있다. 따라서 전면 재개발보다 이 기능 사이의 관계와 완료 기준을 고치는 것이 우선이다.

| 확인된 현황 | 사용자가 겪을 수 있는 문제 | 개선 방향 |
|---|---|---|
| 사이드바가 칸반·일정 조율·회의록·Hash Vault·기여도로 구성됨 | 처음 들어온 학생이 어떤 순서로 사용해야 하는지 스스로 알아내야 함 | 프로젝트 시작 안내와 현재 단계에 맞는 다음 행동 제공 |
| 홈이 전체 완료율·최근 업무·회의·참여도·연동 안내 중심 | 나에게 배정된 일, 검토 요청, 제출까지 부족한 항목이 우선 보이지 않음 | 오늘 할 일·검토 요청·가장 가까운 제출일을 상단에 배치 |
| 회의에서 업무 생성은 가능하지만 출처를 업무 설명 문자열에 덧붙임 | 회의 결정과 생성된 업무를 안정적으로 양방향 추적하기 어려움 | 회의 결정과 업무를 ID로 연결하고 생성된 업무 상태를 회의에서도 표시 |
| Task 상태가 TODO/IN_PROGRESS/DONE이고 검토·승인 관계가 없음 | 담당자의 완료 표시와 팀이 인정한 완료를 구분하기 어려움 | 검토 요청→수정 요청 또는 승인 흐름 추가 |
| FileVault가 프로젝트·업로더 중심이며 업무 연결 필드가 없음 | 어떤 요구사항을 충족하는 파일인지 확인하려면 별도 설명이 필요함 | 업무 결과물로 등록하고 제출 버전을 선택 |
| 참여도는 완료 업무 존재, 회의 50% 이상 출석, 파일 업로드 존재, 액션아이템 완료 존재로 분류 | 많은 작업을 한 사람과 한 번 작업한 사람이 비슷하게 표시될 수 있음. 역할별 작업 방식도 반영하기 어려움 | 기간·역할·검토된 산출물에 기반한 활동 근거 제공 |
| 완료 액션아이템은 일반 완료 업무에도 포함됨 | 같은 활동이 두 참여 항목에 걸쳐 잡힘 | 활동 종류와 증거를 분리하고 단순 합산을 피함 |
| NONE을 FREE_RIDE 알림으로 연결하고, FULL이 한 명인 상황을 과부하 위험으로 판단 | 활동 기록 부족을 사람에 대한 판단으로 받아들일 수 있음 | 업무 지연·검토 대기·담당자 미지정 등 확인 가능한 상황을 알림 |
| 알림 클릭이 읽음 처리 중심 | 경고를 본 다음 어디서 해결할지 다시 찾아야 함 | 관련 업무 바로 열기와 조치 기록 연결 |
| 기존 발표 문서에는 가중치 점수 엔진 설명이 있지만 현재 서비스는 참여 여부 분류를 사용 | 발표 주장과 시연 결과가 달라질 수 있음 | 실제 구현·이번 학기 개발·향후 확장을 명확히 구분 |

### 교수님이 지적했을 가능성이 큰 이유

1. **PMS의 핵심 질문에 바로 답하지 못한다.** “누가, 무엇을, 언제까지, 어떤 결과로 끝내는가?”가 화면과 데이터에서 이어져야 한다.
2. **기술 설명이 사용자 가치보다 앞선다.** AI·해시·외부 연동이 있어도 학생의 회의 후 정리와 제출 준비가 얼마나 쉬워졌는지 설명해야 한다.
3. **대학생 특화성이 충분히 드러나지 않는다.** 과목, 학기 정보만으로는 부족하다. 중간발표·주간보고·교수 피드백·최종 제출이 실제 행동으로 연결되어야 한다.
4. **기여도에 대한 주장이 근거보다 강하다.** 출석과 업로드는 활동 흔적이지 작업의 품질이나 공정한 성적을 뜻하지 않는다.
5. **고도화의 전후 비교가 모호하다.** 신규 버튼의 수보다 회의 결정이 제출 결과로 이어지는 과정을 보여줘야 한다.

이는 교수님의 의도를 단정한 설명이 아니다. 실제 피드백을 확보하면 각 가설과 대조한다.

## 2. 조 소개

기존 자료 기준 팀은 Team Blackbox(손에 송잡고), 4인 팀이다. 송병철·송승준·손정협·손정효로 구성되어 있다. 이름과 팀 구성은 제출 전 현재 명단과 대조한다.

소개 문장: “저희는 대학생 팀 프로젝트에서 업무 분담 이후 진행 상황과 결과물이 흩어지는 문제를 해결하는 Team Blackbox입니다.”

## 3. 조 이름 및 각오

- 조 이름: Team Blackbox / 손에 송잡고 — 기존 자료 기준.
- 각오 제안: “기능을 많이 만드는 데서 끝나지 않고, 학생들이 실제 팀 프로젝트 한 과목을 처음부터 제출까지 운영할 수 있는 서비스를 만들겠습니다.”

## 4. 진출 목표 산업

- 목표 산업 제안: 교육 소프트웨어(EdTech), 협업 소프트웨어(SaaS).
- 첫 대상: 한 학기 동안 과제를 수행하는 3~6명 대학생 팀.
- 주 사용자: 팀원과 팀장. 교수자는 제출물과 진행 근거를 확인하는 보조 사용자.
- 초기 검증 범위: 한 과목의 소수 팀. 대학 전체 학사 시스템이나 기업용 PMS 확장은 후속 과제로 둔다.
- 가치 가설: 학생은 중복 정리 시간을 줄이고, 팀장은 지연 업무를 발견하며, 교수자는 결과물의 진행 맥락을 확인할 수 있다. 효과는 파일럿으로 검증한다.

## 5. 신구 EXPO 출품 희망 여부

미정 — 팀 합의 필요. 출품 제안은 가능하지만 희망 여부를 확정 사실로 기재하지 않는다.

출품 시 시연 주제: “회의 결정 하나가 업무, 결과물, 검토, 주간보고서까지 이어지는 3분 데모.” 실제 계정이나 개인 자료 없이 가상 수업·가상 팀 데이터로 준비한다.

## 6. 프로젝트 주제

**학기별 목표와 제출 일정을 중심으로 회의·업무·산출물·피드백을 연결하는 대학생 팀 프로젝트 관리 시스템.**

기존의 참여도 확인 중심 서비스를 일상적인 프로젝트 수행을 돕는 PMS로 고도화한다. 활동 근거는 수행 과정에서 자연스럽게 축적한다.

## 7. 프로젝트 이름 및 개요

- 프로젝트 이름: Team Blackbox — 기존 이름 유지 제안.
- 한 줄 소개: “회의에서 정한 일을 제출 가능한 결과물까지 연결하는 대학생 팀플 PMS.”
- 핵심 문제: 회의에서는 일을 정했지만 담당자·마감일이 빠지고, 완료된 파일이 흩어져 주간보고와 최종 제출 때 다시 정리해야 한다.
- 해결 방식: 수업의 마일스톤에 업무를 연결하고, 업무마다 완료 기준과 결과물을 남긴 뒤 검토와 제출 자료 생성으로 이어지게 한다.
- 성공 경험: 학생이 접속했을 때 오늘 할 일이 보이고, 작업을 끝내면 팀 검토와 보고서에 같은 기록이 반영된다.

### 대표 사용 흐름

1. 팀장이 과목·프로젝트 기간·최종 제출일을 입력하고 팀원을 초대한다.
2. ‘중간발표, 최종발표’ 기본 마일스톤을 수정하고 각 제출물의 체크리스트를 정한다.
3. 회의에서 결정사항을 기록한다. AI가 제안한 업무의 담당자·마감일·완료 기준을 사람이 확인하여 등록한다.
4. 팀원은 ‘내 할 일’에서 업무를 진행하고 파일 또는 링크와 작업 설명을 첨부한다.
5. 검토자에게 검토를 요청한다. 수정 요청은 사유와 함께 진행 중으로 돌아가고, 승인은 완료로 기록된다.
6. 팀장은 지연·검토 대기·담당자 없는 업무를 확인하고 재배정이나 일정 조정을 기록한다.
7. 주간보고서 초안에 기간 내 완료·진행·문제·다음 계획과 결과물 링크가 모인다. 팀장이 수정·확정하여 내보낸다.
8. 최종 제출 시 체크리스트 누락을 확인하고 제출 버전을 확정한다.

예시: “인터뷰 결과를 정리하자” → ‘인터뷰 5명 결과 요약’ 업무 → 담당자·금요일 마감·비교표 포함 조건 → 요약 파일 v1 → 검토자의 근거 보완 요청 → v2 승인 → 중간발표 자료와 주간보고서에 연결.

## 8. 핵심 기능 소개

### A. 수업 목표와 연결되는 프로젝트 시작

과목명, 기간, 제출일을 먼저 입력하고 마일스톤 템플릿을 제공한다. 팀원 초대와 첫 업무 등록이 초기 안내의 중심이다. 외부 연동은 필요할 때 설정한다.

### B. 내 할 일과 검토 요청

홈 상단에 오늘 마감, 지연, 검토 요청을 보여준다. 업무 상세에는 목적, 담당자, 마감일, 완료 기준, 연결 회의, 산출물, 검토 이력이 모인다. 카드 클릭 시 바로 해당 업무를 연다.

### C. 회의 결정에서 업무로 전환

기존 AI 추출 기능을 활용한다. 추출 결과는 초안으로 표시하고 담당자 누락·불명확한 날짜는 확인을 요구한다. 확정된 업무는 원본 결정과 연결하며 반복 클릭 시 중복 생성되지 않게 한다. AI 실패 시 수동 등록이 가능하다.

### D. 산출물 검토와 버전 관리

파일·링크를 업무 결과물로 등록하고 검토자에게 전달한다. 승인과 수정 요청을 기록한다. 제출 파일은 승인된 버전 중 선택한다. 링크는 외부 내용이 바뀔 수 있음을 표시하며, 확정 제출본은 파일 스냅샷으로 남길 수 있게 한다.

### E. 주간보고와 제출 준비

선택한 기간의 기록을 완료 업무·진행 업무·어려움·다음 계획·산출물로 정리한다. 기본 초안은 규칙 기반으로 만들고, AI 문장 정리는 선택 기능으로 둔다. 출처 업무를 열어 확인하고 수정한 뒤 PDF로 확정한다. 자동 제출은 하지 않는다.

### F. 설명 가능한 진행 현황

사람 순위 대신 마일스톤별 완료 상황, 지연 업무, 검토 대기, 역할별 활동 근거를 제공한다. 공동 작업자는 복수로 기록한다. 기록이 부족하면 ‘확인 필요’로 표시하며 점수로 성적을 자동 결정하지 않는다.

## 9. 적용 기술 및 기능

아래는 현재 저장소 기술을 유지하는 구현 제안이다. 최신 기술 비교나 버전 업그레이드 계획은 아니다.

| 영역 | 기술 | 고도화에 사용할 기능 |
|---|---|---|
| 화면 | TypeScript, Next.js, React, Tailwind CSS | 역할별 홈, 업무 상세, 제출 준비 화면과 일관된 컴포넌트 |
| 상태·통신 | Zustand, Axios | 프로젝트 선택 유지, 변경 후 관련 화면 데이터 갱신, 오류·재시도 안내 |
| 업무 보드 | 기존 dnd-kit | 검토 상태를 포함한 보드. 서버에서 상태 전환 조건 검증 |
| 서버 | Java 17, Spring Boot, Spring Security | 권한, 검토 승인, 회의-업무 연결, 보고서 API |
| 데이터 | PostgreSQL, JPA, Flyway | 마일스톤·검토·산출물 관계와 변경 이력 추가 |
| AI | 기존 Claude 연동 | 회의 업무 초안 추출, 선택적 보고서 문장 정리. 사람 확인 후 반영 |
| 보고서 | 기존 OpenPDF 및 ZIP 생성 | 기간별 보고서, 확정 버전과 결과물 목록 내보내기 |
| 파일 | 기존 파일 저장소와 SHA-256 | 저장된 기준 해시와 비교하는 파일 변경 탐지, 제출 버전 식별 |
| 운영·도구 | Docker Compose, Nginx, Git, Gradle, npm | 재현 가능한 실행·배포, 변경 관리와 검증 |
| 외부 연동 | 기존 Notion·Discord·Google Calendar | 선택적 내보내기·알림·일정 조율. 핵심 업무 수행과 독립적으로 작동 |

SHA-256과 DB 수정 제한만으로 작성자의 진실성, 저작권, 관리자까지 포함한 절대적 위변조 불가를 증명할 수는 없다. 발표에서는 ‘제출 버전 고정 및 변경 탐지’로 범위를 설명한다.

## 10. 구현 범위

### 필수: 한 과목을 끝까지 운영하는 흐름

- 프로젝트 시작 안내와 마일스톤·제출 체크리스트.
- 내 할 일·검토 요청 중심 홈.
- 회의 결정과 업무의 명시적 연결, AI 초안 확인 및 중복 생성 방지.
- 업무 완료 기준, 산출물 첨부, 검토 요청·승인·수정 요청.
- 기간별 주간보고서 초안·수정·PDF 출력.
- 기존 참여도 화면을 활동 근거 중심으로 정리하고 단정적인 경고 문구 교체.
- 프로젝트·역할별 접근 제어 및 전체 흐름 검증.

### 후순위: 필수 흐름 검증 후 진행

- 교수자 열람 화면과 피드백을 후속 업무로 연결.
- 예상 작업량·가용 시간에 따른 업무 편중 참고 표시.
- 최종 제출 패키지의 버전 확정 UI 확장.
- 선택적 AI 보고서 문장 정리와 외부 연동 안정화.

### 이번 학기 제외 제안

GitHub/Drive 신규 자동 수집, 성적 자동 산정, 고급 간트·의존성 엔진, 채팅·화상회의 자체 구축, 음성 전사, 대학 전체 수업 관리, 결제. 현재 핵심 흐름의 완성도가 확보되기 전에는 범위를 늘리지 않는다.

## 11. 고도화할 기능: 설명·적용 기술·차별성

| 우선순위 | 기존 → 개선 | 적용 기술 | 차별성/우수성 가설 | 완료 판정 |
|---|---|---|---|---|
| P0 | 전체 현황 홈 → 내 행동 중심 홈 | Next.js, 사용자별 업무 조회 API | 접속 즉시 해야 할 일을 찾음 | 담당 업무·검토 요청에서 상세로 직접 이동 |
| P0 | 회의 설명 문자열 → 결정-업무 관계 | JPA 관계, 구조화 AI 응답, 중복 방지 키 | 회의 약속의 실행 상태를 추적 | 회의에서 업무 상태 확인, 업무에서 원본 회의 열기 |
| P0 | 완료 표시 → 결과물 검토 후 완료 | 상태 전환 API, 검토 테이블, 트랜잭션 | 완료의 의미가 결과물 수준에서 명확해짐 | 반려·재제출·승인 이력이 남고 권한 위반 차단 |
| P0 | 프로젝트 파일 보관 → 업무 산출물·버전 | 산출물 관계 테이블, 기존 저장소 | 보고서와 제출물에 근거가 이어짐 | 승인 버전을 보고서에서 열 수 있음 |
| P0 | 개별 기록 내보내기 → 주간보고 초안 | 기간별 집계, OpenPDF | 수업 보고 형식으로 재정리하는 부담 감소 | 원본 링크가 있는 초안을 수정·확정·출력 |
| P0 | 참여 여부 판정 → 활동 근거 확인 | 업무·검토·기간별 조회 | 역할과 공동 작업을 확인할 근거 제공 | 출처와 기간 확인, 누락 활동 보완 |
| P1 | 보고서 확인 → 교수 피드백 후속 업무 | 관찰자 권한, 피드백-업무 관계 | 교육 과정의 피드백 반영 여부 추적 | 피드백에서 연결 업무 상태 확인 |

‘기존 제품에는 없는 유일한 기능’이라고 주장하지 않는다. 본 프로젝트의 차별화 방향은 대학 수업의 제출 주기와 근거 추적을 하나의 짧은 흐름으로 묶는 것이다. 경쟁 우위는 사용자 검증 전까지 가설이다.

## 12. 화면 구성과 UX 원칙

기본 메뉴: **프로젝트 홈 / 업무 / 회의 / 산출물 / 보고서 / 설정**. 일정 조율은 회의 내부에, 활동 근거는 보고서 내부에 배치한다. 실제 사용성 평가에 따라 조정한다.

홈 배치 순서:
1. 현재 프로젝트·과목·다음 제출일.
2. 내 할 일과 내 검토 요청.
3. 이번 주 마일스톤과 누락 제출물.
4. 팀의 지연·도움 요청 및 최근 결정사항.

각 화면에는 대표 행동 하나를 강조한다. 업무는 ‘업무 추가’, 회의는 ‘회의 기록’, 보고서는 ‘이번 주 초안 만들기’다. 빈 화면은 첫 행동을 안내하고, 저장 성공 후 다음 행동을 제시한다. 미연동 상태를 오류처럼 강조하지 않는다. 색상은 지연·대기·완료 등 의미를 일관되게 표현한다.

알림 예시: “무임승차 감지” 대신 “이번 주 담당 업무 2건의 진행 상태 확인이 필요합니다.” 클릭하면 해당 업무 목록을 열고 확인·재배정·마감 변경 중 실제 조치로 이어진다.

## 13. 데이터와 업무 규칙

신규 또는 확장 모델:
- Milestone: 프로젝트, 제목, 마감일, 제출 체크리스트.
- MeetingDecision: 회의, 결정 내용, 확인자.
- Task: 마일스톤, 회의 결정 참조, 완료 기준, 검토자, 상태 추가.
- TaskDeliverable: 업무, 파일 또는 URL, 버전, 등록자, 작업 설명.
- TaskReview: 대상 산출물 버전, 검토자, 결과, 의견, 시각.
- WeeklyReport: 기간, 초안 내용, 확정 스냅샷, 확정자, 확정 시각.
- ActivityEvent: 변경 주체, 대상, 변경 전후 상태, 시각.

업무 상태: 할 일 → 진행 중 → 검토 요청 → 완료. 수정 요청은 사유를 남기고 진행 중으로 돌아간다. ‘막힘’은 진행 상태와 별도로 사유·도움 요청 대상을 기록한다.

검토 요청에는 담당자, 완료 기준, 산출물 또는 결과 설명이 필요하다. 승인 권한과 검토자 변경 규칙을 서버에서 검사한다. 검토자는 기본적으로 수행자와 다른 팀원으로 설정하고 예외 변경은 이력에 남긴다. 완료 후 새 버전 제출 시 재검토하며 기존 승인 기록은 보존한다. 공동 작업은 참여자와 역할을 함께 남긴다.

기존 DONE 업무를 신규 승인 완료로 소급해서 꾸미지 않는다. ‘기존 완료·검토 기록 없음’으로 보존한다. 기존 회의 출처 문자열은 가능한 항목만 연결하고 불명확한 경우 수동 확인한다. 보고서 확정 후 원본이 바뀌어도 확정본은 유지하고 새 보고서 버전을 만든다.

## 15. 식별된 요소 및 요소별 담당자

기존 자료의 4인 명단과 주 역할을 바탕으로 한 **배정 제안**이다. 확정된 담당표가 아니며 제출 전에 팀 합의가 필요하다. 발표 슬라이드는 이름을 생략할 수 있지만 업로드 자료에는 확정 담당자를 기입한다. 1인 팀이라면 담당자를 생략한다.

| 식별 요소 | 주 담당 제안 | 검토·협업 | 결과물 |
|---|---|---|---|
| 요구사항·범위·일정 | 송병철 | 전원 | 요구사항표, 일정, 완료 기준 |
| 프로젝트·업무 상태·권한 API | 송병철 | 송승준 | 상태 전환 및 권한 검증 |
| DB·회의 연결·파일 버전·검토 | 송승준 | 송병철 | ERD, 마이그레이션, 검토 API |
| AI 초안·주간보고·활동 근거 | 손정협 | 송승준 | 구조화 추출, 보고서, 집계 API |
| 사용자 흐름·공통 UI·홈·업무 상세 | 손정효 | 송병철 | 핵심 화면과 공통 컴포넌트 |
| 회의·검토 화면 연결 | 손정효 | 송승준 | 원본 추적과 검토 화면 |
| 보고서 화면 연결 | 손정협 | 손정효 | 보고서 편집·출력 화면 |
| 사용성 평가·발표·최종 확인 | 전원 | 송병철 취합 | 검증 결과, 발표·제출본 |

프론트엔드 전체를 한 명에게 집중시키는 기존 분담을 완화한다. 손정효가 화면 규칙과 공통 구조를 정하고, 기능 담당자가 정해진 컴포넌트로 해당 화면 연결까지 맡는 방식을 제안한다. 개인 기여율은 현재 자료의 임의 백분율을 재사용하지 않고 실제 작업 기록으로 합의한다.

## 16. 검증 계획과 성공 기준

아래 수치는 실적이 아니라 목표다. 기존 서비스와 개선 서비스를 같은 과제·같은 데이터로 비교하고, 수행 순서를 나눠 학습 효과를 줄인다. 소규모 결과를 전체 대학생에게 일반화하지 않는다.

| 검증 항목 | 방법 | 목표 |
|---|---|---|
| 시작 용이성 | 외부 설명 없이 생성·초대·첫 업무 등록 | 참여자 80% 이상 성공 |
| 업무 발견 | 로그인 후 자신의 다음 업무 찾기 | 중앙값 10초 이내 |
| 회의 후 실행 | 결정에서 담당자·마감일 포함 업무 등록 | 기존 대비 소요시간 30% 감소 |
| 제출 준비 | 동일 기록으로 주간보고서 작성 | 기존 대비 소요시간 50% 감소 |
| 전체 흐름 | 업무→산출물→반려→재제출→승인→보고서 | 필수 단계 누락 없이 완료 |
| 추적성 | 보고서 항목에서 원본 업무·결과물 확인 | 연결된 항목 100% 접근 가능 |

기술 검증은 다른 프로젝트 데이터 접근 차단, 승인 권한, AI 결과 수정, 중복 업무 생성 방지, 업로드 실패 재시도, 보고서 확정본 유지, 기존 데이터 보존에 집중한다. 보고서 PDF는 한글·페이지 나눔·긴 제목·링크를 실제 출력하여 확인한다.

## 17. 발표 구성 제안

1. 표지: 팀명·프로젝트명·한 줄 소개.
2. 조 소개·각오·목표 산업·EXPO 희망 여부.
3. 기존 프로젝트: 구현된 기능과 현재 대표 흐름.
4. 개선점 도출: 회의→업무→결과물→검토→보고에서 끊기는 지점.
5. 프로젝트 주제와 대상 사용자.
6. 개선 사용자 시나리오와 홈·업무 상세 화면.
7. 핵심 고도화 ① 회의 결정-업무 연결.
8. 핵심 고도화 ② 결과물 검토와 완료 기준.
9. 핵심 고도화 ③ 주간보고와 제출 준비.
10. 적용 기술·데이터 관계·기존 대비 차별화 가설.
11. 필수 구현 범위·후순위·스터디 일정·담당 요소.
12. 검증 계획과 3분 시연.

발표 핵심 문장: “기존 Team Blackbox는 팀원의 활동을 확인하는 기능은 갖췄지만, 회의에서 정한 일이 검토된 결과물과 제출 자료로 이어지는 과정이 부족했습니다. 이번 고도화에서는 대학 수업의 일정과 제출물을 기준으로 회의·업무·산출물·주간보고를 연결하겠습니다.”
