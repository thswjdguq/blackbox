## 회의 사용자 흐름

프로젝트 초대 코드로 참여하면 미마감 회의의 참석 대상에 자동 포함된다. 회의 생성 시 현재 팀장·팀원을 등록하며, 생성자를 자동 참석 처리하지 않는다. 관찰자는 조회만 가능하며 참석 대상에서 제외한다. 팀원 역할로 바뀌면 미마감 회의에 등록한다. 이미 마감된 회의에는 가입자를 소급 등록하지 않는다.

- 참석 확인 시작: 회의 시작 10분 전.
- 기본 지각 기준: 시작 후 10분까지 참석, 이후 지각. 기준 시각과 정확히 같으면 참석.
- 기본 확인 마감: 시작 후 60분. 마감과 정확히 같거나 이후면 요청 거절. 미확인은 불참으로 조회된다.
- 불참 예정은 마감 전 사전 표시 가능. 본인 확정 기록의 반대 상태로 변경은 거절하고 팀장이 정정한다.
- 팀장은 시작 후 참석/지각/불참 정정 가능. 정정자·대상·상태를 활동 기록에 남긴다.
- 팀장은 일시·기준 변경 가능하나 참석 기록이 생긴 회의는 변경하지 못한다. 개별 정정으로 처리한다.
- 모든 판정은 서버 시간 기준. UI는 30초마다 현황을 조회한다. 자동 불참은 조회 시 계산하므로 별도 스케줄러가 DB에 불참 행을 쓰지 않는다.
- 예전 코드·체크인 DB 컬럼과 기록은 보존하고 응답의 checkinCode는 null로 제공한다. 코드 참여·재생성 API와 대시보드 체크인 경로는 제거했다. 코드로 프로젝트에 가입하는 우회도 제거된다.
- 이전 checked_in 기록은 `LEGACY`(이전 출석 기록)로 표시하며 새 시간 기준으로 소급 판정하지 않는다.

### API 제안

`GET /api/projects/{projectId}/meetings/{meetingId}/attendance`

응답: serverTime, opensAt, lateAfter, closesAt, attendees(userId, name, email, status, recordedAt). 상태는 PENDING/PRESENT/LATE/ABSENT/LEGACY.

`PUT .../attendance`: `{ "attending": true/false }`. 본인 기록. 동일 상태 재전송은 최초 기록을 돌려준다. 대상 행 잠금으로 동시 재전송을 직렬화한다. TIMESTAMPTZ 저장 정밀도에 맞춰 시각을 마이크로초로 제한한다.

`PUT .../attendance/{userId}`: `{ "status": "PRESENT|LATE|ABSENT" }`. 팀장 정정.

회의 생성/수정과 응답에 attendanceGraceMinutes, attendanceWindowMinutes 추가. 지각 기준 0~120분, 확인 마감은 기준보다 큰 값이며 최대 480분. 비회원·관찰자 쓰기 403, 다른 프로젝트 회의 404, 시간/상태 충돌 409, 잘못된 값 400.

## 회의록 편집

- 본문·중제목(H2)·소제목(H3)을 드롭다운에서 선택한다. 현재 커서의 서식도 선택값에 반영한다.
- 기본 양식에 회의 개요(H2), 논의 안건(H2), 안건 세부 내용(H3), 결정사항 및 다음 할 일(H2)을 제공한다.
- 화면 제목은 `회의록`. 노션 연결 관련 불필요한 설명은 제거했다.

## 업무 자료와 검토

제출물에서 업무를 누르면 현재 화면에서 상세 패널을 연다. `업무 정보`와 `자료·검토·피드백`을 오가며 파일 등록, 다운로드, 검토 요청, 피드백 처리를 진행한다. 미저장 업무 변경이 있으면 자료/검토 쓰기를 막고 정보 저장을 먼저 안내한다.

- 새 task_files 관계로 파일 버전의 id와 업무를 연결한다. 파일 원본·불변성·해시·기존 프로젝트 단위 버전 정책은 기존 FileVaultService를 그대로 사용한다.
- 동일 이름의 버전 번호는 업무별이 아닌 기존 프로젝트 단위다. 각 업무는 실제로 연결한 파일 버전만 표시한다.
- 업무 파일은 프로젝트 자료에도 같은 id로 나타나고, 연결된 제출물의 `업무에서 모인 자료`에 표시된다. 복사본을 별도 생성하지 않는다.
- 업로드만으로 업무 상태를 변경하거나 제출물 승인 처리하지 않는다.
- `이 자료로 검토 요청`은 연결된 제출물의 새 회차를 연다. 기존 승인 무효 의미는 기존 K-10을 유지한다. 요청 전에 이를 확인한다.
- 상세 패널의 피드백은 해당 업무만의 독립 승인 기능이 아니라 연결된 제출물의 기존 검토 회차다. 화면에서도 그 범위를 명시한다.
- 업무 삭제 시 연결만 삭제되고 프로젝트 파일은 남는다. 파일 삭제·연결 해제 UI는 이번 범위에 추가하지 않았다.
- 업무/파일 프로젝트 경계는 서버 검사와 복합 FK로 보장한다.

### API 제안

- GET/POST `/api/projects/{projectId}/tasks/{taskId}/files` — 목록 / multipart file 업로드·연결.
- POST `.../tasks/{taskId}/files/{fileId}/review` — 해당 업무에 연결된 파일로 제출물 검토 요청.
- GET `.../deliverables/{deliverableId}/task-files` — 연결 업무들의 파일 목록.
- 파일 응답은 `{taskId, taskTitle, file: 기존 FileHistoryResponse}`. 조회는 관찰자 포함 멤버, 쓰기는 팀장·팀원. 다른 프로젝트/연결되지 않은 파일은 404, 제출물 미연결 검토 요청은 409.
- DB 메타데이터와 관계는 동일 트랜잭션에 저장한다. 기존 디스크 파일 저장은 DB 트랜잭션으로 되돌아가지 않으므로 업로드 이후 DB 실패 시 남은 파일 정리는 별도 운영 과제다.

## 팀 검토

회의·업무 서비스(B) 외에 ProjectService, Meeting DTO/엔티티, migration(A), TaskModal/제출물 상세/편집기(C)를 사용자 승인된 별도 시연 범위에서 변경했다. main에 가져가기 전 A·C가 API 필드, 파일 삭제 정책, migration 번호, UI와 기존 계약 호환을 검토해야 한다. 계약 AGREED/IMPLEMENTED 상태를 임의 선언하지 않는다.
