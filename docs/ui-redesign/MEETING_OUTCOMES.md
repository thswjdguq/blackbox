# 회의록 한 번 작성 → 결정사항·할 일 정리

## 범위

사용자 요청으로 별도 UI 개선 폴더에서 구현한 제안이다. 현행 main과 기존 시연 환경은 변경하지 않는다. 팀 공통 계약으로 합의되었거나 PR이 병합되었다는 의미가 아니다.

## 사용자 흐름

1. 팀장·팀원이 회의록 편집기 하나에 안건과 논의 내용을 작성한다.
2. `결정사항·할 일 추출`을 누르면 회의록을 먼저 저장하고 AI에 본문을 전달한다.
3. AI의 결정사항·할 일 후보와 원문 근거를 확인하고, 필요한 후보를 선택·수정한다. 처음에는 아무 항목도 선택하지 않는다.
4. 선택한 결정사항을 기존 결정사항 뒤에 추가하거나, 선택한 할 일을 기존 회의 업무 API로 등록한다. 담당자·기한은 사람이 지정한다.
5. AI를 사용할 수 없으면 결정사항 직접 정리와 직접 업무 등록을 사용한다.

기존 결정사항은 삭제하지 않고 접힌 조회 영역에서 확인·수정한다. 기존 AI 요약 데이터와 기존 API도 삭제하지 않는다. 화면의 중복 요약·추출 버튼만 새 흐름으로 통합한다.

## API 제안

`POST /api/projects/{projectId}/meetings/{meetingId}/ai/extract-outcomes`

- 요청 본문 없음. 서버에 저장된 회의록을 분석한다.
- 팀장·팀원만 사용. 관찰자·비회원은 403. 회의 조회는 기존 프로젝트 경계 검사를 사용한다.
- 응답: `{ "decisions": [{ "text": "결정", "evidence": "원문" }], "actions": [{ "text": "할 일", "evidence": "원문" }] }`
- 배열마다 최대 20개, 항목 text 최대 255자. evidence가 회의록의 연속된 원문인지 서버에서 검사한다. 원문 인용 일치는 의미의 정확성을 보장하지 않으므로 사용자 검토를 거친다.
- 빈 본문·30,000자 초과는 400. 제공자 호출 실패 503, 응답 형식·근거 검증 실패 502. 공통 오류 처리기는 5xx 내부 상세를 숨기며 화면은 재시도·직접 정리를 안내한다.
- 추출 서비스 자체는 결정사항·업무를 저장하지 않는다. 기존 AiService.rawCall을 사용하며 제공자 설정과 DB 스키마는 변경하지 않는다.

## 변경 및 검증 경계

- 새 서비스·컨트롤러와 회의 화면 변경. A 소유 AI 인프라 구현은 수정하지 않음. main 반영 전 새 API와 C 소유 화면의 팀 검토 필요.
- MeetingOutcomeServiceTest 9개, MeetingNotesTest 6개 통과. 실제 ProjectAccessChecker와 저장소 mock을 사용한다. AI 응답도 mock이다.
- 새 서비스의 프로젝트 경계 실패 전파 테스트는 MeetingService를 mock 처리한다. 실제 MeetingService 프로젝트 경계는 기존 MeetingNotesTest에서 별도로 확인한다.
- 실제 외부 AI 생성 품질과 브라우저 조작은 아직 검증하지 않았다.
- 회의록이 바뀌면 기존 AI 후보의 반영을 막고 재추출을 요구한다. 다른 사용자와의 동시 변경까지 원자적으로 막는 것은 아니며 기존 저장 전 비교의 한계가 남는다.
- 업무 등록은 성공 응답을 받은 항목을 표시해 재시도에서 제외한다. 네트워크 단절로 서버 저장 여부를 알 수 없는 경우의 완전한 중복 방지는 보장하지 않는다.
- 후보는 화면 임시 상태이다. 새로고침하면 사라지며, 선택해 저장한 결정사항·업무만 서버에 남는다.

- git diff --check 통과. 커밋·push·main 병합 미수행.
