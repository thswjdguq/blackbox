# 업무 순서 · 완료 조건 · 팀장 승인

> 후속 변경: 팀장 전용 완료 승인을 다른 팀원의 결과 확인으로 변경했다. 현재 권한과 UI는 [TASK_RESULT_UX.md](TASK_RESULT_UX.md)가 우선한다. 아래 내용과 검사 결과는 최초 팀장 승인 구현 시점의 기록이다.

## 요청과 범위

2026-10-12 사용자 요청으로 별도 UI 환경에서 구현했다. 업무에 처리 순서와 파일 첨부 같은 완료 조건을 정하고, 팀장 승인 없이 완료로 이동하는 경로를 제한한다.

기준 `98d073b`, `codex/ui-flow-redesign`, `C:/blackbox/teamplay-ui`. 이 변경은 업무 API의 공통 의미와 DB를 확장한 시연용 제안이다. main 반영 전 A·C가 검토해야 하며, V27 번호는 A와 조정한다. 기존 migration과 기존 완료 데이터를 삭제하거나 재작성하지 않는다.

## 동작

`할 일 → 진행 중 → 완료 요청(진행 중·승인 대기) → 팀장 승인 → 완료`

- 완료 요청이 있어도 status는 IN_PROGRESS다. 카드·목록에 승인 대기 표시를 추가한다. 완료 수·진척 계산은 기존 DONE 기준을 유지한다.
- 업무 생성/수정에서 완료 조건 문구, 파일 필수 여부, 선행 업무 하나를 설정한다. 선행 업무가 없으면 병렬로 진행할 수 있다.
- 선행 업무가 DONE이고 팀장 승인 기록이 있어야 다음 업무를 시작하거나 파일을 등록하거나 완료를 요청할 수 있다.
- 자신/후속 업무를 선행으로 설정하는 순환 연결, 다른 프로젝트의 선행 업무, 참조 중인 선행 업무 삭제를 거절한다.
- 완료 요청에는 완료 조건 문구가 필요하며, 파일 필수 업무는 이 업무에 실제 연결된 파일이 있어야 한다. 다른 업무·프로젝트에만 올린 파일은 충족으로 보지 않는다.
- 조건 문구의 실제 품질 충족은 자동 판정하지 않는다. 팀장이 결과와 첨부 자료를 확인하고 확인 체크를 한 뒤 승인한다.
- 담당자 또는 팀장이 완료를 요청할 수 있다. 미배정 업무는 생성자도 요청 가능하다. 관찰자는 조회만 가능하다.
- 승인 대기/완료 업무는 내용·완료 조건·선행 연결·담당자·자료 업로드·일반 상태 변경을 잠근다. 보완 요청 후 수정·재요청 가능하다.
- 보완 요청은 사유 필수이며 진행 중 상태로 돌아온다. 요청자·승인자·시각·조건·파일 id·보완 사유를 활동 기록에 남긴다.
- 동일 완료 요청과 승인 재전송은 기존 결과를 반환하여 완료 이벤트를 중복 생성하지 않는다.
- 팀장은 완료 업무를 사유와 함께 재개할 수 있다. 진행 중인 후속 업무가 있으면 먼저 후속 업무를 정리해야 한다.
- 업무 승인과 제출물 검토는 별개다. 승인된 업무의 파일로 제출물 검토를 요청할 수 있다. 업무 파일 등록은 잠기지만 제출물의 기존 검토 권한은 유지한다.

## 우회 제한

- 일반 상태 PATCH의 DONE 요청과 DONE으로 업무 생성은 서버에서 409로 거절한다. 팀장도 일반 이동으로 승인 절차를 우회할 수 없다.
- 보드의 완료 칸은 드롭 대상에서 제외한다. 카드의 완료 버튼은 완료 조건 확인 화면을 열며 직접 상태를 바꾸지 않는다.
- 상세 상태 선택에서도 완료를 직접 고를 수 없다. 완료 요청·팀장 승인 버튼을 사용한다.
- 프로젝트 행 잠금으로 순서 변경·상태 변경·완료 요청·승인·자료 등록을 직렬화한다. 승인 시에도 완료 조건을 다시 검사한다.
- DB CHECK는 새로 생성/수정되는 승인 없는 DONE을 거절한다. NOT VALID로 기존 완료 행은 보존한다.
- 기존 완료 행은 '이전 완료 · 승인 기록 없음'으로 표시한다. 팀장 재개 후 조건을 정하고 새 승인 흐름으로 검토한다. 과거 완료 수를 임의로 소급 변경하지 않는다.

## API 제안

Task 응답에 predecessorId/Title, attachmentRequired, completionRequestedAt/ByName, completionApprovedAt/ByName, completionRejectionReason을 추가한다.

- GET `.../projects/{projectId}/tasks/{taskId}/completion`: 업무·자동 확인 조건·요청/승인 가능 여부. 관찰자 포함 멤버.
- POST `.../completion-request`: 담당자/팀장 완료 요청.
- PUT `.../completion-decision`: `{approved:true, criteriaConfirmed:true}` 승인 또는 `{approved:false, reason:"…"}` 보완 요청. 팀장.
- POST `.../reopen`: `{reason:"…"}` 완료 업무 재개. 팀장.
- 생성/수정에 predecessorId, attachmentRequired 추가. 수정의 clearPredecessor로 연결 해제. 기존 완료 기준 completionCriteria 사용.
- 조건/상태 충돌 409, 순환·잘못된 확인/사유 400, 권한 403, 다른 프로젝트 업무 404. 위 경로 모두 `/api` 아래다.

## 제한과 팀 검토

- 선행 업무 하나를 지정하는 순서 모델이다. 여러 선행 업무를 동시에 요구하는 관계와 제출물의 요구사항 자동 승인 기능은 추가하지 않았다.
- 파일 검사는 연결 파일 존재 여부다. 형식·파일 내용·문구 충족 여부를 자동 승인하지 않는다.
- 완료 조건과 순서를 작성/수정하는 권한은 기존 팀장·팀원 권한이다. 승인 요청 후에는 동결된다. 팀장만 완료 조건을 정하게 할지는 팀 계약 검토 항목이다.
- 팀장 자신의 업무도 팀장 승인 절차를 거친다. 제출물 파일의 본인 승인 금지 규칙은 기존 K-10 그대로다.
- Task DTO/상태 의미, TaskService/TaskFileService, DB V27(A), 프론트(C), 기존 K-12 업무 생성·K-13 진척 소비를 A·C와 함께 검토해야 한다.
